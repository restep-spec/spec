Restep 1 · especificación

1. Estado y alcance

Borrador 7, 25 de noviembre de 2026 (borrador 6: 20 de noviembre de 2026; borrador 5: 20 de noviembre de 2026; borradores 4, 3 y 2: 19 de noviembre de 2026; borrador 1: 12 de noviembre de 2026). Puede cambiar sin aviso hasta que se publique la versión 1.0. Un servidor que lo implementa declara "restep": "1.0-draft.7" (1.1).

URI de esta versión: https://w3id.org/restep/1/, un identificador permanente que redirige al texto inglés en restep.wubytes.com.

Se publica en inglés y en español. Si las dos versiones no coinciden, prevalece la inglesa, que es a la que llevan las URI de perfil y de error.

También en un solo archivo Markdown, para agentes y para comparar versiones: spec.md.

Restep es un perfil para APIs HTTP que intercambian JSON y se organizan en recursos: el nivel 2 del modelo de madurez de Richardson. Fija lo que ese nivel deja abierto (formato de colecciones y errores, consulta, escrituras seguras, relaciones y sincronización) y lo reparte en seis perfiles que se adoptan de uno en uno, más unas extensiones opcionales.

Fuera del alcance quedan la autenticación y la autorización (se recomienda OAuth 2.0, con OpenID Connect si la API necesita la identidad del usuario; la extensión oauth dice dónde pide el token el cliente), el diseño del dominio de cada API y el transporte por debajo de HTTP. Restep no exige esquema ni generador de código: un servidor core se puede escribir a mano.

1.1 Versiones de Restep

  • Restep tiene versión mayor y menor. La mayor va en todas sus URI (/1/); el documento de descubrimiento declara la completa: "restep": "1.0".
  • Una versión menor solo añade: perfiles; extensiones; miembros del descubrimiento; valores y formas que este texto reserva para versiones menores; significados para peticiones y declaraciones que este texto prohíbe o reserva; y códigos de error para casos nuevos (nunca un código nuevo para un caso que ya tenía uno; un estado que no está en la tabla de 5.4 ya tiene su código: http_ y su número). No añade ningún requisito sobre lo que define la 1.0, así que lo que cumple la 1.0 sigue cumpliendo la 1.1, salvo en los perfiles y extensiones experimentales (1.2). Añadir códigos de error es seguro porque los clientes tratan los que no conocen por la clase del estado (5.4), y añadir lo demás, porque los clientes ignoran lo que no conocen (3, 4.2).
  • El valor de restep DEBE cumplir esta gramática (ABNF, RFC 5234, con las cadenas que distinguen mayúsculas del RFC 7405), así que los números no llevan ceros a la izquierda y el sufijo va en minúsculas: 
    restep-version = major "." minor [ "-" pre-release ]
pre-release    = ( %s"draft" / %s"rc" ) "." number
major          = number
minor          = number
number         = "0" / ( %x31-39 *DIGIT )
    Sin sufijo ("1.0", "1.1") nombra una versión publicada. Con sufijo nombra un borrador ("1.0-draft.7", "1.1-draft.2") o una candidata ("1.0-rc.1") de la versión que va antes del guion. Un servidor que implementa un borrador o una candidata DEBERÍA declararlo así y no como la versión publicada. Un cliente de Restep 1 NO DEBE tratar como documento de descubrimiento de Restep 1 uno cuyo restep no cumpla esta gramática o cuya versión mayor no sea 1, y ante uno de otra versión mayor NO DEBE recurrir tampoco a suponer solo core, como pide 4.2 a un cliente que no encuentra documento de descubrimiento: esa API no es una que pueda usar como Restep 1.
  • Un borrador o una candidata pueden diferir de forma incompatible de la versión publicada del mismo número y de cualquier otro borrador. Un cliente NO DEBE suponer, para una versión con sufijo, las garantías de este apartado: que cumple alguna versión publicada o algún otro borrador. Un cliente que no conoce ese borrador exacto PUEDE trabajar con él según las reglas de la versión sin sufijo, salvo en sus partes experimentales (1.2), y trata lo que difiera como trata cualquier error. Los ejemplos de este texto dicen "1.0".
  • Una versión menor NO DEBE reservar más nombres de parámetro que los de 5.3, salvo los que empiezan por $, que quedan para versiones futuras de Restep. De ellos, $api_version ya está reservado para las versiones con fecha (5.5).
  • Un cambio incompatible será Restep 2, con URI nuevas (/2/core…). Las URI de /1/, bajo https://w3id.org/restep/1/, no cambiarán nunca; si el texto se muda a otro sitio, solo cambia adónde redirigen.
  • Hasta que se publique la 1.0, los borradores sí pueden cambiar de forma incompatible.

1.2 Perfiles y dependencias

Cada perfil solo añade requisitos; ninguno cambia el tipo ni el significado de lo que define otro anterior, así que anunciar un perfil nuevo nunca rompe a un cliente que ya funcionaba. Algunos perfiles necesitan otros:

Perfil o extensiónRequiereEstado
coreNada; toda API Restep lo implementaEstable
query, writes, cache, relationscoreEstable
synccore y query (para pedir por id los elementos cambiados)Experimental
actions, oauthcoreEstable
batch, inheritcoreExperimental
filter-expr, query-methodqueryExperimental

Un servidor NO DEBE anunciar un perfil o una extensión sin los que requiere.

Cada perfil y cada extensión es estable o experimental, como dice la tabla y repite el título de su apartado.

  • Uno estable sigue 1.1: las versiones menores posteriores solo le añaden cosas.
  • Uno experimental PUEDE cambiar de forma incompatible en una versión menor, hasta que una versión lo declare estable. Es la única excepción a «lo que cumple la 1.0 sigue cumpliendo la 1.1». Pasar de experimental a estable solo es un cambio de ese tipo si cambia el texto.
  • Se anuncia como cualquier otro, con su nombre en profiles o extensions; su forma experimental no tiene un nombre aparte. Un servidor DEBE implementar, para todo lo que anuncia, partes experimentales incluidas, el texto de la versión que declara en restep.
  • Un cliente NO DEBE usar un perfil o una extensión experimental salvo que restep declare una versión cuyo texto de ese perfil o extensión implemente el cliente; si es un borrador o una candidata, ese mismo. Así, un cliente escrito para el sync experimental de la 1.0 deja de usarlo con un servidor que declara la 1.1, hasta que aprenda el texto de la 1.1, en vez de seguir reglas que ya no valen. Un cliente usa un perfil o una extensión experimental cuando envía una petición que solo esa parte define, o cuando se apoya en una regla suya para interpretar una respuesta; ignorar sus miembros no es usarlo.

2. Términos

Las palabras DEBE, NO DEBE, DEBERÍA, NO DEBERÍA y PUEDE, y sus plurales, tienen el sentido de MUST, MUST NOT, SHOULD, SHOULD NOT y MAY en el RFC 2119 y el RFC 8174, solo cuando aparecen así, en mayúsculas. Todo requisito de esta especificación lleva una de ellas; las frases sin ellas explican o dan ejemplos.

  • Raíz de la API: la URL base con la que se configura un cliente, por ejemplo https://api.ejemplo.com/ o https://ejemplo.com/api/. Las rutas de esta especificación, de los miembros path del descubrimiento y de los lotes y de events (10), como /books, son relativas a ella: bajo https://ejemplo.com/api/, /books es https://ejemplo.com/api/books. Los enlaces de cuerpos y cabeceras no: son referencias URI (RFC 3986) que se resuelven contra la URL de la petición.
  • Colección: un recurso que agrupa elementos de la misma clase, como /books. Sus elementos pueden ser variantes con esquemas distintos (libros, revistas y tarjetas regalo en /products), siempre que cada campo tenga un solo tipo en todas ellas (4.2).
  • Elemento: un recurso de una colección, como /books/7. En inglés, item; en el JSON el campo sigue siendo items.
  • Representación de un elemento: el cuerpo que describe el elemento tal como está ahora; es el único cuerpo con el que un cliente actualiza su copia de ese elemento.
  • Resultado de una acción: el cuerpo de un 200 a una acción segura que declara output (11.1); describe la acción, no el elemento sobre el que se pidió, y no sustituye ninguna copia.
  • Singleton: un recurso que no es una colección ni un elemento de una, declarado aparte en el descubrimiento, en la raíz de la API (/me) o bajo un elemento u otro singleton (/readers/7/settings); existe mientras existe su padre (5.9).
  • Perfil: un conjunto de reglas con nombre (core, query…), con una URI propia, que se anuncia en profiles, con el que todo cliente de la API puede contar sin leer ninguna declaración y que habilita sus capacidades (RFC 6906). Con writes, todo POST no idempotente admite Idempotency-Key.
  • Extensión: un mecanismo opcional, con una URI propia, que se anuncia en extensions y que no cambia nada para un cliente que no lo usa. Suele tener sintaxis propia (un método, una ruta, una forma de parámetro, un intercambio de cabeceras), pero no es eso lo que lo hace una extensión.
  • Parámetro reservado: un parámetro de consulta cuyo significado define Restep (apartado 5.3).
  • Principal: en nombre de quién actúa una petición, tal como lo autentica el servidor (en OAuth 2.0, el cliente y, si lo hay, el usuario), y quien actúa por cuenta de él, si hay alguien (el claim act del RFC 8693, apartado 4.1). No es la credencial: una petición con un token renovado viene del mismo principal. Un administrador que actúa como un usuario es un principal distinto de ese usuario, así que las claves de idempotencia (7.1), los cursores (6.4) y las respuestas guardadas nunca se comparten entre los dos; qué puede ver y hacer una petición así lo decide el servidor.
  • Capacidad: algo que un recurso declara en el descubrimiento dentro de un perfil o una extensión (un filtro, un operador, un campo de orden, una relación, una acción, un mapa de idioma, un campo traducido, un id elegido por el cliente, una subida). Qué significa una capacidad lo dice un perfil o una extensión; si un recurso la tiene lo dice solo su declaración.
  • Iguales como valores JSON: del mismo tipo y, en los objetos, con los mismos nombres de miembro y valores iguales, sea cual sea su orden y su espacio en blanco; en las listas, con elementos iguales en el mismo orden; en los números, el mismo número decimal (1 y 1.0); en las cadenas, la misma secuencia de puntos de código una vez quitados los escapes, sin normalización Unicode.

Así, una regla va en un perfil cuando todo cliente puede contar con ella sin mirar ninguna declaración, en una extensión cuando no cambia nada para un cliente que no la usa, y en una capacidad cuando solo vale donde un recurso la declara. Con este criterio, ninguna parte de Restep 1 cambia de nivel (1.2).

3. Datos

  • Los cuerpos DEBEN ser JSON (RFC 8259) en UTF-8, y lo que envía cada parte DEBE ser un mensaje I-JSON (RFC 7493, apartado 2): sin sustitutos sin pareja ni no caracteres, y sin nombres de miembro repetidos en un objeto. Las excepciones son las respuestas sin cuerpo (204, 304, HEAD), el flujo de eventos de sync, los bytes de una subida (5.1) y los recursos ajenos a Restep (5.9). El servidor PUEDE rechazar un cuerpo de petición con un sustituto sin pareja, un no carácter o U+0000 con 422 invalid y una entrada format, cuyo pointer es la cadena que lo contiene, o "" si esa cadena es un nombre de miembro o el servidor no sabe localizarla: un puntero a un nombre de miembro tendría que contener el mismo punto de código. Un cuerpo que además tiene un error de sintaxis JSON recibe en cambio 400 bad_request (5.4). El servidor DEBERÍA rechazar un cuerpo de petición con nombres de miembro repetidos con 400 bad_request: la mayoría de los analizadores se quedan con uno de ellos sin avisar, así que el sentido de ese cuerpo dependería del analizador.
  • Una petición con cuerpo a un recurso de Restep (un POST a una colección, a una acción o a un lote; un QUERY) DEBE llevar Content-Type: application/json; un PATCH sigue 5.1, y un POST a una colección que declara upload puede llevar un archivo en su lugar (5.1). El servidor DEBE responder 415 unsupported_media_type a cualquier otro tipo de medio, y a un cuerpo sin Content-Type. Un cuerpo vacío es un cuerpo: sin Content-Type DEBE dar 415, que aquí prevalece sobre el 400 que también permitiría estar vacío (5.4), y con un tipo de medio que el recurso acepta DEBE dar 400 bad_request; esto vale también para un PATCH. Tratar un cuerpo sin tipo como uno de un tipo que el recurso no admite es una elección de Restep: el RFC 9110 (apartado 15.5.16) no dice cómo responderlo. La única excepción es un cuerpo vacío a una acción (11.1). Esto importa sobre todo con cookies: un navegador envía text/plain, application/x-www-form-urlencoded y multipart/form-data desde cualquier origen sin preflight de CORS (5.8), así que un servidor que leyera uno de ellos como JSON aceptaría escrituras que el preflight existe para impedir.
    • El tipo de medio se compara sin distinguir mayúsculas, como dice el RFC 9110. application/json no define parámetros, y el RFC 8259 (apartado 11) observa que añadir un charset no tiene efecto en los destinatarios que lo cumplen; Restep se aparta de esa nota porque el apartado 8.1 exige que el JSON que se intercambian los sistemas sea UTF-8, así que un cuerpo etiquetado con otro charset no puede ser JSON válido. El servidor DEBE aceptar charset=utf-8, en mayúsculas o minúsculas y con comillas o sin ellas, DEBE responder 415 a cualquier otro charset y DEBE ignorar los demás parámetros.
    • Una respuesta 2xx con cuerpo DEBE llevar Content-Type: application/json, que PUEDE añadir charset=utf-8, como pueden las peticiones. Las excepciones son el flujo de eventos (text/event-stream), un JSON Schema, que PUEDE usar application/schema+json (no está registrado en la IANA, así que un cliente acepta también application/json para un esquema), los bytes de una subida, y el estado del servicio, que PUEDE usar application/health+json (de un Internet-Draft individual caducado, y tampoco registrado; 4.4). Los errores usan application/problem+json (5.4) diga lo que diga Accept: el servidor NO DEBE responder 406 solo porque Accept no incluya application/problem+json.
  • Los nombres de los campos que define Restep van en snake_case. Los de cada API son cosa suya, pero DEBERÍAN seguir un único convenio.
  • Un nombre que da una API y que declara el descubrimiento o lleva un parámetro (la clave de una colección, un singleton, una acción, una relación, un filtro con nombre o una razón, y un campo que declara el descubrimiento o que nombran filter, sort, fields, include o filter-expr) DEBE cumplir esta gramática (ABNF, RFC 5234): 
    name = ALPHA *63( ALPHA / DIGIT / "_" / "-" )
    Sirve para snake_case y para camelCase, y distingue mayúsculas de minúsculas. Nunca lleva ., ,, [, ], : ni espacios, que los parámetros y las rutas usan para separar rutas con puntos, listas, operadores y acciones, y nunca empieza por -, que marca un orden descendente (6.2). Una ruta con puntos (author.id) son nombres unidos por ., salvo que su último segmento puede ser una etiqueta de idioma (name.es-mx, 6.1). Un campo cuyo nombre no cumpla la gramática PUEDE aparecer en las representaciones, pero el servidor NO DEBE declararlo en el descubrimiento, y un parámetro que lo nombre recibe el error de un campo que no existe o no está declarado. Una API no necesita renombrar los campos que nunca declara y que ningún parámetro nombra.
  • Los nombres de miembro que empiezan por _ son de Restep (como _actions o _etag). Una API NO DEBE definir campos con ese prefijo, salvo los que empiezan por _x_.
  • Los nombres de miembro que empiezan por _x_ quedan para extensiones ajenas a Restep, que nunca define ninguno. Son anotaciones del servidor, como los miembros _ de Restep: una escritura los ignora (5.1), fields los conserva (6.3) y los clientes DEBEN ignorar los que no conocen. Sus valores NO DEBEN cambiar entre dos lecturas de la misma versión de un elemento, porque cuentan para su ETag (7.2). Lo que una extensión necesite que el cliente escriba va en campos normales. Ni _x_ ni el x- de los miembros del descubrimiento (4.2) marcan un nombre como no estándar, cosa que desaconseja el BCP 178 (RFC 6648, apartado 4): separan los nombres que definirán las versiones menores posteriores de Restep de los que añade un servidor o una extensión. Como sugiere el RFC 6648 (apartado 3), el resto del nombre DEBERÍA llevar el nombre de la organización o de la extensión (_x_acme_audit, x-acme-region), para que dos extensiones no choquen.
  • El identificador de un elemento se llama id. DEBE ser una cadena no vacía hecha solo de caracteres no reservados del RFC 3986 (A–Z a–z 0–9 - . _ ~), para que vaya en una ruta sin escapar nada, y NO DEBE ser . ni .., que la resolución de URI eliminaría. NO DEBE cambiar. Por eso, un alias que pasa de un elemento a otro, como «la versión actual», es una relación o un elemento propio, nunca un id (apéndice D). Dos id son el mismo solo cuando son la misma secuencia de puntos de código: el servidor NO DEBE dar abc por ocupado porque exista ABC, ni servir un elemento en una ruta cuyo último segmento no sea su id, como el elemento 7 en /books/07. El servidor DEBE comparar cada segmento de una ruta tras decodificar sus porcentajes, así que /books/%37 es /books/7. Un segmento que no decodifica a UTF-8 válido, como %FF, no nombra ningún elemento: el servidor DEBE responderlo como responde a un elemento que no existe, salvo que un servidor HTTP delante de la API lo rechace antes (5.4).
  • Un campo cuyos valores puedan salirse de ±(253−1), que un receptor I-JSON no tiene por qué tratar como exactos (RFC 7493, apartado 2.2), o que necesite aritmética decimal exacta (los importes), DEBE ir como cadena en todas las representaciones, sea cual sea el valor: "price": "18.50". Un importe DEBERÍA ir acompañado de su moneda ISO 4217.
  • Los instantes DEBEN seguir el date-time del RFC 3339 (apartado 5.6), tal como lo actualiza el RFC 9557, con desfase: "2026-11-12T09:30:00Z". Un servidor DEBE escribir T y Z en mayúsculas (RFC 7493, apartado 4.3) y DEBE aceptar las formas en minúsculas que permite el RFC 3339. Dos instantes son iguales cuando denotan el mismo punto en el tiempo, sean cuales sean sus desfases. Un instante PUEDE llevar el desfase local en que ocurrió ("2026-11-12T10:30:00+01:00"); desde el RFC 9557 (apartado 2.2), Z dice que el desfase local se desconoce, no que sea UTC. Un servidor nunca escribe un segundo intercalar (:60), ni en un instante ni en una hora local (más abajo), y DEBE rechazar uno en el cuerpo de una petición con 422 invalid y una entrada format, como lo rechaza un filtro (6.1), salvo en un campo que solo pone el servidor, que un POST ignora sea cual sea su valor (5.1). Las fechas de calendario DEBEN usar full-date: "1987-03-14".
  • Las duraciones DEBERÍAN ser cadenas que cumplan esta gramática; un campo con segundos como número DEBERÍA acabar en _seconds: 
    duration   = "P" ( dur-date / dur-time / dur-week )
dur-date   = ( dur-day / dur-month / dur-year ) [ dur-time ]
dur-time   = "T" ( dur-hour / dur-minute / dur-second )
dur-year   = 1*DIGIT "Y" [ dur-month ]
dur-month  = 1*DIGIT "M" [ dur-day ]
dur-week   = 1*DIGIT "W"
dur-day    = 1*DIGIT "D"
dur-hour   = 1*DIGIT "H" [ dur-minute ]
dur-minute = 1*DIGIT "M" [ dur-second ]
dur-second = 1*DIGIT [ "." 1*9DIGIT ] "S"
    Es la regla duration del RFC 3339 (apéndice A), que allí no es normativa y aquí se copia, más una cosa de ISO 8601: una fracción decimal de hasta nueve cifras, solo en los segundos ("PT1.5S", "PT0.250S"). Fracciones, porque los tiempos de espera, las latencias y la duración de audios y vídeos bajan del segundo y, si no, necesitarían un número aparte; solo en los segundos, para que ningún valor necesite una fracción de hora o de minuto ("PT1H30M", nunca "PT1.5H") y dos longitudes se comparen como números decimales de segundos; hasta nueve cifras, los nanosegundos que guardan los tipos de duración habituales de los lenguajes de programación. Como con los instantes, un servidor DEBE escribir en mayúsculas las letras de una duración y DEBE aceptarlas en minúsculas. Un filtro de tipo duration las compara de forma exacta, como decimales (6.1).
  • Una hora local es una fecha de calendario y una hora de reloj sin desfase, el full-date "T" partial-time del RFC 3339 (apartado 5.6): "2027-03-30T19:00:00". Solo denota un instante junto con una zona, un nombre de la base de datos de zonas horarias de la IANA ("Europe/Madrid"). El descubrimiento declara en local_times qué campos de una colección guardan horas locales y de dónde sale la zona de cada uno (4.2). Convertir una en instante DEBE seguir el RFC 5545 (apartado 3.3.5) y el RFC 8984 (apartado 1.4.5): una hora local que ocurre dos veces es la primera de ellas, y una que no ocurre, por caer en un salto, toma el desfase de antes del salto. Una API que ofrece el instante lo da en un campo datetime aparte y de solo lectura (starts_at_instant).
  • Ausente y null no son lo mismo. En una lectura, un campo sin valor PUEDE omitirse o ir a null, salvo un mapa de idioma, que es {}; en un PATCH, null borra y ausente no toca (RFC 7396).
  • Una relación, cuando una representación la incluye, DEBE ser un objeto con al menos id (a uno), una lista de esos objetos (a muchos), null (a uno, vacía) o [] (a muchos, vacía). Nunca un identificador suelto, para que el tipo del campo no cambie al incluir el elemento relacionado (apartado 9). Si una relación puede apuntar a más de una colección, cada objeto DEBE llevar también type con el nombre de la colección de destino. Un objeto PUEDE llevar href, la ruta del elemento relacionado como enlace absoluto (véase abajo), y DEBE llevarlo cuando la colección de destino es una subcolección, cuyas rutas de elemento no se pueden construir solo con el id (apartado 9).
  • Los enlaces de los cuerpos (next, href) DEBEN ser URI absolutas o rutas absolutas, que empiezan por / e incluyen la ruta de la raíz de la API (/api/books?cursor=…), para que unos dos puntos dentro de un segmento (/orders/2001:cancel) nunca se lean como esquema, como pasaría en la referencia relativa 2001:cancel. Como el RFC 3986 (apartado 3.4) no admite [ ni ] sin codificar en una query, el servidor los codifica con porcentajes en los enlaces que construye (5.2). Una URI absoluta entre estos enlaces, entre los enlaces del documento de descubrimiento y en las cabeceras Location y Link de las respuestas de la API DEBE usar https o el esquema de la raíz de la API; un cliente NO DEBE seguir una con otro esquema, como file: o data:.
  • Los clientes DEBEN ignorar los campos que no conocen y tolerar valores de enumeración nuevos, también los que no lista su copia guardada del descubrimiento o de un esquema: un cliente NO DEBE rechazar una respuesta por uno de esos valores, y PUEDE avisar de él. Antes de enviar uno, un cliente PUEDE comprobar su propia entrada contra lo que tiene guardado.
  • Las respuestas correctas (2xx) de colecciones, elementos y acciones NO DEBEN depender del idioma de quien las lee, lo saque el servidor de donde lo saque (Accept-Language, un ajuste guardado para el principal, una cookie), salvo los campos traducidos que una colección declara en localized, que dependen de Accept-Language y de nada más (5.6), y lo que una petición deriva de ellos: los elementos que selecciona un filtro sobre uno, el orden que da una ordenación por uno, total y el cursor de next (6.1, 6.2, 6.4). Las respuestas que ni llevan campos traducidos ni filtran u ordenan por uno no necesitan Vary: Accept-Language. Los números, importes, fechas, instantes y duraciones van siempre en las formas de este apartado; presentarlos en un idioma es cosa del cliente. Solo cambian con el idioma los textos propios de la API y los campos traducidos (5.6).
  • Un mapa de idioma guarda el mismo texto en varios idiomas: un objeto JSON cuyas claves son etiquetas de idioma (BCP 47: RFC 5646) y cuyos valores son cadenas. Solo los campos de primer nivel de un elemento pueden ser mapas de idioma. El idioma de los campos de texto que no lo son no lo dice Restep. 
    "name": { "en": "Zucchini", "en-gb": "Courgette", "es-es": "Calabacín", "es-mx": "Calabacita" }
    • Cada clave DEBE ser una etiqueta bien formada (la gramática del apartado 2.1 del RFC 5646; no hace falta que esté en el registro) y en minúsculas. El servidor NO DEBE cambiar una clave (iw no pasa a he). Un valor puede ser cualquier cadena, también "".
    • El tipo de un mapa de idioma NO DEBE cambiar: es un objeto aunque tenga una sola traducción o ninguna, y aunque la API hable un solo idioma. Un mapa sin traducciones DEBE darse como {}, no ausente ni null, salvo que la representación no lleve el campo (por fields o por permisos). El servidor NO DEBE rellenar una traducción que no existe con el texto de otro idioma: el cliente elige qué mostrar entre las claves que recibe.
    • En un POST, un mapa de idioma es un objeto de cadenas. En un PATCH se fusiona como cualquier objeto (RFC 7396): {"name": {"fr": "Courgette"}} añade o cambia el francés sin tocar el resto, {"name": {"fr": null}} lo borra, y borrar una clave que no está no hace nada. Tras fusionar, un mapa de idioma que falta vale {}, así que {"name": null} lo vacía. Si se declara el esquema update (4.3), DEBE admitir null en el campo y en cualquier clave bien formada en minúsculas.
    • El servidor DEBE validar el cuerpo antes de fusionar, también las claves que borra, y DEBE responder 422 invalid con una entrada en errors por cada fallo, con pointer a lo que falla y este code: type si el campo no es un objeto o un valor no es una cadena (en un PATCH, null vale en los dos sitios; en un POST, no); format si una clave no es una etiqueta bien formada en minúsculas (/name/ES); unknown si se añade una traducción, o se le da un valor distinto del guardado, en una etiqueta bien formada que la API no acepta.
  • Un campo traducido es un campo de primer nivel y de solo lectura cuyo valor es el texto de un mapa de idioma del mismo elemento, su source, en el idioma de la respuesta (5.6): "name": "Novela negra" a partir de "name_i18n": {"es-es": "Novela negra", "en": "Crime fiction"}. Su valor es una cadena o null. El descubrimiento DEBE listar todos los campos traducidos de una colección en localized, con su fuente: "localized": {"name": {"source": "name_i18n"}}; el resto del objeto de cada campo queda para versiones menores. Si al mapa le falta el idioma de la respuesta, el servidor PUEDE rellenar el campo traducido con el texto de otro idioma; el mapa en sí nunca se rellena (véase arriba). Un cliente escribe el mapa, nunca el campo traducido (5.1).

4. Anunciar Restep

4.1 Cabecera de perfil

Toda respuesta de la API DEBERÍA llevar un enlace rel="profile" (RFC 6906) a la URI de la versión, y solo ese, para que la cabecera mida lo mismo anuncie lo que anuncie el servidor:

Link: <https://w3id.org/restep/1/>; rel="profile"

Qué perfiles y extensiones implementa el servidor lo dice solo el documento de descubrimiento (4.2). Cada uno sigue teniendo su URI, la de la versión seguida de su nombre (https://w3id.org/restep/1/query), que lo nombra en un problema o en un documento, pero el servidor NO DEBERÍA listarlos en las cabeceras de cada respuesta.

Los perfiles valen para toda la API. Las reglas de un perfil que solo se aplican donde un recurso las declara (filter, sync…) son sus capacidades (2), y qué recurso tiene cuál lo dicen solo las declaraciones del documento de descubrimiento.

4.2 Documento de descubrimiento

Un GET a la raíz de la API devuelve un documento con los perfiles, las extensiones y las capacidades del servidor. Un servidor que solo tiene core DEBERÍA servirlo; uno que anuncia cualquier otro perfil o extensión, o que tiene mapas de idioma (3), DEBE servirlo. Si la raíz ya está ocupada, el servidor PUEDE servirlo en otra ruta y enlazarlo desde sus respuestas con Link: <…>; rel="service-desc" (RFC 8631). Una respuesta PUEDE llevar varios enlaces service-desc, por ejemplo uno a un documento OpenAPI; el que apunta al documento de descubrimiento DEBERÍA llevar type="application/json", y el cliente DEBE quedarse con el primer destino que sea un documento de descubrimiento de Restep 1 (1.1).

El cliente DEBE tratar una respuesta como documento de descubrimiento solo si es un 2xx cuyo cuerpo es un objeto JSON con un miembro restep de tipo cadena. Si el GET tiene éxito sin ese miembro, o da 404, DEBE suponer solo core; cualquier otro error, como un 401 o un 503, no dice nada de los perfiles. Si una cabecera Link lista perfiles y no coincide con el documento, prevalece el documento.

Un documento para todos. El documento de descubrimiento describe la API, no lo que un principal puede hacer con ella:

  • Su contenido NO DEBE depender del principal (2) ni de si la petición lleva credenciales; solo cambian sus textos, con Accept-Language (5.6). Dos documentos que el mismo despliegue de la API sirve a la vez con el mismo Accept-Language DEBEN ser iguales como valores JSON (2). Así, dos principales reciben el mismo documento, y una copia guardada con el código de un cliente se puede comparar con la siguiente. Todo lo que declara lo ve quien pueda leerlo (13.12). Una API cuyas colecciones, campos o capacidades declaradas cambian según el inquilino DEBE dar a cada inquilino su propia raíz de la API, con su propio documento de descubrimiento.
  • El servidor PUEDE exigir credenciales para servirlo, y responder 401 si no las hay o 403 a un principal que no puede leerlo; a todo aquel a quien se lo sirve le da el mismo documento. Su respuesta depende entonces de las credenciales (5.1) y DEBE llevar Cache-Control con private o no-store; solo un documento servido sin credenciales PUEDE ser public y guardarse en una caché compartida.
  • Su respuesta DEBERÍA llevar un ETag y un Cache-Control con max-age. Un cliente PUEDE guardarlo mientras ese Cache-Control lo permita, y DEBERÍA revalidarlo después. Un cliente que recibe unsupported_parameter (5.3) o 405 por algo que su copia declara DEBERÍA volver a pedir el documento antes de concluir que la capacidad ya no existe.
  • Lo que un principal no puede hacer lo dice la respuesta a la petición, nunca su ausencia del descubrimiento. Un método, una acción o un singleton declarados que este principal no puede usar DEBEN dar 403 forbidden, o 404 not_found donde su existencia se oculta (5.4), nunca 405 ni unsupported_parameter. Para filtros, orden y fields sobre un campo que el principal no puede leer, véase 6.1. Donde la estructura es la misma para todos los inquilinos y un inquilino no puede usar parte de ella, esa parte DEBE dar 403 forbidden con una reason que lo diga (5.4).

  • Cada perfil añade sus campos al documento; se describen en su apartado. Cuando un miembro que define Restep tiene un valor que el cliente no conoce (el type de un filtro o de un filtro con nombre, el on o el method de una acción, un valor de methods o de item_methods, el kind de una retirada, un valor reservado para versiones menores), el cliente NO DEBE fallar por ello y NO DEBE usar lo que ese valor califica: trata ese filtro, ese filtro con nombre, esa acción, ese método o ese aviso como si no estuviera declarado, salvo que este texto dé otra regla para ese miembro:
    • un operador de ops que no conoce se ignora solo, y el cliente sigue usando los demás operadores de ese filtro (6.1);
    • una declaración de filtro cuyo quantifier no conoce se ignora (6.1);
    • un campo de inherit, o una declaración inherit_items, cuya declaración lleva un miembro que no conoce y cuyo nombre no empieza por x- se trata como no heredado (11.6);
    • un valor de effects que no conoce cuenta como los tres efectos, también en una acción declarada segura (11.1);
    • id_from (5.1), los singletons (5.9), collations (6.1) y from (11.6) tienen sus propias reglas.
  • language_maps: los campos de una colección que son mapas de idioma (3), como objeto cuyas claves son los nombres de campo: "language_maps": {"name": {}, "description": {}}. DEBE declararlos todos; si falta, la colección no tiene ninguno. El objeto de cada campo queda para versiones menores.
  • local_times: los campos de una colección que guardan horas locales (3), como objeto cuyas claves son los nombres de campo, y de dónde sale la zona de cada uno: "local_times": {"starts_at": {"zone": "store.time_zone"}, "meets_at": {}}. zone nombra un campo de tipo timezone, del elemento o al que se llega por una relación a uno (una ruta con puntos, 6.1); un campo sin zone es una hora local flotante, que por sí sola no denota ningún instante.
  • shared_cache está reservado, en la raíz y en cada colección y cada singleton: una versión menor puede usarlo para declarar cuándo una caché compartida puede guardar una respuesta que depende de las credenciales. Un servidor de esta versión NO DEBE enviarlo, y un cliente lo ignora (véase arriba).

Sus variables DEBEN ser expresiones de cadena simples ({var}, nivel 1) cuyos nombres cumplan ALPHA *( ALPHA / DIGIT / "_" ), porque el RFC 6570 (apartado 2.3) no admite - en el nombre de una variable, y DEBEN tener nombres distintos, así que /authors/{author_id}/books/{book_id}/reviews, no {id} dos veces; toman por orden los id de los elementos padre (5.1). Una colección así DEBE nombrar en parent la colección de cuyos elementos cuelga, y su path DEBE ser el path de esa colección seguido de /, de su última variable, de / y de uno o varios segmentos literales: "reviews": {"path": "/books/{book_id}/reviews", "parent": "books"}. Las mismas reglas valen para el path de un singleton con parent (5.9).
  • id_from, reusable_ids, upsert (5.1), upload (5.1) y collations (6.1) son capacidades de una colección; singletons lista los singletons de la API (5.9).
  • Los tipos de campo, donde el descubrimiento los declara, salen de esta lista: string, integer, number, decimal (una cadena que cumple -?[0-9]+(\.[0-9]+)?), boolean, date, datetime, localdatetime (una hora local, 3), timezone (el nombre de una zona, 3), duration (la gramática de 3) y enum (con sus values). El descubrimiento solo declara tipos donde Restep los necesita, como en los filtros; la forma de las representaciones y de los cuerpos de las peticiones va en los esquemas de 4.3. Un nombre de campo DEBE tener el mismo tipo en todos los elementos de una colección, sea cual sea su variante (2); un esquema puede distinguir las variantes con oneOf (4.3). Una representación también PUEDE enlazar su esquema con rel="describedby".
  • Un origen que lista sus APIs en /.well-known/api-catalog (RFC 9727) PUEDE incluir ahí una API Restep, con la raíz de la API como anchor, un enlace service-desc a su documento de descubrimiento y sus enlaces service-doc, si los hay.

4.3 Describir las operaciones

Miembros opcionales con los que un cliente, sea una persona que lee el documento o un agente que elige herramienta, sabe qué hace y qué acepta cada colección sin probarlo. El servidor PUEDE declarar cualquiera de ellos en cualquier colección; Restep no exige ninguno, así que un servidor core se sigue pudiendo escribir a mano.

  • methods e item_methods: los métodos que admiten una colección y sus elementos, de entre GET, POST, PATCH y DELETE (HEAD va con GET; las acciones y QUERY se anuncian aparte; PUT nunca está entre ellos, 5.1). Si falta la lista, no se sabe; no significa que estén todos. Una lista declarada DEBE ser exacta: un método que no está da 405, salvo que se dé otro error aplicable (5.4), uno de la lista nunca lo da, y la cabecera Allow de un 405 DEBE nombrar todos los métodos declarados, HEAD donde nombre GET, y ningún otro de esos cuatro (RFC 9110, apartado 15.5.6). Una colección cuyos methods no incluyen GET no se puede listar: NO DEBE declarar filter, named_filters, sort, count ni sync (5.2).
  • method_effects e item_method_effects: los efectos (11.1) de los métodos no seguros de una colección y de sus elementos (un singleton declara method_effects para su PATCH, 5.9), como objetos cuyas claves son métodos de methods y de item_methods: "item_method_effects": {"DELETE": ["destroys"], "PATCH": []}. Un DELETE que no declaran tiene ["destroys"], que es lo que el propio método ya dice; "DELETE": [] dice que el borrado se puede deshacer. Cualquier otro método no seguro que no declaran cuenta como si tuviera los tres efectos. Una description nunca sustituye a esta declaración.
  • description: una explicación breve, en texto plano, de una colección, un singleton, un campo de filtro, una relación, una acción, un campo heredado (11.6) o una razón (5.4). DEBERÍA ser una frase.
  • schemas: esquemas JSON Schema (2020-12) del item de una colección (su representación sin fields ni include), de create (el cuerpo de un POST) y de update (el cuerpo de un PATCH: un merge patch, donde lo ausente deja el campo como está y null lo borra). Cada uno es un objeto de esquema o un enlace a uno, absoluto como los enlaces en los cuerpos (3). Los esquemas pueden describir cada campo con su propio description. El esquema item de una colección con variantes (2) puede ser un oneOf cuyas ramas fijan cada una con const una propiedad que las distingue ("kind": {"const": "book"}). En una colección que declara upload, create dice además si crea elementos desde JSON (5.1).
  • Un default en una propiedad de primer nivel de create es el valor que toma el campo cuando un POST no lo trae, y el servidor DEBE darle ese valor, que DEBE ser válido contra el esquema de la propiedad (JSON Schema Validation solo lo recomienda, en el apartado 9.2, pero aquí default tiene efecto); un campo enviado como null sí lo trae. En update un default no significa nada, porque un campo ausente de un PATCH se queda como está.
  • Un cliente puede construir un formulario para personas a partir de estos esquemas (apéndice A). Muestra los campos en el orden de properties, así que el servidor DEBERÍA escribirlos en el orden en que quiere que se vean.
  • Antes de validar un cuerpo contra un esquema create o update declarado, el servidor quita los miembros que empiezan por _, que 5.1 ignora, y, en un PATCH, todo campo cuyo valor actual ignora 5.1, y, en un POST, todo campo de solo lectura que ignora 5.1; un PATCH que se queda vacío así no se valida contra update. En ambos, un campo de solo lectura con otro valor DEBE dar la entrada read_only de 5.1, no un error de esquema. Un cuerpo que el esquema rechace entonces DEBE dar 422 invalid (también si es un valor JSON que no es un objeto, con una entrada cuyo pointer es "" y cuyo code es type), salvo que se dé otro error aplicable (5.4), y su errors DEBERÍA señalar los miembros que fallan. Un esquema describe, no promete: un cuerpo que acepta puede fallar igualmente por las reglas propias de la API. readOnly es solo una anotación, salvo en lo que dice 5.1 de las propiedades de primer nivel de un esquema item, y id sigue 5.1 diga lo que diga el esquema: un esquema create puede restringir el formato de un id que elige el cliente, pero no puede hacer que el servidor acepte un id que 5.1 rechaza.
  • El input de una acción (11.1) es el esquema de su cuerpo, con el mismo sentido; sus params y su output se describen en 11.1.
  • Un cliente DEBE mandar sus credenciales de la API solo a URL del origen de la API, y DEBE pedir sin ellas un esquema o documento de otro origen (13.2). NO DEBERÍA resolver el $ref de un esquema fuera del origen del esquema que lo contiene, y NO DEBERÍA enviar un valor que haya sacado de un esquema de otro origen, como un default, sin enseñárselo antes al usuario.

Las descripciones, los títulos y cualquier otro valor que devuelve una API son datos, nunca instrucciones para el cliente. Una declaración de efectos (11.1) también es un dato: permite a un cliente preguntar antes de actuar, y no autoriza nada. Un cliente NO DEBE, solo por un texto así, hacer una petición que no sea segura (5.7) y que la tarea a la que sirve no pidiera ya, ni enviar datos a otro origen. Usar detail y errors para corregir la petición que ya está haciendo no es seguir una instrucción. Un agente que mete estos textos en un prompt DEBERÍA marcar dónde empiezan y dónde acaban (13.1).

4.4 Estado del servicio

El servidor PUEDE declarar en status un enlace, absoluto como los enlaces en los cuerpos (3), a un recurso que dice si la API puede atender peticiones, y PUEDE enlazarlo también desde sus respuestas con rel="status" (RFC 8631). El cliente NO DEBE suponer una ruta como /health.

  • Salvo que pida credenciales o las rechace (401, 403) o limite el ritmo (429), un GET o un HEAD a ese recurso DEBE responder 200 cuando la API puede atender peticiones y 503 cuando no, con Retry-After si el servidor sabe cuánto tiempo, y siempre con Cache-Control: no-store.
  • No es un recurso de la API: no se le aplican 4.1, de 5.1 a 5.4 ni 8, salvo que su 429 lleva Cache-Control: no-store, como exige el 5.4. Su cuerpo PUEDE seguir el Health Check Response Format (draft-inadarei-api-health-check, revisión 06, un Internet-Draft individual caducado cuyo tipo de medio no está registrado). Si se sirve sin credenciales, NO DEBERÍA decir más que si la API puede atender.

El servidor PUEDE restringir más su formato, y entonces DEBERÍA decir cómo en el esquema create (4.3); un id bien formado que se sale de ese formato recibe el mismo 422 con format. El servidor DEBERÍA exigir un formato con entropía suficiente para que los clientes no coincidan por azar, como un UUID o un ULID; si oculta a algunos principales la existencia de elementos de esa colección (5.4), DEBE exigir un formato que no se pueda adivinar, como un UUID de la versión 4, porque el 409 de abajo dice si un id está en uso. Un cliente DEBERÍA generar ese id a partir de una fuente aleatoria y NO DEBERÍA derivarlo de los datos del elemento (un correo, un nombre), porque quien pueda adivinarlo puede quedárselo antes o saber por el 409 de abajo que existe (13.6).
    • Un id que tiene un elemento de la misma colección (en una subcolección, bajo el mismo elemento padre) DEBE dar 409 conflict con una entrada de errors cuyo pointer es /id y cuyo code es taken. En una colección que no declara reusable_ids, también lo DEBE dar un id que ha tenido un elemento así. Esa respuesta DEBE ser la misma pueda o no ver el cliente el elemento que tiene el id, o pudiera o no ver el que lo tuvo. El servidor DEBE conocer esos id mientras exista la colección; una subcolección existe mientras exista su elemento padre. Un servidor que reutiliza el id de un elemento padre borrado, cosa que desaconseja el punto siguiente, NO DEBE dejar que la subcolección del padre nuevo tome un id que tuvo la del antiguo. PUEDE guardar solo un hash unidireccional de los id de los elementos borrados. En una colección que declara reusable_ids, el id de un elemento borrado vuelve a estar libre: un POST con él DEBE crear un elemento nuevo (201), y el servidor no necesita recordarlo.

Por lo mismo, el servidor NO DEBERÍA reutilizar en una colección los id que asigna él. En una colección con reusable_ids, cada elemento que vuelve a tomar un id es una encarnación nueva: su ETag de elemento DEBE ser distinto del de cada encarnación anterior con ese id (7.2), sync lo da en created (10), y un DELETE o un PATCH solo se pueden repetir sin riesgo con If-Match (5.7), que el servidor PUEDE exigir desde el momento en que declara la colección (7.2). Una relación con una colección así nombra la clave, no la encarnación; qué le pasa cuando se borra el elemento lo decide el servidor.
    • Así, fuera de reusable_ids, un POST con un id elegido por el cliente nunca crea dos elementos. Un cliente que lo repite y recibe 409 con taken lee el elemento para saber si su primer intento tuvo efecto (5.7); con writes, Idempotency-Key funciona como en cualquier POST y devuelve en su lugar la respuesta guardada (7.1).
    • En una colección que declara upsert, un PATCH a la ruta de un id libre (uno que crearía un POST con ese id, arriba) DEBE crear el elemento, como permite RFC 5789 (apartado 2): el servidor aplica el merge patch a {}, valida el resultado como el cuerpo de un POST (contra el esquema create, si se declara, 4.3) y responde 201 con Location y la representación, como a un POST. El id sigue las reglas de arriba para los id que elige el cliente. El id de un elemento borrado, que no está libre en una colección sin reusable_ids, da 404. If-None-Match: * hace que el PATCH solo tenga éxito si crea, e If-Match, solo si el elemento existe; si no, DEBE dar 412 (7.2). Un PATCH a la ruta de un elemento que existe pero cuya existencia se oculta a este principal (5.4) DEBE dar el 404 que recibe el id de un elemento borrado; como la entrada taken, dice que el id está en uso, y por eso una colección así exige un formato que no se pueda adivinar (arriba, 13.6).
    • Estas reglas valen para todos los elementos de la colección, los cree quien los cree, incluido un recurso fuera de Restep (5.9).
  • Una colección PUEDE declarar upload: {"media_types": ["image/*", "application/pdf"], "max_size": 10485760}. Un POST a ella PUEDE traer, en vez de JSON, los bytes de un archivo de uno de esos tipos de medio (* casa con cualquier subtipo, y */* con cualquier tipo de medio), con su propio Content-Type y, si quiere, su nombre original en Content-Disposition con filename. La colección DEBE declarar un esquema create (4.3) si, y solo si, también crea elementos desde JSON; sin create, solo admite subidas, y quitar create de una colección que sigue declarando upload es un cambio incompatible (5.5), y también lo es añadir create a una cuyos media_types admiten application/json. Solo una petición cuyo propio Content-Type es application/json selecciona la creación de un elemento desde JSON; cualquier otro tipo de medio, también uno +json como application/ld+json, es un archivo como cualquier otro. Donde declara create, un POST con application/json es siempre la creación de un elemento, nunca un archivo: un archivo JSON solo se sube como la parte file de multipart/form-data (más abajo), así que, si media_types admite application/json, también mediante un comodín como */* o application/*, la colección DEBE declarar "multipart": true. Donde no declara create, un cuerpo application/json es un archivo cuando media_types lo admite, también mediante un comodín. El servidor DEBE responder 415 a un tipo de medio que no declara, también a un cuerpo JSON donde la colección no declara create y sus media_types no admiten application/json, tampoco mediante un comodín, y 413 content_too_large a un archivo de más de max_size bytes. Ese 415 DEBERÍA llevar Accept-Post con los tipos de medio que acepta la colección (Linked Data Platform 1.0, apartado 7.1). Crea un elemento corriente, en JSON, con los campos que elija la API, y DEBE darle un miembro _content con el enlace a los bytes, su tipo de medio y su tamaño: "_content": {"href": "/files/f_9/content", "media_type": "image/jpeg", "size": 48213}. Los bytes de ese enlace son un recurso fuera de Restep (5.9). Otros elementos enlazan un elemento así con una relación (9), cuya declaración PUEDE llevar media_types, para que un formulario ofrezca solo esos archivos y el servidor rechace un archivo de otro tipo con 422 invalid y una entrada format cuyo pointer es el id de la relación; o el elemento pertenece a una subcolección que declara upload, como /orders/2001/attachments. Un elemento que nada enlaza PUEDE caducar; la API dice cuándo en un campo del elemento, expires_at.
  • Donde upload declara "multipart": true, el POST PUEDE traer en su lugar multipart/form-data (RFC 7578) con exactamente una parte, llamada file, que lleva los bytes con su propio Content-Type y su filename (apartado 4.2). El cliente DEBE enviar un parámetro filename en la parte file, con un nombre genérico (como file) cuando el original no está disponible o es privado; el servidor NO DEBE exigirlo y DEBE leer como el archivo una parte file por lo demás válida que no lo lleve. Un Content-Type exterior multipart/form-data selecciona siempre la subida multipart y DEBE dar 415 unsupported_media_type salvo que upload.multipart sea true, aunque media_types case con él. Cualquier otro cuerpo multipart DEBE dar 415 también. Un navegador envía este tipo de medio desde cualquier origen sin preflight (5.8): un servidor que acepta credenciales que un navegador adjunta por su cuenta depende aquí de la comprobación de Origin de 5.8, que DEBE aplicar. Una escritura que lleva a la vez un archivo y los campos de otro elemento queda fuera de Restep: son dos peticiones, una subida y una escritura que la enlaza.
  • En una escritura, el servidor DEBE ignorar los miembros cuyo nombre empieza por _, para que el cliente pueda devolver una representación que leyó.
  • Un campo de solo lectura es uno que ningún cliente puede cambiar con un PATCH: id, un campo efectivo (11.6), un campo traducido (3), uno que solo pone el servidor (created_at, un total) o una propiedad de primer nivel que el esquema item marca con "readOnly": true directamente en sus properties (4.3); un servidor NO DEBE marcar así una propiedad que algún cliente o algún estado del elemento deja cambiar con un PATCH. Un valor de un PATCH es el actual cuando es igual al valor del campo tal como se leyó, según el tipo del campo (el mismo decimal, el mismo instante), cuando aplicarlo como dice este apartado (una relación por su id, un mapa de idioma por clave) deja el campo como estaba antes del PATCH, o, en un campo traducido, cuando es igual al texto de ese campo en cualquier idioma que ofrezca el servidor. Si un PATCH trae un campo de solo lectura con su valor actual, el servidor DEBE ignorarlo; con otro valor, DEBE responder 422 invalid con una entrada read_only cuyo pointer es el campo, y NO DEBE aplicar nada de esa petición. Un campo que este cliente, o el estado actual del elemento, no le deja cambiar sigue la primera mitad de esa regla: su valor actual se DEBE ignorar, y otro valor DEBE dar 403 forbidden si este principal no puede cambiarlo, o 409 conflict si el estado del elemento no lo permite, sin aplicar nada de esa petición; los dos DEBERÍAN llevar una entrada de errors cuyo pointer es el campo. En un campo que el cliente puede leer, el servidor compara después de validar un mapa de idioma como dice 3. En uno que no puede leer, no se aplican ni las reglas anteriores ni las comprobaciones de 3 que miran el valor guardado: el servidor PUEDE validar el valor enviado (un campo de solo escritura, como una contraseña, se valida como cualquier otro), pero su respuesta NO DEBE depender del valor guardado. Un campo que distingue las variantes de una colección (kind) DEBERÍA ser de solo lectura una vez que existe el elemento.
  • En un POST, un campo que solo pone el servidor (created_at, un total) se DEBE ignorar, sea cual sea su valor, segundo intercalar (3) incluido: el caso es el de una representación leída que se reenvía, y el elemento nuevo casi nunca recibiría los valores que trae. Un campo que solo pone el servidor es uno que ningún cliente puede fijar directamente, ni en un POST ni en un PATCH (created_at, un total); no lo son id, los campos efectivos ni los campos localizados, y ni un "readOnly": true en el esquema item ni la ausencia del campo en las properties de un esquema create bastan para establecerlo, ni siquiera juntos. Cualquier otro campo de solo lectura distinto de id (cuyas reglas están arriba) se DEBE ignorar si su valor es el que recibiría el elemento, y si no, DEBE dar 422 invalid con una entrada read_only cuyo pointer es el campo.
  • Un PATCH válido que, dejando aparte los campos que ignora, no cambiaría ningún dato del elemento NO DEBE cambiarlo: su representación y su ETag, si la hay, siguen igual, y un campo como updated_at no se mueve. Así, los campos de solo lectura de una representación leída nunca hacen fallar un PATCH ni cambian nada, si el elemento no ha cambiado desde entonces.
  • En una escritura, el objeto de una relación se sustituye entero, no se fusiona: el servidor DEBE leer solo su id (y type, y href cuando su destino es una subcolección) y NO DEBE modificar a través de él el elemento relacionado. Para enlazar un elemento de una subcolección, el cliente DEBE enviar su href, tal como lo leyó; un href que no es la ruta de un elemento de la colección de destino, o cuyo último segmento no es el id enviado, DEBE dar 422 invalid con una entrada format cuyo pointer es ese href. Una relación con un elemento que no existe, o que el principal no puede ver, DEBE dar 422 invalid con una entrada cuyo pointer es el id de la relación (/author/id) y cuyo code es unknown, igual en los dos casos. Una relación cuyo valor es el actual (deja el campo como estaba) no se comprueba así: el servidor DEBE ignorarla, de modo que devolver una representación tal como se leyó nunca falla por ella. {"author": {"id": "4"}} enlaza otro autor; {"author": null} quita el enlace. Una lista a muchos se sustituye entera, como hace Merge Patch con cualquier lista.

5.2 Colecciones

Una colección que admite GET DEBE responder con un objeto que tenga items (una lista) y next: la URL de la página siguiente o null si no hay más. next DEBE estar presente siempre, aunque el servidor no pagine todavía.

{ "items": [ { "id": "7", "title": "La niebla de Portugalete" } ],
  "next": null }
  • El cliente DEBE seguir next tal cual, sin modificarla ni construirla, salvo los parámetros que 6.4 le deja cambiar entre páginas. Codificarla de nuevo no cuenta como modificarla: el servidor DEBE leer los parámetros tras decodificar los porcentajes, así que filter[price] y filter%5Bprice%5D, o %5b y %5B, son lo mismo, y NO DEBE depender del orden de parámetros con nombres distintos. El servidor DEBE leer un + de la query como un espacio, como hace el analizador de application/x-www-form-urlencoded del URL Standard (apartado 5.1), y con él la mayoría de los frameworks HTTP. En los enlaces que construye, el servidor DEBE codificar con porcentajes [ y ] (%5B, %5D), que RFC 3986 (apartado 3.4) no permite sin codificar en una query, y un + literal (%2B), y DEBE escribir tal cual los dos puntos que preceden al nombre de una acción (11.1); un cliente DEBE enviar un + literal como %2B, y PUEDE enviar [ y ] sin codificar, porque el servidor los decodifica. Siempre que este texto dice «tras decodificar los porcentajes» de la query, un + es un espacio.
  • Una colección DEBE tener un orden por defecto determinista. Cuando ese orden, o una ordenación (6.2), usa id, es el orden de sus id que tenga el servidor: total y estable, pero no necesariamente por puntos de código (con id numéricos, "7" puede ir antes que "12"). El cliente NO DEBE suponer ningún orden de los id. Sin escrituras concurrentes, seguir next hasta null DEBE devolver exactamente una vez cada elemento que selecciona la petición: los que el cliente puede ver que cumplen sus filtros y los filtros por defecto que no desactiva (6.1). Una petición que desactiva todos los filtros por defecto y no lleva ningún otro filtro selecciona todos los elementos que el cliente puede ver: es la petición de una copia completa, que solo existe donde la colección admite GET y no exige ningún filtro. Un cliente que copia una colección entera DEBE recorrerla con esa petición. Con escrituras concurrentes puede haber repetidos u omitidos; el cliente que necesite una copia exacta usa sync.
  • El servidor elige el tamaño de página. Sin el perfil query, el cliente no puede cambiarlo.
  • El objeto PUEDE llevar otros campos definidos por los perfiles (total, state).

5.3 Parámetros reservados: fallar en voz alta

Estos nombres de parámetro, con y sin corchetes, son de Restep: filter, sort, fields, include, count, limit, cursor, since y languages (sin uso en Restep 1), más cualquier nombre que empiece por $.

Las formas que define Restep son nombre=valor y, para filter, filter[campo] y filter[campo][op]. Cualquier otra forma con corchetes (filter[a][b][c], filter[], fields[]) es una forma que el recurso no admite.

Salvo que se dé otro error aplicable (5.4), si una petición usa un parámetro reservado, o una forma de uno, que el recurso no implementa para ese método, el servidor DEBE responder 400 con el código unsupported_parameter y el nombre del parámetro, tal como llegó tras decodificar los porcentajes, en parameter. NO DEBE ignorarlo.

Es la regla que permite subir de peldaño sin romper a nadie: un cliente que filtra contra un servidor que no sabe filtrar recibe un error claro, en vez de la colección entera como si el filtro se hubiera aplicado. Los parámetros que no son reservados son de cada API, y Restep no dice nada sobre ellos.

Los dos códigos de parámetro le dicen al cliente si debe corregir la petición o renunciar a la capacidad:

  • unsupported_parameter DEBE usarse cuando la petición pide algo que el recurso no ofrece: un parámetro reservado que no implementa, una forma de parámetro que no admite (filter=… sin filter-expr, sort[…]), un campo u operador de filtro, un campo de orden o una relación que no están declarados, count con cualquier valor en una colección que no lo declara (6.5), o fields o include en un método que no sea GET, HEAD ni QUERY (6.3). Vale para todos los métodos: POST /books?filter[x]=1 también lo da. En una acción GET (11.1), un parámetro de query que sus params no declaran, cualquiera donde no declara params, DEBE dar también unsupported_parameter, aunque no sea reservado.
  • invalid_parameter DEBE usarse cuando una capacidad admitida recibe un valor erróneo: un valor que no encaja con el tipo del campo, un limit fuera de rango, un campo de fields que no existe, una lista vacía, un parámetro repetido, un cursor no válido. Igual que unsupported_parameter, DEBE llevar en parameter el nombre del parámetro que falla, tal como llegó tras decodificar los porcentajes; si falta, su nombre, como filter[isbn] para un filtro obligatorio (6.1); en el cuerpo de un QUERY (11.4), el nombre del parámetro equivalente de un GET, como filter[price][le], o el del propio miembro si no lo hay. Si fallan varios, parameter nombra uno de ellos, y errors PUEDE listar cada uno con su parameter. Un servidor cuyo framework se queda con un solo valor de un parámetro repetido DEBE detectar igualmente la repetición, leyendo él mismo la query si hace falta.
  • Algunos límites se declaran: max_limit (6.4), include_depth (9) y batch.max_operations (11.2). Un servidor PUEDE limitar también, sin declararlo, cuánto pide una petición a una capacidad admitida: los valores de una lista in, el número de filtros, el tamaño de una expresión filter-expr. Una petición que pasa de ese límite DEBE dar invalid_parameter con el nombre del parámetro, y su detail DEBERÍA decir el límite; el servidor NO DEBE aplicar solo una parte, ni responder unsupported_parameter, porque la capacidad existe. Una URL más larga de lo que acepta el servidor DEBE dar 414; un cuerpo más grande de lo que acepta, 413, y demasiadas peticiones o flujos abiertos, 429 (13.8).

5.4 Errores

Toda respuesta 4xx o 5xx que genera la API DEBE ir en application/problem+json (RFC 9457) si tiene cuerpo, con type, title, status (igual al de la respuesta) y code. DEBERÍA llevar detail, que diga, cuando se pueda, cómo arreglar la petición (los valores aceptados, el rango permitido), y PUEDE llevar instance y miembros propios. Los tipos de problema de Restep definen code, errors, parameter, header y reason como miembros de extensión (RFC 9457, apartado 3.2). Un error NO DEBE enviarse como respuesta 200; el único sitio donde va un error dentro de un 200 es el resultado de una operación de batch. Un error que da el servidor HTTP antes de pasar la petición a la API, como por una URL o unas cabeceras más largas que sus límites, no lo genera la API: ni 5.3 ni este apartado se le aplican, tanto si ese servidor está delante de la API como si corre en el mismo proceso.

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{ "type": "https://w3id.org/restep/1/errors#invalid",
  "title": "Datos no válidos",
  "status": 422,
  "code": "invalid",
  "errors": [ { "pointer": "/price", "code": "required", "detail": "«price» es obligatorio." } ] }
  • Para un estado que la tabla de abajo recoge, code DEBE ser el que la tabla da al caso; para cualquier otro estado, DEBE ser http_ seguido de los tres dígitos del estado (http_418, http_431); no se deriva del registro de la IANA. La tabla está cerrada: una versión menor no añade ningún nombre para un estado que la tabla no recoge, porque cambiaría lo que un servidor envía para él (1.1); sí puede añadir un código para un caso nuevo de un estado que la tabla recoge.
  • type DEBERÍA ser https://w3id.org/restep/1/errors# seguido del código, o una URI propia de la API que documente el caso. NO DEBE ser about:blank, que dice que el problema no tiene más semántica que su estado (RFC 9457, apartado 4.2.1), salvo que eso sea cierto: su code es el único que la tabla da a ese estado, o http_ y su número, y no lleva reason, errors, parameter ni header. Su title es entonces la frase de razón del estado.
  • Para errores del dominio de la API (saldo insuficiente, sin existencias) la respuesta PUEDE añadir reason: una cadena que define la API y que no cambia dentro de una versión, que DEBE seguir la gramática de los nombres (3) y DEBERÍA ir en snake_case. code sigue dando la clase (conflict, invalid), así que un cliente genérico sigue sabiendo qué hacer.
  • La API PUEDE declarar sus razones en el descubrimiento, en reasons en la raíz: un objeto cuyas claves son los valores de reason; cada valor lleva el code con el que sale esa razón y PUEDE llevar una description (4.3): "reasons": {"out_of_stock": {"code": "conflict", "description": "No quedan ejemplares que apartar."}}. Si se declara, DEBE estar completo: un error NO DEBE llevar un reason que no figure en él, ni llevarlo con otro code. Esto vale para el reason de primer nivel de todo error, también los de los resultados de batch, y no para los códigos propios de la API dentro de errors. Si falta reasons, no se sabe qué razones hay. El cliente DEBE tratar un reason que no conoce como trata su code, así que añadir una razón nunca lo rompe.
  • Los errores de validación DEBERÍAN listar los problemas en errors. Cada entrada lleva un pointer (JSON Pointer, RFC 6901, al cuerpo de la petición, "" para el cuerpo entero; Restep usa la forma de cadena simple, no el fragmento de URI), o el nombre de un parameter o una header, más un code: required, type, format, range, too_long, unknown, read_only, taken (un id ya usado, 5.1) u otro propio de la API.
  • Un 401 DEBE llevar WWW-Authenticate (RFC 9110, apartado 11.6.1). Un desafío Bearer lleva al menos un auth-param, como realm (RFC 6750, apartado 3).
  • Una respuesta 428, 429, 431 o 511 DEBE llevar Cache-Control: no-store, anuncie o no el servidor cache: RFC 6585 (apartados 3 a 6) dice que ninguna caché puede guardarlas, y private aún dejaría hacerlo a una caché privada. Por lo mismo, NO DEBE llevar ningún campo dirigido a las cachés compartidas, como CDN-Cache-Control, que permita a una guardarla, dependa o no de las credenciales (5.1).
  • El cliente DEBE tratar un code que no conoce según la clase del status.
  • Un error, incluidos su detail y las entradas de su errors, NO DEBE revelar lo que el principal no podría saber de otro modo: valores que no puede leer, o si existe un recurso que se le oculta, salvo que un id está ocupado (5.1). NO DEBERÍA llevar detalles internos, como trazas de la pila, consultas o nombres de servicios internos (13.12).
  • Si a una petición se le aplica más de uno de estos errores, el servidor da uno de ellos, y DEBE dar el mismo cada vez que recibe la misma petición contra el mismo estado guardado. Cuál de ellos no forma parte del contrato de la API, así que puede cambiar sin versión nueva (5.5), salvo por estas precedencias:
    1. No se revela nada: mientras se aplique un 401, o un 403 que no dependa del cuerpo ni del elemento guardado, el servidor NO DEBE dar un error que dependa de si el destino existe, de su estado guardado o de una capacidad que el principal no puede conocer por el descubrimiento.
    2. Las precondiciones siguen el RFC 9110 (apartado 13.2.1), salvo por el 400 por el cuerpo y el 422 idempotency_mismatch, más abajo: 428 y 412 NO DEBEN darse mientras se aplique un error que se puede detectar antes de procesar el contenido de la petición (401, un 403 que no dependa del contenido, 404, 405, 406, 410, 413, 414, 415, un 400 por un parámetro o una cabecera, o un 409 que dependa solo del estado guardado del destino, como una acción que el estado actual del elemento no admite, 11.1); y mientras se aplique 428 o 412 el servidor NO DEBE dar un 422 ni un 409 que salgan de procesar el contenido, ni el 403 por un campo que este principal no puede cambiar (5.1), ni un 422 idempotency_mismatch (7.1), aunque se detecte sin leer el contenido. Ese 409 del estado guardado se da solo después de comprobar el permiso actual del principal sobre el destino (un 403, o el 404 que oculta el destino), para que un principal sin ese permiso no conozca ese estado. Esto no vale para una repetición ni para un 409 request_in_progress, que siguen la tercera regla. Restep ordena el 428, que el RFC 6585 (apartado 3) define sin orden, como una precondición que falla, y va antes que el 412.
    3. Una repetición, o un 409 request_in_progress (7.1), se da después de las comprobaciones que impiden al principal saber lo que no puede, incluido su permiso actual sobre el destino (un 403, o el 404 que oculta el destino), y en lugar de 428, 412 y de los errores que dependen del estado guardado; en particular, cuando lo único que lo impide es que el destino ya no existe, lo borrara la propia primera petición u otra.
    Todo lo demás lo decide el servidor: 404 o 405 (un 405 dado sin buscar el elemento es válido, siempre que su Allow no dependa de ese elemento, lo que diría si existe); 405 o un 400 por un parámetro; cualquiera de 400 por el cuerpo, 415, 406 y 413; 400 por el cuerpo o 412 (leer antes el cuerpo se aparta del RFC 9110 (apartado 13.2.1), que evalúa las precondiciones justo antes de procesar el contenido de la petición; Restep se aparta de él a propósito, porque muchos servidores analizan el cuerpo antes de que se ejecute su propio código; por la segunda regla también se aparta de él al dar 428 o 412 antes que un 422 idempotency_mismatch detectado sin leer el contenido, para que una clave reutilizada en otra petición reciba el mismo error tanto si la diferencia está en el contenido como si está en la consulta); y 422 o 409. Los clientes NO DEBEN depender de ese orden; el servidor PUEDE explicarlo en la documentación que enlaza con rel="service-doc" (4.2). Estas reglas también deciden entre errores que exigen otros apartados (4.3, 5.3, 10, 11), y no dicen nada de 424, 429 y los 5xx. Un error que da un servidor HTTP o un intermediario situado delante de la API antes de que la petición llegue a ella, como un 413, queda fuera de ellas. Algunos casos no son cuestión de orden: un cuerpo con un error de sintaxis JSON da 400 bad_request, aunque además lleve un sustituto sin pareja o un no carácter (3); un cuerpo vacío sin Content-Type da 415 (3), salvo en una acción POST, que lo toma como {} (11.1); si la API no revela si un recurso existe, el servidor DEBE darle la misma respuesta que a un elemento que no existe, salvo lo que dice 5.1 para upsert: nunca 403, ni un 405 cuyo Allow dependa de ese recurso; un recurso retirado DEBE dar 410, no 404, salvo que se oculte su existencia; y un método declarado que este principal no puede usar da 403 o el 404 de un recurso oculto (4.2). Un PATCH a un id libre de una colección que declara upsert no es una petición a un recurso que no existe (5.1): no se le aplica ningún 404, así que se evalúan sus precondiciones.

5.5 Evolución y versiones

Una API Restep evoluciona sin versiones mientras los cambios sean compatibles, y solo crea una versión mayor cuando no queda otro remedio.

Cambios compatibles. El servidor PUEDE hacerlos en cualquier momento: añadir campos a una representación; añadir parámetros opcionales, colecciones, singletons, acciones o valores de enumeración; admitir filtros, órdenes o inclusiones nuevos; añadir perfiles o extensiones; declarar reasons o añadirle razones (5.4); añadir un efecto a una operación (11.1); cambiar cuál de varios errores aplicables se da, dentro de las precedencias de 5.4. Funcionan porque el cliente ignora lo que no conoce (apartado 3, 4.2) y no depende de cuál de varios errores recibe (5.4).

Cambios incompatibles. El servidor NO DEBE hacerlos dentro de una versión, salvo retirándolos (abajo):

  • quitar o renombrar un campo, o cambiar su tipo o su significado;
  • hacer obligatorio un campo de entrada, un parámetro o una cabecera que no lo era (también If-Match mediante 428, e Idempotency-Key);
  • endurecer la validación de forma que se rechace una petición que antes se aceptaba (también hacer de solo lectura un campo que se podía escribir, o empezar a rechazar Idempotency-Key sin credenciales, 7.1), salvo para cerrar un fallo de seguridad;
  • quitar un filtro (también los con nombre), un operador, un campo de orden, una relación, una inclusión, un recuento, una acción, una colección, un singleton, un perfil, una extensión o un método declarados (4.3), un valor de una enumeración declarada, el sync de una colección o los events de la API (10);
  • quitar un efecto de una operación, o declarar [] donde tenía efectos o no se declaraba ninguno (11.1), porque un cliente dejaría de preguntar antes de usarla;
  • cambiar el formato de los id, las URL de los recursos o el orden por defecto de una colección, o la colación de un campo (6.1);
  • cambiar el estado o el code que se devuelve en un mismo caso, cuando solo se le aplica un error;
  • quitar reasons una vez declarado, quitarle una razón o cambiar el code de una razón.

Retirar. Dentro de una versión, un campo o una capacidad declarada solo puede desaparecer si se retira:

  • Primero se anuncia. El descubrimiento DEBE listarlo en deprecations: {"kind": "field", "name": "rating", "announced": "2026-12-01T00:00:00Z", "sunset": "2027-07-01T00:00:00Z"}. kind dice qué se retira y dónde va el aviso:
    • En la raíz: version; profile y extension, con su nombre en name; collection y singleton, con su clave en name; reason (5.4), con la razón en name.
    • En la colección: field; filter (también un filtro con nombre); operator, con el campo de filtro en name y el operador en op; value, con el campo de filtro en name y el valor de la enumeración en value; sort; relation; include, con la relación en name, que retira su expansión pero no la relación; count; max_limit, con el límite más bajo que tendrá en value; action; method e item_method, con el método en name.
    • En un singleton: field; method, con PATCH en name (el GET de un singleton solo se va con el singleton, 5.9); y action, con el nombre de la acción en name.
    announced DEBE ser el instante en que se publicó el aviso por primera vez, y NO DEBE cambiar después. sunset, cuando haya fecha, es el instante de la retirada. Los dos son instantes RFC 3339 y, en todo aviso, DEBEN ir en segundos enteros, sin fracción: las cabeceras Deprecation y Sunset de abajo no pueden llevarla (RFC 9651, apartado 3.3.7; RFC 9110, apartado 5.6.7). Un aviso field abarca también los filtros, campos de orden e inclusiones de ese nombre y todas las rutas con punto que empiezan por él (name.es-mx para name, author.id para author), que se van con el campo. Un aviso count con "value": "estimated" anuncia que un recuento declarado "exact" pasará a "estimated"; sin value, que ese count se quitará. Las respuestas de un recurso que un aviso retira entero DEBEN llevar Deprecation (RFC 9745), cuyo valor es el instante announced del aviso como fecha de campo estructurado (@ y los segundos desde 1970, RFC 9651, apartado 3.3.7), y un Link con rel="deprecation" a la explicación. Son estas: para collection y singleton, toda respuesta de ese recurso y de sus elementos; para action, toda respuesta a ella; para version, toda respuesta. Cuando haya fecha, DEBEN llevar además Sunset (RFC 8594) con sunset como fecha HTTP, que NO DEBE ser anterior a announced (RFC 9745, apartado 4). Un aviso que retira solo una parte de un recurso (field, filter, operator, value, sort, relation, include, count, max_limit, method, item_method, reason) o un profile o una extension se anuncia solo en deprecations: sus respuestas NO DEBEN llevar por él Deprecation, Sunset ni un Link con rel="deprecation", porque RFC 9745 (apartados 2.1 y 3) los lee como la obsolescencia del recurso entero.
  • Entre announced y sunset DEBERÍAN pasar al menos seis meses.
  • Pasada la fecha, un recurso, un singleton, una acción o una versión retirados DEBEN responder 410 retired; un filtro, un operador, un orden, una relación, una inclusión o un recuento retirados (un aviso count sin value) DEBEN dar 400 unsupported_parameter, como cualquiera no declarado; tras un aviso count con "value": "estimated", el descubrimiento DEBE declarar ese count como "estimated", y count=true sigue añadiendo total, con "total_estimated": true cuando el número es aproximado; un valor de enumeración retirado en un filtro DEBE dar invalid_parameter y dejar de aparecer en los datos; un limit mayor que un max_limit rebajado DEBE dar invalid_parameter; un método retirado DEBE dar 405; un campo retirado DEBE faltar en las representaciones y es, para los parámetros y las escrituras, un campo que no existe (6.3); una razón retirada NO DEBE darse; un perfil o una extensión retirados DEBEN salir de profiles o extensions, y sus requisitos dejan de aplicarse. Retirar un perfil o una extensión retira también los que lo requieren (1.2), con el mismo sunset. Pasada la fecha, el descubrimiento DEBE mantener el aviso en deprecations hasta la siguiente versión mayor, para que un cliente sepa por qué falta algo.

Una versión mayor nueva. La exige un cambio incompatible que no pueda hacerse retirando:

Restep aplica estas relaciones, pensadas para las versiones de un documento, a la raíz de la API como recurso con versiones (RFC 5829, apartado 1).

5.6 Idioma de los textos de la API

Los errores, el documento de descubrimiento y los esquemas que sirve la API PUEDEN depender de Accept-Language (RFC 9110, apartado 12.5.4). Solo cambian sus textos para personas: en un error, title y detail, también los de cada entrada de errors; en el descubrimiento, description; en un esquema, también uno incrustado en schemas, las anotaciones title y description de JSON Schema. Los campos traducidos de las colecciones, los elementos y las acciones (3) se eligen del mismo modo. Los demás datos nunca cambian (3).

  • El servidor elige el idioma con el lookup del RFC 4647 (apartado 3.4) entre los idiomas en que puede dar esa respuesta, probando los rangos de Accept-Language de mayor a menor peso y, a igual peso, en el orden de la cabecera; sin distinguir mayúsculas, sin canonicalizar rangos ni etiquetas (iw no encuentra he) y sin quitar antes extensiones ni subetiquetas privadas. Ignora *, los rangos con q=0 y los mal formados (también por un q mal formado). Si ninguno encaja, o no llega la cabecera, DEBE usar su idioma por defecto, que es fijo para la API y nunca es un idioma guardado para el principal o la sesión. Una API con campos traducidos DEBE declararlo en el descubrimiento, en default_language en la raíz, para que un cliente sepa qué da el comportamiento por defecto (el RFC 4647, apartado 3.4.1, pide a una especificación que usa el lookup que lo defina, y la frase anterior lo hace). NO DEBE responder 406 ni 400 por Accept-Language.
  • En un servidor que ofrece sus textos o sus campos traducidos en más de un idioma, toda respuesta cuyos textos o campos traducidos se eligen así, o cuyos elementos o su orden dependen de un campo traducido, también en el idioma por defecto, DEBE llevar Vary: Accept-Language, y un 304 de estos, el mismo Vary que su 200. Una respuesta con cuerpo DEBERÍA llevar Content-Language, y una con campos traducidos DEBE llevarla (RFC 9110, apartado 8.5). Cada idioma es otra representación: una ETag, si la hay, DEBE ser distinta por idioma.
  • El lookup recorta la etiqueta pedida y nunca prueba otras variantes del mismo idioma: con es-es y es-mx pero sin es, Accept-Language: es-AR recibe el idioma por defecto. Un servidor que ofrece variantes regionales de sus textos DEBERÍA ofrecer también el idioma sin región.
  • Una repetición (7.1) devuelve la respuesta guardada, en su idioma, porque Accept-Language no cuenta para «la misma petición».

5.7 Reintentos

Un cliente repite una petición cuando no sabe si tuvo efecto (se cortó la conexión, se agotó el tiempo de espera) o cuando el servidor le dice que vuelva más tarde. Que sea seguro depende del método y de la respuesta.

  • Se pueden repetir tal cual: GET, HEAD, QUERY y las acciones seguras, con las que el cliente no pide ningún cambio de estado (RFC 9110, apartado 9.2.1): lo que el servidor hace por su cuenta, como registrar, cachear o refrescar desde otra fuente, no las hace inseguras, salvo que lo que registra sea algo que el cliente pueda leer después a través de la API como parte de lo que pidió. También las acciones declaradas "idempotent": true; DELETE, cuya repetición PUEDE dar 404 (5.1), que un cliente que lo está repitiendo toma como hecho; y PATCH con un merge patch, que deja el elemento igual se aplique las veces que se aplique, también donde crea el elemento (5.1, upsert). Idempotente significa el mismo efecto, no la misma respuesta (RFC 9110, apartado 9.2.2): un DELETE repetido puede dar 404, y una acción idempotente repetida, 409; para volver a recibir el primer estado y el primer Location, el cliente envía Idempotency-Key donde el servidor aplica el 7.1 a la petición, cosa que no tiene por qué hacer una acción declarada "idempotent": true (11.1); el cuerpo de una repetición no da más de lo que daría ahora una lectura. Un PATCH es idempotente salvo por la concurrencia: entre los dos intentos otro cliente puede haber escrito, y la repetición deshace ese cambio. Con If-Match (7.2) la repetición recibe en cambio 412, también tras un primer intento que salió bien, porque ese cambió la ETag; entonces el cliente lee el elemento para averiguarlo. En una colección que declara reusable_ids (5.1), un DELETE o un PATCH solo se pueden repetir sin riesgo con If-Match, porque para entonces el id puede nombrar otro elemento.
  • No son seguros sin ayuda: un POST a una colección, una acción declarada "idempotent": false y un lote pueden tener efecto dos veces. Un cliente NO DEBERÍA repetir uno de ellos automáticamente cuando no sabe si el primer intento tuvo efecto, salvo que lleve Idempotency-Key y el servidor anuncie writes (7.1), o que cree un elemento con un id elegido por el cliente (5.1), que no se puede crear dos veces. Con la clave, un cliente PUEDE repetirlo solo dentro de la vida de la clave, idempotency.ttl desde su primer intento (24 horas donde no se declara); pasado ese tiempo NO DEBE repetirlo automáticamente, y antes averigua si el primer intento tuvo efecto. En un alta sin id elegido por el cliente, el resultado queda entonces incierto, salvo que el cliente pueda establecerlo por otra vía, como un filtro por un campo que la API mantiene único (6.1) o la lista created de :changes (10). Un id elegido por el cliente es la protección que no caduca, salvo en una colección que declara reusable_ids, donde el id queda libre otra vez cuando se borra su elemento (5.1).
  • 429 rate_limited y 503 unavailable: el servidor NO DEBE dar ninguno de los dos a una petición que tuvo efecto, ni a una de la que no puede saber que no lo tuvo (un tiempo de espera agotado después de confirmar la transacción, un proceso que murió): a esas responde con otro 5xx, como 500, 502 o 504. Una pasarela o un balanceador de carga que el operador de la API pone delante de ella, y que responde con un cuerpo problem+json, está sujeto a esta regla igual que el servidor. Así, el cliente PUEDE enviar de nuevo la misma petición, sea cual sea su método. 409 request_in_progress (7.1) se repite del mismo modo, con la misma clave y dentro de su vida (arriba). Con Retry-After, el cliente NO DEBERÍA repetirla antes de ese momento; sin él, DEBERÍA esperar un tiempo creciente entre intentos, con algo de azar, para que muchos clientes no vuelvan a la vez. Un 429 o un 503 sin cuerpo problem+json puede venir de un intermediario, al que este apartado no obliga.
  • Los demás estados 5xx (500, 502, 504…) y una respuesta perdida no dicen nada del efecto: el cliente solo repite lo que permite el primer punto, o lo que lleva la misma Idempotency-Key, dentro de su vida (arriba).
  • Otro 4xx responde igual a la misma petición, salvo 408, 421 y 425, que HTTP deja repetir a un cliente: 408 tal cual (RFC 9110, apartado 15.5.9), 421 por otra conexión (apartado 15.5.20), y 425 sin datos tempranos de TLS: el RFC 8470 (apartados 4 y 5.2) exige a un cliente que envió la petición en datos tempranos que la reintente, y que ningún reintento vaya en datos tempranos. Un cliente NO DEBERÍA repetir ninguna otra sin cambiar algo antes: credenciales nuevas tras un 401, una lectura nueva tras un 412, If-Match tras un 428, el cuerpo tras un 422.

5.8 Clientes de navegador

Restep no exige acceso desde otros orígenes (Fetch, protocolo CORS). Para las operaciones que un servidor abre a un origen de navegador, DEBERÍA enviar Access-Control-Allow-Origin en todas las respuestas, también en las de error, y DEBERÍA responder a su preflight sin exigir credenciales, porque un preflight no las lleva. Si esas cabeceras dependen del Origin de la petición, todas las respuestas DEBERÍAN llevar Vary: Origin, también las que no las llevan, y toda respuesta de estas que pueda guardar una caché compartida (una que es public) DEBE llevarlo. Si acepta peticiones con credenciales (cookies, autenticación HTTP o certificados de cliente TLS; un token en Authorization no lo es), DEBERÍA nombrar el origen en vez de *, que los navegadores rechazan con credenciales, y enviar Access-Control-Allow-Credentials: true. Ninguna regla de Restep se aplica a OPTIONS (5.1): el preflight de una operación abierta a ese origen recibe su respuesta CORS aunque el elemento no exista, no lleve credenciales o lleve parámetros reservados.

DEBERÍA incluir en Access-Control-Expose-Headers las cabeceras de respuesta que los perfiles y extensiones que anuncia piden leer al cliente; en Restep 1, ETag, Location, Content-Location, Link, Allow, Accept-Patch, Accept-Post, Retry-After, Deprecation, Sunset, Idempotent-Replayed (la define Restep, 7.1), Preference-Applied y Accept-Query, más las de 11.5. DEBERÍA permitir en el preflight las cabeceras de petición y los métodos que usan esas operaciones; en Restep 1, Content-Type, Content-Disposition, If-Match, If-None-Match, Idempotency-Key (de un borrador del IETF, 14.2), Prefer, Authorization y DPoP, con PATCH, DELETE y QUERY. Estas listas son las que define Restep 1; una versión menor posterior puede añadirles otras.

Un navegador añade solo algunas credenciales a las peticiones que inician páginas de otros orígenes: cookies, autenticación HTTP y certificados de cliente TLS. Un servidor que acepta alguna de ellas DEBE rechazar con 403 forbidden, sin aplicarla, toda petición que no es segura (un POST, incluidas las acciones y los lotes, un PATCH o un DELETE), que autenticaría con una credencial de ese tipo y que un navegador envió desde un origen que el servidor no permite. DEBE tratar como tal una petición cuya cabecera Origin (Fetch) está presente y no es ni el origen de la API ni uno que permite. Un origen que permite es uno que nombra: un * en Access-Control-Allow-Origin no permite ninguno a efectos de esta regla, porque los navegadores no lo aceptan con credenciales. PUEDE tratar Origin: null como el origen de la API cuando Sec-Fetch-Site es same-origin, porque un formulario o una navegación desde una página con Referrer-Policy: no-referrer lo envía a su propio origen, y PUEDE decidir por Sec-Fetch-Site (Fetch Metadata) cuando falta Origin. Una petición que el servidor autentica solo con un token en Authorization no está incluida: un navegador nunca añade uno por su cuenta, así que un cliente de navegador de otro origen que el servidor permite mediante CORS sigue funcionando. Esas cookies DEBERÍAN llevar SameSite=Lax o SameSite=Strict (el atributo SameSite de draft-ietf-httpbis-rfc6265bis). El preflight y el tipo de medio de 3 impiden que otros orígenes envíen un cuerpo JSON; esta comprobación cubre además una acción con el cuerpo vacío, que cualquier página puede enviar sin preflight (11.1, 13.7). Una colección que acepta multipart/form-data o text/plain en upload (5.1) recibe cuerpos que cualquier página puede enviar sin preflight: ahí esta comprobación es la única protección.

5.9 Singletons y recursos fuera de Restep

Restep abarca las colecciones, sus elementos, sus acciones, los singletons y los recursos que define esta especificación: el documento de descubrimiento, la ruta del lote, el flujo de eventos, el estado del servicio (4.4) y los metadatos de OAuth (11.5). Si el servidor sirve un documento de descubrimiento, las colecciones y los singletons son los que declara. Cualquier otro recurso de la API, como un PDF o una imagen enlazados con href, o una ruta que la API no ha declarado, queda fuera de Restep: de esta especificación solo se le aplican 5.3, 5.4 y la regla de Cache-Control de 5.1, así que su cuerpo no tiene por qué ser JSON, pero un parámetro reservado que no implementa sigue dando unsupported_parameter, y sus errores siguen siendo problem+json. Un recurso así implementa un parámetro reservado si lo lee, signifique lo que signifique allí.

Un singleton es un recurso sin colección, como el perfil del usuario que ha iniciado sesión (/me) o la configuración de una cuenta, inspirado en AIP-156, con el que comparte que no se crea ni se borra. El servidor lo declara en la raíz, en singletons, con el nombre que elija:

"singletons": {
  "me": { "path": "/me", "methods": ["GET", "PATCH"],
          "description": "Perfil y configuración del usuario que ha iniciado sesión.",
          "schemas": { "item": "/schemas/me.json", "update": "/schemas/me-update.json" } } }
  • Cada singleton DEBE tener un path, y PUEDE llevar methods (de entre GET y PATCH, una lista exacta como en 4.3), description, schemas (item y update), actions (11.1), deprecations (5.5) y method_effects (4.3), cuya única clave puede ser PATCH: "method_effects": {"PATCH": []}; un PATCH que no declara cuenta como si tuviera los tres efectos. Su ruta NO DEBE ser una que tenga o pueda tener una colección o un elemento de una: la ruta de un elemento es la de su colección seguida de un segmento, así que /books/featured no se permite mientras /books sea una colección, y /books/7/summary sí, salvo que una subcolección de books tenga esa ruta.
  • Un singleton PUEDE colgar de un elemento o de otro singleton: entonces declara en parent la clave de esa colección o ese singleton, y su path es una plantilla de URI con las reglas de la de una subcolección (4.2): sus variables toman por orden los id de los elementos padre, y es la ruta de elemento del padre, o la ruta del singleton padre, seguida de / y uno o más segmentos literales: "settings": {"path": "/readers/{reader_id}/settings", "parent": "readers"}. Sin parent, su path NO DEBE ser una plantilla. Un cliente DEBE ignorar un singleton cuyo path es una plantilla sin parent, o cuyo parent no nombra ninguna colección ni ningún singleton del documento.
  • Un singleton se comporta como un elemento sin id ni colección. DEBE admitir GET (y HEAD), que devuelve su representación, un objeto JSON, y PUEDE admitir PATCH con un merge patch, como dice 5.1 para los elementos, que devuelve la representación entera. POST, PUT y DELETE sobre él DEBEN dar 405: el cliente ni crea, ni sustituye, ni borra un singleton. Existe para todo principal que pueda usarlo y, con parent, mientras exista su padre: bajo un elemento padre que no existe, da 404. Uno que un principal no puede usar recibe 403 o 404 (4.2).
  • Lo que esta especificación dice de la representación de un elemento, sus campos de solo lectura, su PATCH, su ETag y su If-Match (3, 4.3, 5.1, 7.2, 8) vale también para un singleton, así que con writes toda respuesta con su representación lleva _etag, y un PATCH evalúa If-Match e If-None-Match contra su ETag; lo que dice de id, de las rutas de los elementos y de las colecciones, no. La representación de un singleton PUEDE llevar un id, como el del usuario, que entonces es de solo lectura.
  • Con query, fields DEBE funcionar en un singleton como en un elemento (6.3). Sus relaciones siguen 3, y cada objeto de relación que lleve DEBE llevar href, porque un singleton no declara relations de las que sacar su destino; declarar relations, include y los mapas de idioma en un singleton quedan fuera de esta versión: include y los demás parámetros reservados DEBEN dar ahí unsupported_parameter. Sus acciones siguen 11.1, y su representación PUEDE listarlas en _actions. Una operación que solo cambia campos del singleton es un PATCH, no una acción.

Cómo modelar un borrador que convive con lo publicado (el elemento es el borrador, o una subcolección con un id fijo) está en el apéndice D.

6. query Perfil

URI del perfil: https://w3id.org/restep/1/query. Estado: estable. Se aplica a las colecciones; fields vale también para los elementos. Ningún parámetro necesita un analizador sintáctico: los lee cualquier framework HTTP, aunque para detectar un parámetro repetido puede hacer falta la query en bruto (5.3).

6.1 Filtros

GET /books?filter[category]=novela-negra&filter[price][le]=20

Los ejemplos muestran la query sin codificar para que se lea mejor. En la red, los espacios y las comillas van codificados con porcentajes, y también [ y ] en los enlaces que construye el servidor (RFC 3986, apartado 3.4); el servidor lee la query tras decodificar los porcentajes (5.2).

  • El documento de descubrimiento DEBE declarar en filter qué campos admiten filtro, con su tipo y sus operadores. Los campos de una relación usan una ruta con punto (author.id), y también los campos de dentro de un objeto del elemento (address.city), que se declaran en filter y sort como cualquier otro campo.
  • Una ruta que atraviesa una relación a muchos (reviews.rating, reviews.reader.id), o un campo cuyo valor es una lista de escalares (formats), PUEDE declararse en filter con "quantifier": "some" y el tipo de sus elementos: "reviews.rating": {"type": "integer", "ops": ["eq", "ge"], "quantifier": "some"}. Sin quantifier, una ruta o un campo así NO DEBE declararse en filter, salvo con null como único operador (abajo), ni listarse en sort (6.2). Una ruta NO DEBE atravesar más de un paso a muchos, y una declaración así NO DEBE declarar ne ni nin; «ningún elemento relacionado casa» se pide con null sobre el grupo (abajo). Los demás valores de quantifier quedan reservados para versiones menores (4.2).
  • Los filtros de una petición cuyas rutas atraviesan la misma relación a muchos, o nombran el mismo campo de lista, forman un grupo. Un elemento DEBE casar con el grupo cuando, y solo cuando, algún elemento relacionado, o elemento de la lista, que el principal puede ver casa con todos los filtros del grupo: filter[reviews.rating]=5&filter[reviews.reader.id]=3 pide una reseña de cinco estrellas del lector 3, no una reseña de cinco estrellas y una reseña del lector 3.
  • La propia relación o el propio campo de lista PUEDEN declarar null: filter[reviews][null]=true devuelve los elementos sin ningún elemento relacionado que el principal pueda ver (una lista vacía, un campo ausente y null son lo mismo), y false, los que tienen alguno. Su declaración lleva como type el del id de los elementos relacionados, string, en una relación, y el de los elementos en un campo de lista, y, cuando null es su único operador, ningún quantifier o "some", que seleccionan los mismos elementos, así que pasar de una forma a la otra es compatible (5.5): "reviews": {"type": "string", "ops": ["null"]}. Junto con otros filtros de su grupo, filter[reviews][null]=true DEBE negar el grupo: filter[reviews.rating]=1&filter[reviews][null]=true son los libros sin ninguna reseña de una estrella. También cuando su declaración lleva quantifier, null prueba la relación o la lista entera, el grupo, nunca cada elemento: por sí solo, como arriba; junto con in u otros filtros de su grupo, true selecciona los elementos en los que ningún elemento relacionado, o de la lista, que el principal puede ver casa con todos los demás filtros del grupo, y false, aquellos en los que alguno casa (filter[formats][in]=epub,pdf&filter[formats][null]=true son los elementos sin ninguno de esos dos formatos). Nunca pregunta si algún elemento es null. Una petición con más de un filtro null sobre la misma relación a muchos o el mismo campo de lista, el suyo propio o el de una ruta que pasa por él, DEBE dar invalid_parameter, aunque sus valores coincidan.
  • Cada elemento sale una vez, casen los elementos relacionados que casen, y total cuenta elementos de la colección (6.5). Sigue valiendo que una ruta con punto que acaba en el id de una relación cuyo destino es una subcolección NO DEBE declararse (abajo).
  • filter[campo]=valor es el mismo filtro que filter[campo][eq]=valor. Los filtros sobre un mismo campo con operadores distintos son filtros distintos (filter[price][ge]=10&filter[price][le]=20). Varios filtros DEBEN combinarse con Y; para O, NO y paréntesis está la extensión filter-expr.
  • Operadores: eq, ne, lt, le, gt, ge, in, nin, null, prefix y contains. Los demás nombres de operador quedan reservados para versiones menores: un servidor NO DEBE declarar un operador fuera de esta lista, y un cliente ignora uno que no conoce (4.2).
  • in y nin llevan valores separados por comas, que se leen tras decodificar los porcentajes; sus valores no pueden contener comas, codificadas o no (para esos están eq, filter-expr o query-method). filter[f][in]= es una lista vacía; un elemento vacío entre comas (a,,b) es la cadena vacía. nin DEBE casar con los elementos cuyo valor no es ninguno de los listados; como todos los operadores salvo null, nunca casa con un valor ausente o null (abajo). null lleva true (sin valor: ausente o null) o false.
  • El servidor DEBE comparar según el tipo declarado: numéricamente para integer, number y decimal (los decimales de forma exacta, sin pasar por coma flotante), cronológicamente para date (como fechas de calendario), datetime (como instantes, de forma exacta: un valor de filtro más preciso que lo que guarda el servidor DEBE compararse de forma exacta o dar invalid_parameter, nunca redondearse; un desfase como +02:00 se envía como %2B02:00, 5.2) y localdatetime (como fechas y horas de reloj, sin ninguna zona, y de forma exacta), por su longitud para duration (un día cuenta como 24 horas, y las longitudes se comparan de forma exacta, como números decimales de segundos; un valor de filtro con años o meses DEBE dar invalid_parameter, porque no tienen longitud fija), y por puntos de código Unicode para string, enum y timezone, distinguiendo mayúsculas y sin reglas de idioma, salvo que la colación del campo diga otra cosa (más abajo). Las cadenas se comparan tal cual, sin normalización Unicode: una é compuesta y una descompuesta son valores distintos. (El < de JavaScript compara unidades de código UTF-16, que ordenan algunos caracteres de fuera del plano multilingüe básico de forma distinta que los puntos de código.) Un campo boolean NO DEBE declarar más operadores que eq, ne y null, y el filtro de id NO DEBE declarar lt, le, gt ni ge, porque el orden de los id es el del servidor (5.2). null puede declararse en un campo de cualquier tipo y comprueba si el valor falta o es null. Con los límites de petición de 5.3, el servidor DEBE comparar un operando numérico como número, de forma exacta, aunque quede fuera del rango de valores que puede tener el campo. Un operando que supera uno de esos límites da invalid_parameter con el límite en detail; nunca se sustituye por otro valor, como un infinito o cero. Una hora con segundo intercalar (:60) DEBE dar invalid_parameter. Dos operandos iguales según el tipo del campo, como lo son los números en 2 (filter[price]=20 y filter[price]=20.0), son el mismo valor, y por tanto el mismo filtro, también para el cursor (6.4). Así, un operando de un campo integer casa con su tipo cuando su valor decimal exacto no tiene parte fraccionaria: 20.0 y 2e1 son el mismo operando que 20, y 20.5 da invalid_parameter. El operando de un campo integer o number, leído tras decodificar los porcentajes, sigue la gramática number del RFC 8259 (apartado 6), exponente incluido (2e1 es 20), y +20, .5, 020 y 0x14 no encajan con ella; el de un campo decimal sigue su propia gramática (4.2).
  • prefix y contains PUEDEN declararse solo en campos de tipo string y en traducciones campo.etiqueta, nunca en id. prefix DEBE casar con los valores que empiezan por el operando y contains con los que lo contienen, con la colación del campo (abajo): por puntos de código con "codepoint", y de forma coherente con el eq propio del servidor con "server". Un operando vacío DEBE dar invalid_parameter.
  • Una ruta con punto que acaba en el id de una relación cuyo destino es una subcolección NO DEBE declararse en filter ni en sort: ese id identifica un elemento solo dentro de su padre.
  • Una traducción se filtra como campo.etiqueta, con un mapa de idioma de la colección y una clave en minúsculas: filter[name.es-mx]=Calabacita. El descubrimiento declara cada una por separado, de tipo string: "name.es-mx": {"type": "string", "ops": ["eq", "in"]}. Lee solo esa clave exacta, sin el emparejamiento del RFC 4647 ni idioma de reserva: si el elemento no tiene la clave, el campo está ausente. El mapa de idioma entero y cualquier otra ruta que acabe en uno o lo atraviese (author.name, author.name.es) NO DEBEN declararse en filter ni en sort, y un mapa de idioma NO DEBE llamarse igual que una relación de su colección, para que name.es-mx nunca sea una ruta de relación. Un campo traducido (3) se filtra, y se ordena, en el idioma de la respuesta (5.6), con la colación que se le declare.
  • Una colección PUEDE declarar en collations cómo se comparan y ordenan un campo que contiene cadenas (de tipo string, un enum de cadenas que es clave de orden, o un campo traducido) o una traducción campo.etiqueta: "collations": {"title": "server"}. El valor se aplica al filtro y a la clave de orden con ese nombre, a filter-expr, y a prefix y contains (arriba). Cada clave DEBE ser un campo declarado en filter con tipo string, un campo listado en sort que contenga cadenas (incluido un enum de cadenas), un campo traducido o una traducción campo.etiqueta, y NO DEBE ser id (5.2).
    • "codepoint", el valor de todo campo de cadena que no aparece: por puntos de código Unicode, como arriba.
    • "server": la igualdad (eq, ne, in) y el orden (lt, le, gt, ge, sort) son los del servidor, como una colación de base de datos que no distingue mayúsculas o tildes. El orden DEBE ser total, determinista y estable, y concordar con la igualdad: dos valores son iguales exactamente cuando ninguno va antes que el otro. El servidor DEBERÍA decir cuál es en la description del campo (4.3). Un cliente NO DEBE suponer puntos de código, ni reproducir en local ese orden o esa igualdad. Como solo se prometen estas propiedades, un cambio en la colación propia del servidor que las conserve, como la actualización de una biblioteca, no cambia el valor declarado.
    • Los demás valores quedan reservados para versiones menores, como colaciones nombradas por etiquetas de Unicode. Un cliente DEBE tratar como "server" un valor que no sea una cadena, o una cadena que no conozca.
  • Los operadores, salvo null, NO DEBEN casar con elementos en los que el campo esté ausente o sea null.
  • Un filtro o una clave de orden sobre un campo que el principal no puede leer en un elemento DEBE tratar el campo como ausente en ese elemento: las comparaciones no casan con él, filter[campo][null]=true sí, y va al final en un orden. Una ruta con punto a través de una relación (author.name) es un campo que el principal no puede leer en un elemento cuyo elemento relacionado no puede ver (9). Así, un filtro declarado nunca revela un valor que el cliente no puede leer, y un recuento tampoco (6.5). El servidor PUEDE responder en su lugar 403 forbidden, con el parámetro en parameter, cuando el principal no puede leer ese campo en ningún elemento.
  • Un operando de null que no sea true o false, un operando de cualquier otro operador que no encaje con el tipo del campo (en in y nin, cada elemento), una lista in o nin vacía o el mismo filtro (mismo campo y operador, en cualquiera de las dos formas) dos veces DEBEN dar invalid_parameter. Un campo u operador no declarados, unsupported_parameter (5.3).
  • En una colección con variantes (2), un campo que solo tienen algunas variantes se declara como cualquier otro: a los elementos de las demás variantes les falta, y se les aplican las reglas de los campos ausentes. El campo que distingue las variantes DEBERÍA declararse como un enum filtrable.

Filtros con nombre. Hay criterios que no comparan un campo: «las sesiones activas» (sin caducar y sin cerrar), «las iniciadas desde el móvil» o «las peticiones que aprueba alguien con este nombre». El servidor los declara por su nombre en named_filters, y el cliente los usa con la forma corta de un filtro:

GET /books?filter[available]&filter[search]=machado&filter[price][le]=20
  • El descubrimiento DEBE declarar cada uno en el named_filters de su colección, con una description que dice qué elementos devuelve y, si lleva valor, su type (4.2, con sus values si es enum): "named_filters": {"available": {"description": "…"}, "search": {"type": "string", "description": "…"}}. Su significado es el que da la descripción, no una comparación con un campo. Un filtro con nombre NO DEBE llamarse igual que una clave de filter de su colección, y su nombre sigue el 3, así que nunca contiene un punto.
  • Sin type, es un interruptor: se aplica con filter[nombre] o filter[nombre]=, y cualquier valor DEBE dar invalid_parameter. Con type, el valor es obligatorio: uno vacío o que no encaja con el tipo DEBE dar invalid_parameter.
  • Un interruptor PUEDE declararse "default": true: entonces se aplica a toda petición de lista de la colección (GET y QUERY) que no lo desactive con filter[nombre]=false (en QUERY, "nombre": false). false lo desactiva, no lo niega: filter[active]=false no pide los elementos inactivos. Un filtro por defecto nunca se aplica a leer un elemento por su ruta. En un interruptor sin default, cualquier valor, también false, DEBE seguir dando invalid_parameter. Con filter-expr, filter[nombre]=false es el único parámetro filter[…] que PUEDE ir con una expresión: desactivar un filtro por defecto elige qué elementos se recorren, no forma parte de la lógica de la expresión (11.3).
  • Un filtro de filter, o un filtro con nombre, PUEDE declararse "required": true: una petición de lista sin él DEBE dar invalid_parameter con su nombre (filter[isbn], 5.3). Una colección con un filtro obligatorio no tiene petición de copia completa (5.2).
  • Un filtro con nombre no tiene operadores: filter[nombre][eq], o con cualquier otro operador, DEBE dar unsupported_parameter, igual que un filtro con nombre que no está declarado. El mismo filtro con nombre dos veces DEBE dar invalid_parameter.
  • En todo lo demás es un filtro: se combina con Y con los demás, el cursor queda ligado a él (6.4) y da unsupported_parameter donde lo dan los filtros, como en :changes (10). Con filter-expr entra en una expresión como dice 11.3.
  • A diferencia de un filtro sobre un campo, no compara nada que describa collations: cómo casa el texto lo dice su description. NO DEBE seleccionar elementos por valores que el principal no puede leer, salvo que su descripción enuncie ese criterio, lo que hace público si un elemento lo cumple: si no, que un elemento case revelaría esos valores (13.4). Un filtro con nombre con type NO DEBE comparar su valor con valores que el principal no puede leer, diga lo que diga su descripción: cada valor que recibe haría una pregunta distinta sobre ellos, y una búsqueda por bisección los encontraría.

6.2 Orden

sort=-rating,title: campos separados por comas, con - delante para orden descendente, como en JSON:API. Los campos ordenables se declaran en sort; cualquier otro DEBE dar unsupported_parameter. El servidor DEBE desempatar de forma estable (por ejemplo, por id). Los elementos sin valor en una clave de orden DEBEN ir al final, en los dos sentidos. Una ruta a muchos declarada con quantifier (6.1) PUEDE listarse en sort: en orden ascendente, ordena por el menor valor entre los elementos relacionados que el principal puede ver, y en descendente, por el mayor; los elementos sin ninguno van al final. Un campo traducido se ordena en el idioma de la respuesta (6.1). Una traducción se ordena como su campo.etiqueta declarado (6.1): sort=name.es-mx. Las cadenas se ordenan por puntos de código, sin reglas de idioma, salvo que collations diga otra cosa (6.1); id se ordena en el orden del servidor (5.2).

6.3 Campos

Con fields=title,price la respuesta DEBE llevar solo esos campos, más id y los miembros que empiezan por _. Vale también en el GET de un elemento, donde, con writes, el elemento lleva además _etag (7.2). Un campo que no existe DEBE dar invalid_parameter; un campo que existe pero que el principal no puede leer simplemente falta en la respuesta, como faltaría sin fields. Un campo que el principal no puede leer y que no nombran ni el descubrimiento ni ningún esquema que sirva la API DEBE tratarse, para ese principal, como uno que no existe, para que fields no le diga que el campo existe. fields=id DEBE aceptarse y devolver solo id y los miembros _; un fields vacío es una lista vacía (5.3). fields e include (9) se aplican a las lecturas: GET, HEAD y QUERY. En una escritura DEBEN dar unsupported_parameter, y la respuesta lleva el elemento entero, o nada con Prefer: return=minimal (7.3). Un mapa de idioma es un solo campo: fields=name lo da entero, y una ruta que entra en él (name.es; con relations, también author.name.es) DEBE dar invalid_parameter.

6.4 Paginación

  • limit fija el tamaño de página, entre 1 y el max_limit declarado. Fuera de ese rango el servidor DEBE dar invalid_parameter, no recortarlo en silencio, a diferencia de AIP-158, que lo lleva al máximo. Una colección que acepta limit DEBE declarar max_limit; en una que no lo declara, limit DEBE dar unsupported_parameter.
  • next DEBE llevar un parámetro cursor opaco, como los tokens de página de AIP-158, y conservar sin cambios los demás parámetros. El cliente NO DEBE interpretar ni fabricar cursores.
  • Un cursor está ligado a lo que tenía la petición para la que se emitió: la colección, los filtros (incluidos los filtros por defecto que la petición no desactiva, 6.1), el orden y, donde la colección tiene campos traducidos, el idioma elegido para la respuesta (5.6); con QUERY, a los miembros filter y sort del cuerpo (11.4). Un cursor que el servidor no emitió (uno manipulado), uno caducado o uno usado con otra colección, otros filtros, otro orden u otro idioma DEBE dar invalid_parameter con parameter: "cursor". Un cursor DEBERÍA estar ligado también al principal (2) que lo recibió, y DEBE estarlo si remite a resultados calculados para ese principal, como una instantánea guardada, para que otro principal no pueda recorrerlos. Firmarlo es la forma más sencilla de reconocer uno manipulado. Un cursor NO DEBERÍA llevar datos de los elementos de forma legible, como los valores de orden de una clave en claro: las URL de next acaban en los registros. Cifrarlo, o guardar la posición en el servidor, lo evita (13.9). Un cursor cifrado con un nonce aleatorio cambia en cada lectura, y con él el cuerpo y la ETag de la página, que entonces nunca recibe 304 (8); un esquema determinista lo evita.
  • Un cursor NO DEBE estar ligado a limit, fields, include ni count: cambian lo que lleva cada página, no qué elementos recorre. Entre páginas, el cliente PUEDE añadirlos, cambiarlos o quitarlos en la URL de next de un GET, o en el cuerpo de un QUERY, y eso NO DEBE invalidar el cursor.
  • El servidor PUEDE empezar con un desplazamiento dentro del cursor y pasar más tarde a paginación por clave sin que el cliente lo note. La garantía es la de 5.2: sin repetidos ni huecos si no hay escrituras concurrentes.

6.5 Recuento

El descubrimiento declara count como "exact" o "estimated". Con count=true, la respuesta DEBE añadir total y, si el número es aproximado, "total_estimated": true. En una colección que declara count, count=false equivale a no enviarlo, y cualquier valor que no sea true o false DEBE dar invalid_parameter. En una colección que no lo declara, y en cualquier servidor sin este perfil, count con cualquier valor, también false, DEBE dar unsupported_parameter (5.3). total DEBE contar solo los elementos que el cliente puede ver y que selecciona la petición (5.2), también cuando es estimado; con un filtro a muchos, elementos de la colección, no elementos relacionados (6.1).

7. writes Perfil

URI del perfil: https://w3id.org/restep/1/writes. Estado: estable. Escrituras que se pueden reintentar sin duplicar y que no se pisan unas a otras. La caché es un perfil aparte, cache.

7.1 Repetir sin duplicar

POST /orders
Idempotency-Key: "8e03978e-40d5-43e8-bc93-6894a57f9324"
  • Todo POST no idempotente, también las acciones declaradas "idempotent": false, DEBE aceptar la cabecera Idempotency-Key, salvo lo que se dice más abajo para las peticiones sin credenciales: una cadena de Structured Fields sin parámetros (RFC 9651); dos claves son la misma solo cuando sus valores son iguales carácter a carácter. Una clave mal formada DEBE dar 400 bad_request, con una entrada de errors cuyo header es Idempotency-Key. En métodos que no sean POST, el servidor DEBE ignorar la cabecera: a diferencia del borrador, que también menciona PATCH, el PATCH de Restep con merge patch ya es idempotente (5.7). Este apartado define la sintaxis y el significado de la cabecera para Restep por sí solo: sigue el borrador del IETF (14.2, revisión 09) en lo que coinciden, y no depende de que ese borrador avance ni de que siga como está.
  • Una clave es de un principal (2), no de un token, y de un destino (método y ruta, comparados tras decodificar los porcentajes, sin la query): un reintento con un token renovado la sigue encontrando. Dos peticiones son la misma cuando comparten clave, principal y destino, sus parámetros de query son los mismos tras decodificar los porcentajes (el orden de los parámetros con nombres distintos no cuenta, como en 5.2; el de los valores repetidos de un mismo nombre sí, porque la API puede darle significado) y sus cuerpos son iguales como valores JSON (2); en una subida (5.1), sus bytes y su tipo de medio son los mismos. Así, la misma clave en la misma ruta con otra query es otra petición, y recibe 422 idempotency_mismatch.
  • Las peticiones sin un principal autenticado cuentan todas como un único principal anónimo y comparten sus claves. El servidor PUEDE rechazar Idempotency-Key en esas peticiones. Si lo hace, DEBE declararlo en el descubrimiento con "anonymous": false en idempotency (si falta, vale true), y DEBE responder con 400 bad_request, con una entrada de errors cuyo header es Idempotency-Key y cuyo code es unknown, antes de cualquier efecto, a un POST sin credenciales que lleve la cabecera y al que, si no, se aplicaría este apartado; un POST a una acción declarada "idempotent": true DEBE en cambio ignorar la cabecera, y no guardar nada con ella (11.1). Mientras anonymous sea false, un recurso que exige la clave NO DEBE exigirla a las peticiones sin credenciales. Un 401 mandaría al cliente a conseguir unas credenciales que el recurso no necesita. Por lo demás, este apartado se les aplica como a cualquier principal. Un cliente DEBERÍA generar cada clave a partir de una fuente aleatoria, con al menos los 122 bits aleatorios de un UUID de versión 4, y NO DEBERÍA usarla para otra petición: quien adivina o averigua una clave puede usarla antes con el mismo principal o, con la misma petición, obtener su respuesta guardada (13.5).
  • El servidor DEBE guardar cada clave al menos 24 horas desde la primera petición, y DEBERÍA declarar cuánto en el descubrimiento ("idempotency": {"ttl": 86400}, en segundos). Pasado ese plazo, la clave cuenta como nueva.
  • Si vuelve a llegar la misma petición, el servidor DEBE devolver el mismo estado que la primera vez, y su Location si lo tenía, sin repetir el efecto, y DEBERÍA añadir Idempotent-Replayed: true, una cabecera que define Restep (el borrador del IETF no) y cuyo valor es el token true (RFC 9651, apartado 3.3.4). Su cuerpo NO DEBE dar más de lo que daría ahora una lectura: el servidor filtra el cuerpo guardado, o devuelve la representación actual, para que no revele nada que el principal ya no pueda leer; si el principal ya no puede leer el elemento en absoluto, recibe el mismo estado sin cuerpo. Una repetición cuyo cuerpo no es la representación actual del elemento, como el cuerpo guardado de un 200 a una acción, NO DEBE llevar Content-Location, ETag ni _etag, que harían que el cliente lo tomara como su copia nueva (11.1): lo que 7.2 exige a un 200 a una acción se aplica a la respuesta original. Cabeceras como Date pueden cambiar. Una repetición, y el 409 request_in_progress para la misma petición mientras la primera sigue en curso, ocupan el lugar que les da 5.4: después de las comprobaciones que impiden al principal saber lo que no puede, incluido su permiso actual sobre el destino, y en lugar de 428, 412 y de los errores que dependen del estado guardado. Ninguno evalúa If-Match, If-None-Match ni la exigencia del 428: una repetición responde como arriba aunque ya no se cumplan, o aunque su destino ya no exista, lo borrara la primera petición u otra. Con un If-Match que falla y un estado guardado 2xx, el RFC 9110 (apartado 13.1.1) lo permite para una petición que cambia el estado y que ya tuvo éxito; con un If-None-Match que falla, al que el apartado 13.1.2 responde con 412 en cualquier método salvo GET y HEAD, o con un estado guardado que no es 2xx, Restep se aparta a propósito del RFC 9110, para que una repetición reciba siempre la respuesta de la primera petición. Una petición distinta con la misma clave las evalúa como siempre, y su 422 idempotency_mismatch no se da mientras se aplique 428 o 412 (5.4).
  • Si el servidor falla después del efecto y antes de guardar la respuesta, un reintento con la misma clave NO DEBE repetir el efecto: el servidor registra las dos cosas de forma atómica, o se recupera como si lo hubiera hecho.
  • Una petición rechazada antes de ejecutarse (un 4xx como 422, o un 5xx que no dejó efecto) PUEDE no guardarse; entonces no gasta la clave, y el cliente puede corregirla y reintentar con la misma. Una petición que tuvo efecto DEBE guardarse.
  • La misma clave con otra petición DEBE dar 422 idempotency_mismatch, también si la primera aún se está procesando. La misma petición mientras la primera aún se procesa DEBE dar un error 409 con code request_in_progress, que DEBERÍA llevar Retry-After, salvo que el servidor espere a que termine la primera y entonces la responda como una repetición, cosa que PUEDE hacer; el cliente PUEDE volver a enviarla con la misma clave, pasado el Retry-After si lo lleva y dentro de la vida de la clave (5.7). Un recurso que exige la clave DEBE dar 400 idempotency_key_required si no llega, salvo a una petición sin credenciales cuando anonymous es false (arriba).
  • Un servidor que solo tiene core no conoce la cabecera y la ignora. El cliente NO DEBE contar con Idempotency-Key si el servidor no anuncia writes.

7.2 Concurrencia optimista

  • Cada elemento tiene una ETag de elemento fuerte: la ETag de su representación completa, sin fields ni include, calculada como si _etag no estuviera; sus demás miembros _ cuentan. Es la ETag de la representación que lee este principal, así que donde esa representación depende del principal (_actions, campos que no puede leer), también depende de él la ETag de elemento, e If-Match se evalúa contra la de quien escribe. Un GET del elemento completo sin codificación de contenido DEBE llevarla, y el servidor NO DEBE usar para ella un validador débil (W/). Con codificación de contenido (gzip), la cabecera ETag DEBE ser distinta de la ETag de elemento o débil, como exige el RFC 9110 (apartados 8.8.1 y 8.8.3.3); _etag sigue llevando la ETag de elemento.
  • Donde el elemento tiene campos traducidos (3), cada idioma es una representación propia: la ETag de elemento DEBE ser distinta por idioma (5.6), y, para un PATCH o un DELETE, el servidor elige la representación con la que evalúa If-Match entre las de todos los idiomas que ofrece: aquella cuya ETag de elemento actual lista el campo, si la hay, y si no, la que elige Accept-Language (el RFC 9110, apartado 3.2, deja esa elección al servidor). Así, If-Match DEBE cumplirse con la ETag de elemento actual de cualquier idioma que ofrezca el servidor, un cliente que lee en un idioma y escribe en otro no recibe 412, y se sigue detectando una actualización perdida.
  • Toda respuesta cuyo cuerpo es la representación de un solo elemento, a una lectura o a una escritura, DEBE llevar la ETag de elemento en _etag, sean cuales sean su codificación de contenido y sus parámetros: un proxy o una CDN que comprime la respuesta puede debilitar o cambiar la cabecera ETag sin que el servidor lo sepa, y el cliente sigue necesitando un validador para If-Match. Su valor es la etiqueta de entidad tal como la llevaría la cabecera ETag, comillas incluidas, para que el cliente la copie sin cambios en If-Match: "_etag": "\"a1b2c3\"" se envía como If-Match: "a1b2c3".
  • La respuesta de un elemento con fields o include es otra representación: su cabecera ETag DEBE cambiar cuando cambie cualquier cosa de ella, también los elementos incluidos, mientras que su _etag sigue siendo la ETag de elemento, para que el cliente pueda escribir sin volver a leer.
  • Un elemento en la respuesta de una colección DEBERÍA llevar en _etag la ETag de elemento de la versión que representa, si admite PATCH o DELETE, para que el cliente pueda escribir sin leerlo antes. En una colección que declara sync (10), ese elemento DEBE llevarla en todas las páginas, con cualquier parámetro de consulta, con GET o con QUERY (11.4).
  • En una colección que declara reusable_ids (5.1), la ETag de elemento de un elemento DEBE ser distinta de las de todos los elementos anteriores que tuvieron su id, para que un If-Match leído de uno de ellos dé 412.
  • PATCH y DELETE DEBEN evaluar If-Match contra la ETag de elemento como dice el RFC 9110 (listas, *, comparación fuerte): si no coincide, 412 precondition_failed. También DEBEN evaluar If-None-Match (listas, *, comparación débil): si coincide, 412 sin aplicar la escritura. Sobre un elemento que no existe, como uno que otra escritura acaba de borrar, DEBEN dar 404 (410 retired solo tras una retirada, 5.5), digan lo que digan las precondiciones: la misma petición sin ellas recibiría ese 404, así que el RFC 9110 (apartado 13.2.1) obliga al servidor a ignorarlas, y 5.4 no deja dar un 412 mientras se aplique un 404. La excepción es un PATCH a un id libre en una colección que declara upsert (5.1), que crearía el elemento: ahí If-Match falla con 412, e If-None-Match: * le deja crear.
  • Un POST a una colección, o a una acción sobre ella, tiene como destino la colección, y Restep no da a una colección ninguna ETag contra la que escribir. El servidor DEBE evaluar ahí If-Match e If-None-Match como dice el RFC 9110 (apartados 13.1.1 y 13.1.2): * depende de si la colección tiene una representación actual para este principal, así que If-Match: * se cumple e If-None-Match: * da 412 cuando el principal puede leer la colección, lleve o no una ETag su GET, y al revés cuando no puede; una lista de etiquetas de entidad se compara con la ETag que llevaría para este principal un GET de la colección sin parámetros; donde no lleva ninguna, no coincide ninguna etiqueta de la lista, así que una lista en If-Match da 412 y una lista en If-None-Match deja seguir la petición. Un cliente NO DEBERÍA enviarlas en un POST así; para crear un elemento solo si su id está libre, elige él el id (5.1).
  • En una acción sobre un elemento, las precondiciones se evalúan contra el elemento y su ETag de elemento. Es una convención de Restep: en HTTP, el destino de POST /orders/2001:cancel es la URI propia de la acción (RFC 9110, apartado 15.3.5). Por eso, un 200 a una acción que cambió el elemento, salvo una repetición (7.1), DEBE llevar Content-Location con la ruta del elemento y ETag con su nueva ETag de elemento o, con una codificación de contenido, una etiqueta distinta de ella o débil, como arriba (RFC 9110, apartados 8.7 y 8.8.3); su _etag lleva la nueva ETag de elemento en los dos casos, y un 204 a una acción no lleva ETag: un cliente que necesita el validador lee el elemento.
  • Evaluar If-Match y aplicar la escritura DEBE ser atómico respecto a las demás escrituras sobre el mismo elemento.
  • Un recurso PUEDE exigir If-Match; sin él DEBE responder 428 precondition_required. Empezar a exigirlo es un cambio incompatible (5.5), salvo que empiece cuando la colección declara reusable_ids (5.1), que ya lo es: ahí solo If-Match distingue un elemento de otro anterior con el mismo id (5.7). En una colección que declara upsert (5.1), If-None-Match: * en un PATCH cumple esa exigencia: el PATCH crea el elemento si su id está libre, y da 412 si no lo está. Solo * la cumple: un If-None-Match con una lista de etiquetas de entidad no, así que una petición que lleva uno sin If-Match recibe 428, en el orden de 5.4.

Campos calculados. Un campo que el servidor calcula a partir de otros datos forma parte de la representación, así que la ETag de elemento cambia cuando cambia él, aunque nadie haya escrito el elemento. Si debe estar ahí depende de cómo cambia. Uno que cambia poco, o del que depende quien escribe el elemento (si un libro tiene un ejemplar libre, para quien lo reserva), va en la representación: un 412 cuando ha cambiado es correcto, como con inherit, y devolverlo cambiado da 422 read_only (5.1). Uno que cambia todo el rato (los segundos hasta que acaba una oferta, los lectores conectados) no: haría fallar con 412 cada escritura y cambiar cada página para sync. Un estado que solo depende de la fecha se da mejor como los datos de los que depende y un filtro con nombre (expected_at y filter[late]) que como un campo que cambia solo.

7.3 Respuesta mínima

Con Prefer: return=minimal (RFC 7240), las escrituras PUEDEN responder sin cuerpo: 201 con Location, o 204. Cuando el elemento que crearon o cambiaron sigue existiendo (no tras un DELETE), esa respuesta DEBE llevar la ETag de ese elemento en ETag, porque no tiene _etag, salvo el 204 de una acción (7.2), y DEBERÍA llevar Preference-Applied: return=minimal. Una repetición (7.1) de un 201 así NO DEBE llevar ETag, aunque el elemento siga existiendo: la guardada puede no ser ya la actual, y la actual no la produjo esta petición; un cliente que necesita un validador lee el elemento en Location. Una respuesta a una escritura que una caché pueda guardar DEBE llevar Vary: Prefer (RFC 7240, apartado 2). Por defecto devuelven la representación.

8. cache Perfil

URI del perfil: https://w3id.org/restep/1/cache. Estado: estable. Lecturas que una caché puede guardar, revalidar e invalidar. Solo requiere core, así que una API de solo lectura puede anunciarlo sin construir el almacén de idempotencia de 7.1.

  • Toda respuesta a GET, HEAD o QUERY, también las de error, DEBE llevar Cache-Control explícito.
  • Una respuesta que depende de las credenciales es private o no-store, como exige 5.1 a todo servidor. Una que no depende de ellas PUEDE ser public, como un documento de descubrimiento servido sin credenciales (4.2).
  • Un GET correcto de un elemento completo o de un singleton (5.9), sin fields ni include, DEBE llevar una ETag. Si el servidor anuncia también writes, es la ETag de elemento de 7.2 cuando la respuesta no tiene codificación de contenido, y es distinta de ella o débil cuando la tiene (7.2); si no, PUEDE ser débil. Toda ETag que dé el servidor DEBE cambiar cuando cambie cualquier cosa de la representación que valida, también los elementos incluidos, y una fuerte DEBE ser distinta en cada codificación de contenido o débil (7.2).
  • If-None-Match en un GET o HEAD DEBE evaluarse como dice el RFC 9110 (listas, *, comparación débil): si coincide, el servidor DEBE responder 304. En un QUERY, si coincide, el servidor DEBE responder 412, como exige el RFC 9110 (apartado 13.1.2) a todo método que no sea GET ni HEAD y mantiene el RFC 10008 (apartado 2.6); para revalidar el resultado de un QUERY, un cliente DEBERÍA enviar un GET condicional al recurso equivalente que da la respuesta en Location, cuando lo da (RFC 10008, apartado 2.7). En las escrituras, If-None-Match es cosa de 7.2.
  • Una respuesta correcta a un GET DEBERÍA llevar Cache-Groups (RFC 9875) con cada elemento que representa, también los incluidos, y, si es una colección, la propia colección, para que una caché pueda descartar las listas en las que entra o de las que sale un elemento. Una respuesta 2xx a un HEAD DEBERÍA llevar los grupos que llevaría el GET. Una respuesta correcta a una escritura que confirmó cambios (en un lote, la respuesta exterior, que abarca todas las operaciones confirmadas) DEBERÍA llevar Cache-Group-Invalidation con cada elemento que cambió y sus colecciones, aunque no tenga cuerpo. Los nombres de grupo son opacos y por origen; la ruta del elemento ("/books/7") y la de la colección ("/books") son la elección obvia. Los nombres de grupo NO DEBEN revelar al cliente lo que no podría saber de otro modo (5.4): una respuesta nombra por su ruta solo un elemento que el cliente puede ver, e invalida los demás a través de un grupo que pueda conocer, como el de su colección. Una caché puede hacerles caso o no, y el RFC 9875 solo garantiza 32 grupos por campo, de 32 caracteres cada uno, así que en una página larga o con un id largo puede que no se invaliden todos los elementos. El RFC 9875 (apartado 2) no da ningún significado al orden de los grupos; un servidor que recorta la lista para no pasar de 32 grupos DEBERÍA conservar el grupo de la colección y quitar los de los elementos.
  • Un elemento que declara acciones que no son seguras DEBERÍA servirse con Cache-Control: no-cache y una ETag: una acción lo cambia a través de otra URI, y HTTP solo exige a una caché que invalide la URI de la acción; puede invalidar también la del elemento, que nombra Content-Location, pero no tiene por qué (RFC 9111, apartado 4.4). Enviar Cache-Group-Invalidation (arriba) sigue siendo solo una recomendación.
  • Una respuesta con campos traducidos lleva Vary: Accept-Language (5.6).

9. relations Perfil

URI del perfil: https://w3id.org/restep/1/relations. Estado: estable. La forma de las relaciones la fija el apartado 3 y cómo se escriben, el 5.1, así que las sigue cualquier servidor; este perfil añade las declaraciones y la expansión.

  • El descubrimiento DEBE declarar cada relación en relations, con su colección de destino en to (una lista, si puede apuntar a varias: ver el apartado 3), "many": true si es a muchos e "include": true si se puede expandir.
  • include=author DEBE rellenar ese objeto con el elemento completo; con una relación a varias colecciones, el elemento de la colección que nombra su type. Admite rutas con punto (include=author.publisher), como las rutas de relación de JSON:API, hasta el include_depth declarado (1 si no se declara). Una relación no declarada o no expandible, o una ruta más profunda que include_depth, DEBE dar unsupported_parameter.
  • A través de una relación a varias colecciones, una ruta en include o en fields (fields=showcase.title) se aplica en los destinos donde existe y se ignora en los demás; una que no existe en ninguno DEBE dar unsupported_parameter en include e invalid_parameter en fields, como un campo que no existe (6.3).
  • Si el cliente no puede ver el elemento relacionado, el objeto DEBE quedarse solo con id (y type, y href donde lo exige el 3 o el 5.9).
  • Cuando el destino es una subcolección, cada objeto de relación lleva href (3): un cliente construye la ruta de un destino normal a partir del path de su colección y del id (5.1), pero el elemento de una subcolección necesita además el id de su padre, que lleva el href. {"id": "3", "href": "/books/7/reviews/3"}.
  • Cuando el servidor implementa también query, fields admite rutas con punto (fields=title,author.name); una ruta con punto cuya relación no está en include DEBE dar invalid_parameter.
  • Las relaciones con muchos elementos (las reseñas de un libro) DEBERÍAN ser subcolecciones, como /books/7/reviews, declaradas con una plantilla en path y un parent (4.2) y que cumplen core y, si se anuncia, query. La relación que lleva a una PUEDE llevar la misma plantilla en su path, como hace reviews en el ejemplo de 4.2. Una relación así DEBE aparecer solo en el descubrimiento, donde la plantilla basta para llegar a la subcolección; la representación del padre NO DEBE llevarla. Una relación con un elemento concreto de una subcolección sigue llevando href (arriba). Una lista a muchos incrustada en una representación NO DEBE paginarse: si puede crecer sin límite, DEBERÍA ser una subcolección.
  • Para filtrar por una relación, el descubrimiento declara la ruta con punto en filter: filter[author.id]=3; a través de una relación a muchos, con quantifier (6.1): filter[reviews.rating][ge]=4.

10. sync Perfil Experimental

URI del perfil: https://w3id.org/restep/1/sync. Estado: experimental (1.2). Mantener al día una copia local de colecciones enteras sin volver a descargarlo todo, como hacen los métodos /changes del RFC 8620 (apartado 5.2). Requiere query.

  • Una colección está sincronizada cuando declara sync en el descubrimiento, como objeto, {} si no tiene nada que decir. Una colección NO DEBE declarar sync salvo que el servidor anuncie este perfil en profiles; sin él, una declaración sync no significa nada y ninguna colección está sincronizada. Solo las colecciones sincronizadas responden a :changes; en cualquier otra, :changes DEBE dar 404 not_found. Toda colección sincronizada DEBE admitir GET, NO DEBE tener un filtro obligatorio (6.1), y DEBE declarar id en filter con in. El resto de este apartado trata de las colecciones sincronizadas.
  • Las respuestas de colección DEBEN llevar state: una cadena opaca que cambia cada vez que cambia algo de la colección que el cliente puede ver. Refleja lo que ve ese cliente: un elemento que el cliente deja de poder ver cuenta como borrado. Una respuesta filtrada lleva el mismo state que la colección entera; un cliente que guarda una copia de la colección la recorre sin filtros.
  • state y :changes abarcan todos los elementos que el cliente puede ver, también los que oculta un filtro por defecto (6.1): un elemento que un filtro por defecto empieza a ocultar, como uno archivado, va en updated, no en destroyed. Un cliente que guarda una copia DEBE recorrer la colección desactivando todos los filtros por defecto y sin ningún otro filtro, y volver a cargar del mismo modo los elementos cambiados, pero con filter[id][in] como único filtro.
  • Una copia está en un solo idioma: state no depende de Accept-Language, pero un cambio en una traducción es un cambio de los elementos que la muestran. Un cliente que cambia de idioma DEBE volver a recorrer la colección antes de dar su copia por actual; :changes da solo identificadores y no depende del idioma.
  • El cliente NO DEBE interpretar ni fabricar un state; PUEDE comparar dos estados para ver si son iguales. Se le aplican las mismas consideraciones que a los cursores (6.4, 13.9).
  • Todas las páginas de un recorrido DEBEN llevar el state de la primera, la petición sin cursor (el servidor puede guardarlo en el cursor). El cliente DEBE usarlo como since en su siguiente sincronización: los cambios hechos durante el recorrido aparecerán ahí.
  • Un recorrido NO DEBE perder elementos: todo elemento que existía, y casaba con la petición, cuando se sirvió la primera página, y que no aparece en :changes desde ese state, sale en alguna página. Los cursores por desplazamiento no lo garantizan; los cursores por clave o una instantánea sí; con un orden por una ruta a muchos (6.2), solo una instantánea.
  • GET /books:changes?since=<state> devuelve los identificadores creados, modificados y borrados desde ese estado. La respuesta DEBE llevar since, state, has_more, created, updated y destroyed. Cada identificador DEBE aparecer como mucho en una lista, elegida según lo que el cliente podía ver entre since y el state devuelto (un elemento que no existe no se ve). Estas reglas cubren los elementos que cambiaron, o cuya visibilidad para el cliente cambió, en ese intervalo:
    • un elemento que podía ver en since y no ve en state DEBE estar en destroyed;
    • un elemento que ve en state DEBE estar en updated si lo podía ver en since y cambió o dejó de verse entre medias, y en created si no lo podía ver en since;
    • un elemento que no ve en ninguno de los dos extremos DEBE estar en destroyed si lo pudo ver entre medias, y NO DEBE aparecer en otro caso;
    • en una colección que declara reusable_ids (5.1), un id borrado y creado de nuevo dentro del intervalo DEBE estar en created: es otro elemento.
    Un elemento que veía en los dos extremos y no cambió PUEDE estar en updated. Si el servidor no puede reconstruir lo que el cliente veía en el intervalo, DEBE responder 410 state_expired; que pueda o no NO DEBE depender de que exista un elemento cuya existencia se oculta al cliente (5.4). Los clientes DEBEN tratar igual created y updated, pidiendo el elemento y sustituyendo su copia, y DEBEN ignorar un id de destroyed que no tienen. (Donde JMAP dejaría fuera un elemento creado y borrado dentro del intervalo, Restep lo da en destroyed si el cliente lo pudo ver, para que un cliente que lo vio lo borre.)
  • Si has_more es true, el state devuelto es intermedio: el cliente DEBE repetir la llamada con él hasta que has_more sea false antes de dar su copia por actualizada. Un state intermedio DEBE ser un punto de la historia de la colección, y cada respuesta DEBE seguir las reglas de arriba para su propia ventana, de su since a su state, de modo que respuestas consecutivas dan los cambios en el orden en que ocurrieron: un elemento que el cliente dejó de ver y volvió a ver está en destroyed en una y en created en una posterior; un id creado de nuevo en una colección que declara reusable_ids es otro elemento. (RFC 8620, apartado 5.2, cuyos estados intermedios no tienen por qué seguir la historia, prohíbe en cambio ese orden.)
  • :changes abarca la colección entera: los filtros y los demás parámetros de query DEBEN dar ahí unsupported_parameter; $api_version no es un parámetro de query: donde lo define una extensión (5.5), :changes lo acepta como cualquier otra petición, y donde ninguna lo define, da ahí unsupported_parameter como todo parámetro reservado que el servidor no implementa (5.3). Si falta since, o es uno que el servidor no emitió (uno manipulado), DEBE dar invalid_parameter, como un cursor manipulado (6.4). Sincronizar una vista filtrada queda fuera de esta versión.
  • El cliente pide los elementos cambiados con GET /books?filter[id][in]=7,12. Un id de created o updated que esa recarga no devuelve, porque el elemento se borró o dejó de verse después del state, se quita de la copia del cliente, y el cliente sigue desde el state de :changes: si el elemento vuelve, una llamada posterior lo informa.
  • El servidor DEBERÍA guardar los cambios al menos 7 días y DEBERÍA declarar cuánto en sync.retention de la colección (en segundos). Si ya no puede calcular los cambios, DEBE responder 410 state_expired, y el cliente vuelve a cargar la colección.
  • El nombre de acción changes queda reservado para este perfil (11.1).
  • El servidor PUEDE ofrecer avisos por Server-Sent Events en la ruta declarada en events, relativa a la raíz de la API como los miembros path del descubrimiento (2); esa respuesta DEBE llevar Cache-Control: no-store. PUEDE limitar los flujos que un principal mantiene abiertos, y DEBE responder 429 rate_limited, con Retry-After, al que pase de ese límite: Restep extiende 429, que el RFC 6585 (apartado 4) define para peticiones a lo largo del tiempo, a los flujos abiertos a la vez. Un EventSource no se reconecta después (HTML Standard, apartado 9.2.3), así que la aplicación vuelve a abrir el flujo. Cada evento dice qué colecciones tienen un estado nuevo, y nombra cada una por su clave o, si es una subcolección, por su ruta relativa a la raíz de la API con la plantilla expandida ("/books/7/reviews"); los datos en sí se piden con :changes. El servidor NO DEBE enviar un evento por un cambio que no cambie el state de ese principal, o el ritmo de los eventos revelaría actividad que no puede ver.
  • Los eventos son pistas: el cliente DEBE tolerar eventos repetidos, fusionados y desordenados. Al abrir el flujo, y en cada reconexión, el cliente DEBE llamar a :changes en cada colección que guarda, desde el último estado que aplicó, y DEBE avanzar ese estado solo después de aplicar los cambios; un evento por sí solo nunca lo avanza. El servidor NO DEBE depender de Last-Event-ID para reanudar.
  • El servidor DEBERÍA mandar un comentario SSE al menos cada 15 segundos, como aconseja el HTML Standard (apartado 9.2.7), para reducir los cortes por inactividad. DEBE cerrar el flujo cuando dejen de valer las credenciales con las que se abrió, y DEBE responder 401 a toda reconexión con credenciales no válidas, también a la automática de EventSource. Después, la aplicación DEBE esperar a tener credenciales válidas antes de volver a abrir el flujo.

11. Extensiones

Cada extensión se anuncia en extensions y tiene su propia URI de perfil (https://w3id.org/restep/1/batch…). Qué requiere cada una, y si es estable o experimental, está en 1.2.

11.1 actions Extensión

Estado: estable. Operaciones que no son crear, leer, actualizar ni borrar, que siguen la AIP-136 en los dos puntos delante del nombre, aunque no en sus nombres en camelCase ni en poner todas las acciones seguras en GET.

Cuándo una operación es una acción. Una acción es para lo que no puede decir una escritura normal. La transición de un campo de estado es una acción cuando tiene reglas o consecuencias, como POST /orders/2001:cancel, con _actions diciendo cuándo se aplica, y un PATCH del campo cuando no tiene ni unas ni otras. Un estado reversible con datos propios (quién, cuándo, por qué) es un par de acciones, :reserve y :release, cuyos datos son campos del elemento, con _actions diciendo cuál se aplica. Algo con datos propios que puede pasar muchas veces, como los recordatorios de un pedido, es una subcolección. Un cambio de estado con efectos fuera de la API (abajo) es una acción, para que se pueda declarar y rechazar por sí solo.

POST /orders/2001:cancel       sobre un elemento
POST /books:import             sobre la colección
GET  /orders/2001:preview      una acción segura declarada con "method": "GET"
  • Cada acción DEBE declararse en actions de su colección o de un singleton (5.9), con safe e idempotent; las acciones de una colección llevan además on ("item" o "collection"), y las de un singleton no llevan on y se usan en {path}:{nombre} (POST /me:verify_email). Una acción declarada "safe": true DEBE declarar también "idempotent": true, porque los métodos seguros son idempotentes (RFC 9110, apartado 9.2.2). idempotent promete el mismo efecto, no la misma respuesta (5.7): para volver a recibir el primer estado y el primer Location, el cliente envía Idempotency-Key donde el servidor aplica el 7.1 a la petición, cosa que no tiene por qué hacer una acción declarada "idempotent": true (11.1); el cuerpo de una repetición no da más de lo que daría ahora una lectura. Los nombres de acción siguen el 3 y DEBERÍAN ir en snake_case; una colección NO DEBE declarar una acción llamada changes, que usa sync.
  • Una acción usa POST salvo que su declaración diga "method": "GET", cosa que solo PUEDEN hacer las acciones seguras. El servidor DEBE aceptar también los dos puntos codificados como %3A, y DEBE escribirlos tal cual en href, en _actions y en todos los demás enlaces que construye, para que una caché vea una sola URI.
  • La declaración PUEDE llevar description, effects (abajo) y: si la acción usa POST, un esquema input (4.3); si usa GET, params; si es segura, output. Una acción GET no tiene cuerpo, así que NO DEBE declarar input.
  • params declara los parámetros de query de una acción GET, como un objeto cuyas claves son sus nombres (3) y cuyos valores llevan un type de 4.2, y PUEDEN llevar "list": true, "required": true y una description: "params": {"with": {"type": "string", "required": true}}. Un parámetro de lista lleva valores separados por comas, que se leen tras decodificar los porcentajes; sus valores no pueden contener comas, codificadas o no. Un cliente que necesita una envía la entrada en el cuerpo de una acción POST declarada safe. Un parámetro string escalar no se divide y puede contener comas. Un valor de un parámetro integer o number, y cada elemento de uno de lista, sigue la regla de los operandos de filtro (6.1): la gramática number, exponente incluido, y, para integer, parte fraccionaria cero. Un parámetro obligatorio que falta, un valor que no encaja con su tipo, una lista vacía y un parámetro repetido DEBEN dar invalid_parameter; un parámetro que la acción no declara, unsupported_parameter (5.3). Una acción GET sin params es una declarada con "params": {}: no admite parámetros de query.
  • output es el esquema del resultado de una acción segura (2): su 200 lleva entonces un objeto JSON con esa forma, que no es una representación del elemento o la colección sobre la que se pide. NO DEBE llevar _etag ni _actions; el cliente no actualiza ninguna copia con él, y HTTP lo cachea según sus propias reglas, con su propia cabecera ETag. GET /books/7:compare?with=12 → {"fields": [{"name": "pages", "from": 320, "to": 352}]}.
  • Una acción POST DEBE tratar un cuerpo vacío, con o sin Content-Type, como {} enviado como application/json; así, un cliente que no tiene nada que enviar puede enviar cualquiera de los dos. Un cuerpo no vacío sigue el 3.
  • La respuesta a una acción que no es segura sobre un elemento o un singleton DEBE ser su representación (200), un recurso nuevo (201 con Location) o nada (204). Una acción que no es segura sobre una colección no tiene representación propia que devolver, así que su respuesta DEBE ser 201 con el Location de lo que crea (una importación, un informe) o 204, nunca 200. La respuesta a una acción segura DEBE ser su resultado (200) donde declara output; si no, su representación (200) o nada (204) en un elemento o un singleton, y 204 en una colección: una acción segura no crea nada, así que nunca responde 201. Un HEAD a una acción GET recibe el mismo estado y las mismas cabeceras sin contenido (RFC 9110, apartado 9.3.2). Un 200 que lleva la representación del elemento después de que la acción lo cambiara lleva Content-Location y ETag como dice 7.2. Publicar una versión, por ejemplo, es POST /books/7:publish, que se responde con 201 y el Location de la versión nueva (apéndice D).
  • Tras una acción que no es segura y que salió bien sobre un elemento, un cliente NO DEBE usar una copia guardada de ese elemento sin revalidarla, salvo que la respuesta llevara la representación del elemento con Content-Location, que es entonces su copia nueva.
  • Una petición a una acción que su colección o su singleton no declara, o que está declarada con on para el otro tipo de recurso, DEBE dar 404 not_found, como cualquier recurso que no existe; una acción declarada con otro método DEBE dar 405 con Allow, salvo HEAD en una acción declarada con "method": "GET", que exige el 5.1. Una acción declarada que el estado actual del elemento no permite DEBE dar 409 conflict, con un reason si la API tiene uno (5.4); una que este principal no puede usar, 403 o 404 (4.2).
  • Con writes, una acción declarada "idempotent": true NO DEBE rechazar una petición porque lleve una Idempotency-Key bien formada: PUEDE ignorarla, porque repetir la acción ya es seguro (5.7), o aplicarle 7.1; una que ignora las claves ignora también una mal formada, en vez de dar 400; a una petición sin credenciales, cuando idempotency declara "anonymous": false, ignora la clave y no guarda nada con ella (7.1). Un cliente PUEDE enviar una a cualquier acción POST.
  • effects lista las consecuencias de una acción que no es segura que una persona puede querer aprobar antes: destroys (borra datos que no se pueden recuperar), external (llega fuera de la API: un correo, un mensaje, una llamada a otro sistema) y charges (cuesta dinero). Una acción segura PUEDE declarar solo charges. "pay": {"effects": ["charges", "external"]}; "cancel": {"effects": []}. Sin effects, un cliente trata una acción que no es segura como si tuviera los tres, y una segura como si no tuviera ninguno; si effects contiene un valor que no conoce, trata la operación como si tuviera los tres efectos (destroys, external y charges), también cuando la acción está declarada segura; y así trata también un método que no es seguro de una colección, de sus elementos o de un singleton (5.9) y que method_effects o item_method_effects no declaran (salvo DELETE, que tiene ["destroys"]) o declaran con un valor que no conoce (4.3). Un cliente que pregunta a una persona antes de las operaciones que no son seguras DEBERÍA preguntar antes de cualquier efecto declarado, y también antes de una operación declarada con [] salvo que confíe en el servidor (13.1), en cuyo caso PUEDE seguir sin preguntar. La declaración no autoriza nada (4.3).
  • Una colección PUEDE declarar una acción de colección segura llamada new, que se usa con GET (GET /orders:new), cuyo resultado da los valores iniciales de un elemento nuevo para este principal y un esquema efectivo: {"values": {…}, "schema": {…}}. El esquema efectivo DEBE solo restringir el esquema create de la colección (4.3), nunca ampliarlo, y es orientativo: lo que decide sigue siendo la respuesta al POST. Una colección con varios formularios los distingue con un parámetro declarado de la acción. Una acción de una colección llamada new DEBE ser esta: declarada on la colección, safe y con "method": "GET".
  • Una representación PUEDE listar en _actions las acciones disponibles en su estado actual, para que el cliente no duplique las reglas de negocio. Un servidor que las lista DEBERÍA dar "_actions": {} donde no hay ninguna disponible, porque un _actions ausente significa que no se calcularon. Toda acción que liste DEBE estar declarada en actions de su colección o su singleton, con el mismo on, donde lo tiene, y el mismo método, para que el cliente sepa si es safe e idempotent:
{ "id": "2001", "status": "paid",
  "_actions": { "cancel": { "method": "POST", "href": "/orders/2001:cancel" } } }
  • Donde las variantes de una colección (2) admiten métodos o acciones distintos, la API DEBERÍA separarlas en colecciones distintas, con relaciones polimórficas que lleven type donde haga falta, o listar en las _actions de cada elemento lo que admite; una acción que la variante de un elemento no admite da 409 conflict.

11.2 batch Extensión Experimental

Estado: experimental (1.2). Varias operaciones en una petición, en orden y con referencias a los resultados de las anteriores, como las referencias hacia atrás del RFC 8620 (apartado 3.7). Se envían a la ruta declarada en batch.path.

POST /batch
{ "atomic": false,
  "operations": [
    { "id": "a", "method": "POST", "path": "/orders", "body": { "book": { "id": "7" } } },
    { "id": "b", "method": "POST", "path": "/orders/{a#/id}:pay",
      "headers": { "idempotency-key": "\"pay-2001\"" },
      "body": { "amount": { "$ref": "a#/total" } } } ] }

→ 200
{ "results": [
    { "id": "a", "status": 201, "headers": { "location": "/orders/2001" }, "body": { … } },
    { "id": "b", "status": 200,
      "headers": { "content-location": "/orders/2001", "etag": "\"o2001-v2\"" }, "body": { … } } ] }
  • Cada operación DEBE tener un id, único en el lote, un method, un path y, opcionalmente, headers (con los nombres en minúsculas) y body. Un id de operación DEBE ser una cadena no vacía sin #, { ni }, para que una referencia (abajo) tenga una sola lectura. Cada operación DEBE seguir las mismas reglas que si se enviara sola, con las excepciones de este apartado.
  • El path de una operación DEBE empezar por / y es relativo a la raíz de la API (2), como los miembros path del descubrimiento; NO DEBE llevar esquema, autoridad, fragmento ni segmentos de punto (., ..), y DEBE nombrar un recurso de Restep (5.9) que no sea el flujo de eventos (10). Un valor que inserte en él una referencia (más abajo) DEBE ser una cadena que sea un id válido (3) o un entero, y el servidor DEBE volver a comprobar esta regla en la ruta resultante; si no, la operación recibe 422 invalid.
  • Sus headers PUEDEN llevar solo if-match, if-none-match, idempotency-key y prefer, además de content-type y accept-language, que el servidor DEBE ignorar: el body de una operación ya es JSON y la petición del lote lleva Content-Type: application/json (3), y se aplica el Accept-Language del lote (más abajo). Toda operación actúa en nombre del principal del lote, con las credenciales, el Origin y el Accept de la petición del lote. El servidor NO DEBE aplicar a ninguna operación el Prefer, el If-Match ni el If-None-Match de la propia petición del lote.
  • Una referencia es <id>#<JSON Pointer> al cuerpo de la respuesta de una operación anterior, donde el puntero usa la forma de cadena JSON del RFC 6901 (apartado 5), no su forma de fragmento de URI: entre llaves literales dentro de path (%7B no lo es), donde el valor DEBE insertarse codificado con porcentajes como segmento de ruta (RFC 3986) y el puntero NO DEBE contener { ni } (si no, la operación recibe 422 invalid; para esas claves, se usa $ref en el cuerpo); o como {"$ref": …} en lugar de un valor del cuerpo. Este $ref no es una JSON Reference: su valor es <id>#<puntero>, no una URI. Un objeto cuyo único miembro es $ref es siempre una referencia, así que un cliente que mete en el cuerpo de un lote datos que no escribió él DEBE asegurarse de que ningún objeto de esos datos tenga $ref como único miembro.
  • Un cuerpo que no es un lote válido, un id de operación repetido o que incumple la regla de arriba para los id de operación, una referencia a una operación que no va antes, un lote anidado, un path que, tomando cada referencia como un id válido, incumple la regla de rutas de arriba o una cabecera fuera de esas seis DEBEN dar 400 bad_request antes de ejecutar ninguna operación. 5.4 se aplica a la petición del lote entera antes de ejecutar ninguna operación; una vez aceptado el lote, se aplica a cada operación por separado, sin perjuicio de las reglas de 424 not_executed que siguen. Más operaciones que max_operations DEBEN dar 413 content_too_large (Restep entiende «contenido demasiado grande» en operaciones, no solo en bytes), que el servidor PUEDE dar sin validar las operaciones: un lote que es a la vez demasiado largo y no válido puede recibir 400 o 413 (5.4).
  • Un lote que pasa estas comprobaciones, la del modo atómico de abajo y las de cualquier petición (credenciales, tipo de contenido, límites de frecuencia, 7.1) DEBE recibir 200 con un resultado por operación, en orden, cada uno con su status, sus headers y su body; un resultado de error es un objeto problem. Es la única excepción a «ningún error dentro de un 200» (5.4).
  • Con "atomic": true, o todas las operaciones tienen efecto o ninguna. Si una falla, lleva su error y todas las demás DEBEN recibir 424 not_executed, también las que se ejecutaron y se deshicieron. Un servidor que no puede deshacer alguna de las operaciones (un pago externo, un correo) DEBE rechazar el lote atómico con 422 invalid antes de ejecutarlo.
  • Sin atomic, cada operación se aplica por su cuenta. Una operación que se refiere a una que falló DEBE recibir 424 not_executed (RFC 4918, apartado 11.4); una cuyo puntero no encuentra nada, o cuyo valor referido no es válido donde va, 422 invalid.
  • Con writes, el lote en sí PUEDE llevar Idempotency-Key; entonces todo el lote sigue 7.1, incluida su regla para las peticiones sin credenciales cuando anonymous es false.
  • Otra excepción: los textos y los campos traducidos (3) de cada resultado nuevo (5.6) siguen el Accept-Language del lote, y el de una operación se ignora; un resultado repetido (7.1) conserva el suyo. Content-Language y Accept-Language en Vary van en la respuesta del lote, no en los headers de cada resultado: Vary incluye Accept-Language solo si algún resultado nuevo puede variar por idioma, y Content-Language se omite salvo que todos los resultados con textos elegidos por idioma compartan uno.

11.3 filter-expr Extensión Experimental

Estado: experimental (1.2). Un filtro como expresión, en la línea de la AIP-160:

GET /books?filter=price <= 20 AND (category = "novela-negra" OR rating >= 4.5)

Como en 6.1, el ejemplo muestra la query sin codificar para que se lea mejor. En la red, los espacios, las comillas, < y > van codificados con porcentajes (RFC 3986, apartado 3.4); el servidor lee la expresión tras decodificar los porcentajes (5.2).

  • Comparadores =, !=, <, <=, > y >=, que equivalen a eq, ne, lt, le, gt y ge; AND, OR, NOT y paréntesis. Campos por nombre o ruta con punto (3); un segmento de ruta puede llevar - (name.es-mx). AND, OR, NOT, true, false y null nunca son nombres de campo en una expresión: un campo que se llame así no se puede usar en una. Valores: cadenas entre comillas dobles (con \" y \\ como únicos escapes), números, true, false y null. campo = null y campo != null equivalen al operador null.
  • NOT es lo que más liga. AND y OR NO DEBEN mezclarse en el mismo nivel sin paréntesis: a AND b OR c DEBE dar invalid_parameter. La AIP-160 da a OR más precedencia que a AND y casi todos los lenguajes hacen lo contrario; Restep pide paréntesis para que nadie tenga que adivinar. La yuxtaposición (a b, que la AIP-160 trata como un Y difuso) también DEBE dar invalid_parameter: Restep exige paréntesis, que la AIP-160 dice que no deberían exigirse.
  • Un campo u operador no declarados en filter DEBEN dar unsupported_parameter. Las comparaciones DEBEN seguir 6.1, también en los valores ausentes y null, las colaciones y los campos que el principal no puede leer; un número comparado con un campo decimal se lee como decimal exacto.
  • Un filtro con nombre (6.1) entra en una expresión por su nombre, igual que va entre corchetes en filter[…]: un interruptor, solo (available), y uno con tipo como nombre = valor (search = "machado"), que no es una comparación con un campo; cualquier otro comparador sobre él DEBE dar unsupported_parameter. Un filtro con nombre DEBE seleccionar en una expresión los mismos elementos que entre corchetes. prefix y contains son funciones: prefix(title, "La"), contains(title, "niebla").
  • Una ruta declarada en filter con quantifier que atraviesa una relación a muchos (6.1) forma un grupo entre corchetes: reviews[rating >= 5 AND reader.id = "3"] DEBE casar cuando, y solo cuando, algún elemento relacionado que el principal puede ver casa con la expresión entera; NOT reviews[…], cuando ninguno; y todos, como NOT reviews[NOT (…)]. Dentro de los corchetes, las rutas son relativas al elemento relacionado, y cada una DEBE declararse en filter con su ruta completa (reviews.rating). Dos grupos sobre la misma relación son independientes: reviews[rating = 5] AND reviews[reader.id = "3"]. Una ruta así solo va entre corchetes: reviews.rating = 5 DEBE dar invalid_parameter, para que nadie tenga que adivinar si dos comparaciones sobre ella hablan del mismo elemento relacionado.
  • Un campo cuyo valor es una lista de escalares, declarado con quantifier (6.1), se compara directamente, sin corchetes: formats = "pdf" DEBE casar cuando, y solo cuando, algún elemento de la lista es "pdf". Cada comparación sobre la lista es independiente de las demás: formats = "pdf" AND formats = "epub" casa con un elemento que tiene los dos formatos. A diferencia del grupo que forma 6.1 con los parámetros filter[…] sobre el mismo campo de lista, las comparaciones no se atan al mismo elemento: los corchetes solo hacen falta para atar condiciones al mismo elemento relacionado, y solo van tras una relación a muchos.
  • No se combina con filter[…] en la misma petición: eso DEBE dar invalid_parameter. La única excepción es filter[nombre]=false, que desactiva un interruptor por defecto (6.1): qué elementos se recorren no forma parte de la lógica de la expresión. En el cuerpo de un QUERY, la expresión va en $expr junto a esos interruptores (11.4).

11.4 query-method Extensión Experimental

Estado: experimental (1.2). Para consultas que no caben en la URL, el método QUERY (RFC 10008): seguro, idempotente y cacheable, con los parámetros de query en el cuerpo.

QUERY /books
Content-Type: application/json

{ "filter": { "price": { "le": "20" }, "category": { "in": ["novela-negra", "poesia"] } },
  "sort": ["-rating"], "fields": ["title", "price"], "limit": 10, "count": true }
  • Las colecciones que lo aceptan DEBEN anunciarlo con Accept-Query: application/json (RFC 10008) en sus respuestas a GET y HEAD.
  • El cuerpo es un objeto JSON con los mismos miembros que los parámetros reservados: filter como objeto de campos y operadores (o, con filter-expr, la expresión como cadena, o un objeto con la expresión en $expr y, junto a ella, solo miembros "nombre": false que desactivan filtros por defecto, como hace filter[nombre]=false junto a una expresión en 11.3: {"$expr": "price <= 20", "available": false}; cualquier otro miembro junto a $expr da invalid_parameter), sort, fields e include como listas, limit como número y count como booleano. Los valores van con su tipo JSON, e in lleva una lista, así que sus valores sí pueden contener comas. Un filtro con nombre va como "nombre": valor, con el valor de su tipo, o "nombre": true si es un interruptor, y "nombre": false para desactivar un filtro por defecto (6.1); false en cualquier otro interruptor, o cualquier otro valor, da invalid_parameter. Un miembro desconocido DEBE dar unsupported_parameter.
  • Un QUERY DEBE seleccionar, ordenar y contar los elementos como lo haría el GET con los mismos parámetros en la query, que Restep trata como su recurso equivalente (RFC 10008, apartado 2.2), con los mismos errores; un valor que una query no puede llevar, como un valor de in con una coma, se compara tal como lo da el cuerpo. Sus enlaces siguen el punto siguiente, y un If-None-Match que coincide da 412 (8). La URL NO DEBE llevar más parámetros reservados que cursor; el servidor DEBE responder a cualquier otro con unsupported_parameter.
  • En la respuesta, next solo lleva cursor, que aquí manda sobre la regla de 6.4 que conserva los demás parámetros. Para la página siguiente, el cliente DEBE enviar a la URL de next un cuerpo con los mismos filter y sort, y PUEDE cambiar limit, fields, include y count (6.4); el servidor DEBE responder a un filter o un sort que no sea igual como valor JSON (2; un miembro ausente, {} y [] valen lo mismo) con invalid_parameter en cursor.
  • Las cachés que guardan respuestas a QUERY usan el cuerpo y su tipo de medio como parte de la clave (RFC 10008, apartado 2.7); muchas CDN aún no lo hacen.

11.5 oauth Extensión

Estado: estable. Cómo averigua un cliente dónde conseguir un token para la API. No define ni la autenticación ni la autorización: ata a la raíz de la API los metadatos de recurso protegido de OAuth 2.0 (RFC 9728). Un servidor que no la anuncia autentica como le parezca.

GET /api/                         (la raíz de la API: https://example.com/api/)
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://example.com/.well-known/oauth-protected-resource/api/"

GET https://example.com/.well-known/oauth-protected-resource/api/
{ "resource": "https://example.com/api/",
  "authorization_servers": ["https://auth.example.com"],
  "scopes_supported": ["books:read", "books:write"] }
  • Un servidor que anuncia oauth DEBE tener una raíz de API con el esquema https y sin fragmento, porque el RFC 9728 (apartado 1.2) no admite otro identificador de recurso.
  • El servidor DEBE servir los metadatos en la URL que el RFC 9728 (apartado 3.1) forma a partir de la raíz de la API: el sufijo well-known va entre el host y la ruta de la raíz, que conserva su barra final; solo cuando la raíz es el host a secas desaparece su barra. Con https://example.com/api/ es https://example.com/.well-known/oauth-protected-resource/api/; con https://api.example.com/, https://api.example.com/.well-known/oauth-protected-resource.
  • En ese documento, resource DEBE ser la raíz de la API, carácter a carácter y con la barra final, y authorization_servers DEBE listar al menos un emisor: el RFC 9728 lo deja opcional, pero sin él el cliente no tiene nada que descubrir. scopes_supported DEBERÍA estar. Cada servidor de autorización se describe con el RFC 8414 o con OpenID Connect Discovery; Restep no le exige nada.
  • Los metadatos no son un recurso de la API: no se les aplican 4.1, 5.1, 5.2 ni 5.3. Se DEBEN servir como application/json sin pedir credenciales, así que nunca dan 401, DEBERÍAN llevar Cache-Control: public con un max-age, y DEBERÍAN servirse con Access-Control-Allow-Origin: *, porque no necesitan credenciales.
  • Cuando la raíz de la API pide credenciales, su 401 DEBE llevar la URL absoluta de los metadatos en resource_metadata (RFC 9728, apartado 5.1), en al menos un reto: Bearer, DPoP u otro que acepte la API. El RFC 9728 (apartado 3.3) obliga al cliente a descartar los metadatos encontrados así cuyo resource no sea la URL que pidió, de modo que en cualquier otro recurso el servidor NO DEBE apuntar resource_metadata a los metadatos de la raíz. Los metadatos de la raíz son para la URL exacta de la raíz, sin query. Un cliente que recibe un 401 sin resource_metadata forma la URL de los metadatos a partir de la raíz.
  • Los errores de OAuth conservan sus códigos de Restep: el reto lleva el error de OAuth y el cuerpo lleva el code de Restep. invalid_request es 400 bad_request; invalid_token, e invalid_dpop_proof y use_dpop_nonce (RFC 9449), son 401 unauthenticated; insufficient_scope es 403 forbidden. Un 403 por falta de scope DEBE llevar error="insufficient_scope" en su reto (RFC 6750, apartado 3.1) y DEBERÍA nombrar el scope necesario en scope, salvo que eso revele permisos que el cliente no debe conocer. Un recurso cuya existencia se oculta sigue dando 404 (5.4), y ese 404 DEBE ser indistinguible, cabeceras incluidas, del de un recurso que no existe: su WWW-Authenticate, si lleva, es el mismo reto genérico, con realm y sin error ni scope (RFC 6750, apartado 3).
  • El servidor DEBE rechazar un token destinado a otro servidor de recursos (RFC 9700, apartado 2.3). Un cliente pide un token restringido a esta API enviando su resource en el parámetro resource (RFC 8707).
  • Con DPoP (RFC 9449) el reto usa el esquema DPoP. Un reintento con una prueba DPoP nueva viene del mismo principal y es la misma petición para 7.1.
  • Un servidor que admite peticiones de otros orígenes (5.8) DEBERÍA incluir WWW-Authenticate en Access-Control-Expose-Headers (y DPoP-Nonce, si usa nonces DPoP), porque si no un cliente de navegador no puede leerlas. EventSource no puede enviar Authorization, así que un cliente de navegador lee el flujo de eventos de 10 con fetch; el servidor NO DEBERÍA aceptar tokens en la query: el RFC 6750 (apartado 2.3) deja que un servidor de recursos los admita, pero el RFC 9700 (apartado 4.3.2) prohíbe a los clientes enviarlos.

11.6 inherit Extensión Experimental

URI del perfil: https://w3id.org/restep/1/inherit. Estado: experimental (1.2).

Un dato puede valer para un elemento sin estar guardado en él: el IVA de un producto es el suyo si lo tiene; si no, el de su categoría, el de la categoría padre o el de la tienda; y si nadie lo tiene, un valor por defecto. Restep lo expresa con dos campos y una declaración en el descubrimiento. Las reglas de este apartado valen solo para los campos que declara inherit y para las subcolecciones que declaran inherit_items (abajo). Una colección NO DEBE declarar inherit ni inherit_items salvo que el servidor anuncie esta extensión en extensions.

  • El campo efectivo (tax_rate) da el valor que vale, ya resuelto. Es de solo lectura.
  • El campo propio (tax_rate_own) da el valor que tiene el propio elemento, o null si no tiene y hereda. Es el que se escribe.

Son dos porque un solo campo tendría que mostrar el valor que vale y a la vez guardar el que se escribe. Entonces un cliente que devuelve lo que leyó (5.1) convertiría cada valor heredado en propio: el valor no cambia, pero el elemento deja de seguir a su fuente y nadie se entera. Con dos campos, escribir el valor que se ve y decidir si se hereda son operaciones distintas en campos distintos.

GET /products/7
→ 200
ETag: "p7-v3"
{ "id": "7", "name": "Calabacín", "category": { "id": "4" },
  "tax_rate": "10",
  "tax_rate_own": null,
  "_inherited": { "tax_rate": { "from": { "href": "/categories/2" } } } }

Declaración. En el objeto de la colección, inherit tiene por claves los campos efectivos:

"products": {
  "path": "/products",
  "relations": { "category": { "to": "categories" } },
  "inherit": {
    "tax_rate": { "own": "tax_rate_own", "from": ["category"], "default": true,
                  "description": "IVA del producto; si no tiene propio, el de su categoría." } } },
"categories": {
  "path": "/categories",
  "relations": { "parent": { "to": "categories" }, "store": { "to": "stores" } },
  "inherit": { "tax_rate": { "own": "tax_rate_own", "from": ["parent", "store"], "default": true } } }
  • own nombra el campo propio. Los dos campos DEBEN ser de primer nivel, y de uno de los tipos escalares de 4.2, u objetos cuyos miembros son de esos tipos, o listas; no pueden ser id, una relación, un mapa de idioma ni un campo traducido (3): en esos, null o el merge patch ya significan otra cosa (3, 5.1).
  • from lista, en orden, las relaciones de las que hereda este paso. Cada una DEBE ser a uno y estar declarada en relations (9), aunque el servidor no anuncie ese perfil, y su colección de destino DEBE tener un campo con el mismo nombre que el efectivo. Si ese campo también se declara en su inherit, la cadena sigue: así una categoría hereda de su categoría padre con la profundidad que haga falta, sin rutas con punto.
  • "default": true dice que al final de la cadena hay un valor por defecto y que el efectivo nunca queda vacío. El valor no se publica: cambiarlo es un cambio de datos, no del descubrimiento.
  • description explica el campo como en 4.3.
  • combine dice cómo se combinan el valor propio y el heredado: "replace", el valor por omisión, toma el propio entero cuando no es null, también si es un objeto o una lista; "fields", solo para objetos de escalares, resuelve cada miembro por separado, a un solo nivel, así que un miembro que falta en el objeto propio o que vale null en él toma el miembro heredado.
  • switch nombra un campo booleano del propio elemento y su valor inicial: "switch": {"field": "takes_chain_hours", "initial": true}. Mientras ese campo vale false, a ese elemento no le llega nada de arriba. Apagarlo no convierte en propio ningún valor ni fila heredados. Un POST que omite el campo le da el valor initial.
  • Un cliente DEBE tratar como no heredado un campo de inherit, o una declaración inherit_items, cuya declaración lleva un miembro que no conoce y cuyo nombre no empieza por x- (4.2).

Resolución. El efectivo DEBE ser el propio, si no es null; si no, el efectivo del elemento enlazado por la primera relación de from que tenga enlace, si ese valor no es null; si no, el valor por defecto; y sin valor por defecto, el campo queda sin valor (3). Con "combine": "fields", esa resolución se aplica a cada miembro del objeto. Mientras un switch está apagado, ninguna relación de from cuenta como enlace: el efectivo DEBE ser el propio; si no, el valor por defecto; y sin valor por defecto, el campo queda sin valor. Un enlace que crearía un ciclo (una categoría que acaba siendo su propia antecesora) DEBE dar 422 invalid.

Lectura.

  • Cuando la representación lleva el campo efectivo, DEBE llevarlo resuelto y con su tipo de siempre. El campo propio va con su valor o con null.
  • El elemento PUEDE explicar el origen en _inherited: un objeto cuyas claves son los campos efectivos presentes en la representación que no salen del propio. Si lo lleva, DEBE nombrarlos todos, así que un campo efectivo que no está en _inherited tiene valor propio. Con fields (6.3), _inherited solo habla de los campos que van en la respuesta. Cada valor es uno de estos:
    • {"from": {"href": "/categories/2"}}: la ruta absoluta (3) de la fuente real del valor, no la del padre inmediato. En el ejemplo, la categoría 4 no tiene valor propio y la 2 sí.
    • {"from": "default"}: sale del valor por defecto.
    • {"from": "hidden"}: es heredado, pero el cliente no puede ver la fuente. El servidor NO DEBE dar la ruta de un elemento que el cliente no puede ver, igual que una relación se queda solo con id (9), ni la de uno cuya existencia no revela (5.4).
    • Con "combine": "fields", {"fields": {"monday": {"from": {"href": "/chains/1"}}}}: cada miembro heredado nombra su propia fuente, con las formas de arriba; los miembros que salen del objeto propio no se listan, y un campo efectivo cuyos miembros salen todos de él no está en _inherited.
    Las demás formas quedan reservadas para versiones menores: un cliente DEBE tratar como "hidden" un from que no conozca.

Escritura. El campo propio es un campo normal y sigue el merge patch sin excepciones. Es el único que cambia la herencia:

Cuerpo del PATCHEfecto
{"tax_rate_own": "4"}Pasa a tener valor propio, el 4
{"tax_rate_own": "10"}, igual al heredadoPasa a tener valor propio, el 10: vale lo mismo, pero ya no sigue a la categoría

Sin tax_rate_ownNo cambia nada

El campo efectivo es de solo lectura (5.1), así que escribirlo nunca cambia nada: un PATCH con su valor actual se ignora, y otro valor da 422 invalid con una entrada read_only, cuyo detail DEBERÍA nombrar el campo propio. Se compara en vez de ignorar siempre para que un cliente que intenta cambiarlo se entere de que no ha cambiado nada, en lugar de recibir un 200 engañoso.

  • En un POST, el campo propio ausente o null hace que el elemento nazca heredando, y el efectivo sigue la misma regla, comparado con el valor que resultaría.
PATCH /products/7
{ "tax_rate": "4" }
→ 422 application/problem+json
{ "type": "https://w3id.org/restep/1/errors#invalid", "title": "Datos no válidos", "status": 422, "code": "invalid",
  "errors": [ { "pointer": "/tax_rate", "code": "read_only",
                "detail": "«tax_rate» es el valor efectivo; escribe en «tax_rate_own»." } ] }

Devolver los campos efectivos tal como se leyeron no cambia nada. Es la regla de 5.1 aplicada a la herencia: un PATCH con los campos efectivos tal como se leyeron deja el elemento igual: coinciden y se ignoran, los propios que no lleva no se tocan, y _inherited se ignora como cualquier miembro _. Un cliente que no sabe que existe el campo propio puede omitirlo sin riesgo, y el único error que puede cometer es escribir en el efectivo, que da el 422 de arriba y le dice dónde escribir. Esto funciona porque en un PATCH lo ausente no se toca: con un PUT, que Restep deja fuera (5.1), omitir el campo propio lo borraría y el elemento volvería a heredar sin que nadie lo pidiera.

PATCH /products/7                el campo efectivo tal como se leyó, sin el propio
{ "id": "7", "tax_rate": "10" }
→ 200, el elemento sin cambios y la misma ETag

Lecturas desfasadas. Si entre la lectura y la escritura cambia la fuente (la categoría 2 pasa al 5 %), el "tax_rate": "10" que devuelve el cliente ya no coincide. Con If-Match da 412, porque la ETag del producto ya cambió (7.2); sin él, 422 con read_only. En los dos casos falla sin cambiar nada, cuando un campo normal desfasado pisaría en silencio el cambio de otro.

Al cambiar una fuente. Cuando cambia el valor de una categoría, cambia el efectivo de todos los elementos que heredan de ella, aunque nadie los haya tocado. Para el cliente, esos elementos han cambiado, así que lo que ya dicen otros apartados se aplica a cada uno:

  • su ETag cambia (7.2: es la de la representación completa), también cuando solo cambia _inherited, por ejemplo si la categoría 4 fija como propio el mismo valor que heredaba;
  • con sync, cambia el state de su colección y :changes los lista (10);
  • con caché compartida, la escritura en la fuente DEBERÍA invalidar también los grupos de esos elementos y de las colecciones que pueden contenerlos (8).

Esto obliga al servidor a guardar los valores efectivos o a propagar cada cambio a todos los descendientes. Es el coste principal de declarar inherit.

Filtros y orden. Con query, filtrar y ordenar por el campo efectivo compara el valor que ve el cliente: filter[tax_rate][eq]=10 da los que valen 10, hereden o no. Los que heredan se piden con filter[tax_rate_own][null]=true, sin operadores nuevos, si se declara ese filtro (6.1).

Filas heredadas. Una subcolección PUEDE declarar inherit_items: {"from": ["store.chain"], "key": ["publisher"], "switch": {"field": "takes_chain_preferences", "initial": true}}. from nombra, en orden, relaciones a uno del elemento padre por las que se encuentra la misma subcolección en la fuente; key lista los campos que identifican una fila de un nivel a otro. La subcolección DEBE listar entonces sus filas propias y las heredadas, ya resueltas: una fila propia con la misma clave que una fila heredada la sustituye, y, cuando se borra esa fila propia, la fila heredada vuelve a listarse; sin key, las heredadas y las propias se suman. Cada fila heredada DEBE llevar _from con la ruta absoluta de su fila de origen ({"href": "/chains/1/preferences/ed-y"}) y un id propio, distinto de su clave; ahí es de solo lectura: un PATCH o un DELETE sobre ella DEBE dar 409 conflict (5.1). switch funciona como en un campo (arriba): mientras está apagado, la subcolección DEBE listar solo sus filas propias. Una fila heredada que deja de listarse, o que vuelve, es un cambio de visibilidad para sync (10).

Algunos casos quedan fuera de inherit: una condición que no es herencia (un tope, una fecha) es un campo calculado de solo lectura; una cadena que depende de quién pregunta va en la ruta o en una acción segura con params (11.1); y las filas dentro de documentos con versiones son una relación con la fuente y una acción segura GET …:effective que da cada fila con su origen.

Evolución. Añadir herencia a un dato nuevo, o a un campo que ya era de solo lectura, es compatible: se añaden el campo propio y la declaración. Convertir en efectivo un campo que hasta ahora se podía escribir no lo es, porque rechazaría escrituras que antes se aceptaban (5.5): se hace en una versión mayor o retirando el campo y añadiendo la pareja con otros nombres.

12. Conformidad

Hay dos clases de conformidad, y cada una se declara por perfil y por extensión:

  • Un servidor cumple un perfil o una extensión cuando cumple todos los requisitos dirigidos al servidor marcados con DEBE o NO DEBE de los apartados 1, 3, 4 y 5 y del apartado de ese perfil o esa extensión, y anuncia los que este requiere (1.2). Un servidor que anuncia un perfil o una extensión declara que lo cumple.
  • Un cliente cumple un perfil o una extensión cuando, en todo uso que hace de él, cumple todos los requisitos dirigidos al cliente marcados con DEBE o NO DEBE de esos mismos apartados. Todo cliente usa core; un cliente que nunca manda un QUERY no tiene que cumplir las reglas de query-method. Una biblioteca, un proxy o un agente que habla con una API Restep es un cliente, y un proxy es además un servidor para sus propios clientes.

Los requisitos marcados con DEBERÍA, NO DEBERÍA o PUEDE no deciden la conformidad. El apartado 13 y los apéndices no añaden requisitos.

12.1 Servidores

Estas son las comprobaciones que hace un comprobador de conformidad sobre un servidor; cuáles hace hoy restep-check está en su página. Algunas necesitan lo que se le da al comprobador más que lo que puede observar: credenciales de dos principales, una sesión con cookies, o una forma de provocar 429, 503 o dos escrituras que compiten. Van marcadas con «dado»; un comprobador hace cada una solo cuando se le da eso, y, si no, la da por no hecha, no por superada.

core

  • Toda colección responde con {items, next}, con next presente.
  • Sin escrituras concurrentes, seguir next hasta null devuelve cada elemento exactamente una vez.
  • Un elemento que no existe da 404 en problem+json con code: "not_found". La ruta de un elemento con su id cambiado (otras mayúsculas, un cero a la izquierda) da 404 salvo que algún elemento tenga ese id, y también la ruta con una barra al final (/books/7/); la ruta con un carácter del id codificado con porcentajes (/books/%37) responde como la del propio elemento, y /books/%FF da 404.
  • El restep del documento de descubrimiento encaja con la gramática de 1.1. Donde una respuesta lleva varios enlaces service-desc, el primero de sus destinos que es un documento de descubrimiento de Restep 1 es este. Con el mismo Accept-Language, su cuerpo es igual como valor JSON con credenciales y sin ellas (salvo que sin ellas responda 401) y, dados dos principales, entre los dos. Si solo se sirve con credenciales, lleva Cache-Control con private o no-store.
  • Todo miembro que el servidor añade al descubrimiento fuera de Restep empieza por x-, y el descubrimiento no lleva shared_cache. Toda clave de collections, singletons, filter, named_filters, relations, actions, params, language_maps, localized, local_times, collations, reasons e inherit, y todo campo que declara el descubrimiento, encaja con la gramática de los nombres, o es una ruta con puntos: nombres unidos por ., cuyo último segmento puede ser una etiqueta de idioma (3).
  • Un POST a una colección que lo admite, con un cuerpo JSON enviado como text/plain o como application/x-www-form-urlencoded (donde la colección no declara upload con ese tipo de medio), sin Content-Type o como application/json; charset=latin1, da 415 unsupported_media_type y no crea nada, igual que un cuerpo vacío sin Content-Type; con application/json; charset=UTF-8 o charset="utf-8" se acepta, y un cuerpo vacío con application/json da 400 bad_request. Todo 2xx con cuerpo JSON lleva Content-Type: application/json.
  • Todo next y todo href de un cuerpo es una ruta absoluta o una URI absoluta cuyo esquema es https o el de la raíz de la API, y toda URI absoluta de una cabecera Location o Link tiene uno de esos esquemas. En esos enlaces, [ y ] van codificados con porcentajes y los dos puntos que preceden al nombre de una acción no.
  • Donde una colección no declara id_from, un POST con id da 422 invalid. Donde declara "client", uno sin id da 422 con una entrada required en /id; con "client" o "either", un id con un carácter fuera de los de 3 da 422 con una entrada en /id, y repetir un POST que tuvo éxito o, donde no declara reusable_ids, reutilizar el id de un elemento borrado, da 409 conflict con una entrada taken en /id y no crea nada. Donde una colección declara reusable_ids, un POST con el id de un elemento borrado lo vuelve a crear, y un If-Match con la ETag del elemento antiguo da 412. Donde declara upsert, un PATCH a un id libre crea el elemento con 201, If-None-Match: * sobre uno existente da 412, y también If-Match: * sobre uno libre; donde además exige If-Match, un PATCH con If-None-Match: * a un id libre crea el elemento en vez de dar 428.
  • Cada singleton declarado responde a GET con un objeto JSON, y a POST, PUT y DELETE con 405; si declara methods, su Allow coincide con ellos. Sus objetos de relación llevan href, e include sobre él da unsupported_parameter. Uno con parent da 404 bajo un elemento padre que no existe, y su path empieza por el de su padre.
  • Una subcolección declara parent, y la plantilla de su path tiene variables con nombres distintos que encajan con ALPHA *( ALPHA / DIGIT / "_" ) y es el path de su padre seguido de /, de su última variable, de / y de uno o varios segmentos literales.
  • Todo parámetro reservado no implementado, y toda forma que 5.3 no define (filter[a][b][c], fields[]), da 400 unsupported_parameter, en todos los métodos, salvo que se dé otro error aplicable (5.4), como el 404 not_found de un elemento que no existe. La misma petición con más de un fallo, enviada dos veces, recibe las dos veces el mismo code.
  • Un método que el servidor conoce pero que el recurso no admite da 405 con Allow, y PUT lo da en toda colección, todo elemento y todo singleton; HEAD funciona donde funciona GET. Si el descubrimiento declara methods o item_methods, ese Allow coincide con ellos y nombra HEAD donde nombra GET.
  • Si el descubrimiento declara status, GET y HEAD a ese recurso dan 200 o 503 con Cache-Control: no-store, o si no 401, 403 o 429, un 429 con Cache-Control: no-store.
  • Todo invalid_parameter y todo unsupported_parameter nombran su parámetro en parameter.
  • Si el descubrimiento declara un esquema create, un POST sin una propiedad que exige da 422, y uno sin una propiedad de primer nivel con default crea un elemento con ese valor, que es válido según el esquema de la propiedad; si declara un esquema update cerrado, un PATCH con un miembro que el esquema no admite, aunque valga null, da 422, después de quitar los miembros que 5.1 ignora.
  • Todo error lleva type, title, un status igual al de la respuesta y un code de la tabla de 5.4 o http_ seguido del estado; type es about:blank solo donde 5.4 lo permite. Un 428, y dada una forma de provocarlos un 429, llevan Cache-Control: no-store.
  • Toda reason de un error encaja con la gramática de los nombres. Si el descubrimiento declara reasons, todo error con reason, también en los resultados de batch, lleva una declarada y con su code.
  • Un PATCH con {"author": {"id": "4", "extra": 1}} cambia el enlace, no guarda extra y no toca a ninguno de los dos autores, salvo que lo rechace un esquema update declarado. Una relación a un id que no existe da 422 invalid con una entrada unknown en su id, y un href a un elemento de una subcolección que no es la ruta de un elemento de la colección destino da 422 invalid con una entrada format cuyo pointer es ese href. Dado un principal que no puede ver el elemento relacionado, devolver la relación tal como se leyó, con otro campo cambiado, funciona.
  • Merge Patch sigue el RFC 7396 (una lista o un escalar sustituidos por un objeto pierden su contenido anterior), salvo que los objetos de relación se sustituyen enteros (5.1) y los mapas de idioma que quedan sin traducciones se leen como {} (3) y que, con inherit, borrar o cambiar un campo propio cambia también su campo efectivo (11.6), y una escritura que cambia el id da 422; un parche que es un valor JSON pero no un objeto da 422 invalid con una entrada cuyo pointer es "".
  • Un PATCH con los campos de solo lectura de un elemento tal como se leyeron no cambia su cuerpo ni su ETag, si la hay; otro valor en id, o en una propiedad de primer nivel que el cliente puede leer y que su esquema item marca readOnly directamente en properties, da 422 invalid con una entrada read_only en su puntero, sin cambiar nada.
  • Un error pedido con un Accept-Language que el servidor no ofrece, o mal formado, da el mismo code que sin cabecera, nunca 406 ni 400 por ella. Si el cuerpo del descubrimiento o de un error cambia entre dos Accept-Language, las dos respuestas, también la del idioma por defecto, llevan Vary: Accept-Language y, si llevan ETag, distinta.
  • Con Accept-Encoding: identity, el GET de un elemento da el mismo cuerpo con cualquier Accept-Language, salvo sus campos traducidos; un elemento sin ellos recibe además la misma ETag, con writes o cache. Dados dos principales que pueden leer los mismos campos y cuyos ajustes de idioma guardados son distintos, la misma petición sin Accept-Language recibe el mismo cuerpo para los dos.
  • Dada una forma de provocarlos: un 429 o un 503 con cuerpo problem+json no deja ningún efecto, así que repetir la petición pasado el Retry-After crea un elemento, no dos.
  • Un 401 o un 403, salvo los del estado del servicio (4.4) y los de los metadatos de OAuth (11.5), lleva Cache-Control con private o no-store. Dadas credenciales: si un GET hecho con ellas recibe otro estado u otro cuerpo que la misma petición sin ellas o, dados dos principales, con las del otro, su respuesta lleva Cache-Control con private o no-store, también cuando no se anuncia cache.
  • Dada una sesión con credenciales que el navegador añade solo (cookies, autenticación HTTP, un certificado de cliente): un POST, PATCH o DELETE con ellas y con un Origin que el servidor no permite, también una acción con cuerpo vacío, da 403 forbidden y no tiene efecto, aunque el servidor envíe Access-Control-Allow-Origin: *.
  • Una petición que pasa de un límite que el servidor no declara, como una lista in de miles de valores, da el resultado completo, invalid_parameter con el nombre del parámetro, 413 o 414; nunca una parte del resultado.
  • En un elemento, cada campo de language_maps es un objeto de cadenas con claves en minúsculas. Donde se admite PATCH: una clave en mayúsculas da 422 invalid con una entrada format en /name/ES; borrar con null una traducción existente conserva las demás, y volver a ponerla la restaura; {"name": null} deja {}.
  • Donde una colección tiene campos traducidos, el descubrimiento declara default_language; toda respuesta con ellos lleva Content-Language y Vary: Accept-Language; devolver uno en otro idioma no cambia nada, y otro valor da 422 con una entrada read_only.
  • Ninguna respuesta repite el nombre de un miembro en un objeto.
  • Una respuesta con private o no-store no lleva ningún campo dirigido a las cachés compartidas, como CDN-Cache-Control, que permita guardarla.
  • Una colección cuyos methods no incluyen GET no declara filter, named_filters, sort, count ni sync.
  • Una colección con upload responde a un archivo de un tipo de medio declarado con 201 y un elemento con _content, a uno de un tipo no declarado con 415, también a un cuerpo JSON donde no declara create y sus media_types no admiten application/json, tampoco mediante un comodín, y a un archivo que pasa de max_size con 413; donde declara create, un cuerpo JSON crea un elemento, y, donde sus media_types admiten además application/json, también mediante un comodín, declara "multipart": true; donde no lo declara, un cuerpo JSON que sus media_types admiten, también mediante un comodín, es un archivo. Un cuerpo de un tipo +json, como application/ld+json, nunca es la creación de un elemento desde JSON. Un cuerpo multipart/form-data da 415 donde upload no declara "multipart": true, aunque media_types lo admita, y, donde lo declara, una parte file sin filename se lee como el archivo.
  • Todo valor de effects, method_effects e item_method_effects es uno conocido, y una acción segura solo declara charges.

Evolución

  • Lo que el descubrimiento lista en deprecations con un kind que retira un recurso entero (collection, singleton, action, version) lleva Deprecation con el instante announced del aviso en las respuestas que enumera 5.5 y, cuando el aviso ya tiene fecha en sunset, Sunset con esa fecha, que no es anterior a announced; las respuestas a las que se refieren los demás avisos no llevan ninguna de las dos. Pasado su sunset responde como dice 5.5. Todo aviso tiene un kind conocido y un instante announced en segundos enteros que no cambia entre dos lecturas, y su sunset, si lo hay, va también en segundos enteros.
  • Comparando los documentos de descubrimiento de dos despliegues de la misma versión, no desaparece nada declarado salvo lo listado en deprecations cuyo sunset ya pasó.

query

  • Cada filtro declarado devuelve solo los elementos que lo cumplen, comparando según el tipo declarado (los decimales, de forma exacta).
  • Un campo de filtro, un operador o un campo de orden no declarados dan unsupported_parameter; un valor del tipo equivocado, un parámetro repetido o un valor duration con años o meses, invalid_parameter.
  • Un operando de un filtro integer o number sigue la gramática number de JSON: 2e1 filtra como 20, y +20, .5, 020 y 0x14 dan invalid_parameter; en un campo integer, 20.0 filtra como 20 y 20.5 da invalid_parameter. Un operando fuera del rango de valores que puede tener el campo se compara como número, de forma exacta, y uno que supera un límite de petición da invalid_parameter, sin sustituirse nunca por otro valor, como un infinito o cero.
  • Un + en la query se lee como un espacio: filter[f]=a+b y filter[f]=a%20b dan la misma página.
  • Un filtro con nombre declarado se aplica sin operadores; con un operador da unsupported_parameter, y un interruptor con valor (también false, salvo que declare default), o uno con tipo sin valor o con un valor que no encaja, invalid_parameter. Ninguno se llama como una clave de filter. Un filtro por defecto se aplica salvo que filter[nombre]=false lo desactive, y nunca a la lectura de un elemento; un filtro obligatorio que falta da invalid_parameter con su nombre.
  • No se declara ningún operador fuera de la lista de 6.1; prefix y contains, solo en campos string y en traducciones, nunca en id; ningún ne ni nin en una ruta con quantifier. Ningún filtro boolean declara operadores distintos de eq, ne y null, y el filtro de id no declara ninguno de lt, le, gt y ge.
  • sort ordena y desempata de forma estable entre páginas. Un campo de cadena que no figura en collations filtra y ordena por puntos de código; ninguna clave de collations es id, ni un campo que no sea un filtro string, un enum de cadenas listado en sort, un campo traducido o una traducción.
  • Ningún campo que es una lista y ninguna ruta que pasa por una relación a muchos se declaran en filter sin quantifier, salvo con null como único operador, ninguna atraviesa dos pasos a muchos, y ninguna ruta que acaba en el id del elemento de una subcolección se declara en filter ni en sort.
  • Repetir un parámetro de next codificado con porcentajes de otra forma, o reordenar los parámetros, da la misma página.
  • limit por encima de max_limit da invalid_parameter, y limit en una colección sin max_limit da unsupported_parameter; un cursor manipulado, o reutilizado con otros filtros, otro orden u otra colección, después de desactivar un filtro por defecto, o con otro idioma donde la colección tiene campos traducidos, da invalid_parameter; cambiar limit, fields, include o count entre páginas lo mantiene válido.
  • Ni un campo de language_maps ni una ruta que acabe en uno o lo atraviese se declaran en filter ni en sort; un filtro u orden campo.etiqueta declarado lee solo esa clave, y los elementos que no la tienen cuentan como ausentes.
  • fields devuelve solo esos campos, más id y los miembros que empiezan por _; fields=id se acepta. fields o include en un POST o un PATCH da unsupported_parameter.
  • Dado un principal que no puede leer un campo en algunos elementos: un filtro declarado sobre él no encaja con ninguno de ellos salvo con null a true, un orden por él los pone al final, y total cuenta solo los elementos que ese principal puede ver.
  • count=true añade total si count está declarado; count=true y count=false dan unsupported_parameter si no lo está.
  • Los filtros sobre la misma relación a muchos encajan con los elementos en los que un mismo elemento relacionado los cumple todos, cada elemento una vez; null a true sobre la relación niega su grupo, también donde se declara con quantifier: filter[formats][in]=epub,pdf&filter[formats][null]=true devuelve los elementos sin ninguno de esos dos formatos. Con otros filtros del grupo, los niega todos a la vez: ningún elemento relacionado los cumple todos. Dos filtros null sobre el mismo grupo, como filter[reviews][null] y filter[reviews.id][null], dan invalid_parameter, aunque tengan el mismo valor.
  • nin, prefix y contains devuelven solo los elementos que los cumplen, por puntos de código donde la colación es "codepoint"; un operando vacío de prefix o contains da invalid_parameter.
  • Un filtro duration compara las fracciones de segundo de forma exacta; un filtro localdatetime compara sin zona.

writes

  • Repetir un POST con la misma Idempotency-Key una vez terminada la primera devuelve el mismo estado y el mismo Location y no crea nada nuevo; dado un principal que ha perdido el acceso a parte del elemento, su cuerpo no revela nada de esa parte.
  • La misma clave con otro cuerpo, o en la misma ruta con otra query, da 422 idempotency_mismatch; una clave mal formada, o una con parámetros, da 400 bad_request en un POST, salvo a una acción declarada "idempotent": true que ignora las claves.
  • La ETag de un elemento completo, pedido con Accept-Encoding: identity, es fuerte, y con gzip es distinta de ella o es débil; toda respuesta cuyo cuerpo es un elemento, con fields o sin él y con cualquier Accept-Encoding, lleva esa ETag del elemento en _etag, que dos lecturas de un elemento sin cambios dan igual; una escritura ignora los miembros _.
  • En una colección que declara sync y cuyos elementos admiten PATCH o DELETE, cada elemento listado lleva en _etag la ETag que da su propio GET con Accept-Encoding: identity para la misma versión.
  • If-Match con una ETag antigua da 412, también con un cuerpo JSON que de otro modo recibiría 422 (con un cuerpo que no es JSON, 400 o 412, 5.4), y una lista que contiene la vigente funciona; dada una forma de hacer competir dos escrituras con el mismo If-Match, una de ellas recibe 412. If-None-Match con la vigente, débil o fuerte, da 412 a una escritura y no la aplica.
  • If-Match con una etiqueta de entidad inventada en un POST a una colección da 412 y no crea nada, e If-Match: * ahí funciona donde el principal puede leer la colección.
  • Un PATCH o DELETE con If-Match a un elemento que se acaba de borrar da 404, no 412.
  • Una escritura con Prefer: return=minimal respondida sin cuerpo lleva la ETag del elemento, salvo que lo haya borrado o haya respondido a una acción con 204; la repetición de un 201 así con la misma Idempotency-Key no lleva ninguna.
  • La misma petición enviada otra vez mientras la primera sigue en curso da 409 request_in_progress o, cuando la primera termina, su respuesta; nunca un segundo efecto.
  • Donde se acepta sin credenciales un POST no idempotente, la misma petición con la misma Idempotency-Key y también sin credenciales o se repite como para cualquier principal o, si el descubrimiento declara "anonymous": false en idempotency, recibe 400 bad_request con una entrada para la cabecera, sin efecto; un recurso que exige la clave no da ahí idempotency_key_required a una petición sin credenciales.
  • Un 200 a una acción que cambió el elemento lleva Content-Location con la ruta del elemento y su nueva ETag; su repetición con la misma Idempotency-Key, tras otra escritura en el elemento, no lleva ninguna de las dos, ni _etag, salvo que su cuerpo sea la representación actual del elemento.
  • Donde el elemento tiene campos traducidos, If-Match con su ETag vigente en otro idioma funciona.

cache

  • Todas las respuestas a GET, HEAD o QUERY, también las de error, llevan Cache-Control; dadas credenciales, con ellas private o no-store (como en core).
  • El GET de un elemento completo lleva ETag, e If-None-Match con ella, débil o fuerte, da 304 a un GET y a un HEAD.

relations

  • Todo campo que el descubrimiento declara en relations es, donde un elemento lo lleva, un objeto con id o una lista de ellos, también sin include. Uno que puede apuntar a varias colecciones lleva type; una cuyo destino es una subcolección lleva un href al que un GET responde con ese elemento. Ningún elemento lleva una relación cuyo path lleva a una subcolección.
  • include de una relación declarada y expandible rellena el objeto; de cualquier otra, unsupported_parameter. Con query, una ruta con punto en fields cuya relación no está en include da invalid_parameter.

sync

  • Ninguna colección declara sync salvo que profiles lo liste. Toda colección que declara sync admite GET, no tiene ningún filtro obligatorio y declara id en filter con in; :changes en una que no lo declara da 404.
  • :changes recoge, en las listas que pide 10, la creación, el cambio y el borrado de un elemento desde el state anterior, y todas las páginas de un recorrido llevan el mismo state; borrar un elemento a mitad de recorrido no hace que se pierda otro. Donde la colección declara reusable_ids, un id borrado y creado de nuevo aparece en created.
  • La respuesta de events, si se declara, lleva Cache-Control: no-store. Dado un principal que ha llegado a su límite de flujos abiertos, uno nuevo recibe 429 rate_limited.

actions

  • Una acción POST responde igual a un cuerpo vacío que a {}; una acción no declarada da 404 not_found, y una declarada con otro método, 405 con Allow; toda acción de _actions está declarada con el mismo método, y su href lleva los dos puntos tal cual; ninguna acción se llama changes, toda acción segura se declara "idempotent": true, y una acción de una colección llamada new se declara on la colección, safe y con "method": "GET". Las acciones de un singleton siguen las mismas reglas.
  • Una acción GET responde a un parámetro que sus params no declaran, cualquiera donde no declara params, con unsupported_parameter y a uno obligatorio que falta con invalid_parameter; un parámetro integer o number toma 2e1 como 20 y responde a +20 con invalid_parameter; el resultado de una acción con output no lleva _etag ni _actions; una acción no segura sobre una colección nunca responde 200; donde una colección declara new, su esquema efectivo no añade ninguna propiedad a create ni quita ninguna de sus required.
  • Con writes, una acción declarada "idempotent": true no rechaza una petición por llevar una Idempotency-Key bien formada, con credenciales o sin ellas, diga lo que diga idempotency.anonymous.

batch

  • Un id de operación repetido, o vacío o con #, { o }, una referencia a una operación posterior, un lote anidado, un path con esquema, autoridad o segmentos de punto o que va al flujo de eventos, o una cabecera que 11.2 no permite, dan 400 bad_request y no ejecutan nada; más operaciones que max_operations dan 413; un lote con los dos fallos recibe cualquiera de los dos. Un valor insertado en path que no es un id válido ni un entero, como ../admin, o una referencia en path cuyo puntero lleva { o }, recibe 422 invalid.
  • Con "atomic": true y una operación que falla, todos los demás resultados son 424 not_executed y no persiste nada.
  • Sin atomic, una operación que se refiere a una que falló recibe 424 not_executed, y una cuyo puntero no encuentra nada, 422 invalid.

filter-expr

  • Una expresión devuelve los mismos elementos que los parámetros filter[…] equivalentes; AND y OR mezclados en un mismo nivel sin paréntesis, la yuxtaposición, una ruta que atraviesa una relación a muchos fuera de corchetes, o una expresión junto con un filter[…] distinto de filter[nombre]=false, dan invalid_parameter; un campo o un operador no declarados dan unsupported_parameter.
  • Un filtro con nombre en una expresión devuelve los mismos elementos que entre corchetes; un grupo ruta[…] devuelve lo mismo que los filtros entre corchetes de 6.1 para ese grupo, y NOT ruta[…], los elementos sin ningún elemento relacionado que lo cumpla; una comparación sobre un campo de lista devuelve los elementos con algún elemento de la lista que la cumple, cada comparación por separado.

query-method

  • Una colección cuyo GET lleva Accept-Query responde a un QUERY como al GET equivalente, también en los errores; un miembro desconocido, o un parámetro reservado distinto de cursor en la URL, da unsupported_parameter; la página siguiente con otro filter u otro sort da invalid_parameter en cursor; y un QUERY con un If-None-Match que coincide da 412.

oauth

  • La raíz de la API usa https y no tiene fragmento. Los metadatos están en la URL que el RFC 9728 forma a partir de la raíz, como JSON, sin pedir credenciales, con resource igual a la raíz y al menos un servidor de autorización.
  • Los metadatos no dan 401 (y, como recomendación, llevan Cache-Control: public).
  • Si la raíz pide credenciales, su 401 lleva esa URL absoluta en resource_metadata; ningún 401 de otro recurso apunta ahí.
  • Dado un token sin el scope que necesita una petición: salvo que se oculte la existencia del recurso, la petición recibe 403 con code: "forbidden" y error="insufficient_scope" en el reto. Dado un recurso cuya existencia se oculta a un principal, su 404 lleva las mismas cabeceras que el de un recurso que no existe.

inherit

  • Ninguna colección declara inherit salvo que extensions lo liste. Si una lo hace y se admite PATCH: devolver con PATCH solo los campos efectivos de un elemento tal como se leyeron, sin sus campos propios, no cambia su cuerpo ni su ETag; {"tax_rate_own": null} deja el efectivo igual al de su fuente y, si hay _inherited, este lo nombra; y un valor distinto en el campo efectivo da 422 invalid con una entrada read_only en /tax_rate, sin cambiar nada.
  • Con "combine": "fields", _inherited nombra la fuente de cada miembro heredado; con un switch a false, no llega nada de arriba; en una subcolección con inherit_items, las filas heredadas llevan _from, un PATCH o un DELETE sobre una de ellas da 409 conflict, y, cuando se borra una fila propia con la misma clave que una fila heredada, la fila heredada vuelve a listarse.

12.2 Clientes

Estos son los requisitos que el texto dirige a los clientes, reunidos por perfil y extensión. Cada uno está en el apartado citado, que prevalece.

core

  • No trata como documento de descubrimiento de Restep 1 uno cuyo restep no encaja con la gramática o cuya versión mayor no es 1, ni supone solo core para uno de otra versión mayor; para un valor de restep con sufijo, no supone que cumpla ninguna versión publicada ni ningún otro borrador (1.1).
  • No usa un perfil o una extensión experimentales salvo que restep declare una versión cuyo texto de ese perfil o esa extensión implementa el cliente (1.2).
  • Ignora los campos y los miembros _x_ que no conoce, y no rechaza una respuesta por un valor de enumeración que no figura en su copia guardada del descubrimiento o de un esquema (3).
  • No sigue un enlace cuyo esquema no es https ni el de la raíz de la API (3).
  • Manda el cuerpo de un POST a una colección, a una acción o a un lote, y el de un QUERY, con Content-Type: application/json (3).
  • Trata una respuesta como documento de descubrimiento solo si es un 2xx cuyo cuerpo es un objeto JSON con un miembro de tipo cadena restep, y supone solo core tras un 2xx sin él o un 404, nunca tras otro error; de varios enlaces service-desc, usa el primer destino que sea un documento de descubrimiento de Restep 1 (4.2).
  • Ignora los miembros del documento de descubrimiento que no conoce, no falla por un valor que no conoce, y no usa un filtro, un filtro con nombre, una acción, un método o un aviso cuyo type, on, method o kind no conoce; ignora solo el operador que no conoce, y un filtro cuyo quantifier no conoce; y cuenta un valor de effects que no conoce como los tres efectos, también en una acción declarada segura (4.2).
  • Manda sus credenciales de la API solo a URL del origen de la API, y pide sin ellas los esquemas y documentos de otros orígenes (4.3).
  • No hace ninguna petición que no sea segura, ni manda datos a otro origen, solo porque se lo pida un texto que devolvió la API (4.3).
  • No supone una ruta para el estado del servicio, como /health (4.4).
  • No manda id en un POST a una colección cuyo id_from tiene un valor que no conoce, lo manda donde id_from es "client", y enlaza un elemento de una subcolección por su href (5.1).
  • En una subida multipart/form-data, manda un filename en la parte file, uno genérico como file cuando el original no está disponible o es privado (5.1).
  • Sigue next tal cual, cambiando solo los parámetros que 6.4 le deja cambiar, manda un + literal de la query como %2B, y no supone ningún orden de los id (5.2).
  • Para copiar una colección entera, la recorre desactivando todos los filtros por defecto y sin ningún otro filtro (5.2).
  • Trata un code que no conoce según la clase del status, y una reason que no conoce como su code (5.4).
  • Ignora un singleton cuyo path es una plantilla de URI sin parent, o cuyo parent no nombra ninguna colección ni ningún singleton del documento (5.9).

query

  • No supone puntos de código para un campo cuya colación es "server", ni reproduce en local ese orden o esa igualdad, y trata como "server" un valor de colación que no es una cadena o que no conoce (6.1).
  • No interpreta ni construye cursores (6.4).

writes

  • No cuenta con Idempotency-Key salvo que el servidor anuncie writes (7.1).
  • No repite una petición de forma automática con la misma Idempotency-Key pasado idempotency.ttl desde su primer intento, o 24 horas donde no se declara (5.7).

sync

  • No interpreta ni construye un state, y compara estados solo por igualdad (10).
  • Usa el state de la primera página de un recorrido como since de su siguiente sincronización, y vuelve a llamar a :changes mientras has_more sea true antes de dar su copia por actual.
  • Trata igual created y updated, ignora un id de destroyed que no tiene, y quita de su copia un id de created o updated que su recarga no devuelve, siguiendo desde el state de :changes.
  • Recorre la colección desactivando todos los filtros por defecto y sin ningún otro filtro, y vuelve a cargar los elementos cambiados con filter[id][in] como único filtro, desactivando también todos los filtros por defecto; cuando cambia de idioma, vuelve a recorrer la colección antes de dar su copia por actual.
  • Tolera eventos repetidos, fusionados y desordenados; al abrir el flujo y en cada reconexión llama a :changes desde el último estado que aplicó, y avanza ese estado solo después de aplicar los cambios, nunca por un evento solo.
  • Tras un 401 en el flujo, espera a tener credenciales válidas antes de volver a abrirlo.

actions

  • Tras una acción no segura con éxito sobre un elemento, no usa una copia guardada de ese elemento sin revalidarla, salvo que la respuesta llevara la representación del elemento con Content-Location (11.1).

batch

  • Cada operación tiene un id único en el lote, no vacío y sin #, { ni }, un method y un path; se asegura de que ningún objeto de un cuerpo que no escribió tenga $ref como único miembro (11.2).

query-method

  • La URL de su QUERY no lleva ningún parámetro reservado distinto de cursor, y para la página siguiente manda a la URL de next un cuerpo con el mismo filter y el mismo sort (11.4).

oauth

  • Usa los metadatos de recurso protegido solo si su resource es idéntico al identificador a partir del cual formó la URL de los metadatos o, para los metadatos encontrados por resource_metadata, a la URL que pidió (RFC 9728, apartado 3.3), y no manda tokens de acceso en la query (RFC 9700, apartado 4.3.2; 11.5).

inherit

  • Trata como "hidden" un from de _inherited que no conoce, y como no heredado un campo de inherit, o una declaración inherit_items, cuya declaración lleva un miembro que no conoce y cuyo nombre no empieza por x- (11.6, 4.2).

Los demás perfiles y extensiones (relations, cache y filter-expr) no dirigen a los clientes ningún requisito marcado con DEBE o NO DEBE.

13. Consideraciones de seguridad y privacidad

Este apartado explica los riesgos de una API Restep y remite a los requisitos que los tratan, que están en los apartados que cita. No añade requisitos. Una API tiene además los riesgos de HTTP (RFC 9110, apartado 17), de JSON (RFC 8259, apartado 12), de los detalles de problema (RFC 9457, apartado 5) y de OAuth (RFC 9700); este apartado trata lo que Restep les añade o decide sobre ellos.

13.1 Los textos de la API son datos

Un agente que elige una herramienta a partir del documento de descubrimiento mete en su prompt las descripciones, los títulos de los esquemas, las razones y los detalles de los errores, y con ellos los datos de cada elemento. Quien escribe el nombre de un elemento, o controla la API, puede escribir ahí una instrucción. Ningún agente basado en un modelo puede prometer que nunca seguirá una, así que 4.3 pide lo que se puede comprobar: un cliente no hace ninguna petición que no sea segura, ni manda datos a otro origen, solo porque se lo pida un texto así, y un agente marca en su prompt dónde empieza y dónde acaba el texto de la API. Un cliente tampoco da nunca más permisos a un agente porque una descripción los pida. Los nombres que da una API siguen una gramática sin espacios ni puntuación (3), así que son seguros como partes de nombres de herramientas; un agente que añade un prefijo (list_, get_), o cuyo registro de herramientas no distingue mayúsculas o solo admite nombres más cortos, sigue teniendo que resolver las colisiones que resultan. Un parameter de un error es el parámetro tal como llegó, que un atacante puede escribir en un enlace: un cliente que lo muestra lo escapa. Una declaración de effects (11.1) de un servidor en el que el cliente no confía no basta para dejar de preguntar a una persona: a un servidor que quiere que un agente actúe sin preguntar le basta con declarar [].

13.2 Credenciales y orígenes

  • Un cliente manda sus credenciales solo a URL del origen de la API (4.3). Un documento de descubrimiento puede enlazar esquemas, documentación, un estado del servicio y, con href, recursos de cualquier origen; un enlace next también podría. Pedido con las credenciales de la API, cualquiera de ellos entregaría esas credenciales a quien controle el otro origen.
  • Los enlaces usan https o el esquema de la raíz de la API, y un cliente no sigue uno con otro esquema (3), así que un documento de descubrimiento no puede mandarlo a file: ni a data:. Un cliente que sigue enlaces de un servidor, como un explorador o un agente alojado, sigue teniendo que mantenerlos lejos de su propia red interna. Un esquema de otro origen lo controla ese origen, así que un cliente no resuelve su $ref en otro sitio ni manda su default sin mostrárselo antes al usuario (4.3).
  • Una redirección a otro origen es una URL de otro origen. El Fetch Standard quita Authorization en una redirección así, pero una biblioteca que copia las cabeceras a mano puede no hacerlo.
  • Un token de la API está restringido a ella: el servidor rechaza uno destinado a otro servidor de recursos (11.5), así que un token filtrado de otra API no funciona aquí.

13.3 Ocultar la existencia

Un 403 dice que algo existe. Restep deja que una API lo oculte:

  • un recurso cuya existencia la API no revela da 404, no 403, y uno retirado da 410 solo si no se oculta su existencia (5.4); un método, una acción o un singleton declarados que un principal no puede usar dan 403 o ese 404 (4.2);
  • una relación a un elemento que el cliente no puede ver conserva solo su id (9), que aun así revela ese id, y su href y su type revelan el id de su padre y su colección; una API que tiene que ocultar incluso eso deja fuera el campo para ese principal, como cualquier campo que no puede leer (6.3);
  • una escritura que enlaza un elemento que el cliente no puede ver recibe el mismo 422 que una que enlaza un elemento que no existe (5.1), y los grupos de caché de una escritura solo nombran por su ruta elementos que el cliente puede ver (8);
  • un campo que el principal no puede leer y que el descubrimiento no nombra es, para fields, un campo que no existe (6.3), y los eventos de 10 se mandan solo cuando cambia el state de ese principal;
  • un valor heredado cuya fuente el cliente no puede ver dice "hidden", nunca la ruta de la fuente (11.6);
  • en :changes, las listas siguen lo que el cliente podía ver, y que el servidor responda o no 410 state_expired no depende de elementos ocultos (10);
  • un error no revela lo que el principal no podría saber de otro modo (5.4).

Los sitios donde Restep revela la existencia a propósito son la entrada taken de un id elegido por el cliente y el 404 de un PATCH en una colección que declara upsert (13.6). Los tiempos de respuesta también pueden distinguir un elemento que existe de uno que no; Restep no pide respuestas en tiempo constante. La ETag de un elemento y el state de una colección pueden cambiar cuando cambia algo que el principal no puede ver, lo que le dice que algo cambió; un servidor que tiene que ocultarlo los calcula a partir de lo que el principal puede ver.

13.4 Oráculos de consulta

Un filtro es una pregunta sobre un valor. Si el servidor la respondiera con valores que el principal no puede leer, que un elemento esté o no en los resultados la respondería, bit a bit: filter[salary][lt]=50000, y luego 40000, encuentra un salario por bisección. El orden da la misma respuesta por la posición, total por el número, y filter[campo][null] dice si existe un valor. Las defensas:

  • Un filtro o un campo de orden sobre un campo que el principal no puede leer en un elemento lo trata como ausente en él, también una ruta con punto que pasa por un elemento relacionado que no puede ver; null, el orden y total se siguen de eso (6.1, 6.5). filter-expr sigue la misma regla (11.3). El 403 que 6.1 permite en su lugar depende solo de que el campo no se pueda leer en ningún elemento, lo que no dice nada de los valores. Un filtro a través de una relación a muchos, su null y un orden por una ruta así cuentan solo los elementos relacionados que el principal puede ver (6.1), así que no revelan nada de los demás.
  • Un filtro con nombre no compara nada que declare el descubrimiento, así que el servidor decide qué lee; no selecciona por valores que el principal no puede leer salvo que su descripción diga el criterio (6.1). «Tiene al menos un ejemplar libre» puede ser público aunque las existencias de cada tienda no lo sean. Un filtro con nombre que recibe un valor nunca lo compara con valores que el principal no puede leer, diga lo que diga su descripción: «salario por encima de la cantidad dada» encontraría cada salario por bisección.
  • Un total estimado sigue siendo un recuento de lo que el principal puede ver (6.5): un servidor no puede sacarlo de las estadísticas de la tabla entera si algunos elementos están ocultos para ese principal.
  • Un cursor de paginación por clave guarda los valores de orden del último elemento que devolvió; 6.4 pide que no se puedan leer (13.9).

13.5 Claves de idempotencia

Una clave pertenece a un principal y a un destino (7.1). Las peticiones sin un principal autenticado comparten uno, así que todos los clientes anónimos comparten un mismo espacio de claves. Quien adivina o ve la clave de otro cliente puede entonces:

  • mandar antes una petición distinta con ella, para que la petición de la víctima reciba 422 idempotency_mismatch y nunca se ejecute;
  • mandar la misma petición, si conoce el cuerpo entero, y recibir la respuesta guardada, con lo que el servidor le añadió: un id, una marca de tiempo, un secreto o un enlace pensado solo para quien la mandó;
  • saber por Idempotent-Replayed que alguien ya mandó exactamente esa petición.

Los clientes generan las claves a partir de una fuente aleatoria y usan cada una para una sola petición (7.1). Un servidor cuyas respuestas a escrituras anónimas llevan algo que solo puede ver quien las mandó puede rechazar las claves sin credenciales: lo declara en idempotency y responde 400 (7.1), no 401, que mandaría al cliente a buscar unas credenciales que el recurso no necesita. Las claves viajan en una cabecera y acaban en los mismos registros que el resto de la petición. Un administrador que actúa como un usuario es otro principal (2), así que las claves de uno nunca repiten las respuestas guardadas para el otro. Una repetición nunca da más de lo que daría ahora una lectura (7.1): un principal que ha perdido el acceso a parte de un elemento no la recupera de una respuesta guardada.

13.6 Identificadores elegidos por el cliente

  • Colisiones. Dos clientes que eligen el mismo id obtienen un elemento y un 409. El servidor exige un formato con entropía suficiente, y los clientes lo generan al azar (5.1).
  • Adelantarse con un id. Si un cliente deriva sus id de datos (un correo, un número de pedido) o los elige en secuencia, otro puede crear un elemento con el id que va a usar, y la creación del propio cliente falla con 409.
  • El 409 como oráculo. taken responde lo mismo pueda o no ver el cliente el elemento, así que no revela lo que el cliente puede ver; sí revela que el id está o estuvo en uso (5.1), y también lo revela el 404 que recibe un PATCH en una colección que declara upsert. Con id aleatorios, adivinar uno no es viable. Con un formato que se puede adivinar, dice si un elemento existe, así que una colección cuyos elementos se ocultan a algunos principales (13.3) exige un formato que no se pueda adivinar (5.1). El servidor puede comprobar el formato pero no la entropía: un UUID de versión 4 bien formado puede haberse derivado igualmente de datos, así que la protección solo llega hasta donde todo cliente genere sus id al azar.
  • El tiempo en el id. Los identificadores ordenables (ULID, y UUID de versión 7: RFC 9562, apartado 5.7) llevan el instante de su creación, y los secuenciales cuántos elementos vinieron antes. Quien ve el id lo sabe. Esto vale también para los id que asigna un servidor.
  • Hashes de id borrados. Un servidor puede guardar solo un hash unidireccional de los id de los elementos borrados (5.1). Si esos id se derivaron de datos personales, el hash no los anonimiza: quien lo tiene puede volver a calcularlo para cada candidato, como cada dirección de correo de una lista. Esto no se aplica a una colección que declara reusable_ids, que no tiene que guardar los id de los elementos borrados (5.1).

13.7 Navegadores y peticiones entre sitios

  • Un navegador añade cookies a las peticiones que inician páginas de otros orígenes. Una petición con un método o un tipo de medio no simples necesita antes un preflight de CORS, que el servidor puede rechazar; un POST enviado como text/plain, application/x-www-form-urlencoded o multipart/form-data, no. Por eso un servidor exige application/json en los cuerpos de las peticiones (3): un servidor que leyera un formulario como JSON aceptaría escrituras desde cualquier página.
  • Una acción con cuerpo vacío tampoco necesita preflight (11.1). Un servidor que acepta credenciales que el navegador añade solo (cookies, autenticación HTTP, certificados de cliente) rechaza toda petición que no es segura y las lleva desde un origen que no permite, por Origin o por Sec-Fetch-Site (5.8), lo que cubre también los navegadores o los caminos que se les escapan a las reglas anteriores; las cookies SameSite son una segunda línea. Un formulario o una navegación desde una página con Referrer-Policy: no-referrer manda Origin: null incluso a su propio origen, cosa que Sec-Fetch-Site distingue. Una subida que acepta multipart/form-data (5.1) tampoco necesita preflight, así que la comprobación de Origin de 5.8 es su única protección.
  • GET y HEAD no tienen efectos (5.1), y una acción solo puede usar GET si es segura (11.1), así que un enlace o una imagen no pueden escribir.
  • CORS con credenciales nombra el origen (5.8). Un servidor que copia el Origin de cualquier petición en Access-Control-Allow-Origin junto con Access-Control-Allow-Credentials: true da a cualquier sitio el acceso del usuario.
  • El navegador no añade un token de Authorization, así que este no queda expuesto a las peticiones entre sitios; dónde lo guarda una página queda fuera de Restep.

13.8 Límites y abuso

  • Límites declarados: max_limit (6.4), include_depth (9) y max_operations (11.2). Pasar de ellos da invalid_parameter, unsupported_parameter y 413.
  • Los límites no declarados, como los valores de una lista in, el número de filtros o el tamaño de una expresión, dan invalid_parameter con el límite en detail, nunca un resultado parcial (5.3). Un cliente que sincroniza parte un filter[id][in] largo en varias peticiones, o usa query-method. Si no: 414 para una URL, 413 para un cuerpo, 429 para las peticiones y los flujos de eventos (10).
  • Algunas peticiones cuestan más de lo que parece: un include multiplica la página por su profundidad, un count exacto recorre la tabla (un servidor puede declarar "estimated"), un filtro puede no tener índice, un lote atómico retiene bloqueos, y el almacén de idempotencia y el registro de cambios crecen con ttl y retention. Un servidor declara solo lo que puede servir con carga, y limita las peticiones por principal y, para las anónimas, por dirección de red.
  • 429 y 503 con cuerpo problem+json significan que no hubo efecto, también cuando los da la propia pasarela de la API (5.7), así que un cliente que espera lo que dice Retry-After, o que espacia los intentos con algo de azar, no convierte un fallo en una avalancha de reintentos.

13.9 Cursores y estados

  • Los clientes no interpretan ni construyen cursores (6.4). El servidor liga un cursor a su colección, sus filtros y su orden, y debería ligarlo al principal; tiene que hacerlo cuando el cursor se refiere a resultados calculados para ese principal, como una instantánea (6.4). Firmarlo deja ver cuándo se ha manipulado, y uno manipulado da invalid_parameter, nunca otra página.
  • Un cursor va en la URL de next, y las URL acaban en los registros, en el historial del navegador y en Referer. 6.4 pide que no lleve datos de los elementos que se puedan leer, como los valores de la clave en claro; cifrarlo, o guardar la posición en el servidor, lo evita.
  • Un state de sync es opaco de la misma forma. Los cambios a los que lleva se calculan para el principal que pregunta (10), así que un state que recibió un principal y envía otro solo lista lo que podía ver el segundo.

13.10 Caché

  • Una caché compartida que guardara una respuesta destinada a un principal se la daría al siguiente. Todo servidor, con el perfil cache o sin él, marca private o no-store una respuesta que depende de las credenciales (5.1). El RFC 9111 (apartado 3.5) ya impide que las cachés compartidas reutilicen las respuestas a peticiones con Authorization, salvo que la respuesta lleve public, s-maxage o must-revalidate, y no cubre las de peticiones enviadas con cookies o con un certificado de cliente.
  • Vary: Authorization tampoco basta, ni siquiera donde muchos clientes comparten una credencial, como una por inquilino: depende de que toda caché respete Vary sobre ese campo, y algunas no lo hacen, y mientras la respuesta está fresca nadie comprueba el acceso del cliente. Un campo dirigido a las cachés compartidas (RFC 9213), como CDN-Cache-Control, hace que una caché que lo reconoce ignore Cache-Control, así que una respuesta que depende de las credenciales no lleva uno que le permita guardarla (5.1). Una caché que guarda una respuesta con una URL que eligió el atacante (cache deception) es otra razón para mantenerlas private o no-store. Una versión menor posterior puede permitir una excepción, declarada con shared_cache, que esta versión reserva (4.2).
  • Un 404 que oculta un elemento a un principal también depende de las credenciales, igual que su 200 para otro.
  • El documento de descubrimiento es el mismo para todos los principales (4.2), así que no lleva nada que un principal pueda saber y otro no. Una caché compartida puede guardarlo solo cuando se sirve sin credenciales: uno que solo se sirve con credenciales es private o no-store (4.2), o una caché se lo daría a quien no tiene ninguna.
  • Las respuestas cuyas cabeceras CORS dependen de Origin llevan Vary: Origin, que impide que una caché compartida dé a un origen la respuesta de otro (5.8).
  • Un elemento servido con un max-age que cambia una acción puede seguir obsoleto en una caché durante ese tiempo: la URI de la acción no es la del elemento, y una caché no tiene por qué invalidar la URI del elemento (7.2, 8).
  • El RFC 9110 (apartado 13.2.1) hace que un servidor evalúe las precondiciones solo cuando la petición tendría éxito de otro modo, así que un 304 nunca le dice a un principal sin acceso que su ETag coincide.

13.11 Tokens

  • El servidor rechaza los tokens destinados a otro servidor de recursos, y un cliente pide uno restringido a la API con un indicador de recurso (11.5, RFC 8707).
  • Los tokens en la query acaban en los registros, en el historial y en Referer: el RFC 9700 (apartado 4.3.2) prohíbe a los clientes mandarlos, y el servidor no debería aceptarlos; un navegador lee el flujo de eventos con fetch, que puede mandar Authorization (11.5). DPoP liga un token a una clave que tiene el cliente (RFC 9449).
  • Solo el 401 de la raíz apunta a los metadatos de la raíz (11.5), porque el RFC 9728 hace que un cliente descarte los metadatos cuyo resource no es la URL que pidió.
  • Los metadatos se sirven sin credenciales y listan los servidores de autorización y los scopes; un 403 por un scope que falta deja fuera scope cuando nombrarlo revelaría permisos (11.5).

13.12 Privacidad

  • Descubrimiento. Quien puede leer el documento de descubrimiento conoce todas las colecciones, los singletons, los campos por los que se puede filtrar, las acciones y las razones que declara la API. Es el mismo para todos (4.2): una API que no puede publicar tanto exige credenciales para leerlo y lo sirve private (4.2), da a cada inquilino su propia raíz de API, o deja fuera de su API lo que tiene que seguir sin conocerse.
  • Errores. Una reason dice por qué falló la petición, nada sobre otros; su declaración en reasons es pública. detail y errors no revelan lo que el principal no podría saber de otro modo, ni detalles internos (5.4). El estado del servicio servido sin credenciales solo dice si la API puede atender (4.4).
  • Repeticiones. Idempotent-Replayed dice que la misma petición ya se hizo antes con el mismo principal; para el principal anónimo, quizá la hizo otro (13.5).
  • Identificadores. Los id ordenables y secuenciales revelan cuándo se creó un elemento y cuántos hay (13.6).
  • Consultas en las URL. Un filtro como filter[email]=… pone datos personales en la URL, y por tanto en los registros. query-method los pone en el cuerpo.
  • Sincronización. destroyed lista los id de los elementos que el cliente podía ver y ya no puede; no revela nada de los elementos que el cliente nunca vio (10).
  • Idioma. El idioma que pide un lector es un dato personal que lleva cada petición; un cliente que manda una sola etiqueta en lugar de toda su lista de preferencias revela menos (RFC 9110, apartado 12.5.4). El servidor nunca saca el idioma de los datos de un ajuste guardado para el principal (3).

Apéndice A. Construir formularios a partir de esquemas

Este apéndice no es normativo. Describe cómo un cliente genérico puede mostrar a las personas un formulario a partir de los esquemas de 4.3, para que un servidor sepa cómo se verán sus esquemas en pantalla.

  • El formulario de un elemento nuevo sale de create; el de edición sale de update, relleno con el elemento tal como se leyó.
  • title y description son la etiqueta y la ayuda de un campo, en el idioma de 5.6.
  • default es el valor con el que empieza el formulario. En create es también el valor que el servidor da a un campo ausente (4.3), así que dejarlo sin cambiar y dejar fuera el campo significan lo mismo. Un esquema de otro origen es de ese origen, así que su default se muestra antes de enviarse (4.3).
  • examples se muestran como ejemplos y nunca se envían.
  • Un oneOf de valores const, cada uno con su title, da las opciones y sus etiquetas.
  • maxLength y las demás aserciones, y la anotación format, dicen cómo introducir un valor y dejan que el cliente lo compruebe antes de enviarlo; el servidor lo vuelve a comprobar.
  • Un campo readOnly se muestra y no se edita; uno writeOnly, como una contraseña, nunca se rellena con un valor leído.
  • Un campo traducido (3) se muestra y no se edita; lo que edita el formulario es su mapa de idioma.
  • Un localdatetime (3) es una fecha y una hora sin zona.
  • Una relación a una colección que declara upload (5.1) es un control de archivo, limitado a los media_types de la relación.
  • Los campos aparecen en el orden de properties (4.3), donde el analizador JSON del cliente conserva el orden de los miembros; si no, el orden es cosa del cliente.
  • La disposición, los grupos y los controles que se usan son cosa del cliente.

Un formulario cuyos valores iniciales dependen del usuario o del momento (la fecha de hoy, un valor heredado) no puede salir del descubrimiento, que es el mismo para todos; sale de la acción new de la colección (11.1).

Apéndice B. Trabajo futuro

Este apéndice no es normativo. Estos casos quedan fuera de Restep 1. Ninguno necesita un cambio incompatible: cada uno puede llegar como añadido en una versión menor (1.1) o como una extensión nueva, cuando las implementaciones muestren cómo debería funcionar. Hasta entonces, una API que necesite uno lo resuelve a su manera, con nombres fuera de los que reserva Restep (5.3).

  • Operaciones largas: 202 Accepted y un recurso de operación (como en la AIP-151), para que cada API no se invente el suyo. Aplazado porque la forma de la operación, su cancelación y cómo se combina con Idempotency-Key y con las acciones necesitan antes una implementación.
  • Sincronizar vistas filtradas (como el queryChanges de JMAP). Aplazado porque necesita saber qué elementos tenía una vista en el pasado, y el propio sync sigue siendo experimental.
  • Añadidos pequeños: vistas con nombre ($view), un enlace prev para paginar hacia atrás, resultados de un lote a medida que terminan y reutilizar un QUERY con el Location que ya define el RFC 10008. Aplazado porque ningún caso los ha necesitado todavía.
  • Mensajes firmados (RFC 9421, con Content-Digest del RFC 9530 y las claves publicadas como JWKS, RFC 7517) para la integridad entre empresas a través de intermediarios. Aplazado porque Restep 1 no tiene ningún caso que los necesite: TLS cubre al cliente y al servidor, y los eventos de 10 no llevan datos. Además, una firma que caduca daría 401 a un reintento antes de llegar al almacén de idempotencia de 7.1.
  • Una extensión openapi: qué dice una descripción OpenAPI de una API Restep (una descripción por operación, los cuerpos de las peticiones, los errores como problem+json) y cómo comprueba un comprobador que concuerda con el documento de descubrimiento, que seguiría prevaleciendo. Aplazado hasta que las herramientas que traducen entre los dos muestren qué merece la pena exigir.
  • Una búsqueda de texto propia de Restep, con orden por relevancia, que tendría que decir cómo se combina ese orden con sort y con los cursores. Aplazado porque esa combinación no está diseñada; hoy una búsqueda es un filtro con nombre de tipo string (6.1).
  • El operador suffix, junto a prefix y contains (6.1). Aplazado porque solo lo ha pedido una implementación.
  • Elegir el idioma con un parámetro, para los enlaces que tienen que llevarlo, y una proyección por idiomas (languages, ya reservado), para que los clientes no tengan que recibir los mapas de idioma enteros. Aplazado porque Accept-Language cubre los casos vistos hasta ahora (5.6) y en ellos los mapas son pequeños.
  • Ordenar con reglas de idioma (colación del CLDR): con puntos de código, sort=name.es-es pone «Ñora» detrás de «Zanahoria», y "server" (6.1) no deja que el cliente conozca el orden. Los valores de collations distintos de "codepoint" y "server" se reservan para colaciones nombradas con etiquetas Unicode (-u-co-, -u-ks-, RFC 6067). Aplazado porque las bases de datos implementan esas etiquetas de forma desigual.
  • La dirección del texto (dir, de Strings on the Web del W3C), que la etiqueta de idioma no basta para deducir. Iría en el objeto de cada campo de language_maps, sin cambiar nunca el tipo de los valores. Aplazado porque ninguna implementación lo ha necesitado todavía.
  • Declarar de antemano qué operaciones exigen Idempotency-Key (7.1) o If-Match (7.2), en vez de enterarse por un 400 o un 428. Aplazado porque el error ya le dice al cliente qué hacer, y exigir cualquiera de los dos es de todos modos un cambio incompatible (5.5).
  • Más herencia (11.6): un mapa de idioma traducción a traducción; una lista de escalares como la unión de sus niveles; bloquear un valor desde arriba; quitar una fila heredada; filas heredadas con su clave dentro de un campo de un elemento; y si un valor propio que falta al crear el elemento debería heredar sin decirlo. Aplazado hasta que el propio inherit tenga evidencias: bloquear un valor y quitar una fila heredada han tenido un caso cada uno.
  • Borrado lógico: qué responde un GET a un elemento borrado, restaurar con el mismo id y purgar. La papelera como lista ya es un filtro por defecto que el cliente desactiva (6.1), y en una colección que declara reusable_ids restaurar es volver a crear el elemento (5.1). Según 10, un elemento que vuelve a verse aparece como created o updated, según el intervalo. Aplazado porque, en las demás colecciones, restaurar un id choca con la regla de que los id no se reutilizan (5.1).
  • Unidades de medida: una unidad fija por campo, declarada en el descubrimiento con códigos UCUM sin cambiar el tipo del valor, a diferencia de una unidad que varía por elemento, que va con su valor como un importe va con su moneda (3). Aplazado porque ninguna implementación lo ha necesitado todavía.
  • Orden manual: mover un elemento entre otros sin reescribirlos todos (claves fraccionarias ordenadas por punto de código, o una acción :move con before y after). Aplazado porque los dos diseños funcionan y ninguno se ha probado en una API Restep.
  • Valores a una fecha ($as_of): separar cuándo rige un valor de cuándo se registró, y qué hace con los validadores, state y los cursores. Aplazado porque toca todos los perfiles.
  • Relaciones, include y mapas de idioma en los singletons, y singletons que pueden no existir, que crea y borra el cliente (5.9). Aplazado porque un singleton no declara relations de las que sacar un destino, y ninguna API ha necesitado todavía uno que cree el cliente; un cliente ignora lo que no conoce de la declaración de un singleton (4.2), así que pueden llegar en una versión menor.
  • Más tipos de retirada: bajar include_depth o batch.max_operations, y quitar sync de una colección o events de la API (5.5). Hoy cada uno necesita una versión mayor nueva. Aplazado porque ninguna API los ha necesitado; los clientes ignoran los avisos de un kind que no conocen (4.2), así que los tipos nuevos pueden llegar en una versión menor.
  • Una versión por cada parte experimental: servir una versión menor nueva de Restep conservando el texto de una anterior para sync o batch, para que un servidor no tenga que mover a la vez todas las partes experimentales y un cliente no tenga que actualizarse por una parte cuyo texto no cambió. Hoy la versión de restep decide el texto de todas las partes (1.2). Aplazado porque necesita un miembro nuevo del descubrimiento y todavía no hay una segunda versión con la que probarlo; es el primer candidato después de la 1.0, por sync.
  • Cuánto tiempo se guardan los id de los elementos borrados (5.1): hoy, mientras exista la colección, salvo en una colección que declara reusable_ids, que no tiene que guardarlos, así que un límite solo afectaría a las demás. Un límite, como sync.retention, acotaría el coste, pero, olvidado un id, el servidor podría aceptarlo de nuevo para un elemento nuevo mientras la copia de un cliente, guardada durante más tiempo que ese límite, aún tiene el elemento antiguo con ese id. Aplazado porque cambia lo que sync puede prometer.
  • QUERY en las acciones seguras (11.4), para una entrada que se repite y no cabe en una URL. Aplazado porque una acción segura POST ya la recibe (11.1).
  • Campos calculados a petición, fuera de la representación completa, de su ETag y del state, para valores que cambian todo el tiempo (7.2). Un campo que ya estaba en la representación no puede pasar a ser uno sin retirarlo (5.5). Aplazado porque no está diseñado cómo los pide un cliente.
  • Una extensión para documentos con versiones: borradores, publicación y alias, cuando más de una API use el patrón del apéndice D.
  • Subidas reanudables para upload (5.1), cuando el borrador del IETF sobre ellas sea un RFC.
  • Sustituir un elemento entero, borrando lo que una petición deja fuera, cosa que PATCH no hace fuera de las listas (5.1). Aplazado porque PUT borraría los campos añadidos después de escribirse un cliente.
  • Variantes declaradas en el descubrimiento (2), con operaciones por variante. Aplazado porque un esquema con oneOf ya las distingue (4.3).
  • Versiones con fecha ($api_version, 5.5). La extensión experimental que permite 5.5 tendría que resolver: una lista cerrada de fechas y el error para una desconocida; un valor por defecto fijo; un tipo nuevo de retirada; la fecha en lo que cuenta como la misma petición idempotente; cursores, state y eventos ligados a su fecha; un lote con la fecha de su petición; y que, tras una escritura, las variantes con fecha de una URL no se invalidan por URI (RFC 9111, apartado 4.4), lo que mitiga Cache-Groups (8).
  • Una excepción para las cachés compartidas con credenciales, que reserva shared_cache (4.2, 13.10). Aplazado hasta que un caso muestre qué respuestas que dependen de las credenciales puede guardar con seguridad una caché compartida.

Apéndice C. Cambios

Este apéndice no es normativo. Lista lo que resolvió cada borrador, del más reciente al más antiguo. Los apartados citados son los de este borrador.

Borrador 7

Incompatible con el borrador 6. Lo que tiene que cambiar una API que seguía el borrador 6:

  • El orden total de los errores deja paso a unas precedencias (5.4): si se aplican varios errores, la misma petición contra el mismo estado guardado recibe el mismo; no se da nada que dependa del destino mientras se aplique un 401, o un 403 que no dependa del cuerpo ni del elemento guardado; 428 y 412 no se dan mientras se aplique un error que se puede detectar antes de procesar el contenido, entre ellos 406, un 403 que no dependa del contenido y un 409 que dependa solo del estado guardado del destino, y van antes que un 422 o un 409 que salgan de procesar el contenido; y una repetición o un 409 request_in_progress va después de las comprobaciones que impiden al principal saber lo que no puede, incluido su permiso actual sobre el destino, y en lugar de 428, 412 y de los errores que dependen del estado guardado. Una API que mantuvo el orden del borrador 6 las cumple salvo en dos casos: la repetición, o el 409 request_in_progress, cuyo destino ya no existe, lo borrara la primera petición u otra, recibe ahora el estado guardado o ese 409, no 404 ni 410 (7.1); y una acción que el estado actual del elemento no admite, enviada con una precondición que falla, recibe ahora 409, no 412 (11.1).
  • El principal incluye a quien actúa por cuenta de él: un principal que actúa y el que representa nunca comparten claves de idempotencia, cursores ni respuestas guardadas (2).
  • Los cuerpos son mensajes I-JSON, sin nombres de miembro repetidos, sustitutos sin pareja ni no caracteres; los instantes y las duraciones se escriben con letras mayúsculas, y se aceptan las minúsculas; un instante con segundo intercalar (:60) en el cuerpo de una petición da 422 invalid con una entrada format, salvo en un campo que solo pone el servidor, que un POST ignora; la entrada de un sustituto sin pareja apunta a la cadena que lo contiene, o a "" si esa cadena es un nombre de miembro o no se localiza, y un cuerpo que además tiene un error de sintaxis JSON recibe 400 bad_request (3, 5.4).
  • Ninguna respuesta de una colección, un elemento o una acción depende de un ajuste de idioma guardado para el principal ni de una cookie; solo los campos traducidos dependen del idioma, y solo de Accept-Language (3).
  • Un segmento de ruta que no decodifica a UTF-8 da 404, como un elemento que no existe (3).
  • Una API cuyas colecciones, campos o capacidades declaradas cambian según el inquilino da a cada inquilino su propia raíz de API (4.2).
  • El path de una subcolección sigue tras su última variable con uno o varios segmentos literales (4.2).
  • Un default de create es válido según su propiedad, y un cuerpo que es un valor JSON pero no un objeto da 422 invalid con una entrada en "", tanto frente a un esquema como en un PATCH (4.3, 5.1).
  • La cabecera Allow de un 405 nombra HEAD donde nombra GET (4.3).
  • Una respuesta que depende de las credenciales no lleva ningún campo dirigido a las cachés compartidas, como CDN-Cache-Control, que permitiera guardarla a una de ellas (5.1).
  • En un POST, un campo que solo fija el servidor se ignora sea cual sea su valor, en lugar de responderse con 422; un campo así es uno que ningún cliente puede fijar directamente, nunca id, un campo efectivo ni uno traducido, y ni readOnly en el esquema item ni su ausencia de create lo convierten en uno (5.1).
  • La tabla de códigos de error es cerrada: un estado que no recoge recibe http_ y sus tres dígitos, no un nombre derivado del registro de la IANA; type es about:blank solo en un error que no tiene nada más que su estado; 428, 429, 431 y 511 llevan Cache-Control: no-store y ningún campo dirigido a las cachés compartidas, como CDN-Cache-Control, que permitiera guardarlas a una de ellas (5.4).
  • Deprecation va solo en las respuestas de un recurso retirado entero, con el instante announced del aviso; un aviso que retira parte de un recurso no pone nada en sus respuestas (5.5).
  • El descubrimiento mantiene un aviso de retirada en deprecations después de su sunset, hasta la siguiente versión mayor (5.5).
  • Los instantes announced y sunset de todo aviso de retirada van en segundos enteros, sin fracción (5.5).
  • No se declara ningún operador fuera de la lista de 6.1, y collations solo admite campos de cadena, claves de orden que guardan cadenas, campos traducidos y traducciones (6.1). Un cursor está ligado a los filtros por defecto que la petición no desactiva y, con campos traducidos, al idioma (6.4).
  • Un operando numérico de filtro fuera del rango del campo se compara como número, de forma exacta, sin error, y uno que supera un límite de petición del servidor da invalid_parameter, nunca otro valor como un infinito o cero (5.3); una hora con segundo intercalar da invalid_parameter, y los operandos iguales según el tipo del campo son el mismo filtro, también para el cursor, así que 20.0 es un operando válido de un campo integer; un operando integer o number sigue la gramática number de JSON, así que 2e1 es 20, y +20, .5, 020 y 0x14 dan invalid_parameter (6.1).
  • Una repetición da el mismo estado y el mismo Location, pero nunca un cuerpo que revele más de lo que revelaría ahora una lectura, y, con un cuerpo que no es la representación actual del elemento, ni Content-Location, ni ETag ni _etag; la repetición de un 201 sin cuerpo no lleva ETag (7.1, 7.3).
  • Para Idempotency-Key, el orden de los valores repetidos de un mismo parámetro de la query cuenta para «la misma petición» (7.1).
  • Con una codificación de contenido, la ETag de un elemento es distinta de la ETag de elemento o es débil; con campos traducidos, la ETag de elemento cambia con el idioma e If-Match funciona con la de cualquier idioma; _etag lleva la etiqueta de entidad con sus comillas (7.2).
  • En un POST a una colección, * depende de si el principal puede leerla; un 200 a una acción que cambió el elemento lleva Content-Location y la nueva ETag, y un 204 a una acción no lleva ETag (7.2).
  • Toda respuesta a un QUERY lleva Cache-Control, y un QUERY cuyo If-None-Match coincide recibe 412, no 304 (8).
  • Una relación cuyo path lleva a una subcolección aparece solo en el descubrimiento: la representación del padre no la lleva (9).
  • Una colección que declara sync admite GET y no tiene ningún filtro obligatorio; un estado intermedio es un punto de la historia de la colección, y cada respuesta da los cambios de su propia ventana en el orden en que ocurrieron (10).
  • Con sync, un since que el servidor no emitió da invalid_parameter, y el 429 de un flujo por encima del límite lleva Retry-After (10).
  • Los dos puntos que preceden al nombre de una acción van sin codificar en todos los enlaces que construye el servidor, y una acción no segura sobre una colección responde 201 o 204, nunca 200 (11.1).
  • Una acción declarada "idempotent": true que ignora las claves ignora también una mal formada, en lugar de responder 400 (11.1).
  • Una acción GET sin params responde a cualquier parámetro de query con 400 unsupported_parameter (5.3, 11.1).
  • Una acción declarada "safe": true declara "idempotent": true, y una acción de una colección llamada new es la acción GET segura que da los valores iniciales de un elemento nuevo (11.1).
  • En un lote, un valor insertado en path que no es válido ahí, una referencia en path cuyo puntero lleva { o } y un puntero que no encuentra nada dan 422 invalid, no 424, que queda para una operación que depende de otra que falló (11.2).
  • En un lote, un id de operación vacío o con #, { o } da 400 bad_request (11.2).
  • Con oauth, la raíz de la API usa https sin fragmento, y el 404 que oculta un recurso lleva las mismas cabeceras que el de uno que no existe, incluido el reto genérico con realm (11.5).
  • Con inherit, cuando el elemento al que lleva el primer enlace no tiene valor efectivo, el efectivo es el valor por defecto (11.6).
  • Un miembro que empieza por x- no cambia el significado de los miembros que este texto define a su lado (4.2).

Lo que tiene que cambiar un cliente que seguía el borrador 6:

  • No depende de cuál de varios errores aplicables recibe más allá de esas precedencias: un elemento que no existe con un parámetro no admitido puede dar 404 o 400; un método que no está en la lista con uno, 405 o 400; y un cuerpo que no es JSON con un If-Match obsoleto, 400 o 412 (5.4). Cuál da una API puede cambiar sin versión nueva (5.5).
  • Lee el sufijo de restep distinguiendo mayúsculas: 1.0-DRAFT.7 no encaja con la gramática (1.1).
  • Acepta Content-Type: application/json; charset=utf-8 en una respuesta 2xx (3).
  • De varios enlaces service-desc, usa el primer destino que sea un documento de descubrimiento de Restep 1; ignora solo el operador que no conoce, ignora un filtro cuyo quantifier no conoce, cuenta un valor de effects que no conoce como los tres efectos, también en una acción declarada segura, y trata como no heredado un campo heredado cuya declaración lleva un miembro que no conoce y cuyo nombre no empieza por x- (4.2).
  • Supone solo core cuando el GET del descubrimiento tiene éxito sin restep o da 404, no tras otro error, como un 401 o un 503 (4.2).
  • Ya no ignora todo singleton con parent, solo uno cuyo path es una plantilla sin parent o cuyo parent no nombra nada del documento (5.9).
  • No repite de forma automática una petición con la misma Idempotency-Key pasado idempotency.ttl (5.7).
  • Tras una acción no segura con éxito sobre un elemento, no usa su copia guardada del elemento sin revalidarla, salvo que la respuesta llevara el elemento con Content-Location (11.1).
  • Revalida el resultado de un QUERY con un GET condicional al recurso equivalente, porque un If-None-Match que coincide en un QUERY da 412, no 304 (8, 11.4).
  • Con sync, quita de su copia un id de created o updated que su recarga no devuelve, y sigue desde el state de :changes (10).
  • En un lote, da a cada operación un id no vacío sin #, { ni } (11.2).
  • Con oauth, comprueba resource en los metadatos de recurso protegido y no manda ningún token de acceso en la query (11.5).

Borrador 6

Incompatible con el borrador 5. Lo que tiene que cambiar una API que seguía el borrador 5:

  • Un POST a una colección, a una acción o a un lote, y un QUERY, con un cuerpo de otro tipo de medio, sin Content-Type, vacío sin Content-Type o con un charset distinto de UTF-8, da 415, igual que un PATCH con otro tipo de medio; todo 2xx con cuerpo JSON dice application/json (3, 5.1).
  • Los nombres que declara el descubrimiento y que llevan los parámetros, y toda reason, siguen una gramática, y no se puede declarar un campo cuyo nombre no la sigue (3, 5.4). Dos id son el mismo solo si coinciden punto de código a punto de código, y un elemento responde solo en su propia ruta, comparada segmento a segmento después de decodificar los porcentajes (3). Los enlaces, en los cuerpos y en Location y Link, usan https o el esquema de la raíz de la API, y los miembros _x_ no cambian entre dos lecturas de la misma versión de un elemento (3).
  • El documento de descubrimiento es el mismo para todos los principales, igual como valor JSON, y private o no-store cuando solo se sirve con credenciales; un método, una acción o un singleton declarados que un principal no puede usar dan 403 o 404, nunca 405 ni unsupported_parameter (4.2).
  • La plantilla de una subcolección usa variables con nombres distintos y declara parent, y una relación a uno de sus elementos lleva href (3, 4.2, 9).
  • Un POST con id a una colección sin id_from lleva en su 422 una entrada read_only en /id; otro campo de solo lectura en un POST se ignora solo con el valor que recibiría el elemento, y se quita antes de validar contra un esquema create (4.3); un campo que este principal no puede cambiar da 403, y uno que el estado del elemento no deja cambiar, 409, los dos ordenados con 422 (5.4); una relación a un elemento que no existe o que el principal no puede ver da 422 con unknown, salvo que se devuelva con su valor actual; un servidor que reutiliza el id de un elemento padre borrado no deja que su subcolección tome los id que tenía la antigua (5.1).
  • Una respuesta que depende de las credenciales lleva private o no-store en todo servidor, no solo con caché, también los 401 y 403 y los recursos fuera de Restep (5.1).
  • Los parámetros se leen después de decodificar los porcentajes, sea cual sea el orden de los de nombre distinto, y un + en la query es un espacio dondequiera que la query se lea después de decodificar los porcentajes, también en parameter y en la comparación de 7.1 (5.2).
  • count con cualquier valor donde no está declarado, fields o include en una escritura, y una forma con corchetes que Restep no define dan unsupported_parameter (5.3, 6.3, 6.5). Una petición que pasa de un límite no declarado da invalid_parameter, nunca una parte de un resultado (5.3).
  • Los errores no revelan lo que el principal no podría saber de otro modo (5.4).
  • Todo aviso de retirada lleva un instante announced que no cambia, y los seis meses cuentan desde él; un aviso count dice con value si el recuento pasa a ser estimado o desaparece; las respuestas que llevan Deprecation se enumeran por kind; quitar el sync de una colección o los events de la API es un cambio incompatible (5.5).
  • 429 y 503 van solo a peticiones que no tuvieron efecto, nunca a una cuyo efecto el servidor no puede saber, también desde las propias pasarelas de la API (5.7).
  • Un servidor que acepta cookies, autenticación HTTP o certificados de cliente rechaza con 403 una petición que no es segura, las lleva y viene de un origen que no permite (5.8).
  • La ruta de un singleton no es una que pudiera tener un elemento, y sus objetos de relación llevan href (5.9).
  • Los filtros y el orden tratan como ausente un campo que el principal no puede leer, y un filtro con nombre no selecciona por esos valores salvo que su descripción lo diga, ni, si recibe un valor, lo compara con ellos; ni un campo que es una lista, ni una ruta que pasa por una relación a muchos, ni una ruta al id del elemento de una subcolección se declaran en filter ni en sort; un filtro boolean declara solo eq, ne y null, y el filtro de id, ningún operador de orden; el valor de un filtro datetime nunca se redondea (6.1).
  • Una colección que acepta limit declara max_limit, y un cursor que se refiere a resultados calculados para un principal está ligado a él (6.4).
  • La query cuenta para «la misma petición» de Idempotency-Key, que es una cadena de Structured Fields sin parámetros y se ignora en los métodos distintos de POST; un servidor que rechaza las claves sin credenciales declara "anonymous": false y responde 400, no 401, a un POST sin credenciales que lleva una, salvo una acción idempotente, que la ignora, y entonces no exige la clave a ninguna petición sin credenciales (7.1). If-Match e If-None-Match se evalúan en un POST a una colección (7.2).
  • Con writes, toda respuesta cuyo cuerpo es un elemento lleva _etag, sea cual sea su codificación de contenido; una escritura a un elemento que se acaba de borrar da 404, no 410; una respuesta mínima lleva la ETag del elemento (7.2, 7.3).
  • writes ya no trae Cache-Control ni 304: un servidor que los daba anuncia también cache; los nombres de los grupos de caché no revelan elementos que el cliente no puede ver (8).
  • Solo una colección que declara sync, con el perfil sync, responde a :changes; events es relativo a la raíz de la API, nombra una subcolección por su ruta relativa a la raíz de la API, y no manda nada cuando no cambia el state del principal (10).
  • Acciones: un cuerpo vacío es {}; una acción no declarada da 404; _actions lista solo acciones declaradas, con su método; una acción idempotente no rechaza una Idempotency-Key bien formada, y la ignora sin credenciales donde anonymous es false (11.1).
  • Una operación de un lote tiene un path relativo a la raíz de la API, sin segmentos de punto, a un recurso de Restep distinto del flujo de eventos, en el que una referencia solo inserta un id válido o un entero, que se vuelve a comprobar después de insertarlo; lleva solo las cabeceras que lista 11.2, actúa con las credenciales del lote y no toma Prefer, If-Match ni If-None-Match de la petición del lote (11.2).
  • Los valores heredados son la extensión inherit, que se lista en extensions (11.6).
  • Las URI de la versión, de los perfiles y de los tipos de error, y el $id de los JSON Schemas, pasan a https://w3id.org/restep/1/, que redirige al texto: el enlace de perfil es Link: <https://w3id.org/restep/1/>; rel="profile", y el type de un error es https://w3id.org/restep/1/errors# seguido de su código (4.1, 5.4). Las URI https://restep.wubytes.com/1/ ya no son identificadores, aunque el texto se sigue leyendo allí (1.3).

Apéndice D. Documentos con borradores y versiones

Este apéndice no es normativo. Restep ya expresa un documento que se edita como borrador y se publica en versiones; así es como.

  • El borrador. O el propio elemento es el borrador (/books/7, que se edita con PATCH), o el borrador es un elemento de una subcolección con un id fijo, que declara upsert y reusable_ids (5.1): PATCH /books/7/drafts/current lo crea o lo edita y DELETE lo descarta.
  • Las versiones son una subcolección inmutable con id que asigna el servidor (/books/7/versions/3) y que nunca se reutilizan.
  • Publicar es una acción sobre el borrador, como POST /books/7:publish, con If-Match sobre la ETag del borrador, que se responde con 201 y el Location de la versión nueva (11.1, 7.2).
  • La versión actual es una relación del elemento ("current": {"id": "3", "href": "/books/7/versions/3"}) o un elemento aparte, nunca un id, porque un id que nombra cada vez otra versión rompería las cachés, sync y las relaciones (3). Los alias con nombre son elementos aparte.
  • Volver atrás es publicar de nuevo a partir de una versión anterior; comparar dos versiones es una acción segura con params, GET /books/7/versions/3:compare?with=2 (11.1).
  • Los lectores ven una colección de elementos publicados; publicar varios a la vez es un batch atómico o una colección de publicaciones. Las relaciones latest-version, version-history y working-copy del RFC 5829 (apartado 3) pueden enlazarlos.
