Restep 1 · specification

1. Status and scope

Draft 7, 25 November 2026 (draft 6: 20 November 2026; draft 5: 20 November 2026; draft 4, draft 3 and draft 2: 19 November 2026; draft 1: 12 November 2026). It may change without notice until version 1.0 is published. A server that implements it declares "restep": "1.0-draft.7" (1.1).

URI of this version: https://w3id.org/restep/1/, a permanent identifier that redirects to this text at restep.wubytes.com.

Published in English and in Spanish. Where the two differ, the English text prevails; profile and error URIs point to it.

Also as a single Markdown file, for agents and for diffing: spec.md.

Restep is a profile for HTTP APIs that exchange JSON and are organised around resources: level 2 of the Richardson Maturity Model. It settles what that level leaves open (the shape of collections and errors, querying, safe writes, relationships and sync) and splits it into six profiles that are adopted one at a time, plus optional extensions.

Out of scope: authentication and authorization (OAuth 2.0 is recommended, with OpenID Connect where the API needs the user’s identity; the oauth extension says where a client gets a token), each API’s domain design, and anything below HTTP. Restep requires no schema and no code generator: a core server can be written by hand.

1.1 Restep versions

  • Restep has a major and a minor version. The major one is in all its URIs (/1/); the discovery document declares the full one: "restep": "1.0".
  • A minor version only adds: profiles; extensions; discovery members; values and forms that this text reserves for minor versions; meanings for requests and declarations that this text forbids or reserves; and error codes for new cases (never a new code for a case that already had one; a status outside the table of 5.4 already has its code: http_ and its number). It adds no requirement on what 1.0 defines, so whatever conforms to 1.0 still conforms to 1.1, except in the experimental profiles and extensions (1.2). Adding error codes is safe because clients handle unknown ones by the class of the status (5.4), and adding the rest because clients ignore what they do not know (3, 4.2).
  • The value of restep MUST match this grammar (ABNF, RFC 5234, with the case-sensitive strings of RFC 7405), so numbers carry no leading zeros and the suffix is in lowercase: 
    restep-version = major "." minor [ "-" pre-release ]
pre-release    = ( %s"draft" / %s"rc" ) "." number
major          = number
minor          = number
number         = "0" / ( %x31-39 *DIGIT )
    Without a suffix ("1.0", "1.1") it names a published version. With one it names a draft ("1.0-draft.7", "1.1-draft.2") or a release candidate ("1.0-rc.1") of the version before the hyphen. A server that implements a draft or a candidate SHOULD declare it this way rather than as the published version. A client of Restep 1 MUST NOT treat as a Restep 1 discovery document one whose restep does not match this grammar or whose major version is not 1, and for one of another major version it MUST NOT fall back to assuming core only either, as 4.2 asks of a client that finds no discovery document: that API is not one it can use as Restep 1.
  • A draft or a candidate may differ incompatibly from the published version of the same number and from every other draft. A client MUST NOT assume, for a version with a suffix, the guarantees of this section: that it conforms to any published version or to any other draft. A client that does not know that exact draft MAY work with it under the rules of the version without the suffix, except in its experimental parts (1.2), and handles what differs as it handles any error. The examples in this text say "1.0".
  • A minor version MUST NOT reserve parameter names beyond those listed in 5.3, except names starting with $, which are kept for future versions of Restep. Of these, $api_version is already reserved for dated versions (5.5).
  • An incompatible change will be Restep 2, with new URIs (/2/core…). The /1/ URIs, under https://w3id.org/restep/1/, will never change; if the text moves to another site, only where they redirect changes.
  • Until 1.0 is published, drafts may change incompatibly.

1.2 Profiles and dependencies

Each profile only adds requirements; none changes the type or meaning of what an earlier one defines, so announcing a new profile never breaks an existing client. Some profiles need others:

Profile or extensionRequiresStatus
coreNothing; every Restep API implements itStable
query, writes, cache, relationscoreStable
synccore and query (to fetch changed items by id)Experimental
actions, oauthcoreStable
batch, inheritcoreExperimental
filter-expr, query-methodqueryExperimental

A server MUST NOT announce a profile or extension without the ones it requires.

Each profile and extension is stable or experimental, as the table says and the heading of its section repeats.

  • A stable one follows 1.1: later minor versions only add to it.
  • An experimental one MAY change incompatibly in a minor version, until a version declares it stable. This is the only exception to “whatever conforms to 1.0 still conforms to 1.1”. Moving from experimental to stable is itself such a change only if the text changes.
  • It is announced like any other, with its name in profiles or extensions; there is no separate name for its experimental form. A server MUST implement, for everything it announces, experimental parts included, the text of the version it declares in restep.
  • A client MUST NOT use an experimental profile or extension unless restep declares a version whose text of it the client implements; for a draft or a candidate, that exact one. So a client written for the experimental sync of 1.0 stops using it against a server that declares 1.1, until it learns the text of 1.1, instead of following rules that no longer apply. A client uses an experimental profile or extension when it sends a request that only that part defines, or relies on a rule of it to interpret a response; ignoring its members is not using it.

1.3 Licence and process

  • The text of this specification, its JSON Schemas and the Restep tools are published under the MIT licence. The specification’s repository, github.com/restep-spec/spec, holds it in English and Spanish with its JSON Schemas and the reference server. The text is read at restep.wubytes.com; its identifiers (the URIs of the version, profiles, errors and schemas) live under https://w3id.org/restep/, which redirects there.
  • The licence allows anyone to copy and modify the text; the name is a separate matter. Only what meets section 12, for the profiles and extensions it claims, may be presented as “Restep 1” or as conforming to Restep 1. A modified text must not be presented as Restep or as this specification, though it may say that it is based on Restep 1.
  • Questions, proposals and errata are opened as issues in that repository: a requirement that is unclear, two that contradict each other, a case the text does not cover. Pull requests there are welcome as proposals; they are applied at the source, the Restep site, where the specification is written alongside its tools.
  • Until 1.0 is published, each change goes into a new draft, and Appendix C lists it. After that, a correction that changes no requirement (a typo, a broken link, an example that contradicts the text it illustrates) is published as an erratum in Appendix C without changing the version; any other change waits for a minor version (1.1).
  • Sections 1 to 12 are normative, except their examples and the sentences without the key words of section 2. Section 13 explains risks and cites the requirements that address them; the appendices are not normative.

2. Terms

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are to be interpreted as described in RFC 2119 and RFC 8174 when, and only when, they appear in all capitals. Every requirement of this specification carries one of them; sentences without them explain or give examples.

  • API root: the base URL a client is configured with, such as https://api.example.com/ or https://example.com/api/. Paths in this specification, in the path members of discovery and batch and in events (10), such as /books, are relative to it: under https://example.com/api/, /books means https://example.com/api/books. Links in bodies and headers are not: they are URI references (RFC 3986) resolved against the request URL.
  • Collection: a resource grouping items of the same kind, such as /books. Its items may be variants with different schemas (books, magazines and gift cards in /products), as long as each field has one type in all of them (4.2).
  • Item: a resource in a collection, such as /books/7.
  • Representation of an item: the body that describes the item as it is now; it is the only body with which a client updates its copy of that item.
  • Result of an action: the body of a 200 to a safe action that declares output (11.1); it describes the action, not the item it was asked on, and replaces no copy.
  • Singleton: a resource that is neither a collection nor an item of one, declared on its own in discovery, at the API root (/me) or under an item or another singleton (/readers/7/settings); it exists as long as its parent does (5.9).
  • Profile: a named set of rules (core, query…), with its own URI, announced in profiles, that every client of the API may rely on without reading any declaration, and that enables its capabilities (RFC 6906). With writes, every non-idempotent POST takes Idempotency-Key.
  • Extension: an optional mechanism, with its own URI, announced in extensions, that changes nothing for a client that does not use it. It usually has a syntax of its own (a method, a path, a parameter form, a header exchange), but that is not what makes it an extension.
  • Reserved parameter: a query parameter whose meaning Restep defines (section 5.3).
  • Principal: who a request acts for, as the server authenticates it (in OAuth 2.0, the client and, if there is one, the user), and whoever acts on its behalf, if anyone (the act claim of RFC 8693, section 4.1). It is not the credential: a request with a renewed token comes from the same principal. An administrator acting as a user is a different principal from that user, so idempotency keys (7.1), cursors (6.4) and stored responses are never shared between the two; what such a request may see and do is the server’s to decide.
  • Capability: something a resource declares in discovery within a profile or extension (a filter, an operator, a sort key, a relationship, an action, a language map, a localized field, a client-chosen id, an upload). A profile or extension says what a capability means; whether a resource has it is said only by its declaration.
  • Equal as JSON values: of the same type and, for objects, with the same member names and equal values, whatever their order and whitespace; for arrays, with equal elements in the same order; for numbers, the same decimal number (1 and 1.0); for strings, the same sequence of code points once unescaped, without Unicode normalization.

So a rule goes into a profile when every client may rely on it without looking at any declaration, into an extension when it changes nothing for a client that does not use it, and into a capability when it holds only where a resource declares it. No part of Restep 1 changes level under this criterion (1.2).

3. Data

  • Bodies MUST be JSON (RFC 8259) encoded as UTF-8, and what each party sends MUST be an I-JSON message (RFC 7493, section 2): without unpaired surrogates or noncharacters, and without duplicate member names in an object. The exceptions are responses without a body (204, 304, HEAD), the event stream of sync, the bytes of an upload (5.1) and resources outside Restep (5.9). The server MAY reject a request body with an unpaired surrogate, a noncharacter or U+0000 with 422 invalid and a format entry, whose pointer is the string that holds it, or "" when that string is a member name or the server cannot locate it: a pointer to a member name would have to contain the same code point. A body that also has a JSON syntax error gets 400 bad_request instead (5.4). The server SHOULD reject a request body with duplicate member names with 400 bad_request: most parsers silently keep one of them, so the meaning of such a body would depend on the parser.
  • A request with a body to a resource of Restep (a POST to a collection, an action or a batch; a QUERY) MUST carry Content-Type: application/json; a PATCH follows 5.1, and a POST to a collection that declares upload may carry a file instead (5.1). The server MUST answer 415 unsupported_media_type to any other media type, and to a body without Content-Type. An empty body is a body: without Content-Type it MUST give 415, which here prevails over the 400 that its emptiness would also allow (5.4), and with a media type the resource accepts it MUST give 400 bad_request; this holds for a PATCH too. Treating a body without a type as one of a type the resource does not support is Restep’s own choice: RFC 9110 (section 15.5.16) does not say how to answer it. The one exception is an empty body to an action (11.1). This matters most with cookies: a browser sends text/plain, application/x-www-form-urlencoded and multipart/form-data from any origin without a CORS preflight (5.8), so a server that read one of them as JSON would accept writes that the preflight exists to stop.
    • The media type is compared case-insensitively, as RFC 9110 says. application/json defines no parameters, and RFC 8259 (section 11) notes that adding a charset has no effect on compliant recipients; Restep departs from that note because section 8.1 requires JSON exchanged between systems to be UTF-8, so a body labelled with another charset cannot be valid JSON. The server MUST accept charset=utf-8, in any case and quoted or not, MUST answer 415 to any other charset, and MUST ignore other parameters.
    • A 2xx response with a body MUST carry Content-Type: application/json, which MAY add charset=utf-8, as requests may. The exceptions are the event stream (text/event-stream), a JSON Schema, which MAY use application/schema+json (not registered with IANA, so a client accepts application/json for a schema as well), the bytes of an upload, and the service status, which MAY use application/health+json (from an expired individual Internet-Draft, and not registered either; 4.4). Errors use application/problem+json (5.4) whatever Accept says: the server MUST NOT answer 406 only because Accept does not list application/problem+json.
  • Field names defined by Restep are snake_case. Each API chooses its own, but SHOULD stick to one convention.
  • A name that an API gives and that discovery declares or a parameter carries (the key of a collection, a singleton, an action, a relationship, a named filter or a reason, and a field that discovery declares or that filter, sort, fields, include or filter-expr names) MUST match this grammar (ABNF, RFC 5234): 
    name = ALPHA *63( ALPHA / DIGIT / "_" / "-" )
    It fits snake_case and camelCase, and is case-sensitive. It never holds ., ,, [, ], : or a space, which parameters and paths use to separate dotted paths, lists, operators and actions, and never starts with -, which marks a descending sort (6.2). A dotted path (author.id) is names joined by ., except that its last segment can be a language tag (name.es-mx, 6.1). A field whose name does not match MAY appear in representations, but the server MUST NOT declare it in discovery, and a parameter that names it gets the error for a field that does not exist or is not declared. An API need not rename fields that it never declares and that no parameter names.
  • Member names starting with _ are reserved for Restep (such as _actions, _etag). An API MUST NOT define fields with that prefix, except those starting with _x_.
  • Member names starting with _x_ are left to extensions outside Restep, which never defines one. They are annotations of the server, like Restep’s own _ members: a write ignores them (5.1), fields keeps them (6.3), and clients MUST ignore those they do not know. Their values MUST NOT change between two reads of the same version of an item, since they count towards its ETag (7.2). What an extension needs a client to write goes in ordinary fields. Neither _x_ nor the x- of discovery members (4.2) marks a name as non-standard, which BCP 178 (RFC 6648, section 4) advises against: they keep the names that later minor versions of Restep will define apart from those a server or an extension adds. As RFC 6648 (section 3) suggests, the rest of the name SHOULD carry the name of the organisation or of the extension (_x_acme_audit, x-acme-region), so two extensions do not collide.
  • An item’s identifier is called id. It MUST be a non-empty string made only of RFC 3986 unreserved characters (A–Z a–z 0–9 - . _ ~), so it can go into a path without escaping, and MUST NOT be . or .., which URI resolution would remove. It MUST NOT change. An alias that moves from one item to another, such as “the current version”, is therefore a relationship or an item of its own, never an id (Appendix D). Two ids are the same only when they are the same sequence of code points: the server MUST NOT treat abc as taken by ABC, nor serve an item at a path whose last segment is not its id, such as item 7 at /books/07. The server MUST compare each segment of a path after percent-decoding it, so /books/%37 is /books/7. A segment that does not decode to valid UTF-8, such as %FF, names no item: the server MUST answer it as it answers an item that does not exist, unless an HTTP server in front of the API rejects it first (5.4).
  • A field whose values may fall outside ±(253−1), which an I-JSON receiver cannot be expected to treat as exact (RFC 7493, section 2.2), or that needs exact decimal arithmetic (amounts of money), MUST be a string in every representation, whatever the value: "price": "18.50". An amount of money SHOULD come with its ISO 4217 currency.
  • Instants MUST follow date-time of RFC 3339 (section 5.6), as updated by RFC 9557, with an offset: "2026-11-12T09:30:00Z". A server MUST write T and Z in uppercase (RFC 7493, section 4.3) and MUST accept the lowercase forms that RFC 3339 allows. Two instants are equal when they denote the same point in time, whatever their offsets. An instant MAY carry the local offset at which it happened ("2026-11-12T10:30:00+01:00"); since RFC 9557 (section 2.2), Z says that the local offset is unknown, not that it is UTC. A server never writes a leap second (:60), in an instant or in a local date-time (below), and MUST reject one in a request body with 422 invalid and a format entry, as a filter rejects it (6.1), except in a field that only the server sets, which a POST ignores whatever its value (5.1). Calendar dates MUST use full-date: "1987-03-14".
  • Durations SHOULD be strings that match this grammar; a field holding seconds as a number SHOULD end in _seconds: 
    duration   = "P" ( dur-date / dur-time / dur-week )
dur-date   = ( dur-day / dur-month / dur-year ) [ dur-time ]
dur-time   = "T" ( dur-hour / dur-minute / dur-second )
dur-year   = 1*DIGIT "Y" [ dur-month ]
dur-month  = 1*DIGIT "M" [ dur-day ]
dur-week   = 1*DIGIT "W"
dur-day    = 1*DIGIT "D"
dur-hour   = 1*DIGIT "H" [ dur-minute ]
dur-minute = 1*DIGIT "M" [ dur-second ]
dur-second = 1*DIGIT [ "." 1*9DIGIT ] "S"
    This is the duration rule of RFC 3339 (Appendix A), which is not normative there and is copied here, plus one thing from ISO 8601: a decimal fraction of up to nine digits, only in the seconds ("PT1.5S", "PT0.250S"). Fractions, because timeouts, latencies and media lengths go below a second and would otherwise need a number of their own; only in the seconds, so no value needs a fraction of an hour or a minute ("PT1H30M", never "PT1.5H") and two lengths compare as decimal numbers of seconds; up to nine digits, the nanoseconds that common duration types of programming languages carry. As with instants, a server MUST write the letters of a duration in uppercase and MUST accept them in lowercase. A duration filter compares them exactly, as decimals (6.1).
  • A local date-time is a calendar date and a wall-clock time without an offset, full-date "T" partial-time of RFC 3339 (section 5.6): "2027-03-30T19:00:00". It denotes an instant only together with a time zone, a name from the IANA Time Zone Database ("Europe/Madrid"). Discovery declares in local_times which fields of a collection hold local date-times and where each one’s zone comes from (4.2). Converting one to an instant MUST follow RFC 5545 (section 3.3.5) and RFC 8984 (section 1.4.5): a local time that occurs twice is the first of them, and one that does not occur, in a gap, takes the offset from before the gap. An API that offers the instant gives it in a separate read-only datetime field (starts_at_instant).
  • Absent and null are different. On reads, a field with no value MAY be omitted or set to null, except a language map, which is {}; in a PATCH, null deletes and absent leaves untouched (RFC 7396).
  • A relationship, when a representation includes one, MUST be an object with at least id (to-one), a list of such objects (to-many), null (an empty to-one) or [] (an empty to-many). Never a bare identifier, so the field’s type does not change when the related item is included (section 9). When a relationship can point to more than one collection, each object MUST also carry type with the target collection’s name. An object MAY carry href, the related item’s path as an absolute link (below), and MUST carry it when the target collection is a subcollection, whose item paths cannot be built from id alone (section 9).
  • Links in bodies (next, href) MUST be absolute URIs or absolute paths, starting with / and including the API root’s path (/api/books?cursor=…), so a colon inside a segment (/orders/2001:cancel) is never read as a scheme, as it would be in the relative reference 2001:cancel. Since RFC 3986 (section 3.4) allows no unencoded [ or ] in a query, the server percent-encodes them in the links it builds (5.2). An absolute URI among these links, among the links of the discovery document, and in the Location and Link headers of the API’s responses, MUST use https or the scheme of the API root; a client MUST NOT dereference one with another scheme, such as file: or data:.
  • Clients MUST ignore fields they do not know and tolerate new enum values, also those that their stored copy of discovery or of a schema does not list: a client MUST NOT reject a response because of such a value, and MAY warn about it. Before sending one, a client MAY check its own input against what it has stored.
  • Successful (2xx) responses of collections, items and actions MUST NOT depend on the language of whoever reads them, wherever the server takes it from (Accept-Language, a setting stored for the principal, a cookie), except the localized fields that a collection declares in localized, which depend on Accept-Language and nothing else (5.6), and what a request derives from them: the items a filter on one selects, the order a sort by one gives, total and the cursor in next (6.1, 6.2, 6.4). Responses that neither carry localized fields nor filter or sort by one do not need Vary: Accept-Language. Numbers, amounts, dates, instants and durations always take the forms of this section; presenting them in a language is the client’s job. Only the API’s own texts and localized fields change with the language (5.6).
  • A language map holds the same text in several languages: a JSON object whose keys are language tags (BCP 47: RFC 5646) and whose values are strings. Only top-level fields of an item can be language maps. Restep says nothing about the language of text fields that are not. 
    "name": { "en": "Zucchini", "en-gb": "Courgette", "es-es": "Calabacín", "es-mx": "Calabacita" }
    • Each key MUST be a well-formed tag (the grammar of RFC 5646, section 2.1; it need not be in the registry) in lowercase. The server MUST NOT change a key (iw does not become he). A value can be any string, "" included.
    • A language map’s type MUST NOT change: it is an object with one translation or none, even if the API speaks one language. A map with no translations MUST be given as {}, not absent or null, unless the representation leaves the field out (through fields or permissions). The server MUST NOT fill a missing translation with another language’s text: the client picks what to show from the keys it gets.
    • In a POST, a language map is an object of strings. In a PATCH it merges like any object (RFC 7396): {"name": {"fr": "Courgette"}} adds or changes French and leaves the rest, {"name": {"fr": null}} deletes it, and deleting a key that is not there does nothing. After merging, a missing language map is {}, so {"name": null} empties it. A declared update schema (4.3) MUST accept null for the field and for any well-formed lowercase key.
    • The server MUST validate the body before merging, including the keys it deletes, and MUST answer 422 invalid with one errors entry per failure, with a pointer to what fails and this code: type if the field is not an object or a value is not a string (in a PATCH, null is valid in both places; in a POST it is not); format if a key is not a well-formed lowercase tag (/name/ES); unknown if a translation is added, or given a value other than the stored one, under a well-formed tag the API does not accept.
  • A localized field is a top-level, read-only field whose value is the text of a language map of the same item, its source, in the language of the response (5.6): "name": "Novela negra" from "name_i18n": {"es-es": "Novela negra", "en": "Crime fiction"}. Its value is a string or null. Discovery MUST list every localized field of a collection in localized, with its source: "localized": {"name": {"source": "name_i18n"}}; the rest of each field’s object is left for minor versions. Where the map lacks the language of the response, the server MAY fill the localized field with the text of another language; the map itself is never filled (above). A client writes the map, never the localized field (5.1).

4. Announcing Restep

4.1 Profile header

Every API response SHOULD carry one rel="profile" link (RFC 6906) to the version URI, and only that one, so the header has the same size whatever the server announces:

Link: <https://w3id.org/restep/1/>; rel="profile"

Which profiles and extensions the server implements is said only by the discovery document (4.2). Each one still has its own URI, the version URI followed by its name (https://w3id.org/restep/1/query), which names it in a problem or a document, but a server SHOULD NOT list them in the headers of every response.

Profiles apply to the whole API. The rules of a profile that hold only where a resource declares them (filter, sync…) are its capabilities (2), and which resource has which is said only by the declarations in the discovery document.

4.2 Discovery document

A GET on the API root returns a document stating the server’s profiles, extensions and capabilities. A core-only server SHOULD serve it; a server that announces any other profile or extension, or has language maps (3), MUST serve it. A server whose root is taken MAY serve it elsewhere and point to it from its responses with Link: <…>; rel="service-desc" (RFC 8631). A response MAY carry several service-desc links, such as one to an OpenAPI document; the one to the discovery document SHOULD carry type="application/json", and clients MUST use the first target that is a discovery document of Restep 1 (1.1).

Clients MUST treat a response as a discovery document only if it is a 2xx whose body is a JSON object with a string member restep. If the GET succeeds without one, or gives 404, clients MUST assume core only; any other error, such as a 401 or a 503, says nothing about the profiles. If a Link header lists profiles and disagrees with the document, the document prevails.

One document for everyone. The discovery document describes the API, not what a principal may do with it:

  • Its content MUST NOT depend on the principal (2) or on whether the request carries credentials; only its texts change, with Accept-Language (5.6). Two documents that the same deployment of the API serves at the same time under the same Accept-Language MUST be equal as JSON values (2). So two principals get the same document, and a copy kept with a client’s code can be compared with the next one. Everything it declares is visible to whoever can read it (13.12). An API whose collections, fields or declared capabilities differ by tenant MUST give each tenant its own API root, with its own discovery document.
  • The server MAY require credentials to serve it, answering 401 without them or 403 to a principal that may not read it; whoever it serves it to gets the same document. Its response then depends on credentials (5.1) and MUST carry Cache-Control with private or no-store; only a document served without credentials MAY be public and kept by a shared cache.
  • Its response SHOULD carry an ETag and a Cache-Control with a max-age. A client MAY keep it for as long as that Cache-Control allows, and SHOULD revalidate it after that. A client that gets unsupported_parameter (5.3) or 405 for something its copy declares SHOULD fetch the document again before concluding that the capability is gone.
  • What a principal may not do is said by the response to the request, never by leaving it out of discovery. A declared method, action or singleton that this principal may not use MUST give 403 forbidden, or 404 not_found where its existence is concealed (5.4), never 405 or unsupported_parameter. For filters, sorting and fields on a field the principal cannot read, see 6.1. Where the structure is the same for every tenant and a tenant may not use part of it, that part MUST give 403 forbidden with a reason that says so (5.4).

4.3 Describing operations

Optional members that let a client, a person reading the document or an agent picking a tool, know what each collection does and accepts without trying it. A server MAY declare any of them on any collection; Restep requires none, so a core server can still be written by hand.

  • methods and item_methods: the methods a collection and its items support, out of GET, POST, PATCH and DELETE (HEAD goes with GET; actions and QUERY are announced on their own; PUT is never one, 5.1). A missing list means unknown, not all. A declared list MUST be exact: a method left out gives 405, unless another applicable error is reported (5.4), a listed one never does, and the Allow header of a 405 MUST list every declared method, HEAD wherever it lists GET, and no other of those four (RFC 9110, section 15.5.6). A collection whose methods leave out GET cannot be listed: it MUST NOT declare filter, named_filters, sort, count or sync (5.2).
  • method_effects and item_method_effects: the effects (11.1) of the unsafe methods of a collection and of its items (a singleton declares method_effects for its PATCH, 5.9), as objects whose keys are methods of methods and item_methods: "item_method_effects": {"DELETE": ["destroys"], "PATCH": []}. A DELETE they do not declare has ["destroys"], which is what the method already says; "DELETE": [] says the deletion can be undone. Any other unsafe method they do not declare counts as having all three effects. A description never stands in for this declaration.
  • description: a short plain-text explanation of a collection, a singleton, a filter field, a relationship, an action, an inherited field (11.6) or a reason (5.4). It SHOULD be one sentence.
  • schemas: JSON Schemas (2020-12) of a collection’s item (its representation without fields or include), create (the body of a POST) and update (the body of a PATCH: a merge patch, where absent leaves a field untouched and null deletes it). Each is a schema object or a link to one, absolute as links in bodies are (3). Schemas can describe each field with its own description. The item schema of a collection with variants (2) can be a oneOf whose branches each fix a property that tells them apart with const ("kind": {"const": "book"}). In a collection that declares upload, create also says whether it creates items from JSON (5.1).
  • A default in a top-level property of create is the value the field takes when a POST leaves it out, and the server MUST give it that value, which MUST be valid against the property’s schema (JSON Schema Validation only recommends it, section 9.2, but here default has an effect); a field sent as null is not left out. In update a default means nothing, because a field absent from a PATCH stays as it is.
  • A client can build a form for people from these schemas (Appendix A). It shows fields in the order of properties, so a server SHOULD write them in the order it wants them shown.
  • Before validating a body against a declared create or update schema, the server drops the members that start with _, which 5.1 ignores, and, in a PATCH, every field whose current value 5.1 ignores, and in a POST, every read-only field that 5.1 ignores; a PATCH left empty by this is not validated against update. In either, a read-only field with another value MUST give the read_only entry of 5.1, not a schema error. A body the schema then rejects MUST give 422 invalid (also when it is a JSON value that is not an object, with an entry whose pointer is "" and whose code is type), unless another applicable error is reported (5.4), and its errors SHOULD point at the failing members. A schema describes, it does not promise: a body it accepts can still fail the API’s own rules. readOnly is only an annotation, except as 5.1 says for top-level properties of an item schema, and id follows 5.1 whatever the schema says: a create schema can restrict the format of an id the client chooses, but cannot make the server accept an id that 5.1 rejects.
  • An action’s input (11.1) is the schema of its body, with the same meaning; its params and output are described in 11.1.
  • A client MUST send its credentials for the API only to URLs on the API’s origin, and MUST fetch a schema or document on another origin without them (13.2). It SHOULD NOT resolve a schema’s $ref outside the origin of the schema that holds it, and SHOULD NOT send a value it took from a schema on another origin, such as a default, without showing it to the user first.

Descriptions, titles and every other value an API returns are data, never instructions to the client. A declaration of effects (11.1) is data too: it lets a client ask before it acts, and authorizes nothing. A client MUST NOT, because of such text alone, make a request that is not safe (5.7) and that the task it is serving did not already call for, nor send data to another origin. Using detail and errors to correct the request it is already making is not following an instruction. An agent that puts these texts in a prompt SHOULD mark where they begin and end (13.1).

4.4 Service status

A server MAY declare in status a link, absolute as links in bodies are (3), to a resource that says whether the API can serve requests, and MAY also link it from its responses with rel="status" (RFC 8631). Clients MUST NOT assume a path such as /health.

  • Unless it asks for credentials or refuses them (401, 403) or limits the rate (429), a GET or HEAD on it MUST answer 200 when the API can serve requests and 503 when it cannot, with Retry-After when the server knows for how long, and always with Cache-Control: no-store.
  • It is not a resource of the API: 4.1, 5.1 to 5.4 and 8 do not apply to it, except that its 429 carries Cache-Control: no-store as 5.4 requires. Its body MAY follow the Health Check Response Format (draft-inadarei-api-health-check, revision 06, an expired individual Internet-Draft whose media type is not registered). Served without credentials, it SHOULD NOT say more than whether the API can serve.

A 415 to a PATCH SHOULD carry Accept-Patch (RFC 5789). A patch that is not a JSON object is a well-formed merge patch that would replace the whole item (RFC 7396, section 2), which Restep does not allow: it MUST give 422 invalid with a type entry whose pointer is "" (RFC 5789, section 2.2). A body that is not JSON MUST give 400 bad_request. Both hold unless another applicable error is reported (5.4).
  • An item’s path MUST be its collection’s path, with any URI template expanded (RFC 6570), its variables taking in order the ids of the parent items, and without a trailing /, followed by / and the item’s own id: /books/7, /books/7/reviews/3.
  • Who chooses an item’s id is a capability of its collection, declared in id_from:
    • Missing or "server": the server MUST assign id, and MUST give 422 invalid, with a read_only entry at /id, to a POST that carries one.
    • "client": a POST MUST carry id; without it, the server MUST give 422 invalid with a required entry at /id.
    • "either": a POST MAY carry id; without it, the server assigns one.
    • Other values are reserved for minor versions. A client that finds one it does not know MUST NOT send id in a POST to that collection.
    • A collection with "client" MAY declare "reusable_ids": true: its ids are keys, such as an ISBN, that can come back after their item is deleted (below).
    • A collection with "client" or "either" MAY declare "upsert": true: a PATCH to an id that is free creates the item (below).
    Whoever chooses it, an id never changes: a PATCH that carries a different one MUST give 422 invalid with a read_only entry, as below. For an id the client chooses:
    • It follows 3. One that does not (not a string, empty, with other characters, . or ..) MUST give 422 invalid with a type or format entry at /id. The server MAY restrict its format further, and then SHOULD say how in the create schema (4.3); a well-formed id outside that format gets the same 422 with format. The server SHOULD require a format with enough entropy that clients do not collide by chance, such as a UUID or a ULID; where it conceals from some principals the existence of items of that collection (5.4), it MUST require a format that cannot be guessed, such as a version 4 UUID, because the 409 below tells whether an id is in use. A client SHOULD generate such an id from a random source and SHOULD NOT derive it from the item’s data (an email, a name), since whoever can guess it can take it first or learn from the 409 below that it exists (13.6).
    • An id that an item of the same collection (for a subcollection, under the same parent item) has MUST give 409 conflict with an errors entry whose pointer is /id and whose code is taken. In a collection that does not declare reusable_ids, so MUST an id that such an item has had. That response MUST be the same whether or not the client can see the item that holds the id, or could see the one that held it. The server MUST know these ids for as long as the collection exists; a subcollection exists as long as its parent item does. A server that reuses the id of a deleted parent item, which the next point advises against, MUST NOT let the new parent’s subcollection take an id that the old one had. It MAY keep only a one-way hash of the ids of deleted items. In a collection that declares reusable_ids, the id of a deleted item is free again: a POST with it MUST create a new item (201), and the server need not remember it.
    • So, outside reusable_ids, a client never gets back the id of a deleted item: with sync, it could not tell the new item from the old one coming back. For the same reason, the server SHOULD NOT reuse in a collection the ids it assigns itself. In a collection with reusable_ids, each item that takes an id again is a new incarnation: its item ETag MUST differ from that of every earlier incarnation with that id (7.2), sync reports it in created (10), and a DELETE or a PATCH is safe to repeat only with If-Match (5.7), which the server MAY require from the moment it declares the collection (7.2). A relationship to such a collection names the key, not the incarnation; what happens to it when the item is deleted is the server’s to decide.
    • So, outside reusable_ids, a POST with an id chosen by the client never creates two items. A client that repeats it and gets 409 with taken reads the item to learn whether its first attempt took effect (5.7); with writes, Idempotency-Key works as for any POST and returns the stored response instead (7.1).
    • In a collection that declares upsert, a PATCH to the path of an id that is free (one that a POST with that id would create, above) MUST create the item, as RFC 5789 (section 2) allows: the server applies the merge patch to {}, validates the result as the body of a POST (against the create schema, if declared, 4.3) and answers 201 with Location and the representation, as for a POST. The id follows the rules above for client-chosen ids. The id of a deleted item, which is not free in a collection without reusable_ids, gives 404. If-None-Match: * makes the PATCH succeed only if it creates, and If-Match only if the item exists; otherwise it MUST give 412 (7.2). A PATCH to the path of an item that exists but whose existence is concealed from this principal (5.4) MUST give the 404 that the id of a deleted item gets; like the taken entry, it tells that the id is in use, which is why such a collection requires a format that cannot be guessed (above, 13.6).
    • These rules hold for every item of the collection, whoever creates it, a resource outside Restep (5.9) included.
  • A collection MAY declare upload: {"media_types": ["image/*", "application/pdf"], "max_size": 10485760}. A POST to it MAY carry, instead of JSON, the bytes of a file of one of those media types (* matches any subtype, and */* any media type), with its own Content-Type and, optionally, its original name in Content-Disposition with filename. The collection MUST declare a create schema (4.3) if, and only if, it also creates items from JSON; without create, it only takes uploads, and withdrawing create from a collection that keeps upload is a breaking change (5.5), and so is adding create to one whose media_types admit application/json. Only a request whose own Content-Type is application/json selects the creation of an item from JSON; any other media type, a +json one such as application/ld+json included, is a file like any other. Where it declares create, a POST with application/json is always the creation of an item, never a file: a JSON file is uploaded only as the file part of multipart/form-data (below), so, if media_types admits application/json, also through a wildcard such as */* or application/*, the collection MUST declare "multipart": true. Where it does not declare create, a body of application/json is a file when media_types admits it, also through a wildcard. The server MUST answer 415 to a media type it does not declare, a JSON body included where the collection declares no create and its media_types do not admit application/json, also through a wildcard, and 413 content_too_large to a file larger than max_size bytes. Such a 415 SHOULD carry Accept-Post with the media types the collection accepts (Linked Data Platform 1.0, section 7.1). It creates an ordinary item, in JSON, with the fields the API chooses, and MUST give it a _content member with the link to the bytes, their media type and their size: "_content": {"href": "/files/f_9/content", "media_type": "image/jpeg", "size": 48213}. The bytes at that link are a resource outside Restep (5.9). Other items link such an item through a relationship (9), whose declaration MAY carry media_types, so that a form offers only those files and the server rejects a file of another type with 422 invalid and a format entry whose pointer is the relationship’s id; or the item belongs to a subcollection that declares upload, such as /orders/2001/attachments. An item that nothing links MAY expire; the API says when in a field of the item, expires_at.
  • Where upload declares "multipart": true, the POST MAY instead carry multipart/form-data (RFC 7578) with exactly one part, named file, which holds the bytes with their own Content-Type and filename (section 4.2). The client MUST send a filename parameter on the file part, using a generic name (such as file) when the original is unavailable or private; the server MUST NOT require it and MUST read an otherwise valid file part without it as the file. An outer Content-Type of multipart/form-data always selects multipart upload and MUST give 415 unsupported_media_type unless upload.multipart is true, even when media_types matches it. Any other multipart body MUST give 415 too. A browser sends this media type from any origin without a preflight (5.8): a server that accepts credentials a browser attaches on its own relies here on the Origin check of 5.8, which it MUST apply. A write that carries both a file and the fields of another item stays outside Restep: it is two requests, an upload and a write that links it.
  • In a write, the server MUST ignore members whose names start with _, so a client can send back a representation it read.
  • A read-only field is one no client can change with a PATCH: id, an effective field (11.6), a localized field (3), one only the server sets (created_at, a total), or a top-level property that the item schema marks "readOnly": true directly in its properties (4.3); a server MUST NOT mark so a property that some client or some state of the item lets change with a PATCH. A value in a PATCH is current when it equals the field’s value as read under the field’s type (the same decimal, the same instant), when applying it as this section says (a relationship by its id, a language map by key) leaves the field as it was before the PATCH, or, for a localized field, when it equals that field’s text in any language the server offers. If a PATCH carries a read-only field with its current value, the server MUST ignore it; with another value, it MUST respond 422 invalid with a read_only entry whose pointer is the field, and MUST NOT apply any of that request. A field that this client, or the item’s current state, does not let it change follows the first half of that rule: its current value MUST be ignored, and another value MUST give 403 forbidden if this principal may not change it, or 409 conflict if the item’s state does not allow it, without applying any of that request; either SHOULD carry an errors entry whose pointer is the field. For a field the client is allowed to read, the server compares after validating a language map as 3 says. For a field it cannot read, neither the rules above nor the checks of 3 that look at the stored value apply: the server MAY validate the value sent (a write-only field, such as a password, is validated as any other), but its answer MUST NOT depend on the stored value. A field that tells the variants of a collection apart (kind) SHOULD be read-only once the item exists.
  • In a POST, a field that only the server sets (created_at, a total) MUST be ignored, whatever its value, a leap second (3) included: the case is a representation that was read and is sent back, and the new item would almost never get the values it carries. A field that only the server sets is one that no client can set directly, neither in a POST nor in a PATCH (created_at, a total); id, effective fields and localized fields are not among them, and neither a "readOnly": true in the item schema nor the field’s absence from the properties of a create schema establishes it, even in combination. Any other read-only field other than id (whose rules are above) MUST be ignored if its value is the one the item would get, and otherwise MUST give 422 invalid with a read_only entry whose pointer is the field.
  • A valid PATCH that, setting aside the fields it ignores, would change no data of the item MUST NOT change it: its representation and its ETag, if any, stay the same, and a field such as updated_at does not move. So the read-only fields of a representation that was read never make a PATCH fail or change anything, if the item has not changed since.
  • In a write, a relationship object is replaced whole, not merged: the server MUST read only its id (and type, and href when its target is a subcollection) and MUST NOT change the related item through it. To link an item of a subcollection the client MUST send its href, as read; an href that is not the path of an item of the target collection, or whose last segment is not the id sent, MUST give 422 invalid with a format entry whose pointer is that href. A relationship to an item that does not exist, or that the principal cannot see, MUST give 422 invalid with an entry whose pointer is the relationship’s id (/author/id) and whose code is unknown, the same in both cases. A relationship whose value is current (it leaves the field as it was) is not checked this way: the server MUST ignore it, so sending back a representation as read never fails because of it. {"author": {"id": "4"}} links another author; {"author": null} unlinks it. A to-many list is replaced whole, as Merge Patch does with any array.

Encoding it again does not count as changing it: the server MUST read parameters after percent-decoding, so filter[price] and filter%5Bprice%5D, or %5b and %5B, are the same, and MUST NOT depend on the order of parameters with different names. The server MUST read a + in the query as a space, as the application/x-www-form-urlencoded parser of the URL Standard (section 5.1) does, and most HTTP frameworks with it. In the links it builds, the server MUST percent-encode [ and ] (%5B, %5D), which RFC 3986 (section 3.4) does not allow unencoded in a query, and a literal + (%2B), and MUST write the colon before an action’s name as is (11.1); a client MUST send a literal + as %2B, and MAY send [ and ] unencoded, since the server decodes them. Wherever this text says “after percent-decoding” of the query, a + is a space.
  • A collection MUST have a deterministic default order. When that order, or a sort (6.2), uses id, it is the server’s order of its ids: total and stable, but not necessarily by code points (with numeric ids, "7" may go before "12"). Clients MUST NOT assume any order of ids. Without concurrent writes, following next until null MUST return exactly once every item the request selects: those the client can see that match its filters and the default filters it does not turn off (6.1). A request that turns off every default filter and carries no other filter selects every item the client can see: it is the request for a full copy, which exists only where the collection supports GET and requires no filter. A client that copies a whole collection MUST traverse it with that request. With concurrent writes, items may be repeated or missed; a client that needs an exact copy uses sync.
  • The server picks the page size. Without the query profile, clients cannot change it.
  • The object MAY carry other fields defined by profiles (total, state).

5.3 Reserved parameters: fail loudly

These parameter names, with or without brackets, belong to Restep: filter, sort, fields, include, count, limit, cursor, since and languages (unused in Restep 1), plus any name starting with $.

The forms Restep defines are name=value and, for filter, filter[field] and filter[field][op]. Any other bracketed form (filter[a][b][c], filter[], fields[]) is a form the resource does not support.

Unless another applicable error is reported (5.4), when a request uses a reserved parameter, or a form of one, that the resource does not implement for that method, the server MUST respond 400 with the code unsupported_parameter and the parameter name, exactly as received after percent-decoding, in parameter. It MUST NOT ignore it.

This is the rule that lets a server climb a step without breaking anyone: a client filtering against a server that cannot filter gets a clear error instead of the whole collection, as if the filter had been applied. Non-reserved parameters belong to each API, and Restep says nothing about them.

The two parameter codes tell a client whether to change the request or give up on the capability:

  • unsupported_parameter MUST be used when the request asks for something the resource does not offer: a reserved parameter it does not implement, a parameter form it does not support (filter=… without filter-expr, sort[…]), a filter field or operator, sort key or relationship that is not declared, count with any value on a collection that does not declare it (6.5), or fields or include on a method other than GET, HEAD and QUERY (6.3). It applies to every method: POST /books?filter[x]=1 gives it too. On a GET action (11.1), a query parameter that its params do not declare, every one where it declares no params, MUST also give unsupported_parameter, although it is not reserved.
  • invalid_parameter MUST be used when a supported capability gets a wrong value: a value that does not match the field’s type, a limit out of range, a field in fields that does not exist, an empty list, a repeated parameter, a bad cursor. Like unsupported_parameter, it MUST carry in parameter the name of the parameter at fault, exactly as received after percent-decoding; for a missing one, its name, such as filter[isbn] for a required filter (6.1); in the body of a QUERY (11.4), the name of the equivalent GET parameter, such as filter[price][le], or the member’s own name when there is none. With several at fault, parameter names one of them, and errors MAY list each with its parameter. A server whose framework keeps only one value of a repeated parameter MUST still detect the repetition, reading the query string itself if it has to.
  • Some limits are declared: max_limit (6.4), include_depth (9) and batch.max_operations (11.2). A server MAY also limit, without declaring it, how much a request asks of a supported capability: the values of an in list, the number of filters, the size of a filter-expr expression. A request over such a limit MUST give invalid_parameter naming the parameter, whose detail SHOULD state the limit; the server MUST NOT apply only part of it, nor answer unsupported_parameter, since the capability exists. A URL longer than the server accepts MUST give 414, a body larger than it accepts 413, and too many requests or open streams 429 (13.8).

5.4 Errors

Every 4xx or 5xx response the API generates MUST use application/problem+json (RFC 9457) when it has a body, with type, title, status (equal to the response’s) and a code. It SHOULD carry detail, saying, where it can, how to fix the request (the accepted values, the allowed range), and MAY carry instance and its own members. The problem types of Restep define code, errors, parameter, header and reason as extension members (RFC 9457, section 3.2). An error MUST NOT be sent as a 200 response; the only place an error goes inside a 200 is a per-operation result of batch. An error that the HTTP server gives before it passes the request to the API, such as for a URL or headers longer than its limits, is not one the API generates: 5.3 and this section do not apply to it, whether that server runs in front of the API or in the same process.

That 409 of the stored state is reported only once the principal’s current permission on the target has been checked (a 403, or the 404 that conceals the target), so that a principal without it does not learn that state. This does not apply to a replay or a 409 request_in_progress, which follow the third rule. Restep orders 428, which RFC 6585 (section 3) defines without an order, as a failed precondition, and it comes before 412.
    3. A replay, or a 409 request_in_progress (7.1), is reported after the checks that keep the principal from learning what it may not, its current permission on the target included (a 403, or the 404 that conceals the target), and in place of 428, 412 and the errors that depend on the stored state; in particular when the only obstacle is that the target no longer exists, whether the first request itself deleted it or another did.
    Everything else is left to the server: 404 or 405 (a 405 given without looking up the item is valid, as long as its Allow does not depend on that item, which would tell whether it exists); 405 or a 400 for a parameter; any one of 400 for the body, 415, 406 and 413; 400 for the body or 412 (reading the body first departs from RFC 9110 (section 13.2.1), which evaluates preconditions just before it would process the request content; Restep departs from it on purpose, because many servers parse the body before their own code runs; by the second rule it also departs from it in reporting 428 or 412 before a 422 idempotency_mismatch found without reading the content, so that a key reused for another request gets the same error whether the difference is in the content or in the query); and 422 or 409. Clients MUST NOT rely on that order; the server MAY describe it in the documentation it links with rel="service-doc" (4.2). These rules also decide between errors that other sections require (4.3, 5.3, 10, 11), and say nothing about 424, 429 and 5xx. An error that an HTTP server or an intermediary placed in front of the API gives before the request reaches it, such as a 413, is outside them. Some cases are not a matter of order: a body with a JSON syntax error gives 400 bad_request, even if it also carries an unpaired surrogate or a noncharacter (3); an empty body without Content-Type gives 415 (3), except to a POST action, which takes it as {} (11.1); when the API does not reveal whether a resource exists, the server MUST give it the same response as an item that does not exist, except as 5.1 says for upsert: never 403, nor a 405 whose Allow depends on that resource; a retired resource MUST give 410, not 404, unless its existence is concealed; and a declared method that this principal may not use gives 403 or the 404 of a concealed resource (4.2). A PATCH to a free id of a collection that declares upsert is not a request to a resource that does not exist (5.1): no 404 applies to it, so its preconditions are evaluated.

5.5 Evolution and versions

A Restep API evolves without versions as long as changes are compatible, and only creates a major version when there is no other way.

Compatible changes. A server MAY make them at any time: adding fields to a representation; adding optional parameters, collections, singletons, actions or enum values; supporting new filters, sorts or includes; adding profiles or extensions; declaring reasons or adding reasons to it (5.4); adding an effect to an operation (11.1); changing which of several applicable errors is reported, within the precedences of 5.4. They work because clients ignore what they do not know (section 3, 4.2) and do not rely on which of several errors they get (5.4).

Breaking changes. A server MUST NOT make them within a version, except through retirement (below):

  • removing or renaming a field, or changing its type or meaning;
  • making an input field, parameter or header required when it was not (including If-Match through 428, and Idempotency-Key);
  • tightening validation so that a request accepted before is now rejected (making read-only a field that could be written, or starting to refuse Idempotency-Key without credentials, 7.1, too), unless it closes a security hole;
  • removing a declared filter (named ones too), operator, sort key, relationship, inclusion, count, action, collection, singleton, profile, extension or method (4.3), a value of a declared enum, a collection’s sync or the API’s events (10);
  • removing an effect from an operation, or declaring [] where it had effects or none was declared (11.1), since a client would stop asking before it;
  • changing the format of ids, resource URLs or a collection’s default order, or a field’s collation (6.1);
  • changing the status or the code returned for the same case, when only one error applies to it;
  • removing reasons once declared, removing a reason from it, or changing a reason’s code.

Retiring. Within a version, a field or a declared capability can only disappear by retiring it:

  • It is announced first. Discovery MUST list it in deprecations: {"kind": "field", "name": "rating", "announced": "2026-12-01T00:00:00Z", "sunset": "2027-07-01T00:00:00Z"}. kind says what is retired, and where the notice goes:
    • At the root: version; profile and extension, with its name in name; collection and singleton, with its key in name; reason (5.4), with the reason in name.
    • In the collection: field; filter (also a named filter); operator, with the filter field in name and the operator in op; value, with the filter field in name and the enum value in value; sort; relation; include, with the relationship in name, which retires its expansion but not the relationship; count; max_limit, with the lower limit it will have in value; action; method and item_method, with the method in name.
    • In a singleton: field; method, with PATCH in name (a singleton’s GET goes only with the singleton, 5.9); and action, with the action’s name in name.
    announced MUST be the instant the notice was first published, and MUST NOT change afterwards. sunset, once there is a date, is the instant of the removal. Both are RFC 3339 instants and, in every notice, MUST be in whole seconds, without a fraction: the Deprecation and Sunset headers below cannot carry one (RFC 9651, section 3.3.7; RFC 9110, section 5.6.7). A field notice also covers the filters, sort keys and inclusions of that name and every dotted path that starts with it (name.es-mx for name, author.id for author), which go with the field. A count notice with "value": "estimated" announces that a declared "exact" count will become "estimated"; without value, that count will be removed. Responses of a resource that a notice retires whole MUST carry Deprecation (RFC 9745), whose value is the notice’s announced instant as a Structured Field Date (@ and the seconds since 1970, RFC 9651, section 3.3.7), and a Link with rel="deprecation" to the explanation. They are: for collection and singleton, every response of that resource and of its items; for action, every response to it; for version, every response. Once there is a date, they MUST also carry Sunset (RFC 8594) with sunset as an HTTP-date, which MUST NOT be earlier than announced (RFC 9745, section 4). A notice that retires only part of a resource (field, filter, operator, value, sort, relation, include, count, max_limit, method, item_method, reason) or a profile or extension is announced in deprecations only: its responses MUST NOT carry Deprecation, Sunset or a Link with rel="deprecation" for it, since RFC 9745 (sections 2.1 and 3) reads them as the deprecation of the whole resource.
  • At least six months SHOULD pass between announced and sunset.
  • After the date, a retired resource, singleton, action or version MUST respond 410 retired; a retired filter, operator, sort, relationship, inclusion or count (a count notice without value) MUST give 400 unsupported_parameter, like any undeclared one; after a count notice with "value": "estimated", discovery MUST declare that count as "estimated", and count=true still adds total, with "total_estimated": true when the number is approximate; a retired enum value in a filter MUST give invalid_parameter and no longer appear in data; a limit above a lowered max_limit MUST give invalid_parameter; a retired method MUST give 405; a retired field MUST be absent from representations and is, for parameters and writes, a field that does not exist (6.3); a retired reason MUST NOT be given; a retired profile or extension MUST leave profiles or extensions, and its requirements no longer apply. Retiring a profile or extension also retires those that require it (1.2), with the same sunset. After the date, discovery MUST keep the notice in deprecations until the next major version, so that a client knows why something is missing.

A new major version. A breaking change that cannot go through retirement requires one:

  • The major version MUST go in the path, as v followed by an integer: /v2/. Each major version is a separate API root with its own discovery document, which MUST declare it as "version": "2".
  • The major version MUST NOT go in headers, parameters or media types: in the path it is visible, cacheable and routable with no code.
  • Within a major version, the only version a request can name is a dated version, in the reserved parameter $api_version (5.3), which a minor version of Restep may define as an experimental extension; this version does not. A request without it gets what this specification defines for that API, which changes only through retirement (above). Such an extension keeps a resource’s identity without the date: links, href and Location never carry it, a client adds it to each request, and the server repeats it only in next. It is meant for removing fields or changing their meaning; renaming a field is still adding the new one and retiring the old.
  • The two major versions MUST link to each other with Link (RFC 5829), at least in the discovery document: rel="successor-version" from the old one and rel="predecessor-version" from the new one. Restep applies these relations, made for the versions of a document, to the API root as a versioned resource (RFC 5829, section 1).

5.6 Language of the API’s texts

Errors, the discovery document and the schemas the API serves MAY depend on Accept-Language (RFC 9110, section 12.5.4). Only their texts for people change: in an error, title and detail, also those of each errors entry; in discovery, description; in a schema, also one embedded in schemas, the JSON Schema title and description annotations. The localized fields of collections, items and actions (3) are picked the same way. Other data never changes (3).

  • The server picks the language with the lookup of RFC 4647 (section 3.4) over the languages it can give that response in, trying the ranges of Accept-Language from highest to lowest weight and, at equal weight, in header order; case-insensitively, without canonicalizing ranges or tags (iw does not find he), and without first dropping extensions or private-use subtags. It ignores *, ranges with q=0 and malformed ranges (a malformed q included). If none matches, or the header is missing, it MUST use its default language, which is fixed for the API and is never a language stored for the principal or the session. An API with localized fields MUST declare it in discovery, in default_language at the root, so a client knows what the defaulting behaviour gives (RFC 4647, section 3.4.1, asks a specification that uses lookup to define it, which the sentence above does). It MUST NOT answer 406 or 400 because of Accept-Language.
  • In a server that offers its texts or localized fields in more than one language, every response whose texts or localized fields are picked this way, or whose items or their order depend on a localized field, in the default language too, MUST carry Vary: Accept-Language, and a 304 of these the same Vary as its 200. A response with a body SHOULD carry Content-Language, and one with localized fields MUST carry it (RFC 9110, section 8.5). Each language is a different representation: an ETag, if present, MUST differ by language.
  • Lookup truncates the requested tag and never tries sibling variants: with es-es and es-mx but no es, Accept-Language: es-AR gets the default language. A server that offers regional variants of its texts SHOULD also offer the bare language.
  • A replay (7.1) returns the stored response, in its language, because Accept-Language does not count towards “the same request”.

5.7 Retries

A client repeats a request when it does not know whether it took effect (the connection dropped, it timed out) or when the server tells it to come back later. Whether that is safe depends on the method and on the answer.

  • Safe to repeat as is: GET, HEAD, QUERY and safe actions, with which the client requests no change of state (RFC 9110, section 9.2.1): what the server does on its own, such as logging, caching or refreshing from another source, does not make them unsafe, unless what it records is something the client can later read through the API as part of what it asked for. Also actions declared "idempotent": true; DELETE, whose repetition MAY give 404 (5.1), which a client that is repeating it takes as done; and PATCH with a merge patch, which leaves the item the same however many times it is applied, also where it creates the item (5.1, upsert). Idempotent means the same effect, not the same response (RFC 9110, section 9.2.2): a repeated DELETE may give 404 and a repeated idempotent action 409; to get the first status and Location again, a client sends Idempotency-Key where the server applies 7.1 to the request, which an action declared "idempotent": true need not do (11.1); the body of a replay gives no more than a read would now. A PATCH is idempotent except for concurrency: between the two attempts another client may have written, and the repetition undoes that change. With If-Match (7.2) the repetition gets 412 instead, also after a first attempt that succeeded, since that one changed the ETag; the client then reads the item to find out. In a collection that declares reusable_ids (5.1), a DELETE or a PATCH is safe to repeat only with If-Match, since by then the id may name another item.
  • Not safe without help: a POST to a collection, an action declared "idempotent": false and a batch can take effect twice. A client SHOULD NOT repeat one of them automatically when it does not know whether the first attempt took effect, unless it carries Idempotency-Key and the server announces writes (7.1), or it creates an item with an id the client chose (5.1), which cannot be created twice. With the key, a client MAY repeat it only within the key’s lifetime, idempotency.ttl from its first attempt (24 hours where it is not declared); after that it MUST NOT repeat it automatically, and first finds out whether the first attempt took effect. For a creation without an id chosen by the client, the outcome then stays uncertain, unless the client can establish it another way, such as a filter on a field the API keeps unique (6.1) or the created list of :changes (10). A client-chosen id is the protection that does not expire, except in a collection that declares reusable_ids, where the id is free again once its item is deleted (5.1).
  • 429 rate_limited and 503 unavailable: the server MUST NOT give either of them to a request that had an effect, nor to one that it cannot tell had none (a timeout after the commit, a process that died): it answers those with another 5xx, such as 500, 502 or 504. A gateway or load balancer that the API’s operator places in front of it, and that answers with a problem+json body, is bound by this rule as the server is. So the client MAY send the same request again, whatever its method. 409 request_in_progress (7.1) is repeated in the same way, with the same key and within its lifetime (above). With Retry-After, the client SHOULD NOT repeat it before that time; without it, it SHOULD wait an increasing time between attempts, with some randomness, so that many clients do not come back at once. A 429 or 503 without a problem+json body may come from an intermediary, which this section does not bind.
  • Other 5xx statuses (500, 502, 504…) and a lost response say nothing about the effect: the client repeats only what the first point allows, or what carries the same Idempotency-Key, within its lifetime (above).
  • Another 4xx answers the same request in the same way, except 408, 421 and 425, which HTTP lets a client repeat: 408 as is (RFC 9110, section 15.5.9), 421 over another connection (section 15.5.20), and 425 without TLS early data: RFC 8470 (sections 4 and 5.2) requires a client that sent the request in early data to retry it, and any retry not to be sent in early data. A client SHOULD NOT repeat any other one without changing something first: new credentials after a 401, a fresh read after a 412, If-Match after a 428, the body after a 422.

5.8 Browser clients

Restep does not require cross-origin access (Fetch, CORS protocol). For the operations a server makes available to a browser origin, it SHOULD send Access-Control-Allow-Origin on every response, errors included, and SHOULD answer their preflight without requiring credentials, since a preflight carries none. When those headers depend on the request’s Origin, every response SHOULD carry Vary: Origin, also one that does not carry them, and every such response that a shared cache may store (one that is public) MUST carry it. If it accepts credentialed requests (cookies, HTTP authentication or TLS client certificates; a token in Authorization is not one), it SHOULD name the origin rather than *, which browsers reject with credentials, and send Access-Control-Allow-Credentials: true. No rule of Restep applies to OPTIONS (5.1): the preflight of an operation open to that origin gets its CORS answer even for a missing item, without credentials or with reserved parameters.

It SHOULD list in Access-Control-Expose-Headers the response headers that the profiles and extensions it announces ask a client to read; in Restep 1, ETag, Location, Content-Location, Link, Allow, Accept-Patch, Accept-Post, Retry-After, Deprecation, Sunset, Idempotent-Replayed (defined by Restep, 7.1), Preference-Applied and Accept-Query, plus those of 11.5. It SHOULD allow in a preflight the request headers and methods those operations use; in Restep 1, Content-Type, Content-Disposition, If-Match, If-None-Match, Idempotency-Key (from an IETF draft, 14.2), Prefer, Authorization and DPoP, with PATCH, DELETE and QUERY. These lists are what Restep 1 defines; a later minor version may add to them.

A browser attaches some credentials on its own to requests that other origins’ pages start: cookies, HTTP authentication and TLS client certificates. A server that accepts any of them MUST refuse with 403 forbidden, without applying it, every request that is not safe (a POST, including actions and batches, a PATCH or a DELETE), that it would authenticate with such a credential and that a browser sent from an origin the server does not allow. It MUST treat as such a request whose Origin header (Fetch) is present and is neither the API’s origin nor one it allows. An origin it allows is one it names: a * in Access-Control-Allow-Origin allows none for this rule, since browsers do not accept it with credentials. It MAY treat Origin: null as the API’s origin when Sec-Fetch-Site is same-origin, since a form or a navigation from a page with Referrer-Policy: no-referrer sends it to its own origin, and MAY decide by Sec-Fetch-Site (Fetch Metadata) when Origin is missing. A request that the server authenticates only with a token in Authorization is not covered: a browser never adds one on its own, so a browser client of another origin that the server allows through CORS keeps working. Those cookies SHOULD carry SameSite=Lax or SameSite=Strict (the SameSite attribute of draft-ietf-httpbis-rfc6265bis). The preflight and the media type of 3 keep other origins from sending a JSON body; this check also covers an action with an empty body, which any page can send without a preflight (11.1, 13.7). A collection that accepts multipart/form-data or text/plain in upload (5.1) takes bodies that any page can send without a preflight: there this check is the only protection.

5.9 Singletons and resources outside Restep

Restep covers collections, their items, their actions, singletons and the resources this specification defines: the discovery document, the batch path, the event stream, the service status (4.4) and the OAuth metadata (11.5). When the server serves a discovery document, collections and singletons are those it declares. Any other resource of the API, such as a PDF or an image linked with href, or a path the API has not declared, is outside Restep: of this specification only 5.3, 5.4 and the Cache-Control rule of 5.1 apply to it, so its body need not be JSON, but a reserved parameter it does not implement still gives unsupported_parameter, and its errors are still problem+json. Such a resource implements a reserved parameter if it reads it, whatever the parameter means there.

A singleton is a resource with no collection, such as the signed-in user’s profile (/me) or an account’s settings, inspired by AIP-156, with which it shares having no create or delete. The server declares it at the root, in singletons, under a name of its choosing:

"singletons": {
  "me": { "path": "/me", "methods": ["GET", "PATCH"],
          "description": "The signed-in user’s profile and settings.",
          "schemas": { "item": "/schemas/me.json", "update": "/schemas/me-update.json" } } }
  • Each singleton MUST have a path, and MAY carry methods (out of GET and PATCH, exact as in 4.3), description, schemas (item and update), actions (11.1), deprecations (5.5) and method_effects (4.3), whose only key can be PATCH: "method_effects": {"PATCH": []}; a PATCH it does not declare counts as having all three effects. Its path MUST NOT be a path that a collection or an item of one has or could have: an item’s path is its collection’s path followed by one segment, so /books/featured is not allowed while /books is a collection, and /books/7/summary is, unless a subcollection of books has that path.
  • A singleton MAY hang from an item or from another singleton: it then declares in parent the key of that collection or singleton, and its path is a URI template with the rules of a subcollection’s (4.2): its variables take in order the ids of the parent items, and it is the parent’s item path, or the parent singleton’s path, followed by / and one or more literal segments: "settings": {"path": "/readers/{reader_id}/settings", "parent": "readers"}. Without parent, its path MUST NOT be a template. A client MUST ignore a singleton whose path is a template without parent, or whose parent names no collection or singleton of the document.
  • A singleton behaves as an item without id or collection. It MUST support GET (and HEAD), which returns its representation, a JSON object, and MAY support PATCH with a merge patch, as 5.1 says for items, returning the whole representation. POST, PUT and DELETE on it MUST give 405: a singleton is neither created, replaced nor deleted by the client. It exists for every principal that may use it and, with a parent, for as long as its parent exists: under a parent item that does not exist, it gives 404. One that a principal may not use gets 403 or 404 (4.2).
  • What this specification says of an item’s representation, its read-only fields, its PATCH, its ETag and its If-Match (3, 4.3, 5.1, 7.2, 8) applies to a singleton too, so with writes every response with its representation carries _etag, and a PATCH evaluates If-Match and If-None-Match against its ETag; what it says of id, item paths and collections does not. A singleton’s representation MAY carry an id, such as the user’s, which is then read-only.
  • With query, fields MUST work on a singleton as on an item (6.3). Relationships in it follow 3, and each relationship object in it MUST carry href, since a singleton declares no relations to find its target from; declaring relations, include and language maps on a singleton are outside this version: include and the other reserved parameters MUST give unsupported_parameter there. Its actions follow 11.1 and its representation MAY list them in _actions. An operation that only changes fields of the singleton is a PATCH, not an action.

How to model a draft that coexists with what is published (the item is the draft, or a subcollection with a fixed id) is in Appendix D.

6. query Profile

Profile URI: https://w3id.org/restep/1/query. Status: stable. It applies to collections; fields also applies to items. None of its parameters needs a parser: any HTTP framework reads them, though detecting a repeated parameter may need the raw query string (5.3).

6.1 Filters

GET /books?filter[category]=novela-negra&filter[price][le]=20

Examples show the query unencoded for readability. On the wire, spaces and quotes are percent-encoded, and so are [ and ] in the links the server builds (RFC 3986, section 3.4); the server reads the query after percent-decoding (5.2).

  • The discovery document MUST declare in filter which fields can be filtered, with their type and operators. Fields of a relationship use a dotted path (author.id), and so do fields inside an object of the item (address.city), which are declared in filter and sort as any other field.
  • A path through one to-many relationship (reviews.rating, reviews.reader.id), or a field whose value is a list of scalars (formats), MAY be declared in filter with "quantifier": "some" and the type of its elements: "reviews.rating": {"type": "integer", "ops": ["eq", "ge"], "quantifier": "some"}. Without quantifier, such a path or field MUST NOT be declared in filter, except with null as its only operator (below), nor listed in sort (6.2). A path MUST NOT go through more than one to-many step, and such a declaration MUST NOT declare ne or nin; “no related item matches” is asked with null on the group (below). Other values of quantifier are reserved for minor versions (4.2).
  • The filters of a request whose paths go through the same to-many relationship, or name the same list field, form a group. An item MUST match the group when, and only when, some related item, or element, that the principal can see matches all the filters of the group: filter[reviews.rating]=5&filter[reviews.reader.id]=3 asks for a five-star review by reader 3, not for a five-star review and a review by reader 3.
  • The relationship or the list field itself MAY declare null: filter[reviews][null]=true returns the items with no related item the principal can see (an empty list, an absent field and null are the same), and false those with some. Its declaration carries as type that of the related items’ id, string, for a relationship, and that of the elements for a list field, and, when null is its only operator, no quantifier or "some", which select the same items, so changing from one form to the other is compatible (5.5): "reviews": {"type": "string", "ops": ["null"]}. Together with other filters of its group, filter[reviews][null]=true MUST negate the group: filter[reviews.rating]=1&filter[reviews][null]=true are the books with no one-star review. Also where its declaration carries quantifier, null tests the relationship or the list as a whole, the group, never each element: alone, as above; together with in or other filters of its group, true selects the items where no related item or element that the principal can see matches all the other filters of the group, and false those where some does (filter[formats][in]=epub,pdf&filter[formats][null]=true are the items with neither format). It never asks whether some element is null. A request with more than one null filter on the same to-many relationship or list field, its own or that of a path through it, MUST give invalid_parameter, even when their values agree.
  • Each item appears once, however many related items match, and total counts items of the collection (6.5). A dotted path that ends in the id of a relationship whose target is a subcollection still MUST NOT be declared (below).
  • filter[field]=value is the same filter as filter[field][eq]=value. Filters on the same field with different operators are different filters (filter[price][ge]=10&filter[price][le]=20). Several filters MUST be combined with AND; for OR, NOT and parentheses there is the filter-expr extension.
  • Operators: eq, ne, lt, le, gt, ge, in, nin, null, prefix and contains. Other operator names are reserved for minor versions: a server MUST NOT declare an operator outside this list, and a client ignores one it does not know (4.2).
  • in and nin take values separated by commas, read after percent-decoding; their values cannot contain commas, encoded or not (use eq, filter-expr or query-method for those). filter[f][in]= is an empty list; an empty element between commas (a,,b) is the empty string. nin MUST match the items whose value is none of those listed; like every operator but null, it never matches an absent or null value (below). null takes true (no value: absent or null) or false.
  • The server MUST compare by the declared type: numerically for integer, number and decimal (decimals exactly, without going through floating point), chronologically for date (as calendar dates), datetime (as instants, exactly: a filter value more precise than what the server stores MUST be compared exactly or give invalid_parameter, never be rounded; an offset such as +02:00 is sent as %2B02:00, 5.2) and localdatetime (as wall-clock date-times, without any zone, and exactly), by length for duration (a day counts as 24 hours, and lengths are compared exactly, as decimal numbers of seconds; a filter value with years or months MUST give invalid_parameter, because they have no fixed length), and by Unicode code points for string, enum and timezone, case-sensitively and without language rules, unless the field’s collation says otherwise (below). Strings are compared as they are, without Unicode normalization: a composed and a decomposed é are different values. (JavaScript’s < compares UTF-16 code units, which order some characters outside the Basic Multilingual Plane differently from code points.) A boolean field MUST NOT declare operators other than eq, ne and null, and the id filter MUST NOT declare lt, le, gt or ge, since the order of ids is the server’s (5.2). null may be declared on a field of any type and tests whether the value is absent or null. Subject to the request limits in 5.3, the server MUST compare a numeric operand as a number, exactly, even when it falls outside the range of values the field can hold. An operand over such a limit gives invalid_parameter with the limit in detail; it is never replaced by another value, such as an infinity or zero. A time with a leap second (:60) MUST give invalid_parameter. Two operands equal under the field’s type, as numbers are in 2 (filter[price]=20 and filter[price]=20.0), are the same value, so the same filter, also for the cursor (6.4). So an operand of an integer field matches its type when its exact decimal value has no fractional part: 20.0 and 2e1 are the same operand as 20, and 20.5 gives invalid_parameter. The operand of an integer or number field, read after percent-decoding, follows the number grammar of RFC 8259 (section 6), exponent included (2e1 is 20), and +20, .5, 020 and 0x14 do not match it; that of a decimal field follows its own grammar (4.2).
  • prefix and contains MAY be declared only on fields of type string and on translations field.tag, never on id. prefix MUST match the values that start with the operand and contains those that contain it, with the collation of the field (below): by code points with "codepoint", and consistently with the server’s own eq with "server". An empty operand MUST give invalid_parameter.
  • A dotted path that ends in the id of a relationship whose target is a subcollection MUST NOT be declared in filter or sort: that id identifies an item only under its parent.
  • A translation is filtered as field.tag, with a language map of the collection and a lowercase key: filter[name.es-mx]=Calabacita. Discovery declares each one on its own, of type string: "name.es-mx": {"type": "string", "ops": ["eq", "in"]}. It reads only that exact key, with no RFC 4647 matching and no fallback: if the item lacks the key, the field is absent. The language map itself and any other path that ends in or goes through one (author.name, author.name.es) MUST NOT be declared in filter or sort, and a language map MUST NOT share its name with a relationship of its collection, so name.es-mx is never a relationship path. A localized field (3) is filtered, and sorted, in the language of the response (5.6), with the collation declared for it.
  • A collection MAY declare in collations how a field that holds strings (of type string, an enum of strings that is a sort key, or a localized field), or a translation field.tag, is compared and sorted: "collations": {"title": "server"}. The value applies to the filter and to the sort key of that name, to filter-expr, and to prefix and contains (above). Each key MUST be a field declared in filter with type string, a field listed in sort that holds strings (an enum of strings included), a localized field, or a translation field.tag, and MUST NOT be id (5.2).
    • "codepoint", the value of every string field not listed: by Unicode code points, as above.
    • "server": equality (eq, ne, in) and order (lt, le, gt, ge, sort) are the server’s, such as a database collation that ignores case or accents. The order MUST be total, deterministic and stable, and agree with the equality: two values are equal exactly when neither goes before the other. The server SHOULD say which it is in the field’s description (4.3). A client MUST NOT assume code points, nor reproduce that order or that equality locally. Since only these properties are promised, a change in the server’s own collation that keeps them, such as a library update, does not change the declared value.
    • Other values are reserved for minor versions, such as collations named by Unicode tags. A client MUST treat a value that is not a string, or a string it does not know, as "server".
  • Every operator except null MUST NOT match items where the field is absent or null.
  • A filter or sort key on a field that the principal cannot read in an item MUST treat the field as absent in that item: comparisons do not match it, filter[field][null]=true does, and it goes last in a sort. A dotted path through a relationship (author.name) is a field the principal cannot read in an item whose related item it cannot see (9). So a declared filter never reveals a value the client cannot read, and neither does a count (6.5). The server MAY instead answer 403 forbidden, naming the parameter in parameter, when the principal cannot read that field in any item.
  • A null operand other than true or false, an operand of any other operator that does not match the field’s type (for in and nin, each element), an empty in or nin list, or the same filter (same field and operator, in either form) twice MUST give invalid_parameter. An undeclared field or operator, unsupported_parameter (5.3).
  • In a collection with variants (2), a field that only some variants have is declared as any other: the items of the other variants lack it, and the rules for absent fields apply to them. The field that tells variants apart SHOULD be declared as a filterable enum.

Named filters. Some criteria do not compare a field: “active sessions” (neither expired nor logged out), “those started from a phone” or “requests approved by someone with this name”. The server declares them by name in named_filters, and the client uses them with the short form of a filter:

GET /books?filter[available]&filter[search]=machado&filter[price][le]=20
  • Discovery MUST declare each one in its collection’s named_filters, with a description that says which items it returns and, if it takes a value, its type (4.2, with its values if it is enum): "named_filters": {"available": {"description": "…"}, "search": {"type": "string", "description": "…"}}. Its meaning is the one its description gives, not a comparison with a field. A named filter MUST NOT share its name with a key of its collection’s filter, and its name follows 3, so it never contains a dot.
  • Without type, it is a switch: it applies with filter[name] or filter[name]=, and any value MUST give invalid_parameter. With type, the value is required: an empty one or one that does not match the type MUST give invalid_parameter.
  • A switch MAY be declared "default": true: it then applies to every list request of the collection (GET and QUERY) that does not turn it off with filter[name]=false (in QUERY, "name": false). false turns it off, it does not negate it: filter[active]=false does not ask for the inactive items. A default filter never applies to reading an item by its path. On a switch without default, any value, false included, still MUST give invalid_parameter. With filter-expr, filter[name]=false is the one filter[…] parameter that MAY go with an expression: turning a default filter off chooses which items are traversed, it is not part of the expression’s logic (11.3).
  • A filter of filter, or a named filter, MAY be declared "required": true: a list request without it MUST give invalid_parameter naming it (filter[isbn], 5.3). A collection with a required filter has no request for a full copy (5.2).
  • A named filter has no operators: filter[name][eq], or with any other operator, MUST give unsupported_parameter, as does an undeclared named filter. The same named filter twice MUST give invalid_parameter.
  • In everything else it is a filter: it is combined with AND with the others, the cursor is bound to it (6.4) and it gives unsupported_parameter wherever filters do, as in :changes (10). With filter-expr it goes into an expression as 11.3 says.
  • Unlike a filter on a field, it compares nothing that collations describes: how it matches text is said by its description. It MUST NOT select items by values the principal cannot read, unless its description states that criterion, which makes whether an item meets it public: whether an item matches would otherwise reveal those values (13.4). A named filter with a type MUST NOT compare its value with values the principal cannot read, whatever its description says: each value it is given would ask a different question about them, and bisection would find them.

6.2 Sorting

sort=-rating,title: comma-separated fields, with a leading - for descending order, as in JSON:API. Sortable fields are declared in sort; any other MUST give unsupported_parameter. The server MUST break ties in a stable way (for instance, by id). Items without a value for a sort key MUST go last, in both directions. A to-many path declared with quantifier (6.1) MAY be listed in sort: ascending, it sorts by the least value among the related items the principal can see, and descending by the greatest; items without any go last. A localized field sorts in the language of the response (6.1). A translation is sorted as its declared field.tag (6.1): sort=name.es-mx. Strings sort by code points, without language rules, unless collations says otherwise (6.1); id sorts in the server’s order (5.2).

6.3 Fields

With fields=title,price the response MUST carry only those fields, plus id and members starting with _. It also works on a single item’s GET, where, with writes, the item also carries _etag (7.2). A field that does not exist MUST give invalid_parameter; a field that exists but that the principal cannot read is simply absent from the response, as it would be without fields. A field that the principal cannot read and that neither discovery nor a schema the API serves names MUST be treated, for that principal, as one that does not exist, so fields does not tell it that the field exists. fields=id MUST be accepted and return only id and the _ members; an empty fields is an empty list (5.3). fields and include (9) apply to reads: GET, HEAD and QUERY. On a write they MUST give unsupported_parameter, and the response carries the whole item, or nothing with Prefer: return=minimal (7.3). A language map is one field: fields=name returns it whole, and a path into it (name.es; with relations, also author.name.es) MUST give invalid_parameter.

6.4 Pagination

  • limit sets the page size, between 1 and the declared max_limit. Outside that range the server MUST give invalid_parameter, not clamp it silently, unlike AIP-158, which coerces it to the maximum. A collection that accepts limit MUST declare max_limit; on one that does not declare it, limit MUST give unsupported_parameter.
  • next MUST carry an opaque cursor parameter, like the page tokens of AIP-158, and keep the other parameters unchanged. Clients MUST NOT interpret or build cursors.
  • A cursor is bound to what the request it was issued for had: the collection, the filters (the default filters the request does not turn off included, 6.1), the sort and, where the collection has localized fields, the language picked for the response (5.6); with QUERY, to the filter and sort members of the body (11.4). A cursor the server did not issue (a tampered one), an expired one, or one used with another collection, other filters, another sort or another language MUST give invalid_parameter with parameter: "cursor". A cursor SHOULD also be bound to the principal (2) that received it, and MUST be if it refers to results computed for that principal, such as a stored snapshot, so that another principal cannot page through them. Signing it is the simplest way to tell a tampered one. A cursor SHOULD NOT carry item data in readable form, such as the sort values of a keyset in clear: next URLs end up in logs. Encrypting it, or keeping the position on the server, avoids that (13.9). A cursor encrypted with a random nonce changes on every read, and with it the body and the ETag of the page, which then never gets 304 (8); a deterministic scheme avoids that.
  • A cursor MUST NOT be bound to limit, fields, include or count: they change what each page carries, not which items the traversal visits. Between pages, a client MAY add, change or remove them in the next URL of a GET, or in the body of a QUERY, and that MUST NOT invalidate the cursor.
  • A server MAY start with an offset inside the cursor and later move to keyset pagination without clients noticing. The guarantee is the one in 5.2: no repeats and no gaps without concurrent writes.

6.5 Counts

Discovery declares count as "exact" or "estimated". With count=true, the response MUST add total and, if the number is approximate, "total_estimated": true. On a collection that declares count, count=false is the same as leaving it out, and any value other than true or false MUST give invalid_parameter. On a collection that does not declare it, and on any server without this profile, count with any value, false included, MUST give unsupported_parameter (5.3). total MUST count only the items the client can see that the request selects (5.2), also when it is estimated; with a to-many filter, items of the collection, not related items (6.1).

7. writes Profile

Profile URI: https://w3id.org/restep/1/writes. Status: stable. Writes that can be retried without duplicating and that do not overwrite each other. Caching is a profile of its own, cache.

7.1 Retry without duplicating

POST /orders
Idempotency-Key: "8e03978e-40d5-43e8-bc93-6894a57f9324"
  • Every non-idempotent POST, including actions declared "idempotent": false, MUST accept the Idempotency-Key header, except as below for requests without credentials: a Structured Fields String without parameters (RFC 9651); two keys are the same only when their values are equal character by character. A malformed key MUST give 400 bad_request, with an errors entry whose header is Idempotency-Key. On other methods than POST, the server MUST ignore the header: unlike the draft, which also mentions PATCH, Restep’s merge-patch PATCH is already idempotent (5.7). This section defines the header’s syntax and meaning for Restep on its own: it follows the IETF draft (14.2, revision 09) where they agree, and does not depend on that draft advancing or staying as it is.
  • A key belongs to one principal (2), not to a token, and one target (method and path, compared after percent-decoding, without the query): a retry with a renewed token still finds it. Two requests are the same when they share key, principal and target, their query parameters are the same after percent-decoding (the order of parameters with different names does not count, as in 5.2; that of repeated values of one name does, since the API may give it meaning), and their bodies are equal as JSON values (2); for an upload (5.1), their bytes and media type are the same. So the same key on the same path with another query is a different request, and gets 422 idempotency_mismatch.
  • Requests without an authenticated principal all count as one anonymous principal and share its keys. The server MAY refuse Idempotency-Key on such requests. If it does, it MUST declare it in discovery with "anonymous": false in idempotency (missing means true), and MUST answer with 400 bad_request, with an errors entry whose header is Idempotency-Key and whose code is unknown, before any effect, a POST without credentials that carries the header and to which this section would otherwise apply; a POST to an action declared "idempotent": true MUST ignore the header instead, and store nothing under it (11.1). While anonymous is false, a resource that requires the key MUST NOT require it of requests without credentials. A 401 would send the client to get credentials that the resource does not need. Otherwise this section applies to them as to any principal. A client SHOULD generate each key from a random source, with at least the 122 random bits of a version 4 UUID, and SHOULD NOT use it for another request: whoever guesses or learns a key can take it first under the same principal or, with the same request, get its stored response (13.5).
  • The server MUST keep each key for at least 24 hours from the first request, and SHOULD declare how long in discovery ("idempotency": {"ttl": 86400}, in seconds). After that, the key counts as new.
  • If the same request arrives again, the server MUST return the same status as the first time, and its Location if it had one, without repeating the effect, and SHOULD add Idempotent-Replayed: true, a header that Restep defines (the IETF draft does not) and whose value is the token true (RFC 9651, section 3.3.4). Its body MUST NOT give more than a read would give now: the server filters the stored body, or returns the current representation, so that it reveals nothing the principal can no longer read; if the principal can no longer read the item at all, it gets the same status without a body. A replay whose body is not the item’s current representation, such as the stored body of a 200 to an action, MUST NOT carry Content-Location, ETag or _etag, which would make a client take it as its new copy (11.1): what 7.2 requires of a 200 to an action applies to the original response. Headers such as Date may differ. A replay, and the 409 request_in_progress for the same request while the first one is still running, take the place that 5.4 gives them: after the checks that keep the principal from learning what it may not, its current permission on the target included, and in place of 428, 412 and the errors that depend on the stored state. Neither evaluates If-Match, If-None-Match or a 428 requirement: a replay answers as above even if they no longer hold, or if its target no longer exists, whether the first request deleted it or another did. With a failed If-Match and a stored 2xx, RFC 9110 (section 13.1.1) allows this for a state-changing request that has already succeeded; with a failed If-None-Match, which section 13.1.2 answers with 412 in any method but GET and HEAD, or with a stored status that is not 2xx, Restep departs from RFC 9110 on purpose, so that a replay always gets the response of the first request. A different request under the same key evaluates them as usual, and its 422 idempotency_mismatch is not reported while 428 or 412 applies (5.4).
  • If the server fails after the effect and before storing the response, a retry with the same key MUST NOT repeat the effect: the server records both atomically, or recovers as if it had.
  • A request that was rejected before it ran (a 4xx such as 422, or a 5xx that left no effect) MAY be left unstored; then it does not use up the key, and the client can fix it and retry with the same one. A request that had an effect MUST be stored.
  • The same key with a different request MUST give 422 idempotency_mismatch, also while the first one is still running. The same request while the first one is still running MUST give a 409 problem with code request_in_progress, which SHOULD carry Retry-After, unless the server waits for the first one to finish and then answers it as a replay, which it MAY do; the client MAY send it again with the same key, after Retry-After when present and within the key’s lifetime (5.7). A resource that requires the key MUST give 400 idempotency_key_required without it, except to a request without credentials where anonymous is false (above).
  • A core-only server does not know the header and ignores it. Clients MUST NOT rely on Idempotency-Key unless the server announces writes.

7.2 Optimistic concurrency

  • Each item has a strong item ETag: the ETag of its full representation, without fields or include, computed as if _etag were absent; its other _ members count. It is the ETag of the representation this principal reads, so where that representation depends on the principal (_actions, fields it cannot read), so does the item ETag, and If-Match is evaluated against the writer’s. A GET of the full item without content coding MUST carry it, and servers MUST NOT use a weak validator (W/) for it. With a content coding (gzip), the ETag header MUST differ from the item ETag or be weak, as RFC 9110 (sections 8.8.1 and 8.8.3.3) requires; _etag still carries the item ETag.
  • Where the item has localized fields (3), each language is a representation of its own: the item ETag MUST differ by language (5.6), and, for a PATCH or a DELETE, the server selects the representation against which it evaluates If-Match among those of every language it offers: the one whose current item ETag the field lists, if any, and otherwise the one that Accept-Language selects (RFC 9110, section 3.2, leaves that selection to the server). So If-Match MUST succeed with the current item ETag of any language the server offers, a client that reads in one language and writes in another does not get 412, and a lost update is still detected.
  • Every response whose body is a single item’s representation, to a read or to a write, MUST carry the item ETag in _etag, whatever its content coding and its parameters: a proxy or a CDN that compresses the response may weaken or change the ETag header without the server knowing, and the client still needs a validator for If-Match. Its value is the entity-tag exactly as the ETag header would carry it, quotes included, so the client copies it unchanged into If-Match: "_etag": "\"a1b2c3\"" is sent as If-Match: "a1b2c3".
  • A single item’s response with fields or include is another representation: its ETag header MUST change whenever anything in it changes, included items too, while its _etag stays the item ETag, so the client can write without another read.
  • An item in a collection response SHOULD carry in _etag the item ETag of the version it represents, when it supports PATCH or DELETE, so a client can write without reading it first. In a collection that declares sync (10), such an item MUST carry it on every page, whatever the query parameters, with GET or QUERY (11.4).
  • In a collection that declares reusable_ids (5.1), the item ETag of an item MUST differ from those of every earlier item that had its id, so that an If-Match read from one of them gives 412.
  • PATCH and DELETE MUST evaluate If-Match against the item ETag as RFC 9110 says (lists, *, strong comparison): if it does not match, 412 precondition_failed. They MUST also evaluate If-None-Match (lists, *, weak comparison): if it matches, 412 without applying the write. On an item that does not exist, such as one another write has just deleted, they MUST give 404 (410 retired only after a retirement, 5.5), whatever the preconditions say: the same request without them would get that 404, so RFC 9110 (section 13.2.1) has the server ignore them, and 5.4 does not let a 412 be reported while a 404 applies. The exception is a PATCH to a free id in a collection that declares upsert (5.1), which would create the item: there If-Match fails with 412, and If-None-Match: * lets it create.
  • A POST to a collection, or to an action on it, has the collection as its target, and Restep gives a collection no ETag to write against. The server MUST evaluate If-Match and If-None-Match there as RFC 9110 says (sections 13.1.1 and 13.1.2): * depends on whether the collection has a current representation for this principal, so If-Match: * succeeds and If-None-Match: * gives 412 when the principal can read the collection, whether or not its GET carries an ETag, and the other way round when it cannot; a list of entity tags is compared with the ETag that a GET of the collection without parameters would carry for this principal; where it carries none, no listed tag matches, so a list in If-Match gives 412 and a list in If-None-Match lets the request go on. A client SHOULD NOT send them on such a POST; to create an item only if its id is free, it chooses the id (5.1).
  • On an action on an item, the preconditions are evaluated against the item and its item ETag. This is a convention of Restep: in HTTP the target of POST /orders/2001:cancel is the action’s own URI (RFC 9110, section 15.3.5). So a 200 to an action that changed the item, other than a replay (7.1), MUST carry Content-Location with the item’s path and ETag with its new item ETag or, with a content coding, a tag that differs from it or is weak, as above (RFC 9110, sections 8.7 and 8.8.3); its _etag carries the new item ETag in either case, and a 204 to an action carries no ETag: a client that needs the validator reads the item.
  • Evaluating If-Match and applying the write MUST be atomic with respect to other writes to the same item.
  • A resource MAY require If-Match; without it, it MUST answer 428 precondition_required. Starting to require it is a breaking change (5.5), unless it starts when the collection declares reusable_ids (5.1), which is one already: there only If-Match tells one item from an earlier one with the same id (5.7). In a collection that declares upsert (5.1), If-None-Match: * on a PATCH meets that requirement: the PATCH creates the item if its id is free, and gives 412 if it is not. Only * meets it: an If-None-Match with a list of entity tags does not, so a request that carries one without If-Match gets 428, in the order of 5.4.

Computed fields. A field the server computes from other data is part of the representation, so the item ETag changes when it changes, even if nobody wrote the item. Whether it belongs there depends on how it changes. One that changes rarely, or that whoever writes the item relies on (whether a book has a copy free, for whoever reserves it), belongs in the representation: a 412 when it has changed is correct, as with inherit, and sending it back changed gives 422 read_only (5.1). One that changes all the time (seconds until a sale ends, readers online) does not: it would make every write fail with 412 and every page change for sync. A state that depends only on the date is better given as the data it depends on and a named filter (expected_at and filter[late]) than as a field that changes on its own.

7.3 Minimal responses

With Prefer: return=minimal (RFC 7240), writes MAY respond without a body: 201 with Location, or 204. When the item it created or changed still exists (not after a DELETE), such a response MUST carry that item’s ETag in ETag, since it has no _etag, except the 204 of an action (7.2), and SHOULD carry Preference-Applied: return=minimal. A replay (7.1) of such a 201 MUST NOT carry ETag, even when the item still exists: the stored one may no longer be current, and the current one was not produced by this request; a client that needs a validator reads the item at Location. A write response that a cache may store MUST carry Vary: Prefer (RFC 7240, section 2). By default they return the representation.

8. cache Profile

Profile URI: https://w3id.org/restep/1/cache. Status: stable. Reads that a cache can store, revalidate and invalidate. It requires only core, so a read-only API can announce it without building the idempotency store of 7.1.

  • Every response to a GET, HEAD or QUERY, errors included, MUST carry an explicit Cache-Control.
  • A response that depends on credentials is private or no-store, as 5.1 requires of every server. A response that does not MAY be public, such as a discovery document served without credentials (4.2).
  • A successful GET of a full item or a singleton (5.9), without fields or include, MUST carry an ETag. If the server also announces writes, it is the item ETag of 7.2 when the response has no content coding, and differs from it or is weak when it has one (7.2); otherwise it MAY be weak. Any ETag the server gives MUST change whenever anything in the representation it validates changes, included items too, and a strong one MUST differ between content codings or be weak (7.2).
  • If-None-Match on a GET or HEAD MUST be evaluated as RFC 9110 says (lists, *, weak comparison): when it matches, the server MUST answer 304. On a QUERY, when it matches, the server MUST answer 412, as RFC 9110 (section 13.1.2) requires of every method other than GET and HEAD and RFC 10008 (section 2.6) keeps; to revalidate a QUERY result, a client SHOULD send a conditional GET to the equivalent resource that the response gives in Location, when it gives one (RFC 10008, section 2.7). On writes, If-None-Match belongs to 7.2.
  • A successful response to a GET SHOULD carry Cache-Groups (RFC 9875) naming every item it represents, included ones too, and, for a collection, the collection itself, so a cache can drop the lists an item enters or leaves. A 2xx response to a HEAD SHOULD carry the groups the GET would. A successful response to a write that committed changes (for a batch, the outer response, covering every committed operation) SHOULD carry Cache-Group-Invalidation naming every item it changed and their collections, even without a body. Group names are opaque and per origin; the item’s path ("/books/7") and the collection’s ("/books") are the obvious choice. Group names MUST NOT reveal to the client what it could not otherwise learn (5.4): a response names by its path only an item the client can see, and invalidates the others through a group it may know, such as their collection’s. A cache may or may not honour them, and RFC 9875 only guarantees 32 groups per field, of 32 characters each, so a long page or a long id may not get every item invalidated. RFC 9875 (section 2) gives the order of groups no meaning; a server that trims the list to stay within 32 groups SHOULD keep the collection’s group and drop those of items.
  • An item that declares unsafe actions SHOULD be served with Cache-Control: no-cache and an ETag: an action changes it through another URI, and HTTP requires a cache to invalidate only the action’s URI; it may also invalidate the item’s, named in Content-Location, but need not (RFC 9111, section 4.4). Sending Cache-Group-Invalidation (above) is still only recommended.
  • A response with localized fields carries Vary: Accept-Language (5.6).

9. relations Profile

Profile URI: https://w3id.org/restep/1/relations. Status: stable. The shape of relationships is set in section 3, and how they are written in 5.1, so any server follows them; this profile adds declarations and expansion.

  • Discovery MUST declare each relationship in relations, with its target collection in to (a list, when it can point to several: see section 3), "many": true if it is to-many, and "include": true if it can be expanded.
  • include=author MUST fill that object with the full item; with a relationship to several collections, the item of the collection its type names. Dotted paths (include=author.publisher), like the relationship paths of JSON:API, are allowed up to the declared include_depth (1 if not declared). A relationship that is not declared or not expandable, or a path deeper than include_depth, MUST give unsupported_parameter.
  • Through a relationship to several collections, a path in include or fields (fields=showcase.title) applies in the targets where it exists and is ignored in the others; one that exists in none of them MUST give unsupported_parameter in include and invalid_parameter in fields, as a field that does not exist does (6.3).
  • If the client cannot see the related item, the object MUST stay with only id (and type, and href where 3 or 5.9 requires it).
  • When the target is a subcollection, each relationship object carries href (3): a client builds the path of an ordinary target from its collection’s path and the id (5.1), but the item of a subcollection also needs its parent’s id, which href carries. {"id": "3", "href": "/books/7/reviews/3"}.
  • When the server also implements query, fields accepts dotted paths (fields=title,author.name); a dotted path whose relationship is not in include MUST give invalid_parameter.
  • Relationships with many items (a book’s reviews) SHOULD be subcollections, such as /books/7/reviews, declared with a path template and a parent (4.2) and following core and, if announced, query. The relationship that leads to one MAY carry the same template in its path, as reviews does in the example of 4.2. Such a relationship MUST appear only in discovery, where the template is enough to reach the subcollection; the parent’s representation MUST NOT carry it. A relationship to an individual item of a subcollection still carries href (above). A to-many list embedded in a representation MUST NOT be paginated: if it can grow without bound, it SHOULD be a subcollection.
  • To filter by a relationship, discovery declares the dotted path in filter: filter[author.id]=3; through a to-many relationship, with quantifier (6.1): filter[reviews.rating][ge]=4.

GET /books/7?include=author&fields=title,author.name
{ "id": "7", "title": "La niebla de Portugalete", "author": { "id": "3", "name": "Inés Arriaga" } }

10. sync Profile Experimental

Profile URI: https://w3id.org/restep/1/sync. Status: experimental (1.2). Keep a local copy of whole collections up to date without downloading everything again, as the /changes methods of RFC 8620 (section 5.2) do. It requires query.

  • A collection is synced when it declares sync in discovery, as an object, {} if it has nothing to say. A collection MUST NOT declare sync unless the server announces this profile in profiles; without it, a sync declaration means nothing and no collection is synced. Only synced collections answer :changes; on any other, :changes MUST give 404 not_found. Every synced collection MUST support GET, MUST NOT have a required filter (6.1), and MUST declare id in filter with in. The rest of this section is about synced collections.
  • Collection responses MUST carry state: an opaque string that changes whenever anything the client can see in the collection changes. It reflects that client’s view: an item it stops being allowed to see counts as destroyed. A filtered response carries the same state as the whole collection; a client that keeps a copy of the collection traverses it without filters.
  • state and :changes cover every item the client can see, those a default filter hides included (6.1): an item that a default filter starts to hide, such as one archived, is updated, not destroyed. A client that keeps a copy MUST traverse the collection turning off every default filter and with no other filter, and reload changed items the same way but with filter[id][in] as its only filter.
  • A copy is in one language: state does not depend on Accept-Language, but a change of a translation is a change of the items that show it. A client that changes language MUST traverse the collection again before treating its copy as current; :changes gives only identifiers and does not depend on the language.
  • Clients MUST NOT interpret or build a state; they MAY compare two states for equality. The same considerations as for cursors apply to it (6.4, 13.9).
  • Every page of a traversal MUST carry the state of its first page, the request without cursor (the server can keep it in the cursor). A client MUST use it as since for its next sync: changes made during the traversal show up there.
  • A traversal MUST NOT miss items: every item that existed, and matched the request, when the first page was served, and does not appear in :changes since that state, appears in some page. Offset cursors do not guarantee this; keyset cursors or a snapshot do; with a sort by a to-many path (6.2), only a snapshot does.
  • GET /books:changes?since=<state> returns the identifiers created, updated and destroyed since that state. The response MUST carry since, state, has_more, created, updated and destroyed. Each identifier MUST appear in at most one list, picked by what the client could see between since and the returned state (an item that does not exist cannot be seen). These rules cover the items that changed, or whose visibility to the client changed, in that window:
    • an item it could see at since and cannot see at state MUST be in destroyed;
    • an item it can see at state MUST be in updated if it could see it at since and it changed or stopped being visible in between, and in created if it could not see it at since;
    • an item it cannot see at either end MUST be in destroyed if it could see it in between, and MUST NOT appear otherwise;
    • in a collection that declares reusable_ids (5.1), an id destroyed and created again within the window MUST be in created: it is another item.
    An item it could see at both ends that did not change MAY be in updated. If the server cannot reconstruct what the client could see in the window, it MUST answer 410 state_expired; whether it can MUST NOT depend on the existence of an item concealed from the client (5.4). Clients MUST treat created and updated alike, fetching the item and replacing their copy, and MUST ignore an id in destroyed that they do not have. (Where JMAP would leave out an item created and destroyed within the window, Restep reports it in destroyed if the client could see it, so a client that saw it deletes it.)
  • If has_more is true, the returned state is intermediate: the client MUST call again with it until has_more is false before treating its copy as current. An intermediate state MUST be a point in the collection’s history, and each response MUST follow the rules above for its own window, from its since to its state, so consecutive responses report the changes in the order they happened: an item that the client stopped seeing and saw again is in destroyed in one and in created in a later one; an id created again in a collection that declares reusable_ids is another item. (RFC 8620, section 5.2, whose intermediate states need not follow history, forbids that order instead.)
  • :changes covers the whole collection: filters and the other query parameters MUST give unsupported_parameter there; $api_version is not a query parameter: where an extension defines it (5.5), :changes accepts it as any other request does, and where none does, it gives unsupported_parameter there as every reserved parameter the server does not implement does (5.3). A missing since, or one the server did not issue (a tampered one), MUST give invalid_parameter, as a tampered cursor does (6.4). Keeping a filtered view in sync is outside this version.
  • The client fetches the changed items with GET /books?filter[id][in]=7,12. An id in created or updated that this reload does not return, because the item was deleted or stopped being visible after the state, is removed from the client’s copy, and the client goes on from the state of :changes: if the item comes back, a later call reports it.
  • The server SHOULD keep changes for at least 7 days and SHOULD declare how long in the collection’s sync.retention (seconds). If it can no longer compute the changes, it MUST answer 410 state_expired, and the client reloads the collection.
  • The action name changes is reserved for this profile (11.1).
  • The server MAY offer notifications over Server-Sent Events at the path declared in events, relative to the API root like the path members of discovery (2); that response MUST carry Cache-Control: no-store. It MAY limit the streams a principal keeps open, and MUST answer 429 rate_limited, with Retry-After, to one over that limit: Restep extends 429, which RFC 6585 (section 4) defines for requests over time, to streams open at once. An EventSource does not reconnect after it (HTML Standard, section 9.2.3), so the application opens the stream again. Each event says which collections have a new state, naming each by its key or, for a subcollection, by its path relative to the API root with the template expanded ("/books/7/reviews"); the data itself is fetched with :changes. The server MUST NOT send an event for a change that does not change that principal’s state, or the rhythm of events would reveal activity it cannot see.
  • Events are hints: clients MUST tolerate repeated, merged and reordered events. On opening the stream, and on every reconnection, a client MUST call :changes for each collection it keeps, from the last state it applied, and MUST advance that state only after applying the changes; an event alone never advances it. Servers MUST NOT rely on Last-Event-ID to resume.
  • The server SHOULD send an SSE comment at least every 15 seconds, as the HTML Standard (section 9.2.7) advises, to reduce idle timeouts. It MUST close the stream when the credentials that opened it stop being valid, and MUST answer 401 to any reconnection that carries invalid credentials, an automatic EventSource one included. After that, the application MUST wait for valid credentials before opening the stream again.

  "created": ["51"], "updated": ["7", "12"], "destroyed": ["34"] }

GET /events            Accept: text/event-stream
event: state
data: {"books": "s131"}

11. Extensions

Each extension is announced in extensions and has its own profile URI (https://w3id.org/restep/1/batch…). What each one requires, and whether it is stable or experimental, is in 1.2.

11.1 actions Extension

Status: stable. Operations that are not create, read, update or delete, following AIP-136 in the colon before the name, though not in its camelCase names nor in putting every safe action on GET.

When an operation is an action. An action is for what a plain write cannot say. A transition of a status field is an action when it has rules or consequences, such as POST /orders/2001:cancel, with _actions saying when it applies, and a PATCH of the field when it has neither. A reversible state with data of its own (who, when, why) is a pair of actions, :reserve and :release, whose data are fields of the item, with _actions saying which one applies. Something with data of its own that can happen many times, such as an order’s reminders, is a subcollection. A change of state with effects outside the API (below) is an action, so that it can be declared and refused on its own.

POST /orders/2001:cancel       on an item
POST /books:import             on the collection
GET  /orders/2001:preview      a safe action declared with "method": "GET"
  • Each action MUST be declared in the actions of its collection or of a singleton (5.9), with safe and idempotent; a collection’s actions also carry on ("item" or "collection"), and a singleton’s carry no on and are used at {path}:{name} (POST /me:verify_email). An action declared "safe": true MUST also declare "idempotent": true, since safe methods are idempotent (RFC 9110, section 9.2.2). idempotent promises the same effect, not the same response (5.7): to get the first status and Location again, a client sends Idempotency-Key where the server applies 7.1 to the request, which an action declared "idempotent": true need not do (11.1); the body of a replay gives no more than a read would now. Action names follow 3 and SHOULD be snake_case; a collection MUST NOT declare an action named changes, which sync uses.
  • An action uses POST unless its declaration says "method": "GET", which only safe actions MAY do. Servers MUST also accept the colon encoded as %3A, and MUST write it as is in href, _actions and every other link they build, so that a cache sees one URI.
  • The declaration MAY carry a description, effects (below) and: if the action uses POST, an input schema (4.3); if it uses GET, params; if it is safe, output. A GET action has no body, so it MUST NOT declare input.
  • params declares the query parameters of a GET action, as an object whose keys are their names (3) and whose values carry a type from 4.2, and MAY carry "list": true, "required": true and a description: "params": {"with": {"type": "string", "required": true}}. A list parameter takes values separated by commas, read after percent-decoding; its values cannot contain commas, encoded or not. A client that needs one sends the input in the body of a POST action declared safe. A scalar string parameter is not split and may contain commas. A value of an integer or number parameter, and each element of a list one, follows the rule of filter operands (6.1): the number grammar, exponent included, and, for integer, a zero fractional part. A required parameter that is missing, a value that does not match its type, an empty list and a repeated parameter MUST give invalid_parameter; a parameter the action does not declare, unsupported_parameter (5.3). A GET action without params is one declared with "params": {}: it takes no query parameters.
  • output is the schema of a safe action’s result (2): its 200 then carries a JSON object of that shape, which is not a representation of the item or collection it is asked on. It MUST NOT carry _etag or _actions; a client updates no copy with it, and HTTP caches it by its own rules, with its own ETag header. GET /books/7:compare?with=12 → {"fields": [{"name": "pages", "from": 320, "to": 352}]}.
  • A POST action MUST treat an empty body, with or without Content-Type, as {} sent as application/json; so a client that has nothing to send can send either. A non-empty body follows 3.
  • The response to an unsafe action on an item or a singleton MUST be its representation (200), a new resource (201 with Location) or nothing (204). An unsafe action on a collection has no representation of its own to return, so its response MUST be 201 with the Location of what it creates (an import, a report) or 204, never 200. The response to a safe action MUST be its result (200) where it declares output; otherwise its representation (200) or nothing (204) on an item or a singleton, and 204 on a collection: a safe action creates nothing, so it never answers 201. A HEAD to a GET action gets the same status and headers without content (RFC 9110, section 9.3.2). A 200 that carries the item’s representation after the action changed it carries Content-Location and ETag as 7.2 says. Publishing a version, for instance, is POST /books/7:publish, answered with 201 and the Location of the new version (Appendix D).
  • After a successful unsafe action on an item, a client MUST NOT use a stored copy of that item without revalidating it, unless the response carried the item’s representation with Content-Location, which is then its new copy.
  • A request to an action that its collection or singleton does not declare, or that is declared on the other kind of resource, MUST give 404 not_found, as any resource that does not exist; a declared action with another method MUST give 405 with Allow, except HEAD on an action declared with "method": "GET", which 5.1 requires. A declared action that the item’s current state does not allow MUST give 409 conflict, with a reason if the API has one (5.4); one that this principal may not use, 403 or 404 (4.2).
  • With writes, an action declared "idempotent": true MUST NOT reject a request because it carries a well-formed Idempotency-Key: it MAY ignore it, since repeating the action is already safe (5.7), or apply 7.1 to it; one that ignores keys ignores a malformed one too, instead of giving 400; to a request without credentials, where idempotency declares "anonymous": false, it ignores the key and stores nothing under it (7.1). A client MAY send one to any POST action.
  • effects lists the consequences of an unsafe action that a person may want to approve first: destroys (it deletes data that cannot be recovered), external (it reaches outside the API: an email, a message, a call to another system) and charges (it costs money). A safe action MAY declare only charges. "pay": {"effects": ["charges", "external"]}; "cancel": {"effects": []}. Without effects, a client treats an unsafe action as having all three and a safe one as having none; if effects contains a value it does not know, it treats the operation as having all three effects (destroys, external and charges), also when the action is declared safe; and so it treats an unsafe method of a collection, of its items or of a singleton (5.9) that method_effects or item_method_effects does not declare (other than DELETE, which has ["destroys"]) or declares with a value it does not know (4.3). A client that asks a person before unsafe operations SHOULD ask before any declared effect, and also before an operation declared with [] unless it trusts the server (13.1), in which case it MAY go ahead without asking. The declaration authorizes nothing (4.3).
  • A collection MAY declare a safe collection action named new, used with GET (GET /orders:new), whose result gives the starting values of a new item for this principal and an effective schema: {"values": {…}, "schema": {…}}. The effective schema MUST only restrict the collection’s create schema (4.3), never widen it, and is advisory: the response to the POST still decides. A collection with several forms tells them apart with a declared parameter of the action. A collection’s action named new MUST be this one: declared on the collection, safe and with "method": "GET".
  • A representation MAY list in _actions the actions available in its current state, so clients do not duplicate business rules. A server that lists them SHOULD give "_actions": {} where none is available, since an absent _actions means they were not computed. Every action it lists MUST be declared in the actions of its collection or singleton, with the same on, where it has one, and the same method, so the client knows whether it is safe and idempotent:
{ "id": "2001", "status": "paid",
  "_actions": { "cancel": { "method": "POST", "href": "/orders/2001:cancel" } } }
  • Where the variants of a collection (2) support different methods or actions, the API SHOULD split them into separate collections, with polymorphic relationships carrying type where needed, or list in each item’s _actions what it supports; an action that an item’s variant does not support gives 409 conflict.

11.2 batch Extension Experimental

Status: experimental (1.2). Several operations in one request, in order, with references to the results of earlier ones, like the back-references of RFC 8620 (section 3.7). They are sent to the path declared in batch.path.

POST /batch
{ "atomic": false,
  "operations": [
    { "id": "a", "method": "POST", "path": "/orders", "body": { "book": { "id": "7" } } },
    { "id": "b", "method": "POST", "path": "/orders/{a#/id}:pay",
      "headers": { "idempotency-key": "\"pay-2001\"" },
      "body": { "amount": { "$ref": "a#/total" } } } ] }

→ 200
{ "results": [
    { "id": "a", "status": 201, "headers": { "location": "/orders/2001" }, "body": { … } },
    { "id": "b", "status": 200,
      "headers": { "content-location": "/orders/2001", "etag": "\"o2001-v2\"" }, "body": { … } } ] }
  • Each operation MUST have an id, unique in the batch, a method, a path and, optionally, headers (with lowercase names) and body. An operation id MUST be a non-empty string without #, { or }, so that a reference (below) has one reading. Each operation MUST follow the same rules as if it were sent alone, with the exceptions of this section.
  • An operation’s path MUST start with / and is relative to the API root (2), like the path members of discovery; it MUST NOT carry a scheme, an authority, a fragment or dot-segments (., ..), and MUST name a resource of Restep (5.9) other than the event stream (10). A value that a reference (below) inserts into it MUST be a string that is a valid id (3) or an integer, and the server MUST check this rule again on the path that results; otherwise the operation gets 422 invalid.
  • Its headers MAY carry only if-match, if-none-match, idempotency-key and prefer, plus content-type and accept-language, which the server MUST ignore: an operation’s body is already JSON and the batch request carries Content-Type: application/json (3), and the batch’s Accept-Language applies (below). Every operation acts for the batch’s principal, with the batch request’s credentials, Origin and Accept. The server MUST NOT apply the Prefer, If-Match or If-None-Match of the batch request itself to any operation.
  • A reference is <id>#<JSON Pointer> into the response body of an earlier operation, where the pointer uses the JSON string form of RFC 6901 (section 5), not its URI fragment form: in literal braces inside path (%7B is not one), where the value MUST be inserted percent-encoded as a path segment (RFC 3986) and the pointer MUST NOT contain { or } (otherwise the operation gets 422 invalid; for such keys, use $ref in the body); or as {"$ref": …} in place of a body value. This $ref is not a JSON Reference: its value is <id>#<pointer>, not a URI. An object whose only member is $ref is always a reference, so a client that puts into a batch body data it did not write MUST make sure that no object in it has $ref as its only member.
  • A body that is not a valid batch, a repeated operation id or one that breaks the rule for operation ids above, a reference to an operation that does not come earlier, a nested batch, a path that, with each reference taken as a valid id, breaks the rule for paths above, or a header outside those six MUST give 400 bad_request before any operation runs. 5.4 applies to the batch request as a whole before any operation runs; once the batch is accepted, it applies to each operation on its own, subject to the 424 not_executed rules below. More operations than max_operations MUST give 413 content_too_large (Restep reads “content too large” in operations, not only in bytes), which the server MAY give without validating the operations: a batch that is both too long and invalid can get 400 or 413 (5.4).
  • A batch that passes these checks, the atomic check below and those of any request (credentials, content type, rate limits, 7.1) MUST get 200 with one result per operation, in order, each with its own status, headers and body; an error result is a problem object. This is the only exception to “no error inside a 200” (5.4).
  • With "atomic": true, either all operations take effect or none does. If one fails, it carries its error and every other operation MUST get 424 not_executed, including those that ran and were rolled back. A server that cannot roll back one of the operations (an external payment, an email) MUST reject the atomic batch with 422 invalid before running it.
  • Without atomic, each operation applies on its own. An operation that refers to one that failed MUST get 424 not_executed (RFC 4918, section 11.4); one whose pointer finds nothing, or whose referenced value is not valid where it goes, 422 invalid.
  • With writes, the batch itself MAY carry Idempotency-Key; then the whole batch follows 7.1, including its rule for requests without credentials where anonymous is false.
  • Another exception: the texts and localized fields (3) of each new result (5.6) follow the batch’s Accept-Language, and an operation’s own is ignored; a replayed result (7.1) keeps its own. Content-Language and Accept-Language in Vary go on the batch response, not in each result’s headers: Vary includes Accept-Language only if some new result can vary by language, and Content-Language is left out unless every result with language-picked texts shares one.

11.3 filter-expr Extension Experimental

Status: experimental (1.2). A filter as an expression, in the spirit of AIP-160:

GET /books?filter=price <= 20 AND (category = "novela-negra" OR rating >= 4.5)

As in 6.1, the example shows the query unencoded for readability. On the wire, spaces, quotes, < and > are percent-encoded (RFC 3986, section 3.4); the server reads the expression after percent-decoding (5.2).

  • Comparators =, !=, <, <=, > and >=, which map to eq, ne, lt, le, gt and ge; AND, OR, NOT and parentheses. Fields by name or dotted path (3); a path segment may contain - (name.es-mx). AND, OR, NOT, true, false and null are never field names in an expression: a field so named cannot be used in one. Values: strings in double quotes (with \" and \\ as the only escapes), numbers, true, false and null. field = null and field != null map to the null operator.
  • NOT binds tightest. AND and OR MUST NOT be mixed at the same level without parentheses: a AND b OR c MUST give invalid_parameter. AIP-160 gives OR precedence over AND, most languages do the opposite; Restep asks for parentheses so nobody guesses. Juxtaposition (a b, which AIP-160 treats as a fuzzy AND) MUST give invalid_parameter too: Restep requires parentheses, which AIP-160 says should not be required.
  • A field or operator not declared in filter MUST give unsupported_parameter. Comparisons MUST follow 6.1, absent and null values, collations and fields the principal cannot read included; a number compared with a decimal field is read as an exact decimal.
  • A named filter (6.1) goes into an expression by its name, as it goes in brackets in filter[…]: a switch alone (available), and one with a type as name = value (search = "machado"), which is not a comparison with a field; any other comparator on it MUST give unsupported_parameter. A named filter MUST select the same items in an expression as in brackets. prefix and contains are functions: prefix(title, "La"), contains(title, "niebla").
  • A path declared in filter with quantifier that goes through a to-many relationship (6.1) forms a group in brackets: reviews[rating >= 5 AND reader.id = "3"] MUST match when, and only when, some related item the principal can see matches the whole expression; NOT reviews[…] when none does; and every one, as NOT reviews[NOT (…)]. Inside the brackets, paths are relative to the related item, and each MUST be declared in filter with its full path (reviews.rating). Two groups on the same relationship are independent: reviews[rating = 5] AND reviews[reader.id = "3"]. Such a path goes only inside brackets: reviews.rating = 5 MUST give invalid_parameter, so nobody guesses whether two comparisons on it are about the same related item.
  • A field whose value is a list of scalars, declared with quantifier (6.1), is compared directly, without brackets: formats = "pdf" MUST match when, and only when, some element of the list is "pdf". Each comparison on the list is independent of the others: formats = "pdf" AND formats = "epub" matches an item that has both formats. Unlike the group that 6.1 forms from filter[…] parameters on the same list field, comparisons are not tied to the same element: brackets are needed only to tie conditions to the same related item, and go only after a to-many relationship.
  • It cannot be combined with filter[…] in the same request: that MUST give invalid_parameter. The one exception is filter[name]=false, which turns off a default switch (6.1): which items are traversed is not part of the expression’s logic. In the body of a QUERY, the expression goes in $expr beside those switches (11.4).

11.4 query-method Extension Experimental

Status: experimental (1.2). For queries that do not fit in a URL, the QUERY method (RFC 10008): safe, idempotent and cacheable, with the query parameters in the body.

QUERY /books
Content-Type: application/json

{ "filter": { "price": { "le": "20" }, "category": { "in": ["novela-negra", "poesia"] } },
  "sort": ["-rating"], "fields": ["title", "price"], "limit": 10, "count": true }
  • Collections that accept it MUST announce it with Accept-Query: application/json (RFC 10008) in their responses to GET and HEAD.
  • The body is a JSON object with the same members as the reserved parameters: filter as an object of fields and operators (or, with filter-expr, the expression as a string, or an object with the expression in $expr and, beside it, only "name": false members that turn off default filters, as filter[name]=false does beside an expression in 11.3: {"$expr": "price <= 20", "available": false}; any other member beside $expr gives invalid_parameter), sort, fields and include as lists, limit as a number and count as a boolean. Values use their JSON type, and in takes a list, so its values can contain commas. A named filter goes as "name": value, with a value of its type, or "name": true if it is a switch, and "name": false to turn off a default filter (6.1); false on any other switch, or any other value, gives invalid_parameter. An unknown member MUST give unsupported_parameter.
  • A QUERY MUST select, order and count items as the GET with the same parameters in the query string would, which Restep treats as its equivalent resource (RFC 10008, section 2.2), with the same errors; a value that a query string cannot carry, such as an in value with a comma, is compared as the body gives it. Its links follow the next point, and a matching If-None-Match gives 412 (8). The URL MUST NOT carry reserved parameters other than cursor; the server MUST answer one with unsupported_parameter.
  • In the response, next carries only cursor, which here overrides the rule of 6.4 that keeps the other parameters. For the next page, the client MUST send a body with the same filter and sort to the next URL, and MAY change limit, fields, include and count (6.4); the server MUST answer a filter or sort that is not equal as a JSON value (2; an absent member, {} and [] are the same) with invalid_parameter on cursor.
  • Caches that store QUERY responses use the body and its media type as part of the key (RFC 10008, section 2.7); many CDNs do not do that yet.

11.5 oauth Extension

Status: stable. How a client finds out where to get a token for the API. It defines neither authentication nor authorization: it ties the OAuth 2.0 Protected Resource Metadata (RFC 9728) to the API root. A server that does not announce it authenticates as it sees fit.

GET /api/                         (the API root: https://example.com/api/)
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://example.com/.well-known/oauth-protected-resource/api/"

GET https://example.com/.well-known/oauth-protected-resource/api/
{ "resource": "https://example.com/api/",
  "authorization_servers": ["https://auth.example.com"],
  "scopes_supported": ["books:read", "books:write"] }
  • A server that announces oauth MUST have an API root with the https scheme and no fragment, since RFC 9728 (section 1.2) admits no other resource identifier.
  • The server MUST serve the metadata at the URL that RFC 9728 (section 3.1) forms from the API root: the well-known suffix goes between the host and the root’s path, which keeps its final slash; only when the root is the bare host does its slash go. Under https://example.com/api/ it is https://example.com/.well-known/oauth-protected-resource/api/; under https://api.example.com/, https://api.example.com/.well-known/oauth-protected-resource.
  • In that document, resource MUST be the API root, character for character, final slash included, and authorization_servers MUST list at least one issuer: RFC 9728 makes it optional, but without it the client has nothing to discover. scopes_supported SHOULD be present. Each authorization server describes itself with RFC 8414 or OpenID Connect Discovery; Restep requires nothing of it.
  • The metadata is not a resource of the API: 4.1, 5.1, 5.2 and 5.3 do not apply to it. It MUST be served as application/json without requiring credentials, so it never gives 401, and it SHOULD carry Cache-Control: public with a max-age, and SHOULD be served with Access-Control-Allow-Origin: *, since it needs no credentials.
  • When the API root requires credentials, its 401 MUST carry the absolute URL of the metadata in resource_metadata (RFC 9728, section 5.1), in at least one challenge: Bearer, DPoP or any other the API accepts. RFC 9728 (section 3.3) makes clients discard metadata found that way whose resource is not the URL they requested, so on any other resource the server MUST NOT point resource_metadata at the root’s metadata. The root’s metadata is for the exact root URL, without a query. A client that gets a 401 without resource_metadata forms the metadata URL from the root.
  • OAuth errors keep their Restep codes: the challenge carries the OAuth error and the body the Restep code. invalid_request is 400 bad_request; invalid_token, and invalid_dpop_proof and use_dpop_nonce (RFC 9449), are 401 unauthenticated; insufficient_scope is 403 forbidden. A 403 for a missing scope MUST carry error="insufficient_scope" in its challenge (RFC 6750, section 3.1) and SHOULD name the scope needed in scope, unless that would reveal permissions the client must not know. A resource whose existence is concealed still gives 404 (5.4), and that 404 MUST be indistinguishable, headers included, from that of a resource that does not exist: its WWW-Authenticate, if it carries one, is the same generic challenge, with realm and without error or scope (RFC 6750, section 3).
  • The server MUST refuse a token meant for another resource server (RFC 9700, section 2.3). A client asks for a token restricted to this API by sending its resource in the resource parameter (RFC 8707).
  • With DPoP (RFC 9449) the challenge uses the DPoP scheme. A retry with a fresh DPoP proof comes from the same principal and is the same request for 7.1.
  • A server that allows cross-origin requests (5.8) SHOULD list WWW-Authenticate in Access-Control-Expose-Headers (and DPoP-Nonce, if it uses DPoP nonces), or a browser client cannot read them. EventSource cannot send Authorization, so a browser client reads the event stream of 10 with fetch; the server SHOULD NOT accept tokens in the query string: RFC 6750 (section 2.3) lets a resource server support them, but RFC 9700 (section 4.3.2) forbids clients to send them.

11.6 inherit Extension Experimental

Profile URI: https://w3id.org/restep/1/inherit. Status: experimental (1.2).

A value can apply to an item without being stored in it: a product’s tax rate is its own if it has one; otherwise its category’s, its parent category’s or its store’s; and if none has one, a default. Restep expresses this with two fields and a declaration in discovery. The rules of this section apply only to the fields that inherit declares and to the subcollections that declare inherit_items (below). A collection MUST NOT declare inherit or inherit_items unless the server announces this extension in extensions.

  • The effective field (tax_rate) gives the value that applies, already resolved. It is read-only.
  • The own field (tax_rate_own) gives the item’s own value, or null if it has none and inherits. It is the one that is written.

There are two because a single field would have to show the value that applies and also store the one that is written. A client that sends back what it read (5.1) would then turn every inherited value into an own value: the value does not change, but the item stops following its source and nobody notices. With two fields, writing the value you see and deciding whether it is inherited are different operations on different fields.

GET /products/7
→ 200
ETag: "p7-v3"
{ "id": "7", "name": "Zucchini", "category": { "id": "4" },
  "tax_rate": "10",
  "tax_rate_own": null,
  "_inherited": { "tax_rate": { "from": { "href": "/categories/2" } } } }

Declaration. In the collection object, the keys of inherit are the effective fields:

"products": {
  "path": "/products",
  "relations": { "category": { "to": "categories" } },
  "inherit": {
    "tax_rate": { "own": "tax_rate_own", "from": ["category"], "default": true,
                  "description": "The product’s tax rate; without its own, its category’s." } } },
"categories": {
  "path": "/categories",
  "relations": { "parent": { "to": "categories" }, "store": { "to": "stores" } },
  "inherit": { "tax_rate": { "own": "tax_rate_own", "from": ["parent", "store"], "default": true } } }
  • own names the own field. Both fields MUST be top-level, and either of one of the scalar types of 4.2, or objects whose members are of those types, or lists; they cannot be id, a relationship, a language map or a localized field (3): in those, null or the merge patch already mean something else (3, 5.1).
  • from lists, in order, the relationships this step inherits from. Each MUST be to-one and declared in relations (9), even if the server does not announce that profile, and its target collection MUST have a field with the same name as the effective one. If that field is also declared in its inherit, the chain continues: so a category inherits from its parent category to whatever depth is needed, without dotted paths.
  • "default": true says there is a default at the end of the chain and the effective value is never empty. The value is not published: changing it is a change of data, not of discovery.
  • description explains the field as in 4.3.
  • combine says how the own value and the inherited one combine: "replace", the default, takes the own value whole when it is not null, objects and lists included; "fields", only for objects of scalars, resolves each member on its own, one level deep, so a member that the own object lacks or sets to null takes the inherited member.
  • switch names a boolean field of the item itself and its initial value: "switch": {"field": "takes_chain_hours", "initial": true}. While that field is false, nothing comes from above for that item. Turning it off makes no inherited value or item its own. A POST that leaves the field out gives it the initial value.
  • A client MUST treat a field of inherit, or an inherit_items declaration, whose declaration carries a member it does not know and whose name does not start with x- as not inherited (4.2).

Resolution. The effective value MUST be the own value, if it is not null; otherwise the effective value of the item linked by the first relationship in from that has a link, if that value is not null; otherwise the default; and with no default, the field has no value (3). With "combine": "fields", that resolution applies to each member of the object. While a switch is off, no relationship in from counts as a link: the effective value MUST be the own value, otherwise the default, and with no default the field has no value. A link that would create a cycle (a category that ends up as its own ancestor) MUST give 422 invalid.

Reading.

  • When the representation carries the effective field, it MUST carry it resolved and with its usual type. The own field carries its value or null.
  • The item MAY explain the origin in _inherited: an object whose keys are the effective fields present in the representation that do not come from the own field. If it carries it, it MUST name them all, so an effective field not in _inherited has its own value. With fields (6.3), _inherited only covers the fields in the response. Each value is one of these:
    • {"from": {"href": "/categories/2"}}: the absolute path (3) of the value’s actual source, not of the immediate parent. In the example, category 4 has no own value and category 2 does.
    • {"from": "default"}: it comes from the default.
    • {"from": "hidden"}: it is inherited, but the client cannot see the source. The server MUST NOT give the path of an item the client cannot see, just as a relationship is left with only id (9), nor of one whose existence it does not reveal (5.4).
    • With "combine": "fields", {"fields": {"monday": {"from": {"href": "/chains/1"}}}}: each inherited member names its own source, with the forms above; members that come from the own object are not listed, and an effective field whose members all come from it is not in _inherited.
    Other forms are reserved for minor versions: a client MUST treat a from it does not know as "hidden".

Writing. The own field is an ordinary field and follows the merge patch with no exceptions. It is the only one that changes inheritance:

PATCH bodyEffect
{"tax_rate_own": "4"}It gets its own value, 4
{"tax_rate_own": "10"}, equal to the inherited oneIt gets its own value, 10: the same value, but it no longer follows the category
{"tax_rate_own": null}Deletes the own value and inherits again
No tax_rate_ownNothing changes

The effective field is read-only (5.1), so writing it never changes anything: a PATCH with its current value is ignored, and another value gives 422 invalid with a read_only entry, whose detail SHOULD name the own field. It is compared rather than always ignored so that a client trying to change it learns that nothing changed, instead of getting a misleading 200.

  • In a POST, an absent or null own field makes the item start out inheriting, and the effective field follows the same rule, compared with the value that would result.
PATCH /products/7
{ "tax_rate": "4" }
→ 422 application/problem+json
{ "type": "https://w3id.org/restep/1/errors#invalid", "title": "Invalid data", "status": 422, "code": "invalid",
  "errors": [ { "pointer": "/tax_rate", "code": "read_only",
                "detail": "“tax_rate” is the effective value; write “tax_rate_own”." } ] }

Sending back the effective fields as read changes nothing. This is the rule of 5.1 applied to inheritance: a PATCH with the effective fields as read leaves the item as it was: they match and are ignored, the own fields it leaves out are not touched, and _inherited is ignored like any _ member. A client that does not know the own field exists can leave it out safely, and the only mistake it can make is writing the effective field, which gives the 422 above and tells it where to write. This works because in a PATCH what is absent is not touched: with a PUT, which Restep leaves out (5.1), leaving out the own field would delete it and the item would inherit again without anyone asking.

PATCH /products/7                the effective field as read, without the own field
{ "id": "7", "tax_rate": "10" }
→ 200, the item unchanged and the same ETag

Stale reads. If the source changes between the read and the write (category 2 moves to 5 %), the "tax_rate": "10" the client sends back no longer matches. With If-Match it gives 412, because the product’s ETag has already changed (7.2); without it, 422 with read_only. Either way it fails without changing anything, where a stale ordinary field would silently overwrite someone else’s change.

When a source changes. When a category’s value changes, the effective value of every item that inherits from it changes, though nobody touched them. For the client those items have changed, so what other sections already say applies to each:

  • its ETag changes (7.2: it is that of the complete representation), also when only _inherited changes, for instance if category 4 sets as its own the same value it inherited;
  • with sync, its collection’s state changes and :changes lists them (10);
  • with a shared cache, the write to the source SHOULD also invalidate the groups of those items and of the collections that can contain them (8).

This forces the server to store the effective values or to propagate each change to every descendant. It is the main cost of declaring inherit.

Filters and sorting. With query, filtering and sorting by the effective field compare the value the client sees: filter[tax_rate][eq]=10 gives those worth 10, inherited or not. Those that inherit are asked for with filter[tax_rate_own][null]=true, with no new operators, if that filter is declared (6.1).

Inherited items. A subcollection MAY declare inherit_items: {"from": ["store.chain"], "key": ["publisher"], "switch": {"field": "takes_chain_preferences", "initial": true}}. from names, in order, to-one relationships of the parent item through which the same subcollection of the source is found; key lists the fields that identify an item across levels. The subcollection then MUST list its own items and the inherited ones, already resolved: an own item with the same key as an inherited item replaces it, and once that own item is deleted the inherited item is listed again; without key, inherited and own items add up. Each inherited item MUST carry _from with the absolute path of its source item ({"href": "/chains/1/preferences/ed-y"}) and an id of its own, different from its key; it is read-only there: a PATCH or DELETE on it MUST give 409 conflict (5.1). switch works as for a field (above): while it is off, the subcollection MUST list only its own items. An inherited item that stops being listed, or comes back, is a change of visibility for sync (10).

Some cases stay outside inherit: a condition that is not inheritance (a cap, a date) is a read-only computed field; a chain that depends on who asks goes in the path or in a safe action with params (11.1); and rows inside versioned documents are a relationship to the source and a safe action GET …:effective that gives each row with its origin.

Evolution. Adding inheritance to a new value, or to a field that was already read-only, is compatible: the own field and the declaration are added. Turning into an effective field one that could be written until now is not, because it would reject writes that used to be accepted (5.5): it takes a major version, or retiring the field and adding the pair under other names.

12. Conformance

There are two classes of conformance, and each is claimed per profile and per extension:

  • A server conforms to a profile or extension when it meets every requirement on servers marked MUST or MUST NOT in sections 1, 3, 4 and 5 and in that profile’s or extension’s section, and announces the ones it requires (1.2). A server that announces a profile or extension claims conformance to it.
  • A client conforms to a profile or extension when, in every use it makes of it, it meets every requirement on clients marked MUST or MUST NOT in the same sections. Every client uses core; a client that never sends a QUERY need not meet the rules of query-method. A library, a proxy or an agent that talks to a Restep API is a client, and a proxy is also a server to its own clients.

Requirements marked SHOULD, SHOULD NOT or MAY do not decide conformance. Section 13 and the appendices add no requirements.

12.1 Servers

These are the checks a conformance checker runs on a server; which of them restep-check runs today is listed on its page. Some need what a checker is given rather than what it can observe: credentials for two principals, a session with cookies, or a way to provoke 429, 503 or two writes that race. They are marked “given”; a checker runs each only when it is given that, and reports it otherwise as not run, not as passed.

core

  • Every collection responds with {items, next}, with next present.
  • Without concurrent writes, following next until null returns every item exactly once.
  • An item that does not exist gives 404 as problem+json with code: "not_found". The path of an item with its id changed (another case, a leading zero) gives 404 unless an item has that id, and so does the path with a trailing slash (/books/7/); the path with a character of the id percent-encoded (/books/%37) answers as the item’s own, and /books/%FF gives 404.
  • The discovery document’s restep matches the grammar of 1.1. Where a response carries several service-desc links, the first of their targets that is a discovery document of Restep 1 is this one. Under the same Accept-Language, its body is equal as a JSON value with and without credentials (unless it answers 401 without them) and, given two principals, between the two. Served only with credentials, it carries Cache-Control with private or no-store.
  • Every member the server adds to discovery outside Restep starts with x-, and discovery carries no shared_cache. Every key of collections, singletons, filter, named_filters, relations, actions, params, language_maps, localized, local_times, collations, reasons and inherit, and every field that discovery declares, matches the grammar of names, or is a dotted path: names joined by ., whose last segment can be a language tag (3).
  • A POST to a collection that supports it, with a JSON body sent as text/plain or as application/x-www-form-urlencoded (where the collection does not declare upload with that media type), without Content-Type, or as application/json; charset=latin1, gives 415 unsupported_media_type and creates nothing, and so does an empty body without Content-Type; with application/json; charset=UTF-8 or charset="utf-8" it is accepted, and an empty body with application/json gives 400 bad_request. Every 2xx with a JSON body carries Content-Type: application/json.
  • Every next and href in a body is an absolute path or an absolute URI whose scheme is https or the API root’s, and every absolute URI in a Location or Link header has one of those schemes. In those links, [ and ] are percent-encoded and the colon before an action’s name is not.
  • Where a collection does not declare id_from, a POST with an id gives 422 invalid. Where it declares "client", one without id gives 422 with a required entry at /id; with "client" or "either", an id with a character outside 3 gives 422 with an entry at /id, and repeating a POST that succeeded or, where it does not declare reusable_ids, reusing the id of a deleted item, gives 409 conflict with a taken entry at /id and creates nothing. Where a collection declares reusable_ids, a POST with the id of a deleted item creates it again, and an If-Match with the old item’s ETag gives 412. Where it declares upsert, a PATCH to a free id creates the item with 201, If-None-Match: * on an existing one gives 412, and so does If-Match: * on a free one; where it also requires If-Match, a PATCH with If-None-Match: * to a free id creates the item instead of giving 428.
  • Each declared singleton answers GET with a JSON object, and POST, PUT and DELETE with 405; where it declares methods, its Allow agrees with them. Its relationship objects carry href, and include on it gives unsupported_parameter. One with a parent gives 404 under a parent item that does not exist, and its path starts with its parent’s.
  • A subcollection declares parent, and its path template has variables with distinct names that match ALPHA *( ALPHA / DIGIT / "_" ) and is its parent’s path followed by /, its last variable, / and one or more literal segments.
  • Every unimplemented reserved parameter, and every form 5.3 does not define (filter[a][b][c], fields[]), gives 400 unsupported_parameter, on every method, unless another applicable error is reported (5.4), such as the 404 not_found of a missing item. The same request with more than one fault, sent twice, gets the same code both times.
  • A method the server knows but the resource does not support gives 405 with Allow, and PUT does on every collection, item and singleton; HEAD works wherever GET does. Where discovery declares methods or item_methods, that Allow agrees with them and lists HEAD wherever it lists GET.
  • Where discovery declares status, GET and HEAD on it give 200 or 503 with Cache-Control: no-store, or else 401, 403 or 429, a 429 with Cache-Control: no-store.
  • Every invalid_parameter and unsupported_parameter names its parameter in parameter.
  • Where discovery declares a create schema, a POST that leaves out a property it requires gives 422, and one that leaves out a top-level property with a default creates an item with that value, which is valid against the property’s schema; where it declares a closed update schema, a PATCH with a member the schema does not allow, even a null one, gives 422, once the members 5.1 ignores are dropped.
  • Every error carries type, title, a status equal to the response’s, and a code from the table of 5.4 or http_ followed by the status; type is about:blank only where 5.4 allows it. A 428, and given a way to provoke them a 429, carry Cache-Control: no-store.
  • Every reason in a problem matches the grammar of names. If discovery declares reasons, every problem with a reason, also in batch results, carries a declared one with its code.
  • A PATCH with {"author": {"id": "4", "extra": 1}} changes the link, does not store extra and leaves both authors untouched, unless a declared update schema rejects it. A relationship to an id that does not exist gives 422 invalid with an unknown entry at its id, and an href to an item of a subcollection that is not the path of an item of the target collection gives 422 invalid with a format entry whose pointer is that href. Given a principal that cannot see the related item, sending back the relationship as read, with another field changed, succeeds.
  • Merge Patch follows RFC 7396 (an array or scalar replaced by an object loses its old content), except that relationship objects are replaced whole (5.1) and language maps left with no translations read as {} (3) and that, with inherit, deleting or changing an own field also changes its effective field (11.6), and a write that changes id gives 422; a patch that is a JSON value but not an object gives 422 invalid with an entry whose pointer is "".
  • A PATCH with an item’s read-only fields as read changes neither its body nor its ETag, if any; another value in id, or in a top-level property the client can read that its item schema marks readOnly directly in properties, gives 422 invalid with a read_only entry at its pointer, changing nothing.
  • An error requested with an Accept-Language the server does not offer, or a malformed one, gives the same code as without the header, never 406 or 400 because of it. Where the body of the discovery document or of an error changes between two Accept-Language values, both responses, the default language’s included, carry Vary: Accept-Language and, if they carry an ETag, different ones.
  • With Accept-Encoding: identity, the GET of an item gives the same body under any Accept-Language, except its localized fields; an item without them also gets the same ETag, with writes or cache. Given two principals that can read the same fields and whose stored language settings differ, the same request without Accept-Language gets the same body for both.
  • Given a way to provoke them: a 429 or 503 with a problem+json body leaves no effect, so repeating the request after Retry-After creates one item, not two.
  • A 401 or 403, other than those of the service status (4.4) and the OAuth metadata (11.5), carries Cache-Control with private or no-store. Given credentials: where a GET made with them gets another status or body than the same request without them, or, given two principals, with the other’s, its response carries Cache-Control with private or no-store, also when cache is not announced.
  • Given a session with credentials that a browser attaches on its own (cookies, HTTP authentication, a client certificate): a POST, PATCH or DELETE with them and an Origin the server does not allow, an action with an empty body included, gives 403 forbidden and has no effect, also where the server sends Access-Control-Allow-Origin: *.
  • A request over a limit the server does not declare, such as an in list of thousands of values, gives the full result, invalid_parameter naming the parameter, 413 or 414; never part of the result.
  • In an item, every field of language_maps is an object of strings with lowercase keys. Where PATCH is supported: an uppercase key gives 422 invalid with a format entry at /name/ES; deleting an existing translation with null keeps the others, and putting it back restores it; {"name": null} leaves {}.
  • Where a collection has localized fields, discovery declares default_language; every response with them carries Content-Language and Vary: Accept-Language; sending one back in another language changes nothing, and another value gives 422 with a read_only entry.
  • No response repeats a member name in an object.
  • A response with private or no-store carries no field aimed at shared caches, such as CDN-Cache-Control, that allows storing it.
  • A collection whose methods leave out GET declares no filter, named_filters, sort, count or sync.
  • A collection with upload answers a file of a declared media type with 201 and an item with _content, one of an undeclared type with 415, also a JSON body where it declares no create and its media_types do not admit application/json, through a wildcard too, and a file over max_size with 413; where it declares create, a JSON body creates an item, and, where its media_types also admit application/json, through a wildcard too, it declares "multipart": true; where it does not, a JSON body that its media_types admit, through a wildcard too, is a file. A body of a +json type, such as application/ld+json, is never the creation of an item from JSON. A multipart/form-data body gives 415 where upload does not declare "multipart": true, even when media_types admits it, and, where it does, a file part without filename is read as the file.
  • Every value of effects, method_effects and item_method_effects is a known one, and a safe action declares only charges.

Evolution

  • Whatever discovery lists in deprecations with a kind that retires a whole resource (collection, singleton, action, version) carries Deprecation with the notice’s announced instant in the responses 5.5 lists and, once the notice has a sunset date, Sunset with that date, which is not earlier than announced; the responses that other notices concern carry neither. After its sunset it responds as 5.5 says. Every notice has a known kind and an announced instant in whole seconds that does not change between two reads, and its sunset, if any, is in whole seconds too.
  • Comparing the discovery documents of two deployments of the same version, nothing declared disappears unless it was listed in deprecations and its sunset has passed.

query

  • Each declared filter returns only items that match it, comparing by the declared type (decimals exactly).
  • An undeclared filter field, operator or sort key gives unsupported_parameter; a value of the wrong type, a repeated parameter, or a duration value with years or months, invalid_parameter.
  • An operand of an integer or number filter follows the number grammar of JSON: 2e1 filters as 20, and +20, .5, 020 and 0x14 give invalid_parameter; on an integer field, 20.0 filters as 20 and 20.5 gives invalid_parameter. An operand outside the range of values the field can hold is compared as a number, exactly, and one over a request limit gives invalid_parameter, never being replaced by another value, such as an infinity or zero.
  • A + in the query is read as a space: filter[f]=a+b and filter[f]=a%20b give the same page.
  • A declared named filter applies without operators; with an operator it gives unsupported_parameter, and a switch with a value (false included, unless it declares default), or a typed one without a value or with one that does not match, invalid_parameter. None shares its name with a key of filter. A default filter applies unless filter[name]=false turns it off, and never to reading an item; a required filter that is missing gives invalid_parameter naming it.
  • No operator outside the list of 6.1 is declared; prefix and contains only on string fields and translations, never on id; no ne or nin on a path with quantifier. No boolean filter declares operators other than eq, ne and null, and the id filter declares none of lt, le, gt and ge.
  • sort orders and breaks ties stably across pages. A string field not listed in collations filters and sorts by code points; no key of collations is id, nor a field other than a string filter, an enum of strings listed in sort, a localized field or a translation.
  • No field that is a list and no path through a to-many relationship is declared in filter without quantifier, unless null is its only operator, none goes through two to-many steps, and no path that ends in the id of a subcollection’s item is declared in filter or sort.
  • Repeating a parameter of next percent-encoded in another way, or reordering parameters, gives the same page.
  • limit above max_limit gives invalid_parameter, and limit on a collection without max_limit gives unsupported_parameter; a tampered cursor, or one reused with other filters, another sort or another collection, after turning off a default filter, or under another language where the collection has localized fields, gives invalid_parameter; changing limit, fields, include or count between pages keeps it valid.
  • No field of language_maps, nor any path that ends in or goes through one, is declared in filter or sort; a declared field.tag filter or sort reads only that key, and items without it are absent.
  • fields returns only those fields, plus id and members starting with _; fields=id is accepted. fields or include on a POST or PATCH gives unsupported_parameter.
  • Given a principal that cannot read a field in some items: a declared filter on it matches none of them except with null set to true, a sort on it puts them last, and total counts only the items that principal can see.
  • count=true adds total when count is declared; count=true and count=false give unsupported_parameter when it is not.
  • Filters on the same to-many relationship match the items where one related item matches them all, each item once; null set to true on the relationship negates its group, also where it is declared with quantifier: filter[formats][in]=epub,pdf&filter[formats][null]=true returns the items with neither format. With other filters of the group, it negates them all at once: no related item matches all of them. Two null filters on the same group, such as filter[reviews][null] and filter[reviews.id][null], give invalid_parameter, even with the same value.
  • nin, prefix and contains return only the items that match, by code points where the collation is "codepoint"; an empty operand of prefix or contains gives invalid_parameter.
  • A duration filter compares fractions of a second exactly; a localdatetime filter compares without a zone.

writes

  • Repeating a POST with the same Idempotency-Key after the first one has finished returns the same status and Location and creates nothing new; given a principal that has lost access to part of the item, its body reveals none of it.
  • The same key with another body, or on the same path with another query, gives 422 idempotency_mismatch; a malformed key, or one with parameters, gives 400 bad_request on a POST, other than to an action declared "idempotent": true that ignores keys.
  • The ETag of a full item, asked for with Accept-Encoding: identity, is strong, and with gzip it differs from it or is weak; every response whose body is one item, with or without fields and under any Accept-Encoding, carries that item ETag in _etag, which two reads of an unchanged item give alike; a write ignores _ members.
  • In a collection that declares sync and whose items support PATCH or DELETE, every listed item carries in _etag the ETag its own GET returns with Accept-Encoding: identity for the same version.
  • If-Match with an old ETag gives 412, also with a JSON body that would otherwise get 422 (with a body that is not JSON, 400 or 412, 5.4), and a list that contains the current one succeeds; given a way to make two writes race with the same If-Match, one of them gets 412. If-None-Match with the current one, weak or strong, gives 412 to a write and does not apply it.
  • If-Match with an invented entity tag on a POST to a collection gives 412 and creates nothing, and If-Match: * there succeeds where the principal can read the collection.
  • A PATCH or DELETE with If-Match on an item that has just been deleted gives 404, not 412.
  • A write with Prefer: return=minimal answered without a body carries the item’s ETag, unless it deleted the item or answered an action with 204; the replay of such a 201 with the same Idempotency-Key carries none.
  • The same request sent again while the first one is still running gives 409 request_in_progress or, once the first one finishes, its response; never a second effect.
  • Where a non-idempotent POST is accepted without credentials, the same request with the same Idempotency-Key and no credentials either is replayed as for any principal or, where discovery declares "anonymous": false in idempotency, gets 400 bad_request with an entry for the header, with no effect; a resource that requires the key does not give idempotency_key_required to a request without credentials there.
  • A 200 to an action that changed the item carries Content-Location with the item’s path and its new ETag; its replay with the same Idempotency-Key, after another write to the item, carries neither, nor _etag, unless its body is the item’s current representation.
  • Where the item has localized fields, If-Match with its current ETag in another language succeeds.

cache

  • Every response to a GET, HEAD or QUERY, errors included, carries Cache-Control; given credentials, with them private or no-store (as in core).
  • The GET of a full item carries an ETag, and If-None-Match with it, weak or strong, gives 304 to a GET and a HEAD.

relations

  • Every field that discovery declares in relations is, where an item carries it, an object with an id or a list of them, also without include. One that can point to several collections carries type; one whose target is a subcollection carries an href that a GET answers with that item. No item carries a relationship whose path leads to a subcollection.
  • include on a declared, expandable relationship fills the object; on any other, unsupported_parameter. With query, a dotted path in fields whose relationship is not in include gives invalid_parameter.

sync

  • No collection declares sync unless profiles lists it. Every collection that declares sync supports GET, has no required filter and declares id in filter with in; :changes on one that does not declare it gives 404.
  • :changes reports, in the lists 10 calls for, the creation, update and deletion of an item since the previous state, and every page of a traversal carries the same state; deleting an item mid-traversal does not make the traversal miss another one. Where the collection declares reusable_ids, an id deleted and created again appears in created.
  • The response of events, where declared, carries Cache-Control: no-store. Given a principal over its limit of open streams, a new one gets 429 rate_limited.

actions

  • A POST action answers an empty body and {} alike; an undeclared action gives 404 not_found, and a declared one with another method 405 with Allow; every action in _actions is declared with the same method, and its href carries the colon as is; no action is named changes, every safe action is declared "idempotent": true, and a collection’s action named new is declared on the collection, safe and with "method": "GET". Actions of a singleton follow the same rules.
  • A GET action answers a parameter that its params do not declare, any parameter where it declares no params, with unsupported_parameter and a missing required one with invalid_parameter; an integer or number parameter takes 2e1 as 20 and answers +20 with invalid_parameter; the result of an action with output carries no _etag nor _actions; an unsafe action on a collection never answers 200; where a collection declares new, its effective schema adds no property to create and drops none of its required.
  • With writes, an action declared "idempotent": true does not reject a request for carrying a well-formed Idempotency-Key, with or without credentials, whatever idempotency.anonymous says.

batch

  • A repeated operation id, or one that is empty or carries #, { or }, a reference to a later operation, a nested batch, a path with a scheme, an authority or dot-segments or to the event stream, or a header that 11.2 does not allow, gives 400 bad_request and runs nothing; more operations than max_operations give 413; a batch with both faults gets either. A value inserted into path that is neither a valid id nor an integer, such as ../admin, or a reference in path whose pointer carries { or }, gets 422 invalid.
  • With "atomic": true and one failing operation, every other result is 424 not_executed and nothing persists.
  • Without atomic, an operation that refers to one that failed gets 424 not_executed, and one whose pointer finds nothing 422 invalid.

filter-expr

  • An expression returns the same items as the equivalent filter[…] parameters; AND and OR mixed at one level without parentheses, juxtaposition, a path through a to-many relationship outside brackets, or an expression together with a filter[…] other than filter[name]=false, give invalid_parameter; an undeclared field or operator gives unsupported_parameter.
  • A named filter in an expression returns the same items as in brackets; a group path[…] returns the same as the bracket filters of 6.1 for that group, and NOT path[…] the items with no related item that matches; a comparison on a list field returns the items with some element that matches it, each comparison on its own.

query-method

  • A collection whose GET carries Accept-Query answers a QUERY as the equivalent GET, errors included; an unknown member, or a reserved parameter other than cursor in the URL, gives unsupported_parameter; the next page with another filter or sort gives invalid_parameter on cursor; and a QUERY with a matching If-None-Match gives 412.

oauth

  • The API root uses https and has no fragment. The metadata is at the URL RFC 9728 forms from the root, as JSON, without requiring credentials, with resource equal to the root and at least one authorization server.
  • The metadata does not give 401 (and, as a recommendation, carries Cache-Control: public).
  • If the root requires credentials, its 401 carries that absolute URL in resource_metadata; no 401 elsewhere points there.
  • Given a token without the scope a request needs: unless the resource’s existence is concealed, the request gets 403 with code: "forbidden" and error="insufficient_scope" in the challenge. Given a resource whose existence is concealed from a principal, its 404 carries the same headers as that of a resource that does not exist.

inherit

  • No collection declares inherit unless extensions lists it. Where one does and PATCH is supported: sending back with PATCH only an item’s effective fields as read, without its own fields, changes neither its body nor its ETag; {"tax_rate_own": null} leaves the effective value equal to its source’s and, if there is _inherited, it names it; and a different value in the effective field gives 422 invalid with a read_only entry at /tax_rate, changing nothing.
  • With "combine": "fields", _inherited names the source of each inherited member; with a switch set to false, nothing comes from above; in a subcollection with inherit_items, inherited items carry _from, a PATCH or DELETE on one gives 409 conflict, and once an own item with the same key as an inherited item is deleted, the inherited item is listed again.

12.2 Clients

These are the requirements on clients that the text makes, gathered by profile and extension. Each one is in the section cited, which prevails.

core

  • It does not treat as a Restep 1 discovery document one whose restep does not match the grammar or whose major version is not 1, nor assumes core only for one of another major version; for a restep value with a suffix, it does not assume conformance to any published version or to any other draft (1.1).
  • It does not use an experimental profile or extension unless restep declares a version whose text of it the client implements (1.2).
  • It ignores fields and _x_ members it does not know, and does not reject a response because of an enum value that its stored copy of discovery or of a schema does not list (3).
  • It does not dereference a link whose scheme is neither https nor the API root’s (3).
  • It sends the body of a POST to a collection, an action or a batch, and of a QUERY, with Content-Type: application/json (3).
  • It treats a response as a discovery document only if it is a 2xx whose body is a JSON object with a string member restep, and assumes core only after a 2xx without one or a 404, never after another error; of several service-desc links, it uses the first target that is a discovery document of Restep 1 (4.2).
  • It ignores members of the discovery document it does not know, does not fail because of a value it does not know, and does not use a filter, named filter, action, method or notice whose type, on, method or kind it does not know; it ignores only the operator it does not know, and a filter whose quantifier it does not know; and it counts a value of effects it does not know as all three effects, also in an action declared safe (4.2).
  • It sends its credentials for the API only to URLs on the API’s origin, and fetches schemas and documents on other origins without them (4.3).
  • It makes no request that is not safe, and sends no data to another origin, only because a text the API returned asks it to (4.3).
  • It does not assume a path for the service status, such as /health (4.4).
  • It does not send id in a POST to a collection whose id_from has a value it does not know, sends one where id_from is "client", and links an item of a subcollection by its href (5.1).
  • In a multipart/form-data upload, it sends a filename on the file part, a generic one such as file when the original is unavailable or private (5.1).
  • It follows next as is, changing only the parameters 6.4 lets it change, sends a literal + in the query as %2B, and does not assume any order of ids (5.2).
  • To copy a whole collection, it traverses it turning off every default filter and with no other filter (5.2).
  • It handles a code it does not know according to the class of the status, and a reason it does not know as its code (5.4).
  • It ignores a singleton whose path is a URI template without parent, or whose parent names no collection or singleton of the document (5.9).

query

  • It does not assume code points for a field whose collation is "server", nor reproduce that order or equality locally, and treats a collation value that is not a string, or that it does not know, as "server" (6.1).
  • It does not interpret or build cursors (6.4).

writes

  • It does not rely on Idempotency-Key unless the server announces writes (7.1).
  • It does not repeat a request automatically with the same Idempotency-Key after idempotency.ttl from its first attempt, or 24 hours where it is not declared (5.7).

sync

  • It does not interpret or build a state, and compares states only for equality (10).
  • It uses the state of a traversal’s first page as since for its next sync, and calls :changes again while has_more is true before treating its copy as current.
  • It treats created and updated alike, ignores an id in destroyed that it does not have, and removes from its copy an id of created or updated that its reload does not return, going on from the state of :changes.
  • It traverses the collection turning off every default filter and with no other filter, and reloads changed items with filter[id][in] as the only filter, also turning off every default filter; when it changes language, it traverses the collection again before treating its copy as current.
  • It tolerates repeated, merged and reordered events; on opening the stream and on every reconnection it calls :changes from the last state it applied, and advances that state only after applying the changes, never on an event alone.
  • After a 401 on the stream, it waits for valid credentials before opening it again.

actions

  • After a successful unsafe action on an item, it does not use a stored copy of that item without revalidating it, unless the response carried the item’s representation with Content-Location (11.1).

batch

  • Each operation has an id unique in the batch, not empty and without #, { or }, a method and a path; it makes sure that no object in a body it did not write has $ref as its only member (11.2).

query-method

  • Its QUERY URL carries no reserved parameter other than cursor, and for the next page it sends to the next URL a body with the same filter and sort (11.4).

oauth

  • It uses protected resource metadata only if its resource is identical to the identifier it formed the metadata URL from or, for metadata found through resource_metadata, to the URL it requested (RFC 9728, section 3.3), and it does not send access tokens in the query string (RFC 9700, section 4.3.2; 11.5).

inherit

  • It treats a from in _inherited that it does not know as "hidden", and a field of inherit, or an inherit_items declaration, whose declaration carries a member it does not know and whose name does not start with x- as not inherited (11.6, 4.2).

The other profiles and extensions (relations, cache and filter-expr) make no requirement of clients marked MUST or MUST NOT.

13. Security and privacy considerations

This section explains the risks of a Restep API and points to the requirements that address them, which are in the sections it cites. It adds no requirements. An API also has the risks of HTTP (RFC 9110, section 17), of JSON (RFC 8259, section 12), of problem details (RFC 9457, section 5) and of OAuth (RFC 9700); this section covers what Restep adds to them or decides about them.

13.1 Texts from the API are data

An agent that picks a tool from the discovery document puts descriptions, schema titles, reasons and error details into its prompt, and the data of each item with them. Whoever writes an item’s name, or controls the API, can write an instruction there. No agent built on a model can promise never to follow one, so 4.3 asks for what can be checked: a client makes no unsafe request, and sends no data to another origin, only because such a text asks it to, and an agent marks where the API’s text begins and ends in its prompt. A client also never grants an agent more permissions because a description asks for them. The names an API gives follow a grammar without spaces or punctuation (3), so they are safe as parts of tool names; an agent that adds a prefix (list_, get_), or whose tool registry ignores case or allows only shorter names, still has to resolve the collisions that result. A parameter in a problem is the parameter as received, which an attacker can write into a link: a client that shows it escapes it. A declaration of effects (11.1) from a server the client does not trust is not enough to skip asking a person: a server that wants an agent to act without asking only has to declare [].

13.2 Credentials and origins

  • A client sends its credentials only to URLs on the API’s origin (4.3). A discovery document can link schemas, documentation, a service status and, through href, resources on any origin; a next link could too. Fetched with the API’s credentials, any of them would hand those credentials to whoever controls the other origin.
  • Links use https or the scheme of the API root, and a client does not follow one with another scheme (3), so a discovery document cannot send it to file: or data:. A client that follows links from a server, such as an explorer or a hosted agent, still has to keep them away from its own internal network. A schema on another origin is controlled by that origin, so a client does not resolve its $ref elsewhere nor send its default without showing it to the user first (4.3).
  • A redirect to another origin is a URL on another origin. The Fetch Standard drops Authorization on such a redirect, but a library that copies headers by hand may not.
  • A token for the API is restricted to it: the server refuses one meant for another resource server (11.5), so a token leaked from another API does not work here.

13.3 Concealing existence

A 403 says that something exists. Restep lets an API conceal it instead:

  • a resource whose existence the API does not reveal gives 404, not 403, and a retired one 410 only if its existence is not concealed (5.4); a declared method, action or singleton that a principal may not use gives 403 or that 404 (4.2);
  • a relationship to an item the client cannot see keeps only its id (9), which still reveals that id, and its href and type reveal its parent’s id and its collection; an API that must conceal even that leaves the field out for that principal, as any field it cannot read (6.3);
  • a write that links an item the client cannot see gets the same 422 as one that links an item that does not exist (5.1), and the cache groups of a write name by its path only items the client can see (8);
  • a field that the principal cannot read and that discovery does not name is, for fields, a field that does not exist (6.3), and the events of 10 are sent only when that principal’s state changes;
  • an inherited value whose source the client cannot see says "hidden", never the source’s path (11.6);
  • in :changes, lists follow what the client could see, and whether the server answers 410 state_expired does not depend on concealed items (10);
  • a problem does not reveal what the principal could not otherwise learn (5.4).

The places where Restep reveals existence on purpose are the taken entry of a client-chosen id and the 404 of a PATCH in a collection that declares upsert (13.6). Response times can also tell an item that exists from one that does not; Restep does not ask for constant-time answers. An item’s ETag and a collection’s state may change when something the principal cannot see changes, which tells it that something did; a server that must conceal that computes them from what the principal can see.

13.4 Query oracles

A filter is a question about a value. If the server answered it with values the principal cannot read, whether an item is in the results would answer it, one bit at a time: filter[salary][lt]=50000, then 40000, finds a salary by bisection. Sorting gives the same answer by position, total by number, and filter[field][null] tells whether a value exists. The defences:

  • A filter or sort key on a field the principal cannot read in an item treats it as absent there, a dotted path through a related item it cannot see included; null, the order and total follow from that (6.1, 6.5). filter-expr follows the same rule (11.3). The 403 that 6.1 allows instead depends only on whether the field is readable in no item, which says nothing about values. A filter through a to-many relationship, its null and a sort by such a path count only the related items the principal can see (6.1), so they reveal nothing about the others.
  • A named filter compares nothing that discovery declares, so the server decides what it reads; it does not select by values the principal cannot read unless its description states the criterion (6.1). “Has at least one copy free” can be public while the stock of each store is not. A named filter that takes a value never compares it with values the principal cannot read, whatever its description says: “salary above the given amount” would find each salary by bisection.
  • An estimated total is still a count of what the principal can see (6.5): a server cannot take it from statistics of the whole table if some items are hidden from that principal.
  • A keyset cursor holds the sort values of the last item it returned; 6.4 asks that they not be readable (13.9).

13.5 Idempotency keys

A key belongs to a principal and a target (7.1). Requests without an authenticated principal share one, so every anonymous client shares one space of keys. Whoever guesses or sees another client’s key can then:

  • send a different request under it first, so that the victim’s request gets 422 idempotency_mismatch and never runs;
  • send the same request, if it knows the whole body, and get the stored response, with what the server added to it: an id, a timestamp, a secret or a link meant only for the sender;
  • learn from Idempotent-Replayed that someone already sent that exact request.

Clients generate keys from a random source and use each for one request (7.1). A server whose responses to anonymous writes carry anything only the sender may see can refuse keys without credentials: it declares so in idempotency and answers 400 (7.1), not 401, which would send the client after credentials the resource does not need. Keys travel in a header and end up in the same logs as the rest of the request. An administrator acting as a user is another principal (2), so the keys of one never replay the responses stored for the other. A replay never gives more than a read would give now (7.1): a principal that has lost access to part of an item does not get it back from a stored response.

13.6 Client-chosen identifiers

  • Collisions. Two clients that pick the same id get one item and one 409. The server requires a format with enough entropy, and clients generate it at random (5.1).
  • Taking an id first. If a client derives its ids from data (an email, an order number) or picks them in sequence, someone else can create an item with the id it will use, and the client’s own creation fails with 409.
  • The 409 as an oracle. taken answers the same whether or not the client can see the item, so it does not reveal what the client may see; it does reveal that the id is or was in use (5.1), and so does the 404 that a PATCH gets in a collection that declares upsert. With random ids, guessing one is impractical. With a format that can be guessed, it tells whether an item exists, so a collection whose items are concealed from some principals (13.3) requires a format that cannot be guessed (5.1). The server can check the format but not the entropy: a well-formed version 4 UUID may still have been derived from data, so the protection holds only as far as every client generates its ids at random.
  • Time in the id. Sortable identifiers (ULID, and UUID version 7: RFC 9562, section 5.7) carry the instant of their creation, and sequential ones carry how many items came before. Whoever sees the id learns them. This holds as well for the ids a server assigns.
  • Hashes of deleted ids. A server may keep only a one-way hash of the ids of deleted items (5.1). Where those ids were derived from personal data, the hash does not anonymise them: whoever holds it can recompute it for each candidate, such as every email address on a list. This does not apply to a collection that declares reusable_ids, which need not keep the ids of deleted items (5.1).

13.7 Browsers and cross-site requests

  • A browser attaches cookies to requests that pages of other origins start. A request with a non-simple method or media type needs a CORS preflight first, which the server can refuse; a POST sent as text/plain, application/x-www-form-urlencoded or multipart/form-data does not. So a server requires application/json on request bodies (3): a server that read a form as JSON would accept writes from any page.
  • An action with an empty body needs no preflight either (11.1). A server that accepts credentials a browser attaches on its own (cookies, HTTP authentication, client certificates) refuses every request that is not safe and carries them from an origin it does not allow, by Origin or Sec-Fetch-Site (5.8), which also covers browsers or paths the rules above miss; SameSite cookies are a second line. A form or a navigation from a page with Referrer-Policy: no-referrer sends Origin: null even to its own origin, which Sec-Fetch-Site tells apart. An upload that accepts multipart/form-data (5.1) needs no preflight either, so the Origin check of 5.8 is its only protection.
  • GET and HEAD have no effects (5.1), and an action can use GET only if it is safe (11.1), so a link or an image cannot write.
  • CORS with credentials names the origin (5.8). A server that copies any request’s Origin into Access-Control-Allow-Origin together with Access-Control-Allow-Credentials: true gives every site the user’s access.
  • A token in Authorization is not attached by the browser, so it is not exposed to cross-site requests; where a page keeps it is outside Restep.

13.8 Limits and abuse

  • Declared limits: max_limit (6.4), include_depth (9) and max_operations (11.2). Going over them gives invalid_parameter, unsupported_parameter and 413.
  • Undeclared limits, such as the values of an in list, the number of filters or the size of an expression, give invalid_parameter with the limit in detail, never a partial result (5.3). A client that syncs splits a long filter[id][in] into several requests, or uses query-method. Otherwise: 414 for a URL, 413 for a body, 429 for requests and event streams (10).
  • Some requests cost more than they look: an include multiplies the page by its depth, an exact count scans (a server can declare "estimated"), a filter may have no index, an atomic batch holds locks, and the idempotency store and the change log grow with ttl and retention. A server declares only what it can serve under load, and limits requests per principal and, for anonymous ones, per network address.
  • 429 and 503 with a problem+json body mean no effect, also when the API’s own gateway gives them (5.7), so a client that waits as Retry-After says, or backs off with randomness, does not turn a failure into a storm of retries.

13.9 Cursors and states

  • Clients do not interpret or build cursors (6.4). The server binds a cursor to its collection, filters and sort, and should bind it to the principal; it must when the cursor refers to results computed for that principal, such as a snapshot (6.4). Signing it shows when it was tampered with, and a tampered one gives invalid_parameter, never another page.
  • A cursor goes in the next URL, and URLs end up in logs, in browser history and in Referer. 6.4 asks that it not carry item data that can be read, such as keyset values in clear; encrypting it, or keeping the position on the server, avoids that.
  • A state of sync is opaque in the same way. The changes it leads to are computed for the principal who asks (10), so a state that one principal received and another sends lists only what the second one could see.

13.10 Caching

  • A shared cache that stored a response meant for one principal would give it to the next. Every server, with or without the cache profile, marks a response that depends on credentials private or no-store (5.1). RFC 9111 (section 3.5) already keeps shared caches from reusing responses to requests with Authorization, unless the response carries public, s-maxage or must-revalidate, and it does not cover those sent with cookies or a client certificate.
  • Vary: Authorization is not enough either, even where many clients share one credential, such as one per tenant: it relies on every cache honouring Vary on that field, which some do not, and for as long as the response is fresh nobody checks the client’s access. A field aimed at shared caches (RFC 9213), such as CDN-Cache-Control, makes a cache that recognises it ignore Cache-Control, so a response that depends on credentials does not carry one that would let it store it (5.1). A cache that stores a response under a URL the attacker chose (cache deception) is another reason to keep them private or no-store. A later minor version may allow an exception, declared with shared_cache, which this version reserves (4.2).
  • A 404 that conceals an item from one principal depends on credentials too, and so does its 200 for another.
  • The discovery document is the same for every principal (4.2), so it carries nothing that one principal may know and another may not. A shared cache may keep it only when it is served without credentials: one served only with credentials is private or no-store (4.2), or a cache would hand it to whoever has none.
  • Responses whose CORS headers depend on Origin carry Vary: Origin, which keeps a shared cache from giving one origin’s answer to another (5.8).
  • An item served with a max-age that an action changes can stay stale in a cache for that long: the action’s URI is not the item’s, and a cache need not invalidate the item’s URI (7.2, 8).
  • RFC 9110 (section 13.2.1) has a server evaluate preconditions only when the request would otherwise succeed, so a 304 never tells a principal without access that its ETag matches.

13.11 Tokens

  • The server refuses tokens meant for another resource server, and a client asks for one restricted to the API with a resource indicator (11.5, RFC 8707).
  • Tokens in the query string end up in logs, in history and in Referer: RFC 9700 (section 4.3.2) forbids clients to send them, and the server should not accept them; a browser reads the event stream with fetch, which can send Authorization (11.5). DPoP binds a token to a key the client holds (RFC 9449).
  • Only the root’s 401 points to the root’s metadata (11.5), because RFC 9728 has a client discard metadata whose resource is not the URL it asked for.
  • The metadata is served without credentials and lists the authorization servers and scopes; a 403 for a missing scope leaves scope out when naming it would reveal permissions (11.5).

13.12 Privacy

  • Discovery. Whoever can read the discovery document learns every collection, singleton, field that can be filtered, action and reason the API declares. It is the same for everyone (4.2): an API that cannot publish that much requires credentials to read it and serves it private (4.2), gives each tenant its own API root, or leaves out of its API what must stay unknown.
  • Errors. A reason says why the request failed, not anything about others; its declaration in reasons is public. detail and errors do not reveal what the principal could not otherwise learn, nor internal details (5.4). The service status served without credentials says only whether the API can serve (4.4).
  • Replays. Idempotent-Replayed says that the same request was made before under the same principal; for the anonymous principal, possibly by someone else (13.5).
  • Identifiers. Sortable and sequential ids reveal when an item was created and how many there are (13.6).
  • Queries in URLs. A filter such as filter[email]=… puts personal data in the URL, and so in logs. query-method puts it in the body instead.
  • Sync. destroyed lists the ids of items the client could see and no longer can; it reveals nothing about items the client never saw (10).
  • Language. The language a reader asks for is personal data that every request carries; a client that sends one tag rather than its whole list of preferences gives away less (RFC 9110, section 12.5.4). The server never takes the language of data from a setting stored for the principal (3).

Appendix A. Building forms from schemas

This appendix is not normative. It describes how a generic client can show a form for people from the schemas of 4.3, so that a server knows what its schemas will look like on screen.

  • The form for a new item comes from create; the form to edit one comes from update, filled with the item as read.
  • title and description are a field’s label and help, in the language of 5.6.
  • default is the value the form starts with. In create it is also the value the server gives a field left out (4.3), so leaving it unchanged and leaving the field out mean the same. A schema on another origin is that origin’s, so its default is shown before it is sent (4.3).
  • examples are shown as examples and never sent.
  • A oneOf of const values, each with its title, gives the choices and their labels.
  • maxLength and the other assertions, and the format annotation, say how to enter a value and let the client check it before sending; the server checks it again.
  • A readOnly field is shown and not edited; a writeOnly one, such as a password, is never filled with a value read.
  • A localized field (3) is shown and not edited; its language map is what the form edits.
  • A localdatetime (3) is a date and a time without a zone.
  • A relationship to a collection that declares upload (5.1) is a file control, limited to the relationship’s media_types.
  • Fields appear in the order of properties (4.3), where the client’s JSON parser keeps the order of members; otherwise the order is the client’s.
  • Layout, grouping and the controls used are the client’s.

A form whose starting values depend on the user or on the moment (today’s date, an inherited value) cannot come from discovery, which is the same for everyone; it comes from the collection’s new action (11.1).

Appendix B. Future work

This appendix is not normative. These cases are left out of Restep 1. None needs an incompatible change: each can come as an addition in a minor version (1.1) or as a new extension, once implementations show how it should work. Until then, an API that needs one solves it its own way, with names outside those Restep reserves (5.3).

  • Long-running operations: 202 Accepted and an operation resource (as in AIP-151), so each API does not invent its own. Deferred because the operation’s shape, its cancellation and how it meets Idempotency-Key and actions need an implementation first.
  • Keeping filtered views in sync (as JMAP’s queryChanges). Deferred because it needs to know which items a view held in the past, and sync itself is still experimental.
  • Small additions: named views ($view), a prev link for backward paging, batch results streamed as they finish, and reusing a QUERY through the Location that RFC 10008 already defines. Deferred because no case has needed them yet.
  • Signed messages (RFC 9421, with Content-Digest from RFC 9530 and keys published as JWKS, RFC 7517) for integrity between companies through intermediaries. Deferred because Restep 1 has no case that needs them: TLS covers the client and the server, and the events of 10 carry no data. A signature that expires would also give 401 to a retry before it reaches the idempotency store of 7.1.
  • An openapi extension: what an OpenAPI description of a Restep API says (a description per operation, request bodies, errors as problem+json) and how a checker holds it to the discovery document, which would still prevail. Deferred until the tools that translate between the two show what is worth requiring.
  • A text search of Restep’s own, with ordering by relevance, which would have to say how that order combines with sort and with cursors. Deferred because that combination is not designed; today a search is a named filter of type string (6.1).
  • The suffix operator, next to prefix and contains (6.1). Deferred because only one implementation has asked for it.
  • Choosing the language by a parameter, for links that must carry it, and a projection by language (languages, already reserved), so clients need not receive whole language maps. Deferred because Accept-Language covers the cases seen so far (5.6) and maps are small in them.
  • Sorting with language rules (CLDR collation): with code points, sort=name.es-es puts “Ñora” after “Zanahoria”, and "server" (6.1) does not let a client know the order. The values of collations other than "codepoint" and "server" are kept for collations named by Unicode tags (-u-co-, -u-ks-, RFC 6067). Deferred because databases implement those tags unevenly.
  • Text direction (dir, from the W3C’s Strings on the Web), which a language tag is not enough to infer. It would go in each field’s object in language_maps, never changing the type of the values. Deferred because no implementation has needed it yet.
  • Declaring in advance which operations require Idempotency-Key (7.1) or If-Match (7.2), instead of learning it from a 400 or a 428. Deferred because the error already tells a client what to do, and requiring either one is a breaking change anyway (5.5).
  • More inheritance (11.6): a language map translation by translation; a list of scalars as the union of its levels; locking a value from above; removing an inherited item; inherited items keyed inside a field of an item; and whether an own value that is absent when the item is created should inherit without saying so. Deferred until inherit itself has evidence: locking a value and removing an inherited item have had one case each.
  • Soft deletion: what a GET on a deleted item answers, restoring with the same id, and purging. The trash as a list is already a default filter that a client turns off (6.1), and in a collection that declares reusable_ids restoring is creating the item again (5.1). Under 10, an item that becomes visible again appears as created or updated, depending on the window. Deferred because, in other collections, restoring an id meets the rule that ids are not reused (5.1).
  • Units of measure: a fixed unit per field, declared in discovery with UCUM codes without changing the value’s type, unlike a unit that varies per item, which goes with its value as an amount goes with its currency (3). Deferred because no implementation has needed it yet.
  • Manual order: moving an item among others without rewriting all of them (fractional keys sorted by code point, or a :move action with before and after). Deferred because both designs work and neither has been tried in a Restep API.
  • Values as of a date ($as_of): separating when a value applies from when it was recorded, and what it does to validators, state and cursors. Deferred because it touches every profile.
  • Relationships, include and language maps on singletons, and singletons that may not exist, created and deleted by the client (5.9). Deferred because a singleton declares no relations to find a target from, and no API has yet needed one the client creates; a client ignores what it does not know in a singleton’s declaration (4.2), so they can come in a minor version.
  • More kinds of retirement: lowering include_depth or batch.max_operations, and withdrawing sync from a collection or events from the API (5.5). Today each needs a new major version. Deferred because no API has needed them; clients ignore notices of a kind they do not know (4.2), so new kinds can come in a minor version.
  • A version per experimental part: serving a new minor version of Restep while keeping the text of an earlier one for sync or batch, so a server need not move every experimental part at once and a client need not be updated for a part whose text did not change. Today the version in restep decides the text of every part (1.2). Deferred because it needs a new member of discovery and there is no second version yet to try it with; it is the first candidate after 1.0, because of sync.
  • How long the ids of deleted items are kept (5.1): today for as long as the collection exists, except in a collection that declares reusable_ids, which need not keep them, so a limit would only concern the others. A limit, such as sync.retention, would bound the cost, but once an id was forgotten the server could accept it again for a new item, while a client’s copy, kept for longer than that limit, still holds the old item under it. Deferred because it changes what sync can promise.
  • QUERY on safe actions (11.4), for an input that repeats and does not fit in a URL. Deferred because a safe POST action already takes it (11.1).
  • Computed fields on request, outside the full representation, its ETag and state, for values that change all the time (7.2). A field that was already in the representation cannot become one without retiring it (5.5). Deferred because how a client asks for them is not designed.
  • An extension for documents with versions: drafts, publication and aliases, once more than one API uses the pattern of Appendix D.
  • Resumable uploads for upload (5.1), once the IETF draft on them is an RFC.
  • Replacing a whole item, deleting what a request leaves out, which PATCH does not do outside lists (5.1). Deferred because PUT would erase the fields added after a client was written.
  • Variants declared in discovery (2), with operations per variant. Deferred because a schema with oneOf already tells them apart (4.3).
  • Dated versions ($api_version, 5.5). The experimental extension that 5.5 allows would have to settle: a closed list of dates and the error for an unknown one; a fixed default; a new kind of retirement; the date in what counts as the same idempotent request; cursors, state and events bound to their date; a batch with its request’s date; and that after a write the dated variants of a URL are not invalidated by URI (RFC 9111, section 4.4), which Cache-Groups mitigates (8).
  • An exception for shared caches with credentials, which shared_cache reserves (4.2, 13.10). Deferred until a case shows which responses that depend on credentials a shared cache can store safely.

Appendix C. Changes

This appendix is not normative. It lists what each draft settled, the most recent first. The sections cited are those of this draft.

Draft 7

Incompatible with draft 6. What an API that followed draft 6 has to change:

  • The total order of errors gives way to precedences (5.4): when several errors apply, the same request against the same stored state gets the same one; nothing that depends on the target is reported while a 401, or a 403 that depends neither on the body nor on the stored item, applies; 428 and 412 are not reported while an error that can be detected before processing the content applies, 406, a 403 that does not depend on the content and a 409 that depends only on the stored state of the target among them, and come before a 422 or 409 that comes from processing the content; and a replay or a 409 request_in_progress comes after the checks that keep the principal from learning what it may not, its current permission on the target included, and in place of 428, 412 and the errors that depend on the stored state. An API that kept the order of draft 6 meets them but in two cases: a replay, or a 409 request_in_progress, whose target no longer exists, whether the first request deleted it or another did, now gets the stored status or that 409, not 404 or 410 (7.1); and an action that the item’s current state does not allow, sent with a precondition that fails, now gets 409, not 412 (11.1).
  • The principal includes whoever acts on its behalf: an acting principal and the one it represents never share idempotency keys, cursors or stored responses (2).
  • Bodies are I-JSON messages, without duplicate member names, unpaired surrogates or noncharacters; instants and durations are written with uppercase letters, and lowercase ones are accepted; an instant with a leap second (:60) in a request body gives 422 invalid with a format entry, except in a field that only the server sets, which a POST ignores; the entry for an unpaired surrogate points to the string that holds it, or to "" when that string is a member name or cannot be located, and a body that also has a JSON syntax error gets 400 bad_request (3, 5.4).
  • No response of a collection, an item or an action depends on a language setting stored for the principal or on a cookie; only localized fields depend on the language, and only on Accept-Language (3).
  • A path segment that does not decode to UTF-8 gives 404, as an item that does not exist does (3).
  • An API whose collections, fields or declared capabilities differ by tenant gives each tenant its own API root (4.2).
  • A subcollection’s path goes on after its last variable with one or more literal segments (4.2).
  • A default in create is valid against its property, and a body that is a JSON value but not an object gives 422 invalid with an entry at "", both against a schema and in a PATCH (4.3, 5.1).
  • The Allow header of a 405 lists HEAD wherever it lists GET (4.3).
  • A response that depends on credentials carries no field aimed at shared caches, such as CDN-Cache-Control, that would let one store it (5.1).
  • In a POST, a field that only the server sets is ignored whatever its value, not answered with 422; such a field is one no client can set directly, never id, an effective or a localized field, and neither readOnly in the item schema nor its absence from create makes a field one (5.1).
  • The table of error codes is closed: a status it does not list gets http_ and its three digits, not a name derived from the IANA registry; type is about:blank only for a problem with nothing beyond its status; 428, 429, 431 and 511 carry Cache-Control: no-store and no field aimed at shared caches, such as CDN-Cache-Control, that would let one store them (5.4).
  • Deprecation goes only on the responses of a resource retired whole, with the notice’s announced instant; a notice that retires part of a resource puts nothing in its responses (5.5).
  • Discovery keeps a retirement notice in deprecations after its sunset, until the next major version (5.5).
  • The announced and sunset instants of every retirement notice are in whole seconds, without a fraction (5.5).
  • No operator outside the list of 6.1 is declared, and collations takes only string fields, sort keys that hold strings, localized fields and translations (6.1). A cursor is bound to the default filters the request does not turn off and, with localized fields, to the language (6.4).
  • A numeric filter operand outside the range of the field is compared as a number, exactly, without an error, and one over a request limit of the server gives invalid_parameter, never another value such as an infinity or zero (5.3); a time with a leap second gives invalid_parameter, and operands equal under the field’s type are the same filter, also for the cursor, so 20.0 is a valid operand of an integer field; an integer or number operand follows the number grammar of JSON, so 2e1 is 20, and +20, .5, 020 and 0x14 give invalid_parameter (6.1).
  • A replay gives the same status and Location, but never a body that reveals more than a read would now, and, with a body that is not the item’s current representation, no Content-Location, ETag or _etag; the replay of a 201 without a body carries no ETag (7.1, 7.3).
  • For Idempotency-Key, the order of repeated values of one query parameter counts towards “the same request” (7.1).
  • With a content coding, the ETag of an item differs from the item ETag or is weak; with localized fields, the item ETag differs by language and If-Match succeeds with that of any language; _etag carries the entity-tag with its quotes (7.2).
  • On a POST to a collection, * depends on whether the principal can read it; a 200 to an action that changed the item carries Content-Location and the new ETag, and a 204 to an action no ETag (7.2).
  • Every response to a QUERY carries Cache-Control, and a QUERY whose If-None-Match matches gets 412, not 304 (8).
  • A relationship whose path leads to a subcollection appears only in discovery: the parent’s representation does not carry it (9).
  • A collection that declares sync supports GET and has no required filter; an intermediate state is a point in the collection’s history, each response reporting the changes of its own window in the order they happened (10).
  • With sync, a since the server did not issue gives invalid_parameter, and the 429 for a stream over the limit carries Retry-After (10).
  • The colon before an action’s name goes unencoded in every link the server builds, and an unsafe action on a collection answers 201 or 204, never 200 (11.1).
  • An action declared "idempotent": true that ignores keys ignores a malformed one too, instead of answering 400 (11.1).
  • A GET action without params answers any query parameter with 400 unsupported_parameter (5.3, 11.1).
  • An action declared "safe": true declares "idempotent": true, and a collection’s action named new is the safe GET action that gives the starting values of a new item (11.1).
  • In a batch, a value inserted into path that is not valid there, a reference in path whose pointer carries { or }, and a pointer that finds nothing give 422 invalid, not 424, which is left for an operation that depends on one that failed (11.2).
  • In a batch, an operation id that is empty or carries #, { or } gives 400 bad_request (11.2).
  • With oauth, the API root uses https without a fragment, and the 404 that conceals a resource carries the same headers as that of one that does not exist, the generic challenge with realm included (11.5).
  • With inherit, when the item that the first link reaches has no effective value, the effective value is the default (11.6).
  • A member starting with x- does not change the meaning of the members this text defines beside it (4.2).

Appendix D. Documents with drafts and versions

This appendix is not normative. Restep already expresses a document that is edited as a draft and published as versions; this is how.

  • The draft. Either the item itself is the draft (/books/7, edited with PATCH), or the draft is an item of a subcollection with a fixed id, which declares upsert and reusable_ids (5.1): PATCH /books/7/drafts/current creates or edits it and DELETE discards it.
  • Versions are an immutable subcollection with ids that the server assigns (/books/7/versions/3), which are never reused.
  • Publishing is an action on the draft, such as POST /books/7:publish, with If-Match on the draft’s ETag, answered with 201 and the Location of the new version (11.1, 7.2).
  • The current version is a relationship of the item ("current": {"id": "3", "href": "/books/7/versions/3"}) or an item of its own, never an id, because an id that names another version every time would break caches, sync and relationships (3). Named aliases are items of their own.
  • Going back is publishing again from an older version; comparing two versions is a safe action with params, GET /books/7/versions/3:compare?with=2 (11.1).
  • Readers see a collection of published items; publishing several at once is an atomic batch or a collection of releases. The relations latest-version, version-history and working-copy of RFC 5829 (section 3) can link them.
